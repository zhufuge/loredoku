## 0. 一句话

两件事、三条迁移：

| 部分 | 表 | 做了什么 | 迁移 |
|---|---|---|---|
| A·角色 | `characters` | 头像的五列收到**只剩 `avatar_path`**：先删 `avatar_mime` / `meta`（零信息），再删 `avatar_size` / `avatar_width` / `avatar_height`（只是缓存） | `…00033` / `…00034` |

A 的两刀性质不同（第一刀删了不丢任何东西，第二刀是「一条信息换三列」的取舍），
所以分开做、分开写理由。B 的六列也是两半：占格是**从没被用过**，回执是**缓存**。

# 第一部分：角色表瘦身（`characters`）

## 1. 这五个字段的来历

`characters` 建表在 `20260101000008_item_character_version_refactor.ts:106-120`，当时是**照抄上传流水线的「回执四件套」**——同一时期 `items`（现 `assets`）表的 `image_mime` / `image_size` / `image_width` / `image_height` 一字不差。它们不是为角色做的设计，是模板：

| 字段 | 型 | 写入点 | 说明 |
|---|---|---|---|
| `avatar_path` | text | `setAvatar` | 相对路径，删头像时置 null；**留下** |
| `avatar_mime` | varchar(64) | `setAvatar` | `detectImageType` 的判定结果 |
| `avatar_size` | integer | `setAvatar` | `buffer.length`，**原图**字节数 |
| `avatar_width` / `avatar_height` | integer | `setAvatar` | `sharp.metadata()`，**原图**像素尺寸 |
| `meta` | jsonb not null default `'{}'` | `create` / `update` | v0.2.0 定义里就写着「扩展」 |

`docs/v0.2.0.md:116-120` 只给了列定义，`meta` 那行的用途就两个字：「扩展」。

## 2. 第一刀：`avatar_mime` 与 `meta`（零信息）

### 2.1 裁定

| 字段 | 读方 | 判定 |
|---|---|---|
| `avatar_mime` | **无** | 删 |
| `meta` | **无** | 删 |

### 2.2 `avatar_mime` 是同一事实的第二份记录

它的值**完全由 `avatar_path` 的扩展名决定**：`detectImageType` 返回 `{mime, ext}`，两者一一对应（png / jpg / webp / svg），写库时一起写，删头像时一起清。而且没有任何一方读过它：

- 静态托管走 `koa-static`（`app.ts:37`），Content-Type 按**扩展名**给，不查库；
- 前端 `<img src={avatarThumbUrl ?? avatarUrl}>`，浏览器按响应头渲染；
- `Character.avatarMime` 从仓库一路透传到前端类型，然后没有消费点。

### 2.3 `meta` 是从来没有读者的写入口

- **从来没人读过**：`CharacterDetailForm` 的保存请求体里没有 `meta`；schema 收、repository 写、`toCharacter` 吐，然后前端扔掉。
- **本来 v0.5.2 就该删**：`docs/v0.5.2.md:337` R8 白纸黑字——删 `items.meta` 时「角色 meta 同样没有 UI，留待后续一并处理」。这一留就是十几个版本。
- **它是一条没有验证的写入口**：`z.record(z.unknown())` 允许任意调用方往这一列灌任意结构的 JSON，而没有任何消费方校验结构。
- **UI 早就删干净了**：`CharacterMetaDialog.tsx`（一个 JSON 文本域编辑器）还在仓库里，但**全仓没有任何 import**——上次删 UI 时漏掉的孤儿，本版一起删。

## 3. 第二刀：`avatar_size` / `avatar_width` / `avatar_height`（只是缓存）

### 3.1 先纠正一个说法

第一轮讨论时我把这三列记作「唯一真源，删了原图信息就没了」。**这个说法过头了**：原图字节仍在磁盘上，尺寸和大小随时能重新读出来（`sharp.metadata()` / `stat`），代价是每次 I/O。它们是**缓存**，不是唯一真源。

### 3.2 唯一的读方，其实没人看

三个值只喂 `ImageUploader` 那行「1024 × 768 · 123 KB」。但这一行显示的是**原图**的尺寸与字节，而界面画的是 **256px 缩略图**：

```
preview = thumbUrl ?? imageUrl        // 只有缩略图挂了才回落到原图
```

也就是说，这行数字描述的是一个界面几乎从不渲染的文件。上传上限本来就是 2 MB（`UPLOAD_MAX_SIZE`），所以那个 KB 数也是用户自己文件管理器里就有的。

### 3.3 决定性论据：仓库已经用脚投票三次

本项目后来做的三类封面，全部**只存路径**，没有 mime / size / 宽高：

| 功能 | 列 | 版本 |
|---|---|---|
| 地图封面 | `maps.cover_path` | v0.4.2 |
| 游戏封面 | `games.cover_path` | v0.4.0 |
| 谜题封面 | `puzzles.cover_path` | v0.7.1 |

而它们走的是**同一个** `processImage`（`utils/image.ts:105-149`），四个值照算不误——封面侧只是选择不落库。「回执四件套」在这个仓库里已经被放弃过三次，`characters` 和 `asset_forms` 是仅剩的两个例外。本版把两个例外一起拉齐（资源侧见 §9.2）。

### 3.4 代价与补偿

代价只有一条：**上传区那行不再显示原图尺寸与体积**。

补偿是与既有做法对齐，不是新增能力——`ImageUploader` 的三个 prop 本来就是可选的，改成「有数才渲染」：

```tsx
{imageUrl ? (hasMetrics ? <p>{w} × {h} · {kb} KB</p> : <p>已上传</p>) : <p>尚未上传图片。</p>}
```

资源形态侧（`asset_variants`）当时仍传这三个值，本版第二部分把那里的四列也删了（§9.2），于是两个调用方（`AssetVariantCard` / `CharacterDetailForm`）都不再传这三个 prop，`hasMetrics` 恒为 `false`、信息行一致显示「已上传」。这个分支本版先留着——改动面已经够大，且两条路径都有测试；等下一次动 `ImageUploader` 时可以连 prop 一起删。

## 4. 数据证据（删之前实测）

改动前对本机库跑了一次只读查询：

```
character 行数                              40
meta 非 '{}' 的行数                          0     ← 零信息量
avatar_mime 有值的行数                       38     ← 与 avatar_path 扩展名 100% 一致
avatar_size / width / height 有值的行数      38     ← 与有没有头像完全同步
avatar_size 最大值                           25 KB  ← 本机库里都是测试塞的小图
```

第一刀不丢任何信息；第二刀丢的是一条**能从磁盘重算**的缓存。两刀都不动 `avatar_path` 与磁盘上的任何字节。

## 5. 设计

### 5.1 迁移

**`20260101000033_v076_drop_character_dead_columns.ts`**

```ts
// up
alterTable('characters') → dropColumn('avatar_mime'), dropColumn('meta')

// down：列回来，并按 avatar_path 扩展名把 mime 回填
alterTable('characters') → string('avatar_mime', 64), jsonb('meta').notNull().defaultTo('{}')
UPDATE characters SET avatar_mime = CASE substring(avatar_path from '\.([a-z0-9]+)$') ...
```

`down` 多做一步回填：只把空列加回来，降级后的服务会看到「38 张头像 mime 全空」，比丢数据更像损坏。这个值能从路径推出来，就顺手补上。

**`20260101000034_v076_drop_character_avatar_metrics.ts`**

```ts
// up
alterTable('characters') → dropColumn('avatar_size' / 'avatar_width' / 'avatar_height')
// down：三列加回来（integer，可空）
```

这一刀的 `down` **补不回值**：三个数只存在于图片文件里，迁移不去翻文件系统。回滚后列为 NULL，上传区那行退化成「已上传」——因为 `ImageUploader` 已经改成「有数才渲染」，不会出现「? × ?」这种残次品。

### 5.2 代码侧

| 层 | 改动 |
|---|---|
| `shared/types/db.ts` | `CharacterRow` 只剩 `avatar_path`，四个元数据列 + `meta` 全部移除 |
| `shared/types/domain.ts` | `Character` 同步（`avatarUrl` / `avatarThumbUrl` 是**算出来的** URL，照旧） |
| `shared/schemas/character.ts` | 两个 schema 去掉 `meta` |
| `server/repository` | `CreateCharacterData` / `UpdateCharacterData` 去掉 `meta`；`setAvatar(id, relativePath)` 只写路径；`clearAvatar` 只清路径；`CharacterImageData` 接口整体删除（只剩一个 `path`，没必要） |
| `server/service` | `createCharacter` 不透传 `meta`；`uploadAvatar` 只传路径 |
| `web/components/asset/ImageUploader.tsx` | 信息行改条件渲染：有尺寸/体积才显示，否则「已上传」 |
| `web/components/character/CharacterDetailForm.tsx` | 不再传 `width` / `height` / `size` |
| `web/api/characters.ts` | 两个 payload 去掉 `meta` |
| `web/components/map-editor/CharacterMetaDialog.tsx` | **删除**（无引用） |

`processImage`（`utils/image.ts`）**一行没改**：它照旧算出 mime / size / width / height 返回给调用方，只是角色侧不再把这三个数写进库——封面上传的调用方本来也没写过。

### 5.3 兼容性：老客户端发 `meta` 会怎样

**不报错，被忽略。** zod 的对象 schema 默认剥掉未声明的键（不是 `.strict()`）。

这是有意选的：删列的动机是「没人读」，不是「禁止别人发」。唯一会改变行为的情形是**只发 `meta` 的更新**——剥完补丁为空，`updateCharacterSchema` 的 `.refine(len > 0)` 拒掉，返回「请提供需要更新的字段」。语义上正确，测试里钉住了。

`Character` 响应里消失的五个字段同理：老前端读 `character.avatarWidth` 会拿到 `undefined`，而它在 UI 里只喂那行说明——本版前端已经不再读。

# 第二部分：资源形态重命名与瘦身（`asset_forms` → `asset_variants`）

## 7. 为什么 `form` 是个坏名字

不是审美问题，是**检索成本**问题。`form` 在这个仓库里已经被别人占满了：

| 已有的 `form` | 与资源形态的关系 |
|---|---|
| `AssetDetailForm`、`MapInfoDrawer`、`EditorInfoDrawer` 里的表单 | 毫无关系 |
| `react-hook-form` 的 `useForm` / `register` | 毫无关系 |
| `const form = new FormData()`（四个 api 文件里各一处） | 毫无关系 |
| `<form onSubmit>` JSX | 毫无关系 |

改名时做了一次机械替换（`form` → `variant`，带词边界），**18 个文件被误伤**，逐个回退：

```
relativeTime.ts            "the relative form stops meaning anything" → variant   ← 回退
segmented-radio.tsx        "the whole form reads as one family"       → variant   ← 回退
MapInfoDrawer.test.tsx     "the drawer is a **form**"                 → variant   ← 回退
api/{characters,games,maps,puzzles}.ts   const form = new FormData()  → variant   ← 回退
三个对话框                react-hook-form / <form>                    → 回退
```

误伤清单本身就是论据：一个名字如果需要靠词边界、英文注释、JSX 标签三套规则才能避开
误伤，它就不适合当标识符。同理中文侧「形态」也不准——v0.6.1 把长相和占格一起塞进
这张表之后，读「这个形态是 2×2」时说不清说的是画多大还是占几格。

改名与删列其实是同一个判断的两半：这张表原来叫「形态」，因为它既管**长相**又管
**占格**；占格一走（§9.1），「形态」这个词就只剩下长相，也就不该再叫 form 了。

## 9. 删六列

两半的理由完全不同，所以分开写。

### 9.1 占格 `width_cells` / `height_cells`（从没被用过）

v0.6.1 把「长相 + 占格」一起搬到形态上，设想是「同一资源的两种样子可以占不同格数」
（关闭的宝箱 1×1、打开的 2×2）。**这个设想在数据里一次都没发生过**：

```
物品锚点总数                          831
其中 w × h > 1 的                     0      ← 一个都没有
实测最大占格                          1
```

831 个已落位的物品，全部是 1×1。而 v0.7.5 之后要「看起来更大」有更好的手段：格子
信息框里的**大小**（`scale` 25%~400%，围绕脚位中心等比缩放，`offsetX/Y` 还能把画
推到格线之外）。也就是说，占格这一列既没人调、又被 `scale` 覆盖了用途。

删掉之后的语义：

- **新放置的物品恒占 1 格**（`placeItem({ …, w: 1, h: 1 })`，`fits(x, y, 1, 1)`）；
- 想画大 → 用「大小」，**只改显示、不改占格**；
- 擦除 / 碰撞 / 阻挡全按 1 格算。

### 9.2 上传回执 `image_mime` / `image_size` / `image_width` / `image_height`（缓存）

与 §3 删 `characters` 那三列是同一套理由，不再重复论证，只摘结论：

- `image_mime` 的值**完全由 `image_path` 的扩展名决定**（`detectImageType` 返回的
  `{mime, ext}` 一一对应），静态托管走 `koa-static`，Content-Type 按扩展名给，不查库；
- `image_size` / `image_width` / `image_height` 只喂过上传区那行说明，而界面画的是
  缩略图，三个数描述的是一个几乎不渲染的文件；
- 仓库里的三类封面（`maps.cover_path` / `games.cover_path` / `puzzles.cover_path`）
  **只存路径**，同一套 `processImage` 照算不误、只是选择不落库。

§6.3 当时写的是「`asset_forms` 的四列：留，另起一版」——这一节就是那一版，两个
「回执四件套」的例外至此清零。

## 10. 草稿键 `formId` → `variantId`

### 10.1 为什么必须落库

`draftCellSchema` 是 **`.strict()`**（v0.5.0 起，为了在导入旧 JSON 时明确报错而不是
静默剥字段）。内层的 `draftAnchorItemSchema` / `draftAssetRefSchema` 不 strict，但
外层 strict 会把没声明的键当成「未知键」拒掉——所以 `formId` 只要还留在库里，
**这 18 张地图和 9 个谜题下次保存就会 400**。

所以迁移里逐行改写 `maps.data` 与 `puzzles.data.map.data`（谜题自带一份地图画布
副本，两处都要改），手法照抄 `…00028`：读出 → 就地改 → 写回，没动过的行不写库。

### 10.2 为什么 schema 还要留别名

库里干净了，但**导出过的 JSON 文件**不干净——作者手里那份 v7 文件仍然写着 `formId`。
如果不管，导入时这个键会被**静默剥掉**（内层锚点不 strict），后果不是报错，而是
「多形态资源悄悄退化成第一个形态」——比报错更难发现。

```ts
function withLegacyAnchorKey<T extends z.ZodTypeAny>(schema: T): T {
  return z.preprocess((raw) => {
    if (raw && typeof raw === 'object' && 'formId' in raw && !('variantId' in raw)) {
      const { formId, ...rest } = raw as Record<string, unknown>;
      return { ...rest, variantId: formId };
    }
    return raw;
  }, schema) as unknown as T;
}
```

包在 `draftAnchorItemSchema` 与 `draftAssetRefSchema` 外面，两个锚点都吃这个别名。
只在**没有新键时**才搬——同时出现两个键时以新键为准，不去猜哪个是真的。

### 10.3 锚点上的 `w` / `h` 保留

这是本版最容易搞错的地方：删的是**形态**上的占格，不是**锚点**上的。

锚点上的 `w` / `h` 描述的是「这一次放置占了几格」，属于放置事实。留着它有两个好处：
已发布地图里若真有 2×2（本机库里没有，别的库可能有），渲染一像素不变；
`MAP_JSON_VERSION` 的这次升级因此只是**键改名**，不是结构调整。

新放置恒写 `1`，老数据原样保留——两者在 schema 里同样合法（`z.number().int().min(1)`）。

## 11. 迁移 `20260101000035_v076_asset_variants.ts`

### 11.1 up：四件事在一个事务里

```ts
renameTable('asset_forms', 'asset_variants')
ALTER TABLE asset_variants RENAME CONSTRAINT asset_forms_pkey TO asset_variants_pkey
  （外键、uq_asset_forms_asset_name、asset_forms_asset_id_index 同理）
dropColumn(width_cells, height_cells, image_mime, image_size, image_width, image_height)
renameLeftoverConstraints('asset_variants', 'asset_forms_', 'asset_variants_')
                                                         // 7 个 <列>_not_null 收尾
moveVariantDirs('forms', 'variants')                     // 逐资源目录 rename
UPDATE asset_variants SET image_path = replace(image_path, '/forms/', '/variants/')
rewriteAnchorKeys(trx, reverse = false)                  // formId → variantId，version → 8
```

四件事必须一起做：只改名不搬目录 → 图全 404；只改库不改草稿 → 下次保存 400；只改
锚点不改 schema → 新写入被 `.strict()` 拒。

`moveVariantDirs` 对「目录不存在」（没传过图的资源）和「目标已存在」都跳过，所以
重复跑不会炸、也不会把搬好的东西搬回去。

约束名要单独说一句：`renameTable` **不会**顺手改约束名，而每列的 NOT NULL 约束都叫
`asset_forms_<列>_not_null`。主键 / 外键 / 唯一索引在上面显式改了，剩下 7 个 NOT NULL
用 `renameLeftoverConstraints` 扫一遍 `pg_constraint` 换前缀（DO 块逐条判断，不同
Postgres 版本起名规则不一样时不会炸）。

### 11.2 down：能补的补，补不了的说清楚

| 列 | down 行为 | 说明 |
|---|---|---|
| `width_cells` / `height_cells` | 加回（notNull default 1），并全表写 1 | 删除时没有备份；1 正是删除后的语义 |
| `image_mime` | 加回，**按 `image_path` 扩展名回填** | 能从路径推出来，就顺手补上（照 00033 的做法） |
| `image_size` / `image_width` / `image_height` | 加回，值为 NULL | 三个数只存在于图片文件里，迁移不翻文件系统 |

其余三步反向：目录搬回 `forms/`、`image_path` 前缀改回、锚点键改回 `formId` 且
`version` 回到 7、约束与索引名改回。

第一版 `down` 有个小毛病：重建 `width_cells` / `height_cells` 时，NOT NULL 约束是按
**当时的表名**（`asset_variants`）起的，表名改回 `asset_forms` 之后这两个约束仍叫
`asset_variants_*_not_null`，回滚后的库和迁移前不同名。往返实测发现后补了
`renameLeftoverConstraints`（§11.1），现在 up / down 对称、可幂等重跑。
