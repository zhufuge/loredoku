# v0.10.1 — 竖屏下棋盘按宽度铺满、收掉视图簇与标尺

> **状态**：已实施（2026-11-11）。
> **来源**：用户的一条——
>
> > - 修改竖屏下地图大小自适应宽度，不展示放大缩小重置和标尺工具栏
>
> 两条要求其实是一件事的两半：把放大 / 缩小 / 重置 / 标尺收掉之后，玩家就没有任何
> 「把棋盘挪回视野」的手段了（触屏上没有中键、没有空格），所以棋盘必须自己**一次就
> 铺满可见宽度**；反过来，只要棋盘按宽度铺满、不再需要缩放平移，那套工具栏也就没有
> 存在意义。
>
> **范围**：`lib/canvasSize.ts`、`pages/GamePage.tsx`；`lib/canvasSize.test.ts` 增加
> 一个 `describe`。**没有**新增存档字段、没有迁移、没有新依赖、没有改
> `tailwind.config.ts`（`portrait` 是 Tailwind 3.4 内置变体）。
> 测试：shared 288 / web **1088（78 文件）** / server 230。

## §1 问题：竖屏下大棋盘只有左上角看得见

v0.10.0 把三栏改成了「上抽屉 / 中棋盘 / 下横条」，棋盘终于有了整屏宽度。但格子大小
仍走 `computeCellSize` 那套**桌面**算法：

```
ideal = min( 按宽度算的格子, 按高度算的格子 )   → 夹在 32 ~ 240
```

24×24 的棋盘在 375 宽里按宽度只能分到 ~12px 一格，撞上 32px 的下限后棋盘变成 864px 宽
——屏幕里只露出左上角，要看到别处只能靠拖动。

`docs/v0.6.2.md:15` 当初给大棋盘配「放大后能拖到角落」正是为了解决这个；但拖拽靠
`pointerdown` 的**中键 / 空格 + 左键**，触屏两样都没有。改前实测（375×812）：

| 关卡 | gridSize | 棋盘边长 | 结果 |
|---|---|---|---|
| `puzzle-the-treasure-hunt` | 24 | 864 | 只看得到左上角 |
| `puzzle-outdoor-painting` | 6 | 660 | 超出视口 285px |
| `puzzle-dao` | 2 | 236 | 刚好 |

## §2 竖屏按宽度铺满

### 2.1 判定：窄**且**竖着

```ts
export const PORTRAIT_BREAKPOINT = 768;          // Tailwind 的 md

export function isPortraitViewport(width, height): boolean {
  if (!Number.isFinite(width) || !Number.isFinite(height)) return false;
  if (width <= 0 || height <= 0) return false;
  return width < PORTRAIT_BREAKPOINT && height > width;
}
```

两个条件缺一不可：

- **只看宽度不够**。手机横过来（740×360）宽度也在 768 以下，但那时受限的是**高度**，
  按宽度铺满会把棋盘顶出上下边；而且横屏下视图簇仍然在（`max-md` 不成立？成立 ——
  但 `portrait` 不成立），玩家自己调得回来。
- **不用 `matchMedia('(orientation: portrait)')`**。`testing/matchMedia.ts` 那个桩的
  `matches` 恒等于「是否深色」、不认 query —— 一旦用它判定，整条分支在测试里失真。
  宽高比是同一件事，而且是个纯函数，好测。

判定量的是 **`window`** 而不是画布容器：CSS 那半边（`portrait:max-md:hidden`）判的就是
窗口，两边必须是同一个条件，否则会出现「按钮收起来了、棋盘还按桌面排」这种半吊子状态。
`PORTRAIT_BREAKPOINT` 是两边共同的出处。

### 2.2 算法：`computeWidthFitCellSize`

```ts
export const PORTRAIT_MIN_CELL_SIZE = 8;

export function computeWidthFitCellSize({ width, gridSize, insets, gap = BORDER_WIDTH, max = MAX_CELL_SIZE }) {
  const available = Math.max(0, width - insets.left - insets.right);
  const share = (available - (gridSize - 1) * gap) / gridSize;
  return Math.max(PORTRAIT_MIN_CELL_SIZE, Math.min(max, Math.floor(share)));
}
```

与 `computeCellSize` 的三处差别都是有意的：

| | 桌面那套 | 竖屏这套 | 为什么 |
|---|---|---|---|
| 约束轴 | 宽高取小 | **只看宽度** | 竖屏要「一屏看全宽」；为了塞进高度把棋盘缩成一条缝更糟 |
| 下限 | `MIN_CELL_SIZE` 32 | `PORTRAIT_MIN_CELL_SIZE` 8 | 24×24 在 375 宽上只有 ~12px 一格，守 32 就必然溢出 |
| 取整 | `Math.round` | `Math.floor` | 宁可少半像素，也不让棋盘比可用宽度多出一线 |

`extraMargin` 在竖屏下传 0：桌面那圈 `EXTRA_MARGIN`（24）是画面呼吸，375 宽上左右各
留 40 等于白扔 80 像素 —— 足够再放一整列。

### 2.3 纵向：贴住上边，不是居中

`centeredPan` 在「棋盘比可视高度还高」时会把上下两头各切掉一块，顶上那截**永远够不着**。
竖屏已经没有平移手段了，所以换成 `topAlignedPan`：横向居中，纵向装不下时贴住 `insets.top`，
至少保证「第 1 行看得见」。

### 2.4 竖屏下不听地图样式里的 `cellSize`

`effectiveCellSize(autoCellSize, style)` = `style.cellSize ?? autoCellSize` —— 作者在
地图样式里填了格子大小就用他的。这在桌面是对的，但竖屏下会把「按宽度铺满」整个抵消：
`puzzle-the-treasure-hunt` 的地图样式写着 `cellSize: 36`，24×36 = 864px，正是要消灭的那个
数。所以竖屏下直接取 `autoCellSize`：

```ts
const cellSize = portraitFit ? autoCellSize : effectiveCellSize(autoCellSize, style);
```

横屏与桌面一个字都没动。实测 12 关的 `puzzle.style.cellSize` 全是 `null`（填了值的是
`map.style.cellSize`，属于作品内容），所以这条在现有数据上不会被触发 —— 但代码不能假设。

## §3 收掉视图簇与标尺

### 3.1 做法：纯 CSS，不做条件渲染

右栏那簇（放大 / 百分比 / 缩小 / 重置视图 / 显示 / 隐藏标尺）追加一个类：

```tsx
'portrait:max-md:hidden'
```

`mt-auto` 与 `border-t` 都留着 —— `GamePage.test.tsx` 的「右栏布局（v0.9.0 §17）」断言
`toolbar().lastElementChild.className` 含 `mt-auto`，能查到那四枚 `button[aria-label=…]`
和 `100%` 文本；「锁定态四枚都 disabled」那条也指着它们。隐藏用的是 CSS，元素仍在树里，
这些断言原样成立。

标尺条（`MapRulerStrips`）跟着一起不画：开关都收起来了，还留 28px 的刻度边，等于让玩家
为一条关不掉的边付宽度。它在 `fit` 里靠 `showRulers && !portrait` 参与 inset 计算，渲染时
用 `showRulers && !portraitFit`。

### 3.2 为什么不是条件渲染

- **媒体查询才是这件事的真源**。转屏 / 拖窗口时 CSS 立刻生效，不必等一次 `fit` 跑完再
  React 重渲染 —— 条件渲染会有「棋盘已经按宽度排了、按钮还在」的一帧。
- **按钮留在树里还有用**。无障碍工具与既有测试仍拿得到它们；隐藏 ≠ 消失。

## §4 验证

### 4.1 真浏览器（agent-browser，375×812 / 320×568 / 414×896 / 740×360 / 1280×800）

| 场景 | 棋盘边长 | 格子 | `scrollWidth` | 视图簇 |
|---|---|---|---|---|
| 375×812，24×24 | 288 | 12 | 375 | `display: none` |
| 375×812，6×6 | 330 | 55 | 375 | `display: none` |
| 375×812，7×7 | 329 | 47 | 375 | `display: none` |
| 375×812，2×2 | 340 | 170 | 375 | `display: none` |
| 320×568，24×24 | 240 | 10 | 320 | `display: none` |
| 414×896，24×24 | 336 | 14 | 414 | `display: none` |
| 740×360（横屏手机，7×7） | 770 | 110 | 740 | `flex`（仍然显示） |
| 1280×800（桌面，2×2） | 480 | 240 | 1280 | `flex` |

- 竖屏下棋盘宽度全部 ≤ `window.innerWidth - 32`，**无横向溢出**（`documentElement.scrollWidth`
  等于视口宽）。
- 1280×800 下 24×24 的棋盘仍是 864px（地图样式里 `cellSize: 36` 说了算）—— 这是**改造前
  就有的桌面行为**，大棋盘在桌面上靠视图簇 + 中键/空格平移看，本次不动它。
- 标尺：竖屏只剩一个空容器（0 条刻度），桌面 3 个节点（1 个空容器 + 列 `C1…C6` +
  行 `R1…R6`）。判据是 `zIndex === UI_Z.ruler` 的那些 div。
- 桌面 1280×800 回归：三栏 `[256, 256, 81]`、main 943×800、棋盘 480（2×2 顶到
  `MAX_CELL_SIZE`）—— **与 v0.10.0 逐像素一致**。
- 横屏手机 740×360 仍走桌面分支（视图簇在、棋盘 770 可平移）：这正是「窄且竖着」这个
  条件要挡住的局面。
- 375 下竖屏落子正常：标记态点一格后 `localStorage` 写出
  `{v:2,gridSize:2,participantCount:2,board:{"0,0":{"kind":"forbidden"}}}`。
- 375 下定案遮罩：`zoom === 0.708`（棋盘 340 / 480），「定案」横向排开、「再玩一次」
  完整可见。

## §5 没做的

- **没把 `PORTRAIT_MIN_CELL_SIZE` 做成配置**。8 是「24 格 × 375 宽」逼出来的数，再低
  格子就点不准了；做成可配只会多一个没人改的旋钮。
- **没在竖屏下重开平移**。棋盘已经一屏看全，平移没有目标；真出现比屏幕还宽的棋盘，
  贴住上边、横向居中已经是最优解。
- **没改编辑器**。`docs/design-system.md` §5.10 那条「编辑器零响应式」仍原样留在账上，
  用户这次说的是游戏页。
- **没碰 `matchMedia` 桩**。整件事走纯函数 + CSS，`testing/matchMedia.ts` 一动没动。
- **没给「隐藏」加过渡**。`portrait:max-md:hidden` 是即时切换的；转屏时棋盘本来就要重排，
  再叠一个淡出只会让人以为卡了一下。
- **没动触摸设备的长按菜单**（`docs/v0.7.10.md:453`）：棋盘容器仍然没有拦 `contextmenu`。
