# v0.11.0 — 主题包瘦身：标记与图标共用主题那一份、未引用的形态不打包、封面统一 768px webp

## 0. 范围与口径

| 能力 | 来源 | 状态 |
| --- | --- | --- |
| 没自定义标记 / 工具图标的关，包里直接用主题那一张（不再逐关复制） | 本版需求 | 已实现（§1） |
| 未被任何格子引用的资源形态不打包 | 本版需求 | 已实现（§2） |
| 关卡封面统一裁到最长边 768px、同时转 webp | 本版需求 | 已实现（§3） |
| 总目标：包变小、资源请求数变少 | 本版需求 | 实测 11.19 MB → 5.93 MB（−47%），276 → 208 条（§4） |

只动服务端导出（`bundleService`）与一个 shared 常量。播放器、编辑器、manifest
结构、`BUNDLE_FORMAT_VERSION`、数据库全没动。

## 1. 没自定义标记 / 工具图标的关，用主题那一份

### 1.1 问题

主题兜底原来的做法是「读主题的图、复制进包、改成这一关的路径」。主题下 18 关
全都没自定义标记时，包里出现 18 份字节完全相同的 `files/marks/<slug>.webp`。

实测红楼梦包（`resources/themes/hlm-bundle-20261116-1540.zip`）：`files/marks` +
`files/icons` 共 72 个条目，sha256 只有 **4 个**（标记 1 张 ×18，clear / undo /
submit 各 1 张 ×18），占 2.10 MB、72 次请求 —— 实际是 4 张图。

### 1.2 做法

- `packages/server/src/service/bundleService.ts:601`（`takeMark`）目标路径从
  `files/marks/${gameKey}${ext}` 改为
  `files/marks/${own ? gameKey : 'theme'}${ext}`，`own = game.puzzle.mark`
  —— 自己传过标记的关仍走自己的路径。
- `bundleService.ts:638`（`takeToolIcons`）同样改为
  `files/icons/${own ? gameKey : 'theme'}-${icon}${ext}`。
- 播放器侧零改动：`FileSink.take` 本来就按目标路径去重（`byPath` Set），多关指向
  同一路径只存一份；`bundleFileUrl` 按相对路径拼 URL，谜题 JSON / manifest 里记
  的就是路径，多关指同一路径天然能读。
- 碰撞：`theme` 在 `GAME_SLUG_RESERVED`（`packages/shared/src/constants/ui.ts`）
  里，关卡 slug 不可能是 `theme`，共享路径与逐关路径不会撞。

### 1.3 验证

| 场景 | 结果 |
| --- | --- |
| 两关都不传标记（夹具） | 包里 `files/marks/` 只有 `theme.webp` 一条，两关 level JSON 的 markPath 都指向它 |
| 两关各传自己的标记（夹具） | 仍是 `files/marks/<slug>.webp` 两条，行为不变 |
| 工具图标兜底（夹具） | `theme-clear / theme-undo / theme-submit` 三条，两关共用 |
| 真实红楼梦包（§4 重放） | 72 → 4 条，2,104,488 → 116,916 B |

### 1.4 没做的

- `files/ring/ring.webp` 本来就是主题级单份，没动。

## 2. 未被引用的资源形态不打包

### 2.1 问题

原来的 `collectSideTables` 给引用闭包里每个资源的**全部形态**补发序号，
`rewriteAssets` 再全量迭代 —— 等于把被引资源的整张形态表都打进包。理由是编辑器
的资源面板要整表，但**播放器没有资源面板**（`EditorBottomBar` 只在编辑器、走
API），关卡只按格子画的形态要图。

实测红楼梦包：139 个形态里只有 136 个被 1197 个格子引用。

### 2.2 做法

- `collectSideTables`（`bundleService.ts:408-414`）序号补齐循环从「全部形态」
  改为「每个被引资源的**首形态**」。
- `rewriteAssets`（`bundleService.ts:441`）加
  `if (!ids.variants.has(variant.id)) continue;` —— 没号 = 形态不进
  `assets.json`、图也不打包。
- **首形态无条件保留**（而不是「格子没写 variantId 才保留」）：联动
  （`linkage.type === 'asset'`）会把一个资源带进引用闭包而没有任何格子画它 ——
  条件式保留会让这类资源 `variants: []`，违反「Asset.variants 永不为空」，
  播放器 `resolveAssetVariant` 的兜底（画 `variants[0]`）也会踩空。代价是
  ≤1 张图/资源：实测红楼梦包里恰好 3 个仅被联动引用的资源（蔷薇丛 / 炕 / 地毯），
  各保留首形态共约 163 KB。
- 重编号安全：`renumberPuzzleDraft` 的 remap 是 `map.get(id) ?? id`（未知 id 原样
  保留），所以被砍掉的形态绝不能还留在 cell 里。引用闭包
  （`collectMapThemeRefs`）每层恒发 asset ref、`variantId` 非空才发 variant ref
  —— 被格子引用的形态都进 `ids.variants`，remap 全命中；保留的形态沿用**原数组
  下标**编号（multiImage 时 `-1` / `-2` 后缀），不因过滤而重排。
- 联动本身只做格子高亮（`findItemPlacements`，`packages/web/src/lib/highlight.ts`），
  不渲染形态图，所以联动带入的资源不需要任何形态的图。

### 2.3 验证

| 场景 | 结果 |
| --- | --- |
| 资源的第二形态没被任何格子引用（夹具） | `assets.json` 的 variants 长度为 1（id=1）；`files/assets/` 只有一条且匹配 `/-1\.webp$/` |
| 纯色块资源（无图） | 仍无 `files/` 条目，行为不变 |
| 真实红楼梦包（§4 重放） | 裁掉 0 B —— 未引用的恰好全都是首形态（蔷薇丛 / 炕 / 地毯，仅被联动带进闭包），按上面的规则保留 |

真实数据上形态裁剪的字节收益是 0；这条规则防的是作者后续加形态后的增量
（加了不用就不进包），代价就是上面那 163 KB。

### 2.4 没做的

- 没把「仅被联动引用」的资源整个踢出 `assets.json`（那 163 KB 首形态图是保留的
  代价，见 2.2）。
- 没对保留形态的图做再次压缩：`assets` / `avatars` 仍走原来的 `_thumb.webp`
  （最长边 512），本版只动封面 / 标记 / 图标。

## 3. 封面统一裁剪 768px、转 webp

### 3.1 问题

封面原来直接搬原图：`files.take(row.cover_path, files/covers/${index}${ext})`。
实测红楼梦包 5 张封面 PNG（900×900 / 960×960 / 1024×1024 等）共 **3.68 MB**，
是全包最大的一项。

### 3.2 做法

- 新常量 `BUNDLE_COVER_MAX_DIMENSION = 768`
  （`packages/shared/src/constants/game.ts:124`），与上传时的
  `GAME_COVER_MAX_DIMENSION = 960` 分开 —— 上传仍按原样存（编辑器里还要看清晰
  预览），**包里**才裁。
- `takeCover`（`bundleService.ts:557`）改用新增的
  `FileSink.takeProcessed`（`bundleService.ts:677`）：读原图 → 转换 → 落
  `files/covers/${index}.webp`。去重语义与 `take` 一致（同一目标路径只存一份）。
- `scaleBundleCover`（`bundleService.ts:561`）：
  `sharp(data, { density: 96 }).resize(768, 768, { fit: 'inside', withoutEnlargement: true }).webp({ quality: 80 })`
  —— 最长边 768、等比、不放大，同时统一转 webp（原图可能是 png / jpg，扩展名
  固定写 `.webp`）。`density: 96` 与 `processImage` 一致，防矢量 / PDF 类源图按
  默认密度爆边。
- manifest 的 `game.cover` 字段结构没变，播放器侧无改动。

### 3.3 验证

| 场景 | 结果 |
| --- | --- |
| 上传 900×600 PNG 当封面（夹具） | 包里 `files/covers/1.webp`；sharp 读回 `format: 'webp'`、`width: 768`、`height: 512` |
| 真实红楼梦包（§4 重放） | 5 张 3,681,025 B → 154,360 B（768×768 / 767×768），**省 3.36 MB** |

### 3.4 没做的

- 没改上传管线的 `processGameCover`（仍按 960 存原图）。
- 没做封面懒加载或分片加载。

## 7. 发布：`npm run publish:player`

> 2026-11-17 补。这一节记录的是**发布动作**，不改任何构建产物格式。

`build:player` 只负责产出 `packages/web/dist-player/`，把它搬到站点仓库一直是手工
三步（构建 → 复制 → 手动补 `404.html`），每次都要人记住「先清空」和「复制 404」。
`scripts/publish-player.mjs` 把这三步收成一条命令：

```
npm run publish:player                                  # 构建 + 覆盖发布
npm run publish:player -- --site=D:/path/to/site-repo   # 指定站点仓库
npm run publish:player -- --no-build                    # 发布现有 dist-player
npm run publish:player -- --bundle=/path/to/hlm.zip     # 临时换包（递给 build:player）
npm run publish:player -- --no-404                      # 不生成 loredoku/404.html
npm run publish:player -- --dry-run                     # 只打印计划
```

站点目录优先级：`--site` > 显式环境变量 `LOREDOKU_SITE` > 仓库根 `.env` 里的
`LOREDOKU_SITE`，相对路径一律按**仓库根**解析。默认值放在 `.env` 而不是猜同级
目录：站点仓库换台机器不一定同名或同级，猜错会递归删掉一个同名的无关目录；
`.env` 已经是放 `LOREDOKU_BUNDLE` / `PGPASSWORD` 这类本机配置的地方（且被
gitignore）。`.env.example` 里有现成的 `LOREDOKU_SITE` 注释块（**不写死任何具体
站点** —— 仓库里不出现个人站点的目录名）。读 `.env` 复用
`packages/web/scripts/playerEnv.mjs` 的 `loadRootEnv()`，不另写解析器。

**它比 `Copy-Item` 多做的三件事**（也就是它存在的理由）：

| 行为 | 为什么必须有 |
| --- | --- |
| 删掉站点里的 `loredoku/` 再整体写入 | `vite.player.config.ts` 用 `emptyOutDir: false`（本机文件系统 shim 递归删目录会失败），换包后旧哈希的 `assets/*` 会留在产物里；不先清空，旧主题的残留会永远堆在站点目录里 |
| 生成 `loredoku/404.html`（`index.html` 的逐字节副本） | 播放器是 SPA，刷新 `/loredoku/hlm/play/xxx` 需要兜底页；React Router（basename `/loredoku`）直接读 `location.pathname` 恢复路由，不需要重定向脚本 |
| 删目录前先校验「是 git 仓库、且不是本仓库自己」 | 下一步是递归删除，一个写错的 `--site` 不能把别的东西删掉 |

**坑 1：`NODE_ENV` 必须钉成 `production`**。脚本用 `spawnSync` 调
`scripts/player.mjs`，会原样继承父进程的环境。从 vitest 里跑时 `NODE_ENV=test`，
Vite 就按「非 production」解析 React 的条件导出，打出 **development 版 React**
（实测 `vendor-react` 从 205 KB 涨到 416 KB，文件里能搜到 `react-dom.development`）。
正常 `npm run build:player` 没有这个问题（它前面没有 vitest），但发布脚本不能把
正确性押在「谁调的」上面，所以显式给子进程 `NODE_ENV=production`。

**坑 2：`main()` 不能无条件执行**。写这个脚本时先漏了守卫，`scripts/publish-player.test.mjs`
一 `import` 就真的构建、真的删掉并覆盖了站点目录。现在用 `isDirectRun()`
（比对 `process.argv[1]` 与 `import.meta.url`；不用 `import.meta.main`，它在
Node 22.18/24 才有，而 `package.json` 承诺 `>=20`）挡住。

**深链的状态码仍是 404**。GitHub Pages 官方文档只保证**站点根**的 `404.html`，
子目录那份是否被服务没有权威证据 —— 这份副本是「生效则深链可用，不生效与不加
相同」，深链的 HTTP 状态码并不会因此变成 200。小游戏可以接受，所以没有采用
spa-github-pages 那套改站点根 `404.html` 的方案（那会被后续博客构建覆盖）。

**不替用户提交**。脚本只写文件，最后打印一条 `git -C <site> add loredoku && …`
提示 —— 站点仓库是个人博客，提交与推送由人决定。

验证：`scripts/publish-player.test.mjs` 30 个用例覆盖参数解析、站点解析（取值顺序
`--site` > 环境变量 > `.env`、相对路径按仓库根、`.env` 里没有配置时必须报错而不是
猜同级目录、三层删除前校验）、主题识别与文件计数，全部用临时目录，不碰真实站点
（AGENTS.md §4.1）。
