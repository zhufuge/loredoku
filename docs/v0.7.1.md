## 0. 一句话

五件事：

1. **导航重排**：资源 → 地图 → 角色 → 谜题，并新增第 5 项「部署」；`/` 直接落到 `/maps`，

2. **地图预览分家**：草稿条目预览**草稿自己**，版本条目 tip 统一为「预览版本」；

3. **谜题列表与地图列表同构**：草稿（卡片 + 列表）/ 版本两块，各自分页、各自的按钮。
4. **puzzles 表版本化**：加 `root_id` / `version` / `deleted_at` / `cover_path`，

## 1. 改之前是什么样

- **导航**：`AppShell.navItems` = 地图 / 资源 / 角色 / 谜题；`/` 重定向到 `/play`（玩家端首页），
  所以从根路径进来时**没有一个工坊 Tab 是亮的**。
- **地图预览**：草稿条目的「预览」按钮走 `/maps/:id/views?v={currentVersionNo}`——
  看的是**血统里最新的已发布版本**，从未发布过的草稿该按钮直接禁用。想看草稿当前的
  样子只能进编辑器。
- **`?v=`**：`MapViewPage` 的缺省版本号来自 `mapEntry.versionNo ?? mapEntry.currentVersionNo`，
  编辑器发布成功后也拼 `?v=`。一个页面两种「缺省来源」，是链接里带 query 的直接原因。
- **谜题列表**：一张 5 列的大表（名称 / 版本 / 部署状态 / 发布时间 / 操作），
  客户端过滤 + 分页（`lib/puzzlesTable.ts`），与地图列表（分块卡片）完全两套。
- **puzzles 表**：`map_project_id` + `map_version_no` 外键引用一个已发布地图版本，
  `grid_size` 冗余列，`status` 列（永远写 `'draft'`）；`data` 是引用式的 `PuzzleDraft`
  （只有名册与调色板，画布靠 join 地图版本）。**谜题没有版本**：改了就是改了，没有发布动作。
- **部署**：任何谜题（草稿）都能部署；`games` 存一份完整 `snapshot`（画布 + 谜题全量拷贝），
  因此 `games` 同时冗余了 `grid_size` / `project_id` / `version_no` / 封面四个尺寸列。
  已部署的游戏**没有地方管理**：只能重新部署覆盖，没有「取消部署」。

## 4. 设计：地图列表的「预览」

### 4.1 三处改动

| 位置 | 现在 | v0.7.1 |
|---|---|---|
| 草稿条目「预览」 | 跳 `?v=<血统最新版本号>`，没发布过就禁用 | 跳 `/maps/{id}/views`，看**草稿自己**；`gridSize === null`（未初始化）才禁用，tip「草稿还没初始化画布」；可用时 tip「预览草稿」 |
| 版本条目「预览」 | tip「预览已发布版本」 | tip 恒为「预览版本」 |
| 预览路由 | `/maps/:mapId/views?v={n}` | `/maps/:mapId/views` |

**可预览判定的单点**：`MapEntryActionsMenu.previewVersionNo(entry)` 现在是
`entry.versionNo ?? entry.currentVersionNo`——「草稿看最新版本」这条规则就在这一行里，
`MapListRow` 与卡片菜单共用它。改后它不再返回版本号，而是直接回答能不能预览：

```ts
/** v0.7.1：草稿行看自己（`gridSize === null` = 没初始化，无可预览）；版本行恒可预览。 */
export function entryPreviewable(entry): boolean {
  return entry.kind === 'version' ? true : entry.gridSize !== null;
}
```

`MapViewPage` 里那份 `versionNo ?? currentVersionNo` 的兜底（§4.2）与它是同一条规则的两个
副本，这次一并收口。

### 4.2 预览页的解析规则（去掉 `?v=` 之后）

`maps` 合并后草稿行与版本行都是 `maps` 行，**每行自带 `data`**，所以不再需要
「草稿行 → 找最新版本号」这一步：

| `:mapId` 命中 | 渲染 | 数据端点 |
|---|---|---|
| 草稿行 | 该行 `data`；`null` 时显示空态「该草稿还没有画布」 | `GET /api/maps/:id/map` |
| 版本行 | 该行 `data`（必然非空） | 同上 |
| 软删版本行 | 照常渲染（读取口不过滤软删，与 fork 源同口径） | 同上 |
| 不存在 | 错误态「地图不存在或加载失败」 | — |

- `MapViewPage` 删掉 `useSearchParams` / `requestedNo` / `useVersionDetail` / `fallbackVersionNo`
  一整段，只留 `useMapCanvas(mapId)`：`mapQuery.data.draft` 就是画布，
  `mapQuery.data.map` 提供名字与版本徽标。**标题与徽标不变**（标题取地图名，
  草稿行显示「草稿」徽标，版本行显示 `v{n}`）。
- 左上「返回」与空态文案保持现状。

### 4.3 编辑器发布后的跳转

`MapEditorPage` 里发布成功后原本拼 `/maps/${ownerId}/views?v=${versionNo}`；
改为用发布响应里的**版本行 id**：`navigate(`/maps/${version.id}/views`)`。
`MapVersionSummary.id` 本来就是版本行 id，不需要额外请求。

## 5. 设计：谜题版本管理（数据模型）

### 5.1 puzzles 表

| 列 | 处置 | 说明 |
|---|---|---|
| `root_id bigint NOT NULL` | **新增** | 血统根；存量行回填 `= id`（与 `maps` 同款） |
| `version text NOT NULL DEFAULT 'draft'` | **新增** | `'draft'` = 工作条目；纯数字串 = 已发布版本 |
| `deleted_at timestamptz` | **新增** | 只有版本行会被设置（软删） |
| `cover_path text` | **新增** | 谜题封面，卡片与列表用 |
| `map_project_id` | **删** | 底图改为自带副本，不再有 FK |
| `map_version_no` | **删** | 同上（来源信息保留在 JSON 里，仅追溯 / 展示） |
| `grid_size` | **删** | 尺寸唯一真源 = `data.map.data.gridSize`（高压线 4） |
| `status` | **删** | `version` 已表达同一信息，与 `maps` 一致 |

约束（与 `maps` 一一对应，命名按 `puzzles_` 前缀）：

```sql
CREATE UNIQUE INDEX uq_puzzles_root_version ON puzzles (root_id, version)
  WHERE version <> 'draft' AND deleted_at IS NULL;
ALTER TABLE puzzles ADD CONSTRAINT puzzles_version_format_check
  CHECK (version = 'draft' OR version ~ '^\d+$');
CREATE INDEX puzzles_root_id_index        ON puzzles (root_id);
CREATE INDEX puzzles_deleted_at_created_at_index ON puzzles (deleted_at, created_at);
```

> **高压线继承**：`version` 是字符串，`Number('draft')` 是 `NaN`——转换只走
> `versionToNo()`，草稿行出参 `versionNo` 短路为 `null`。`puzzles` 与 `maps` 共用这两个函数，
> 不新增第二套。
>
> **版本号的两条 SQL 不许复制一份**：`versionRepository.nextVersionNo` / `versionNoTaken`
> 现在把表名写死成 `maps`。抽 `server/src/repository/versioning.ts`
> （`nextVersionNo(table, rootId)` / `versionNoTaken(table, rootId, no)`），
> `maps` 与 `puzzles` 各传自己的表名——`MAX(CAST(version AS integer))` 这种
> 「含软删行、号不回收」的口径只有一处实现，改错一次就是两个模块一起错。

### 5.2 版本语义（与 `maps` 同构）

| 语义 | 规则 |
|---|---|
| 发布 | INSERT 一条新 `puzzles` 行：`version` = 版本号，`name` / `description` / `cover_path` / `data` 是此刻快照；草稿行不动 |
| 版本号 | 血统 `MAX(CAST(version AS int)) + 1`（含软删行，号不回收）；可由用户指定填空洞号，已存在则 400 |
| 编辑此版本 | fork：新建一条**草稿行**（同 `root_id`），名字「{name} (自 v{n})」，撞名加副本后缀 |
| 删草稿行 | 硬删 |
| 删版本行 | 软删（界面不展示、行保留、号仍占 MAX） |
| 写保护 | 版本行只读：`savePuzzle` / `updatePuzzle` / 封面上传对 `version <> 'draft'` 一律 400 |
| 有部署时 | 版本行挂着未删的 game 时**禁止删除**，提示「请先取消部署」（见 §7.4） |

### 5.3 `PuzzleDraft` v2：底图快照内嵌

```ts
// shared/src/types/domain.ts
interface PuzzleDraft {
  /** `PUZZLE_JSON_VERSION` —— v0.7.1 起为 2。 */
  version: number;
  /** 底图：来源信息（仅追溯 / 展示，无 FK）+ 创建时复制的画布。 */
  map: PuzzleMapSnapshot;
  name: string;
  description: string;
  linkageColors: MapLinkageColor[];
  characterSlots: Array<CharacterSlotEntry | null>;
  rosterCols?: number | null;
}

interface PuzzleMapSnapshot {
  mapId: number;      // 来源地图条目 id
  versionNo: number;  // 来源版本号
  mapName: string;    // 来源地图名快照（展示用）
  /** 创建时复制的画布（`MapDraft`，v7 形状）。尺寸唯一真源 = `data.gridSize`。 */
  data: MapDraft;
}
```

- **`PUZZLE_JSON_VERSION` 1 → 2**。v1 的 `map: { mapId, versionNo, gridSize }` 没有画布，
  v2 才有。导入 v1 的谜题 JSON → 400，提示「该谜题文件不含底图画布，请重新导出」
  （v0.7.1 之前导出的文件无法自洽，不做静默补底图）。
- **导出**仍是整个 `data`（现在自带画布，可离线流转）。
- **schema 分两套**：`puzzleMapRefSchema`（v1 读取用，收 `projectId` → `mapId`、
  带 `gridSize`）保留在 `schemas/puzzle.ts`，新增 `puzzleMapSnapshotSchema`
  （v2 形状：`mapId` / `versionNo` / `mapName` / `data`）。`puzzleDraftSchema` 走 v2；
  读旧 payload 时按 `version` 字段分流到 v1 schema，再由
  `absorbLegacyPuzzleDraft` 补成 v2（与地图 `mapDraftCompat` 的同款双轨）。
- `gridSize` 派生：新增 shared 纯函数 `puzzleGridSize(draft) => draft.map.data.gridSize`，
  列表 / 游戏摘要 / 名册长度校验都走它，杜绝第二真源。
- **后果（预期行为）**：谜题创建后底图固定。地图后来发布新版本**不影响**既有谜题——
  想换底图只能新建谜题（本次不做「换底图」）。
- `PuzzleMapContext` 形状不变（`GET /api/puzzles/:id/map` 现在从谜题自己的副本读，
  `cells` / `regions` / `style` / `gridSize` 照旧）。
- `validatePuzzleReferences` 不再跨表：联动目标（asset / region）对照**自带画布**校验。

### 5.4 迁移 `20260101000031_v071_puzzles_versioning.ts`

单事务，步骤：

1. 加 4 列；`root_id` 回填 `= id` 后收紧 NOT NULL；`version` `DEFAULT 'draft'`。
2. **回填画布**：逐行 `UPDATE puzzles p SET data = jsonb_set(p.data, '{map,data}', v.data)`
   ——`v.data` 取 `maps`（原 `map_project_id` 指向的版本行）的 `data`，过一遍
   `absorbLegacyMapDraft` 升到 v7；同时写 `data.map.mapName`（来自 join 的 `maps.name`）、
   `data.version = 2`。
   - 引用失效的历史脏数据（版本行已硬删）：给一份空画布
     `{ version: 7, gridSize: <旧 grid_size>, cells: {}, regions: [] }`，
     保证 schema 合法、编辑器能打开（名册长度不变）。
3. 建 §5.1 的四个索引 / 约束。
4. 删 `map_project_id` / `map_version_no` / `grid_size` / `status`
   （`puzzles_map_version_index` 随列自动消失）。

`down()` **完全可逆**：因为来源信息留在 JSON 里——

- `data.map` 复原成 v1 形状（`{ mapId, versionNo, gridSize }`，`gridSize` 取 `data.map.data.gridSize`），
  删掉 `map.data` / `map.mapName`，`data.version` 回到 1；
- 加回四列并按上述字段回填（`status` = `'draft'`）；
- 删新增的四列与索引。

### 5.5 谜题编辑器：发布 / 版本历史 / fork

## 7. 设计：发布与部署

### 7.1 只有已发布的谜题版本能部署

部署单元 = **一个谜题版本行**。四层拦截，任何一层漏了都会被下一层挡住：

| # | 层 | 拦截点 |
|---|---|---|
| 1 | 列表 / 卡片 UI | 草稿条目**不渲染**「部署」（不是禁用 —— 草稿永远不可能满足这个条件，禁用按钮只会让人猜为什么）；版本条目才有 |
| 2 | 部署弹窗 | `GameDeployDialog` 的 `puzzle` prop 收窄成**版本条目**（类型带 `versionNo`），草稿条目进不来 |
| 3 | 服务端 | `POST /api/puzzles/:id/games`：目标行 `version = 'draft'` → 400「只有已发布的谜题版本可以部署」 |
| 4 | 数据库 | `games.puzzle_id` NOT NULL + UNIQUE（§7.2）：一个 game 行必然、且只能挂在一个 puzzle 行上 |

- 因为 puzzle 的**版本行只读**，游戏内容依旧是冻结的——冻结性由「版本行不可写」保证，
  不再靠 `games.snapshot` 拷贝。草稿行不能部署 = 玩家永远碰不到「作者还在改」的内容。
- **一个 puzzle 行 ⇄ 一个 game 行**：同一版本行再次部署 = 覆盖（`upsertGame` 的
  delete-then-insert，slug / 难度 / 封面按 OPT-W03 prefill）；**不同版本行**各有一个
  game 行、各有一个 slug，可以同时在线。
- **默认访问路径不带版本号**（作者要求：路径要短、要稳定，`v2` 这种实现细节不进 URL）。
  代价是明摆着的：同一谜题的 v1 / v2 名称相同 → 默认路径一模一样，
  第二个版本提交会被 slug 唯一约束挡住（400「访问路径已被占用，请更换」），
  作者在中段里改一下即可。**不做自动加 `-2` 之类的机器编号**——路径是作者要对外公布的
  东西，机器乱加后缀比报错更难解释。

### 7.2 games 表

| 列 | 处置 |
|---|---|
| `snapshot` | **删**（游戏读 puzzle 行：画布 + 名册都在谜题里） |
| `project_id` / `version_no` | **删**（底图信息随谜题走） |
| `cover_mime` / `cover_size` / `cover_width` / `cover_height` | **删**（封面只需要 path 就能服务） |
| `grid_size` | **删**（从 puzzle 派生） |
| `deleted_at timestamptz` | **新增**（取消部署 = 假删） |
| `puzzle_id` | 提为 `NOT NULL`，FK `ON DELETE RESTRICT`；partial unique 换成普通 UNIQUE |

两个唯一约束**分工不同**，别混：

- `puzzle_id` 普通 UNIQUE = 「一个版本行 ⇄ 一个 game 行」。它对**已删行也生效**，
  但覆盖部署是同一事务里「先 `del` 再 `insert`」（`upsertGame` 的既有行为），
  所以「取消部署 → 重新部署同一版本」不会被自己挡住。
- `slug` 的 partial UNIQUE（`WHERE deleted_at IS NULL`）= **「删除的 slug 可重用」**的机制，
  跟 puzzle_id 那一条无关。

迁移 `20260101000032_v071_games_reference_puzzles.ts`（单事务）：

1. `DELETE FROM games WHERE puzzle_id IS NULL` —— v0.4.x 遗留的无主行，
   `project_id` / `version_no` / `snapshot` 一删就没有画布可渲染，硬删等于取消部署，
   slug 随之释放（已确认）。
2. `puzzle_id` 收紧 NOT NULL；`ON DELETE RESTRICT`（谜题行挂着游戏时不可删）。
3. slug 唯一改**部分唯一索引** —— 这就是「删除的 slug 可重用」的机制：

   ```sql
   ALTER TABLE games DROP CONSTRAINT games_slug_unique;
   CREATE UNIQUE INDEX uq_games_slug_active ON games (slug) WHERE deleted_at IS NULL;
   ```

   旧对象是 knex `table.unique(..., { indexName })` 建的 **constraint**（迁移 `00015` 建、
   `00027` 改名成 `games_slug_unique`），必须 `dropUnique` / `DROP CONSTRAINT`
   而不是 `DROP INDEX`（`00015` / `00017` 的踩坑）。`down()` 反向：删 partial index、
   按**未删行**重建全覆盖 UNIQUE（已删行若撞号，down 会失败——先在 down 里硬删这些行，
   与 up 的「无主行硬删」同口径）。
4. 删 8 列，加 `deleted_at`。
5. `down()`：加回 8 列并按 puzzle 回填（`project_id` 无法复原 → 填 puzzle 行 id 的近似值、
   `snapshot` 由 puzzle 重建），slug 唯一约束还原为全覆盖 —— **结构可逆，数据近似**，
   与 `00021` 的 down 同一口径。

#### 7.6.1 访问路径输入组：前缀 + 中段 + 难度后缀

```
┌─────────────────────────────────────────────────┐
│ puzzle-  │ flower-garden                │ -medium │   ← 一行输入组
└─────────────────────────────────────────────────┘
  /play/puzzle-flower-garden-medium
```

- **前缀**：`GAME_SLUG_PREFIX`（`puzzle`）+ `-`，只读文本（`text-muted-foreground`），
  不是可编辑内容的一部分。
- **中段**：唯一可编辑的部分，作者可以任意改（改名 / 加年份 / 加场合），
  输入时用 `normalizeSlugInput` 净化。默认值 = `slugify(谜题名)`，**不含版本号**
  （路径是对外公布的，不掺 `v1` / `v2` 这种内部实现细节）。
- **后缀**：`-` + `GAME_DIFFICULTY_SLUGS[difficulty]`（如 `-very-easy`），只读；
  **切难度时后缀实时跟着变**，下方预览行同步更新。
- **保存时拼接**：`composeSlug(middle, difficulty)` → `puzzle-{中段}-{难度段}`，
  原样作为 `slug` 提交；服务端只做 `slugError` 校验，不再二次加工。

shared `src/gameSlug.ts` 新增两个纯函数（服务端与 UI 共用一套拼法，杜绝第二真源）：

| 函数 | 作用 |
|---|---|
| `composeSlug(middle, difficulty)` | 拼接：前缀 + `slugify(middle)`（去首尾 `-`）+ `-` + 难度段；超长交给 `truncateSlug` |
| `splitSlug(slug, difficulty)` | 反解已有游戏的 slug → 中段（剥前缀与当前难度后缀；对不上时只剥前缀） |

- `buildDefaultSlug({ name, difficulty })` **签名不变**，实现改成
  `const middle = slugify(name); return middle ? composeSlug(middle, difficulty) : ''`
  —— 空名称仍返回 `''`（v0.4.1 Q13 的口径），其余行为完全一致。
  这样三处（弹窗默认 / 「重新生成」/ 服务端 `resolveSlug` 兜底）共用一套拼法。
- **中段为空不能直接拼**：`composeSlug('', …)` 会退化成 `puzzle-medium`（部件过滤掉的空段），
  看着合法其实丢了名称。所以沿用 v0.4.1（`docs/v0.4.1.md` §4.4 Q13）的口径 —— 中段为空且作者没手动编辑过 →
  「无法根据名称生成访问路径，请手动填写（仅限小写字母、数字与连字符）」；
  手动清空 → 「请填写访问路径」。两种都不提交。
- **已部署游戏回填**：`splitSlug(existingGame.slug, existingGame.difficulty)` 取中段。
  与 OPT-W03 的差别是**难度不再冻结**：改难度会改后缀，因此当 `existingGame` 存在且
  组合结果 ≠ 原 slug 时，预览行下方补一句橙色提示「原访问路径 /play/{原 slug} 将失效」——
  把「已发布的路径是承诺」从"静默不改"改成"明写出来"。
- **「重新生成」按钮**：只把中段重置为 `slugify(谜题名)`，不动难度。
- `slugTouched` 状态改名为 `middleTouched`（语义收窄：只跟踪中段有没有被手动改过），
  难度**永远**实时参与拼接 —— 原来那条「已发布后改难度不重写路径」的冻结规则作废，
  换成上面的显式提示。
- **「覆盖」的语义保持不变**：同一个 puzzle 行的 game 被 `upsertGame` 替换
  （delete-then-insert），不是新增行；取消部署后再部署是新增行（旧行已 `deleted_at`）。

## 11. 风险与待确认（Q&A）

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 谜题自带画布后，地图改了谜题不跟着变，是退步吗？ | **是预期的**：谜题要能发布 / 冻结，就不能挂着活引用。想换底图 → 新建谜题（本次不做「换底图」） |
| Q2 | v0.7.0 之前导出的谜题 JSON 还能导入吗？ | **不能**，明确报错说明「不含底图画布」。导出永远是 v2（自带画布，可离线流转） |
| Q3 | 谜题版本行删不掉怎么办？ | 挂着未删 game 时拒绝删除并提示「请先取消部署」；取消后即可删 |
| Q4 | `games.snapshot` 删了，游戏还会被后续改动影响吗？ | 不会：游戏只挂在**只读的版本行**上，草稿行不能部署 |
| Q5 | 取消部署后玩家手里的链接？ | `/play/{slug}` 404「游戏已下架」；用同一 slug 重新部署后链接复活（浏览器本地存档按 gridSize / 人数指纹不符整条丢弃，v0.6.2 的机制兜住） |
| Q6 | 五个导航项在窄屏会挤吗？ | `<nav>` 加 `flex-wrap`，与头部品牌行同款处理；不做折叠菜单 |
| Q7 | `gridSize` 派生会不会拖慢列表？ | 与 `maps` 同款（列表本来就解析 `data` 取尺寸），已验证过；分页 12 条一次，可接受 |
| Q8 | 谜题编辑器的 `?v=` fork 态不做，列表点版本会多一跳吗？ | 多点一次「编辑此版本」= 一次 fork 请求 + 跳转，用户感知是一步（弹窗里点） |
| Q9 | 游戏封面的四个尺寸列删了，前端有用吗？ | `MapGameSummary` 从未返回过它们（只有 path → `coverUrl`），无影响 |
| Q10 | 同一谜题的 v1 / v2 同时部署，默认访问路径怎么办？ | 中段按作者要求**不带版本号**，所以两版默认路径相同：第一个部署成功，第二个提交时被服务端挡（400「访问路径已被占用，请更换」），作者在中段里写点别的即可。**不做自动加 `-2`**——路径是作者对外公布的，机器编号比报错更难解释（§7.1） |
| Q11 | 草稿条目上要不要留一个「禁用」的部署按钮？ | **不留**。草稿永远不满足条件，禁用按钮只会让人猜为什么；入口只在版本条目上（§7.1 第 1 层） |
| Q12 | 前缀 / 后缀写死了，想要完全自定义的路径怎么办？ | 中段整体可编辑（可写任何 `[a-z0-9-]`），前缀 `puzzle-` 与难度后缀是路径规范的一部分，不给关（玩家端一眼能认出这是谜题游戏、难度直接写在链接里） |
| Q13 | 改难度会把已发布的路径改掉吗？ | **会，但看得见**：后缀实时跟着变，且当组合结果 ≠ 原 slug 时下方明写「原访问路径 /play/{原 slug} 将失效」（§7.6.1）。替代 OPT-W03 的「静默不改」 |

### 12.1 §3 导航与默认落地

`entryPreviewable` / `entryPreviewTitle`（供列表行、卡片菜单、页面共用）。无偏差。

### 12.3 §5 puzzles 版本化（迁移 `…00031`）
- 版本号 SQL 抽到 `repository/versioning.ts`（表名参数化的 `nextVersionNo` /
  `versionNoTaken`），`versionRepository`（maps）与 `puzzleVersionRepository`
  （puzzles）各传自己表名 —— 两处不再各写一份 `MAX(CAST(version AS integer))`。
- v1 ↔ v2 的纯转换放 `service/puzzleDraftMigration.ts`（`buildPuzzleDraftV2` /
  `puzzleDraftToLegacy`），**可脱离 DB 单测**，`down()` 复用它。
- 迁移 up → down → up 实测通过，逐字段核对：回滚后 `puzzles` 回到 v1 形状（`data.version = 1`，
  `map: { mapId, gridSize, versionNo }`，四个旧列回填）；再升级后 `data.version = 2`、
  `map.data.version = 7`、名册长度 = `data.map.data.gridSize`；索引
  `uq_puzzles_root_version` / `puzzles_root_id_index` / `puzzles_deleted_at_created_at_index`
  就位。
- **偏差**：设计 §10 计划单建 `server/test/puzzleVersioning.test.ts`、`gameService.test.ts`。
  实际把这些用例并进 `server/test/api.test.ts` 的 `describe('v0.7.1 谜题版本与部署')`
  （5 例：草稿行 400 / 发布含 422 与号段行为 / fork 同血统 / 同谜题两版默认路径撞车 400 +
  改中段成功 / 取消部署后 slug 可重用）—— 它们都要真 DB 与启动器，`api.test.ts` 已经
  具备这两样，再拆一份只是多一次连接。
- 谜题**编辑器不做 `?v=` fork 态**（有意与地图不同）：列表点版本行 = 先 fork 出新草稿行
  再进编辑器（`POST /puzzles/:id/versions/:versionNo/fork` 直接返回新行）。

### 12.4 §6 谜题列表页与地图同构
- `PuzzlesPage` 整页重写，骨架与 `MapsPage` 一一对应（两块 + 视图切换 + 各自翻页条 +
  `loredoku.puzzles.view` 持久化）；`lib/puzzlesTable.ts` 与其测试**删除**，关键词 / 排序
  全部走服务端（`GET /api/puzzles` 现在返回 `PaginatedData<PuzzleEntrySummary>`）。
- **偏差 1（新增文件）**：`components/puzzle/EditPuzzleDialog.tsx`。落点表没列它，但

  「基本信息」抽屉，列表上没有任何入口。它复用 `EditMapDialog` 的两步套路（PATCH →

### 12.5 §7 只有已发布版本能部署 + 部署模块
- 四层拦截全部落地：列表 `/ 卡片`不渲染（`PuzzleListRow` 有断言）、弹窗 prop 收窄

- `GameDeployDialog` 的访问路径改成「只读前缀 `puzzle-` + 可编辑中段 + 只读难度后缀」：
  `composeSlug` / `splitSlug` 是唯一拼法，难度**永远**实时参与；组合结果 ≠ 原 slug 时
  补一行琥珀色「原访问路径 /play/{原 slug} 将失效」。

- `/deployments` 新建：一行 = 一条在线游戏（封面 / 游戏名 / 来源谜题 `v{n}` / 难度 /
  `n×n` / `/play/{slug}` / 部署时间），三个动作 —— 打开（新标签页）、复制访问路径、取消部署
  （假删，弹窗写明「玩家立刻无法访问 / 同一路径可以再用」）。
- `GamePage` 改读 `detail.map` / `detail.puzzle`；`service/gameSnapshotCompat.ts` 与
  它的测试**删除**（`games.snapshot` 没了，legacy 吸收逻辑无处可用）。
