## 1. 放置参与者功能补充（SPEC-H01 / SPEC-H14）

> 本节先把「参与者」与「参与者编号」两个概念分清（CLAR-H13，§1.1），再给出两条补充规则：
> 落位清扫（SPEC-H01，§1.2）与整框淡化（SPEC-H14，§1.3）。

### 1.1 CLAR-H13 术语：参与者 ≠ 参与者编号

| 术语 | 指什么 | 出现在哪 | 是否进地图 |
|---|---|---|---|
| **参与者**（participant） | 一位角色在这张地图上的「出题对象」身份：`characterSlots[i] = { characterId, themeColor, clue, linkages, positionConditions }` | 左侧参与者面板的**一张卡片**（头像 + 序号 + 名称 + 线索 + 联动） | **否**（CLAR-603：参与者不进入地图） |
| **参与者编号**（participant number） | 数字标号 **1..n**（= 该参与者在面板中的位置 + 1） | 格子内九宫格的一位数字，即 `{kind:'numbers'}` 数组里的元素 | **是**（它正是落格内容本身） |
| **参与者头像**（participant avatar） | 该参与者头像图的**整格**渲染 | 格子 `{kind:'participant'}` | 是 |

由这两个概念推出的三条口径，全文按此执行：

1. **「每个参与者只能放置到一个格子上」**说的是：该参与者的**编号 / 头像**全盘**至多出现在一个格子**里。
   参与者本身（面板卡片）**不在**格子里，它只是"待放置的一方"。
2. **「已放置」的判定** = `placedParticipantIds(board)` —— 该参与者的编号或头像在棋盘上出现 ≥ 1 次；
   面板据此把这张**卡片整体淡化**（SPEC-H14）。
3. **编号落格与头像落格都算放置**：都受唯一性约束、都会淡化卡片；区别只在格子形态
   （九宫格数字 vs 整格头像），**不**改变"是否已放置"。

> 代码标识符**不重命名**（`CharacterSlotEntry` / `numbers` / `slot` 保持原样，避免无谓 diff），
> 只在文档、UI 文案与测试名里统一用词（见 §17 Q15）。

### 1.2 SPEC-H01 参与者的编号在落位后只保留一处

**现状**

- 格子的放置形态有三类：**编号九宫格**（`{kind:'numbers'}`，最多 9 个编号）、
  **头像**（`{kind:'participant'}`）、**禁止符号 ×**（`{kind:'forbidden'}`）。
- 玩家在放置态下**短按**格子 → 把该参与者编号追加进该格九宫格；**长按**（≥500ms）
  → 该格整格替换为该参与者头像（v0.4.0 SPEC-G03 §9.2）。
- v0.4.1 SPEC-G05 已规定「每位参与者全盘至多一处标记」，`placementBlockReason`
  在参与者已在别格时返回 `elsewhere` 并拒绝。
- 但「唯一性」是**实时校验**，以下路径可以绕过它而留下同一参与者的多处编号：
  1. **v0.4.0 时期的存量部署快照**（当时无唯一性约束，同一编号可落在多格）；
  2. **导入的 JSON 草稿**（编辑器导出 / 手工构造，未经放置态校验）；
  3. 其它格子里的编号在**自动 ×**（SPEC-G06）之外被单独清除后，参与者的标记位置
     与「面板淡化集合」的推导可能出现短暂不一致（`placedParticipantIds` 会把它算成"已放置"）。

**需求**

> 参与者**成功放置到一个格子上之后**，把**该参与者对应的编号从所有格子中删除**。

具体规则：

1. **触发时机**：`placeParticipant()` 成功落格的**同一次操作内**（编号落格与头像落格都触发）。
2. **清扫范围**：棋盘上**除落点格子外**的每一格；若其九宫格中含有该参与者编号，则把该编号移除。
3. **清扫后的格子形态**：
   - 该格九宫格**清空** → 该格变为**空格**（删掉该 key），**不是** ×；不可站立遮罩等
     其它视觉状态不因此改变；
   - 该格九宫格仍有其它参与者编号 → 保留形态，只去掉本参与者的那一位。
4. **落点格本身**：
   - 头像落格 → 整格为头像（编号本来就被替换）；
   - 编号落格 → 该格保留该编号（它是"落点标记"本身）。
5. **撤销语义**：清扫与放置**合并为一个历史步**（一次回退同时撤销清扫与放置），
   与 SPEC-G06 的自动 × 采用同一处理方式。
6. **幂等**：正常游玩路径下（v0.4.1 唯一性生效）本规则是**幂等的 no-op**；
   它保证的不变量是「**任意来源**的棋盘，在任意一次落位之后，该参与者不超过一处编号」。
7. **唯一性不放宽**（用户已重申「每个参与者只能放置到一个格子上」，见 §17 Q1）：
   `placementBlockReason` 的 `elsewhere` 判定**保持不变**——本规则只负责"收敛历史 /
   外部数据残留"，不负责放宽实时校验。
8. **清扫范围只含编号，不含头像**：旧数据里若同一参与者「编号在 A 格、头像在 B 格」，
   落位时会被 `elsewhere` 正常拒绝——本规则**不**为此自动解锁，用户先清掉那一处即可
   （与 Q1 不放宽唯一性一致；清扫发生在**落位成功之后**，被拒绝的操作不触发清扫）。

**纯函数落点**

在 `packages/web/src/lib/gamePlacement.ts` 中新增一个可单测的纯函数（命名可调）：

```ts
/** SPEC-H01: remove one participant's number from every cell except `except`. */
export function sweepParticipantNumbers(
  board: GamePlacementBoard,
  input: { participantId: number; except: CellCoord },
): GamePlacementBoard;
```

- 返回**新 board**（无改动时返回等价的新对象即可，由 `placeParticipant` 统一 `commit`）；
- `placeParticipant` 在算完自动 × 之后、`commit` 之前调用它。
- 不新增第二个 `commit`——清扫不能产生额外的撤销步。

**验收**

- 构造「同一参与者在 A、B 两格都有编号」的棋盘（模拟旧快照）→ 在 C 格放置该参与者
  → A、B 两格的该编号消失；A、B 若无其它编号则变为空格；
- 回退一次 → 放置与两处清除**一并**还原；
- 某格同时有参与者 1、2 的编号，落位参与者 1 到别格后该格只剩 2，形态仍是编号格；
- 正常路径（唯一性生效）下棋盘与 v0.4.1 完全一致（无额外变化、无额外撤销步）。

### 1.3 SPEC-H14 放置后参与者框整体淡化

**现状**

v0.4.1 SPEC-G05 把 `GAME_PLACED_OPACITY`（0.45）只加在**头像 `span`** 上
（`ParticipantPanel` 的 `slot-avatar-{index}`），外框、序号、名称、线索等其余内容**不**变淡 ——
视觉上是"半透明头像 + 全不透明卡片"的割裂态，卡片看上去仍像"可放置"。

**需求**

> 参与者**成功放置到某个格子**之后，该参与者的**整张卡片**（框 + 框内全部内容）一并淡化。

1. **作用对象 = 卡片根节点**：外框（背景 / 边框 / 圆角）与**框内全部内容**——头像、序号、
   名称、线索文本、提示词、状态徽标——**统一**取 `GAME_PLACED_OPACITY`（0.45）。
2. **实现口径**：把 `opacity` 从头像 `span` **上提到卡片根**（卡片根上一个
   `style={{ opacity }}`，或 `data-placed` + CSS 类），**不再**对子元素各自设置 ——
   否则父子叠加会让实际透明度变成 `0.45 × 0.45`。
3. **不留子元素级透明度**：删除 `slot-avatar-{index}` 上的 opacity 写法
   （该 `data-testid` 保留，供其它断言使用）。
4. **交互不变**：淡化是**纯视觉**状态 —— 卡片仍可点击（进入放置 / 切换 / 再次点击退出）、
   仍参与联动高亮、仍可悬停。激活时是否恢复不透明见 §17 Q14（默认**不恢复**）。
5. **与 OPT-H06（§6）互不干扰**：头像区只减圆层级，淡化只加在卡片根，两件事各自独立、层级不变。
6. **两个面板一致**：编辑器参与者面板与游戏页只读面板是**同一个** `ParticipantPanel`。
   游戏页由棋盘推导 `placedSlotIndices` 并变淡；编辑器页面板不传该 prop，保持全不透明。

**落点**

| 层 | 变更 |
|---|---|
| `components/editor/ParticipantPanel.tsx` | `Props.placedSlotIndices` 保留；改为在**卡片根**渲染 `style={{ opacity: isPlaced ? GAME_PLACED_OPACITY : undefined }}`，并移除头像 `span` 上的 opacity |
| `packages/shared/src/constants.ts` | **复用**既有 `GAME_PLACED_OPACITY = 0.45`，不新增常量、不改数值（只扩大作用范围） |
| 测试 | `components/editor/ParticipantPanel.placedDim.test.ts` 断言从"头像 span"改到"卡片根"（见 §15.1） |

**验收**

- 某参与者落位后，其卡片**整体**变淡：外框边框、头像、序号、名称、线索文本、提示词的
  视觉浓度一致下降；**不存在**"只有头像淡、框不淡"的混合态；
- 渲染结果里 `opacity`（或 `data-placed`）只出现在**卡片根节点一处**；
- 编辑器参与者面板（无落位概念）保持全不透明，与 v0.4.1 一致；
- 点击已淡化的卡片仍能取消 / 切换放置 —— 淡化不阻断交互。

## 3. FEAT-H03 新建 / 编辑地图时可填封面，卡片展示封面

### 3.1 现状

- `map_projects.cover_path` 列**自 v0.1.0 建表即存在**；`toProject()` 已经把它映射成
  `coverPath` + `coverUrl` 并返回给前端；复制地图时也会带上 `cover_path`（`projectRepository` 的 duplicate）。
- `ProjectGridCard` **已经**在卡片顶部渲染 `project.coverUrl`（有图则 `<img>`，无图则 `ImageIcon` 占位）。
- **缺的是写入路径**：`CreateProjectDialog` / `EditProjectDialog` 都没有封面上传项，
  `projectsRouter` 也没有任何上传接口（只有游戏封面的 `POST /api/games/:id/cover`）。
  也就是说 —— 这个字段目前**永远为 `NULL`**，卡片顶部的封面区永远显示占位图标。

### 3.2 需求

**（a）新建 / 编辑弹窗新增「封面（可选）」区块**

- 位置：名称 / 描述之后（新建弹窗另加"画布尺寸"之后）。
- 形态（对齐游戏部署弹窗的封面区，`GameDeployDialog` 已成熟）：

| 状态 | 展示 | 按钮 |
|---|---|---|
| 未选文件、无既有封面 | 虚线占位框「未设置封面（可选）」 | 「选择图片」 |
| 已选本地文件 | 本地预览（`URL.createObjectURL`） | 「取消选择」/「更换」 |
| 编辑时有既有封面 | 既有封面预览 + 标注「当前封面」 | 「更换」/「移除」 |
| 已点「移除」 | 回到虚线占位 | 「选择图片」 |

- 限制：复用 `UPLOAD_MAX_SIZE`（现约 2MB）；接受 `image/png|jpeg|webp`（与游戏封面一致）；
  不合规时 `toast.error` 并保留原状态。
- 预览比例：**16:10**（与游戏卡片、`MAP_COVER_ASPECT` 一致），`object-cover`。
- 「可选」= 允许不设置；不设置时卡片走首字 / 图标占位。

**（b）保存时机（关键决策）**

封面是**二进制文件**，而新建 / 编辑走的是 JSON 接口。默认采用**两步串行**，与游戏部署一致：

- **新建**：先 `POST /api/projects` 拿到 `id` → 若选了封面，再 `POST /api/projects/:id/cover`
  → 成功后才提示「地图创建成功」并关闭弹窗；上传失败 → **地图已创建**、但封面未上传，
  弹窗保持打开并 `toast.error('封面未上传成功')`，提供「重试上传」。
- **编辑**：先 `PATCH /api/projects/:id` 更新名称 / 描述 → 再按封面三态处理
  （沿用 = 不发请求；替换 = 上传新图；移除 = 调显式清空）。
- 备选方案（一次请求的 `multipart/form-data`）见 §17 Q3，默认不做。

**（c）后端新增接口**

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/projects/:id/cover` | 上传封面（`multipart/form-data`，字段名 `file`），返回更新后的 `ProjectDetail` |
| `DELETE` | `/api/projects/:id/cover` | 移除封面（`cover_path` 置 `NULL`），返回更新后的 `ProjectDetail` |

- 路由注册在 `projectsRouter`（`/:id/cover` 与既有 `/:id/grid-size` 同级）；
- 上传中间件复用 `src/middleware/upload.ts` 的实例（新增导出一个 `projectCoverUpload` 别名即可）；
- 存储路径沿用 `UPLOAD_ROOT` 下的 `projects/{id}/…`（与游戏封面 `games/{id}/…` 同构）；
- 未找到地图 → 404；无文件 → 400。

**（d）卡片展示封面**

- `ProjectGridCard`：已具备，本版把封面区**固定为 16:10**（现状 `h-36` 固定高度，
  在 4 列布局下比例偏扁）、并给无封面态一个更明确的首字占位（取地图名首字符 + 浅色底），
  代替纯图标（与游戏卡片 `GameCard` 的占位风格统一）。
- `ProjectListRow`（列表视图）：**新增**左侧 64×40 的封面缩略图（圆角 + `object-cover`），
  无封面时同样走首字占位；其余列不变。

### 3.3 数据结构与迁移

| DB | **无迁移**（`map_projects.cover_path` 已存在） |

## 5. FEAT-H05 发布确认弹窗与发布成功入口

### 5.1 现状

- 工具栏最右是「发布」按钮（primary）：`onClick={publish}` → 直接调用 `usePublishProject`
  → 成功 `toast.success('发布成功，已生成新作品')`，**没有任何确认、也没有后续入口**。
- 发布前校验失败时弹「无法发布」`AlertDialog`，列出违规项（保留）。
- `publish()` 在 `editor.dirty` 为真时**直接 return**（静默无反应）；按钮也被
  `disabled={saving || dirty}` 置灰 —— 用户点不动时**没有任何解释**。

### 5.2 需求（a）：发布前确认弹窗

点「发布」→ 弹出确认框（`AlertDialog`）：

| 项 | 内容 |
|---|---|
| 标题 | **发布当前地图？** |
| 说明 | 发布会把**当前画布内容**存为一个新的作品版本（v{N}），之后玩家可在作品页查看与预览。 |
| 备注 | 可选 `Input`「发布备注（可选）」，随请求体 `notes` 提交（后端 `publishSchema.notes` 已支持，当前前端恒传空） |
| 次按钮 | 取消 |
| 主按钮 | 确认发布 |

- 确认 → 调用 `publish({ notes })`；
- 发布中：主按钮显示「发布中…」并禁用（沿用 `Loader2` 旋转图标风格）；
- 校验失败 → 关闭确认框，改弹既有的「无法发布」清单弹窗（**不新增第二套失败 UI**）。

### 5.3 需求（b）：发布成功弹窗

发布成功**不再只用 toast**，改为弹出一个成功框：

| 项 | 内容 |
|---|---|
| 标题 | **已发布 v{N}** |
| 说明 | 作品已生成，可直接预览或前往作品页管理。 |
| 主按钮「预览」 | `navigate(\`/works/{versionId}/view?project={projectId}&v={versionNo}\`)`（与作品页「查看效果」同一路由与参数格式） |
| 次按钮「前往作品页」 | `navigate('/works')` |
| 关闭 | 右上 × / Esc，仅关闭 |

- 需要发布接口把新版本一并带回来：`usePublishProject` 的 `PublishResult`
  由 `{ ok: true }` 扩展为 `{ ok: true; version: MapVersionSummary }`
  （`versionsApi.publish` 本就返回 `MapVersionSummary`，含 `id` 与 `versionNo`，无需改后端）。
- 成功后的缓存失效保持现状（`mapKeys.detail` / `versionKeys.*` / `projectKeys.all`）。

### 5.4 需求（c）：保存 / 发布按钮的展示（**已裁定**）

**现状问题**

1. 发布按钮在 `dirty` 时置灰，**没有任何说明**——用户以为是权限或系统问题；
2. 保存（outline）与发布（primary）紧邻，视觉权重接近，主次不够分明；
3. 发布从"一点即发"变成"有确认弹窗"之后，按钮本身承担的语义变轻了，
   有条件把"能不能发"的判断放进弹窗，而不是用灰按钮挡住。

**候选方案（留档，方案 A 的禁用条件被采纳、主次权重按裁定反转）**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A | 发布按钮禁用条件由 `saving \|\| dirty` 改为 `saving \|\| publishing`；弹窗按状态分形态：无未保存修改 → 主按钮「确认发布」；有未保存修改 → 说明行提示「有未保存的修改，将先保存再发布」，主按钮「**保存并发布**」（串行：`save()` 成功后再 `publish()`）。保存按钮维持现状（outline，`disabled={saving \|\| !dirty}`）。 | 消除"灰按钮无解释"；用户少一次来回；保存语义仍显式可见 | 一次点击触发两个请求，失败时需分步提示 |
| B | 维持 `disabled={dirty}`，仅补 `title="有未保存的修改，请先保存"` | 改动最小 | 问题 1 只是被"解释"而没有解决 |
| C | 合并成单个「发布」按钮，内部自动保存，删除独立保存按钮 | 工具栏最简 | 保存与发布语义被混淆；用户无法只保存不发布；与"自动保存"能力重叠 |

**用户裁定（2026-10-16）：两个按钮不合并，保存作为主按钮。**

| 按钮 | 变体 | 禁用条件 | 点击行为 |
|---|---|---|---|
| **保存**（主） | `primary`（实心） | `saving \|\| !dirty` | 立即保存；成功提示沿用现状 |
| **发布**（次） | `outline`（描边） | `saving \|\| publishing` | **不**直接发请求 → 打开确认弹窗（§5.2），确认后才发布 |

即：**采纳方案 A 的禁用条件与"弹窗分形态"，主次权重按用户裁定反转**（保存 primary / 发布 outline）；
方案 B、C 不采用 —— 两个动作语义独立，保存必须能单独使用。

- 发布**不再因 `dirty` 置灰** —— 有未保存修改时改由**弹窗**解释（说明行
  「有未保存的修改，将先保存再发布」+ 主按钮「**保存并发布**」，串行 `save()` → `publish()`，
  两步都成功才算发布成功）；
- `publish()` 里对 `editor.dirty` 的静默 `return` 一并去掉（`dirty` 由弹窗分形态处理）；
- 「发布」在 `publishing` 时文案变「发布中…」，「保存」在 `saving` 时变「保存中…」；
  任一请求进行中**两个按钮都禁用**（避免并发写）；
- 视觉顺序保持「保存」在左、「发布」在右；
- 顶部标题区已有的「未保存」琥珀色徽标保留，作为 `dirty` 的常驻指示
  （与弹窗里的分形态提示互为补充）；「未保存」徽标**可点击**，点后直接执行「保存」（§17 Q10）。

### 5.5 验收

- 点「发布」→ 先出现确认框，不再立即发出请求；
- 确认框取消 → 不发请求，画布与状态不变；
- 填写备注后确认 → 请求体带 `notes`，作品历史里该版本显示该备注；
- 校验失败 → 关闭确认框并弹出「无法发布」清单；
- 发布成功 → 弹出「已发布 v{N}」；点「预览」进入 `/works/{id}/view?project=…&v=…` 且内容正确；
  点「前往作品页」进入 `/works` 并能在表格里看到新行；
- 画布有未保存修改时点「发布」→ 弹窗显示「将先保存再发布」，主按钮为「保存并发布」，
  点击后先保存再发布，两步都成功才提示发布成功；
- **按钮主次**：「保存」为实心主按钮（`primary`）、「发布」为描边次按钮（`outline`），
  源码断言两按钮的 variant 归属与左右顺序；
- 画布 `dirty` 时「发布」**不**置灰、可点击（点开后弹窗按 `dirty` 分形态）；
- 只保存不发布：点「保存」只发保存请求，**不**产生新作品版本；
- 保存 / 发布按钮在请求进行中均禁用，且不会重复提交。

hex 值 + 一个 hex 输入框 + 「应用」按钮。它是抽屉里最高的一块区域，但 90% 的时间用户
只是想**看一眼当前是什么颜色**。

### 8.2 需求

**（a）抽屉内只展示当前选中（一层收束）**

- 「主题色」模块改为**一行**：
  `主题色` 标签 + **一个**当前色圆点（含 hex 文本，`font-mono`）+ 右侧「修改」（或整块可点击）按钮；
- 点击圆点 / 「修改」→ 打开 **`ThemeColorDialog`**（"多套一层"）；
- 抽屉内不再平铺调色板、不再放 hex 输入框。

**（b）`ThemeColorDialog`（新增组件）**

| 项 | 内容 |
|---|---|
| 标题 | 主题色 |
| 内容 1 | 15 色调色板（`THEME_COLOR_PALETTE`），当前色高亮（`scale-110 border-primary`） |
| 内容 2 | 自定义 hex 输入（`placeholder="#RRGGBB"`）+「应用」；（沿用 `normalizeHexColor` 校验） |
| 内容 3 | 预览：一个大圆点 + 主题色 hex 文本，实时反映 draft |
| 底部 | 取消 / 确定 |

- **确定** → 把 draft 色写回抽屉 state（**不落库**，仍由抽屉底部的「保存」提交给 store）；
- **取消 / × / Esc** → 丢弃 draft，抽屉颜色不变；
- 非法 hex → 输入框失焦时回退到当前色（沿用 v0.3.3 MOD-801 行为，不给提示、不阻塞）。

**（c）数据流**

- `ThemeColorDialog` 是**受控**组件：`open` / `value` / `onOpenChange` / `onConfirm(color)`；
- 不在弹窗里碰 store、不触发撤销步——保证「一次修改 = 一次保存 = 一个撤销步」的既有语义。

### 8.3 验收

- 抽屉「主题色」模块只剩一行；打开抽屉时高度明显小于 v0.4.1；
- 点当前色 → 弹窗打开且当前色已高亮；
- 弹窗选色后点「确定」→ 抽屉的当前色圆点与 hex 变化；点「取消」→ 无变化；
- 抽屉「保存」后参与者框主题色更新，且可撤销；
- 白色（`#FFFFFF`）与自定义 hex 都能正常设置。

## 9. FEAT-H09 抽屉底部固定「保存 / 取消」页脚

### 9.1 现状

`ParticipantDrawer` 的「保存」按钮位于**滚动内容区的最底部**（`space-y-2 border-t pt-3`），
当抽屉内容（线索 + 联动列表 + 位置条件列表）较长时，用户必须**滚到底**才能保存；
且**没有取消按钮**——想放弃修改只能关右上角的 ×，语义不明确。

### 9.2 需求

1. **结构**：抽屉改为三段式布局
   `标题栏（shrink-0）` + `内容区（flex-1 overflow-y-auto）` + **`页脚（shrink-0 border-t）`**；
   保存 / 取消按钮放进页脚，**始终可见、不随内容滚动**。
2. **按钮**：`取消`（`variant="outline"`）+ `保存`（primary），等宽或 `flex-1` 平分。
3. **取消语义**：丢弃本次抽屉内的全部本地编辑（主题色 / 线索 / 联动 / 位置条件），
   **关闭抽屉**；不调用 `setParticipantConfig`、不产生撤销步、不改动 store。
4. **关闭（右上 ×）/ Esc 语义**：与「取消」**完全一致**（丢弃并关闭）——把"关闭即丢弃"
   与"取消"统一，避免两种含义相近的动作产生不同结果。见 §17 Q6。
5. **保存语义**：不变（`onSave(slotIndex, { themeColor, clue, linkages, positionConditions })`
   → `editorStore.setParticipantConfig`，原子且可撤销），保存后**关闭抽屉**（现状即如此）。
6. **禁用条件**：线索超长（`clueOverLimit`）时「保存」禁用（现状保留）；
   「取消」永不禁用。
7. **空态**：抽屉打开但没有选中槽位时（`!slot`），页脚**不渲染**（保持现状的提示文案）。

### 9.3 验收

- 抽屉内容较长时，保存 / 取消仍在底部可见（不滚动）；
- 修改主题色 / 线索 / 联动后点「取消」→ 参与者框与数据**完全不变**，无 toast、无撤销步；
- 点「保存」→ 变更生效且可撤销，抽屉关闭；
- 右上 × 与 Esc 的结果与「取消」一致；
- 线索超长时「保存」置灰，「取消」可点。

## 12. DEV-H12 `npm run dev` 支持可选端口参数

### 12.1 现状

```json
"dev": "concurrently -n server,web -c cyan,magenta \"npm:dev:server\" \"npm:dev:web\""
```

- 端口写死在两处：`packages/server` 的 `PORT`（默认 3000）与 `packages/web/vite.config.ts`
  的 `server.port: 5173` + `proxy['/api'].target = 'http://localhost:3000'`；
- 想换端口只能：改 `.env`、或改 `vite.config.ts`（改完还会忘记同步 proxy target），
  或分别手动 `PORT=4000 npm run dev:server` + `npm run dev:web`；
- **最容易踩的坑**：`.env` 里的 `PUBLIC_BASE_URL=http://localhost:3000` 用于拼接
  上传文件的访问 URL（`buildFileUrl`）——只改后端端口而不同步改它，
  角色头像 / 物品图 / 游戏封面会全部 404。

### 12.2 需求

`npm run dev` 支持两个**可选**参数：

| 参数 | 缩写 | 默认 | 作用 |
|---|---|---|---|
| `--server-port <n>` | `-s` | `3000` | 后端监听端口 |
| `--web-port <n>` | `-w` | `5173` | 前端 Vite 端口 |

用法：

```bash
npm run dev                              # 与现在完全一致：3000 + 5173
npm run dev -- --server-port 4000         # 后端 4000，前端 5173
npm run dev -- -w 5180                    # 前端 5180，后端 3000
npm run dev -- -s 4000 -w 5180            # 两个都自定义
```

**行为约定**

1. **参数可选非必填**：不传 = 沿用默认值（3000 / 5173），**行为与 v0.4.1 逐字一致**；
2. **参数优先级**：命令行 > `.env`（即传了就用传入值，覆盖 `.env` 里的 `PORT`）；
3. 启动时先校验：必须是 `1~65535` 的整数；非法值（非数字 / 越界 / 重复传参）→
   打印一行中文错误并以**非 0 退出码**结束，**不启动任何进程**；
4. 两个端口相同时（例如 `-s 5173 -w 5173`）→ 报错退出并指明冲突；
5. 启动后打印一行汇总，便于复制：
   `后端 http://localhost:{serverPort}  ·  前端 http://localhost:{webPort}`；
6. 保留既有的 `dev:server` / `dev:web` 单跑脚本（`dev:web` 仍可 `npm run dev:web -- --port 5180`）。

**实现约定**

- 新增 `scripts/dev.mjs`（Node，无第三方解析库），根 `package.json` 的 `dev` 改为 `node scripts/dev.mjs`；
- 端口注入方式：
  - **server**：环境变量 `PORT`、`PUBLIC_BASE_URL=http://localhost:{serverPort}`（**必须同步**，见 12.1 的坑）；
  - **web**：`vite --port {webPort} --strictPort`，并注入 `VITE_PROXY_TARGET=http://localhost:{serverPort}`；
- `vite.config.ts` 的代理 target 由硬编码改为
  `process.env.VITE_PROXY_TARGET ?? 'http://localhost:3000'`（不设环境变量时行为不变）；
- 保留 `concurrently` 的彩色前缀输出（已依赖）：以编程方式调用
  `concurrently([{ command, name, prefixColor, env }])`；若改用 `child_process.spawn`
  自行转发输出也可，但须保证**两个子进程都随主进程退出而终止**（`SIGINT` 转发）；
- `.env.example` / README 补上新的启动参数说明。

### 12.3 验收

- `npm run dev`（无参数）→ 与 v0.4.1 完全一致（3000 + 5173，代理正常）；
- `npm run dev -- -s 4000 -w 5180` → 后端监听 4000、前端监听 5180，
  前端 `/api` 代理打到 4000，**上传的图片 URL 指向 4000 且能打开**；
- `npm run dev -- --web-port abc` / `--server-port 70000` → 打印错误、退出码非 0、不启动进程；
- `Ctrl+C` 能同时结束两个子进程（不残留占用端口的进程）；
- `npm run dev:server` / `npm run dev:web` 仍可单独使用。

### 18.2 实现期裁定（对 §17 默认取值的细化，语义不变）

1. **Q7 的组件形态**：`RegionSection` 用**一个可选对象参数** `actions?: RegionActionHandlers`
   控制三按钮，而不是 `showActions?: boolean`。两种写法等价，但对象参数让 TypeScript 自己收窄
   「给了 actions 就一定给了三个 handler」，不必在 JSX 里写非空断言。方格分支**完全不传**该参数。
2. **Q5 的百分比展示**：区域信息里的 `填充` 由裸值（`0.35`）改为百分比（`35%`）——§10.2 的目标
   形态写的是「填充 35%」，而 `fillOpacity` 在 schema 里是 `0..1`，因此渲染时 ×100 取整。
3. **Q10 的落点**：「未保存」徽标由 `<span>` 改为 `<button>`，点击即 `onSave`；`disabled={saving}`，
   样式保持不变（`amber` 底色），因此视觉上仍是徽标、行为上是快捷方式。
4. **Q14 的实现方式**：淡化是 `opacity` 的**内联样式**，高亮 / 激活只通过 `box-shadow` 描边叠加，
   两者互不覆盖 —— 所以激活时不会「顺手」恢复不透明。
5. **Q15 的边界**：新测试文件里的**测试名与注释**一律用「编号 / 参与者」；代码标识符
   （`slot` / `numbers` / `placeParticipant`）保持不变。
6. **`ParticipantPanel.placedDim.test.ts` → `.test.tsx`**：本版为 §15.1(b) 补了 jsdom 渲染断言，
   必须走 JSX；`import.meta.glob` 的源码断言与渲染断言放在同一文件的两节里（同
   `MapInfoDrawer.test.tsx` 的做法）。
7. **OPT-H02 的验证方式**：不逐个文件列清单，而是新增 `src/wording.test.ts` 把
   `src/**/*.{ts,tsx}`（除 `.test.` 文件）全量以 `?raw` 读入，断言**没有任何**生产文件含「项目」。
   这同时把「日后新增文案又写回『项目』」变成红灯。
8. **DEV-H12 的命令转发**：根 `dev:server` / `dev:web` 末尾补了一个 `--`，让
   `npm run dev:web -- --port 5180` 能真正把参数透传给 `vite`（否则会被内层 `npm run` 吃掉）。
   `scripts/dev.mjs` 以**编程方式**调用 `concurrently([{ command, name, prefixColor, env }])`，
   保留彩色前缀与 `Ctrl+C` 一起收尾的既有行为；`web` 侧加 `--strictPort`，避免端口被占时
   Vite 静默换端口而让用户以为参数没生效。
