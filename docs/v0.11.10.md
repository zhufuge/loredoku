# v0.11.10 — 主题字体与同一张脸

## 0. 范围与口径

一句话：主题配置多一格「标题字体」，列表页的标题用作者挑的那支字；播放器列表页与工坊列表页
（`/:code/play`）合成一套骨架，两个入口长的是同一张脸。

口径五条：

1. **字体挂在主题上**，不是全站设置：`themes.data.fontFamily`。取值与地图区域标签同一套
   （内置 key `system` / `serif` / `sans` / `kai` / `mono`，或 `src/assets/fonts/` 里的具体
   字族名），校验复用 `isMapStyleFontFamilyName` —— 两个地方认同一批名字，作者不必学两套。
2. **缺席 = 页面自己的衬线**。「默认（衬线）」这一项不写键：旧主题与没动过这一格的主题，
   行为与 v0.11.9 一模一样。
3. **跟着包走**：导出时冻进 `manifest.theme.fontFamily`。播放器没有 `/themes` 查询，只能从包里读；
   改字体要重新导出，与「文案跟着包走」是同一条规矩。老包没这个键，标题按衬线画。
4. **骨架只有一份**：`GameListShell`。两个入口的差别只剩「数据从哪来」与「有没有进入工坊」，
   其余（落花、钉住的页头、只滚卡片区、空态、计数行）都在一个文件里。
5. **加载态统一按播放器**：整页 `LoadingScreen`，不先画骨架。理由见 §2。

## 2. 设计裁定

**为什么字体在主题上，而不是在列表页上。** 标题写的是主题名（「红楼梦」），字体是
「这个空间怎么说话」的一部分，与难度分级、列表页那两行字同一层。放在全站设置里，就得为
每个主题记一遍例外；放在页面上，又没有「页面」这个可持久化的东西可放。

**为什么默认是衬线，而不是系统 sans。** v0.11.9 的标题是 `font-serif`（主题名带一点书的味道）。
换成系统 sans 会是**静默的视觉改版** —— 没配过字体的主题不该因为这次改动变了样，所以
「默认（衬线）」就是「不写这个键」。想用 sans 的作者自己在那一格选 `系统默认`。

**共用骨架的边界。** 骨架管「这一页长什么样、怎么滚、空的时候说什么」；数据、存档键、卡的
落点、有没有进入工坊，由调用方给。播放器的一份包与工坊的一次查询，除了「从哪读」以外没有
共同点，硬把数据层也塞进骨架，两边都得为对方加旁路。

**加载态为什么统一成整页。** 列表页的标题是主题名，而主题名的字体现在是可配的 —— 骨架屏
先把标题画出来、字体到了再换字形，正好是这里要消灭的那一帧。播放器原本就是「包 + 字体 +
封面都齐了才一次画成」，工坊这边既然共用这套骨架，就跟着它走。

**「已通过 0 关」为什么收掉。** 一题没解时这个数字只会让人以为自己漏了什么；v0.11.9 在工坊
列表页收掉了，播放器这一版跟上，两边说法才一致。

## 5. 没做的

- **没做「每关一套字体」**：字体是主题级的说法，关卡不该各自挑字。
- **没做字体预览图**：下拉里就是名字，下面一行用 `theme.name` 实时渲染 —— 名字本身就是预览。
- **播放器的整页加载态没换成骨架屏**：这一版反过来，让工坊跟播放器一致（§2）。
- **没动难度档位与卡片**：它们已经在 v0.11.9 统一过。
- **没改 `document.title`**：播放器那页依旧不写标题 —— 它不是这次要统一的东西。

## 6. 计时、对齐与 iOS（同一轮补上的三件）

用户一口气提了三件：「修改游戏页面的时间，和前面标题上下对齐；同时修改开始计时时间是加载完成后
才开始计时，而不是开始加载就计时。检查全局，修改适配 iOS 的浏览器，『定案』文本又偏移了。」
三件都在 iOS 上会走样，底下是同一个毛病：**拿去对齐 / 定位的东西，各引擎算出来的不是一样多。**

**计时从「加载完成」起。** 水合只把存档装进表、**不放开走**（`hydrateTimer(startFrom, false)`），
另有一条 effect 等 `resourcesLoading`（三个查询 + `useImagePreload`）落下来的第一拍才
`resumeTimer()`。加载里那几秒玩家还什么都没看见，不该记进成绩。已完成再进入（`revisitedRef`）
照旧定格 00:00。检查放在 `GamePage.test.tsx`：图没到齐时过去 10 秒、就绪那一刻仍写 `01:00`，
再走 2 秒才是 `01:02` —— 旧做法在这一条上会把那 10 秒算进去。

**计时与标题对齐用中线。** 那一行原来是 `items-baseline`，而标题那个 `<p>` 带 `truncate`
（`overflow: hidden`）。Safari 给这种盒子取的「基线」是盒底而不是文字基线，iOS 上计时会整行
往下沉一截；两者的行盒本来就同高（14px / 20px），改 `items-center` 各引擎一致，盒与盒也仍然
对齐（实测 `top 56 / bottom 76 / h 20` 两边相同）。

**「定案」不再靠竖排 + 字距。** 原来是 `[writing-mode:vertical-rl]` 加 `tracking-[0.25em]`。
竖排里的 `letter-spacing` 在最后一个字后面补的那一格，Safari 与 Chromium 给的不一样 —— 两字
整体就沿着字列蹿一截。改成 `flex flex-col` 装两个 `<span>`（「定」「案」各一行）、间距用
`gap-[0.25em]`：字形间距与原来同一档（0.25em），但盒子不再取决于引擎在行尾怎么处理字距。
`textContent` 仍是「定案」，卡片与遮罩两档都不动字体、颜色与 `-rotate-[14deg]`。

**全局的 iOS 收口。** 扫了一遍 `packages/web/src` 里会走样的写法，只有一处成片：`h-screen` /
`min-h-screen` 在 iOS 上取的是「地址栏收起后」的高度，整屏壳子会有一条落到工具栏底下。
全部换成 `h-dvh` / `min-h-dvh`（`100dvh`，跟着可见区走），共 14 个文件：`LoredokuLoader`、
`GameListShell`、`AppShell`、`WorkspaceLayout`、`EditorShell`、`ErrorBoundary`、`GamePage`
（出错态）、`MapEditorPage`、`MapViewPage`（三处）、`PuzzleEditorPage`、`PuzzleViewPage`（两处）、
`PlayerGamePage`。其余几样早年已经收过：`zoom` 不再用于缩放（v0.11.3 §5）、`backdrop-filter`
带 `-webkit-` 前缀、`user-drag` 带 `-webkit-`、主屏 `GamePage` 本来就是 `h-dvh`。

验证：`npm run typecheck` 无 error、`npm run lint`（oxlint 0 警告 0 错误）、`npm run build`（3.62s）、
`node scripts/run-tests.mjs packages/web`（95 文件 / 1,287 用例）。浏览器实测（Chromium）：
计时行 `align-items: center`、计时与标题同高同位；进关计时 `00:00 → 00:01 → 00:04` 在走；
列表页已完成卡片上的「定案」仍是两字一列、斜 -14°、印在右。**iOS 本机复验留给用户**：
本机没有 Safari / WebKit，只能把「取基线取盒底」「竖排字距收尾」这两处不确定的算式从布局里删掉。

**竖屏的谜题描述弹框。** 那个弹框的标题是 `sr-only`，正文原来直接落在 `DialogContent` 的
`p-6` 上 —— 右上角那枚 X 是绝对定位在 `top-4`，第一行字正好从它底下穿过去。给 `DialogContent`
加 `pt-12` 让开那 16px 的 X，底部补一枚「关闭」：竖屏单手够不到右上角，读完描述顺手就能收；
按钮落在 `DialogFooter` 里，竖屏是整行宽。
