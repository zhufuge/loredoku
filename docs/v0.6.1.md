# 设计：资源多形态 + 删除资源占格子宽高字段（v0.6.1）

> **状态**：**已实施**（2026-10-19，含「背景资源也多形态」第二阶段）。设计即本文；
> 落地记录见 §13。
> 需求原文：`v0.6.1 资源的多形态功能设计；同时，资源删除占格子宽高字段`
> 第二阶段追加：`背景资源也有多个形态`
>
> **背景**：v0.6.0 把资源库改名叫 `assets`、画布物件层改叫物品（`item`），三层语义
> （`asset` 资源库行 / `item` 画布实例 / 联动指向 `asset`）已落地。本版在 `assets`
> **内部再拆一层**：资源行只剩「身份 + 行为」，**外观与占格全部下沉到形态行** ——
> 一个资源由此可拥有多个形态（如「关闭 1×1」「打开 2×2」），每个形态有自己的
> 图片 / 纯色 / 填充方式 / 占格宽高。**第二阶段把「一个资源一个形态」的最后限制也
> 取消**：背景资源同样可以挂多个形态（草地 / 沙地 / 雪地），只有占格仍恒 1×1。

## 0. 一句话

`assets` 瘦身成「这是什么 + 阻不阻挡」；新建表 `asset_forms` 承载「长什么样 +
占几格」；画布锚点从 `{ assetId, w, h }` 变成 `{ assetId, formId, w, h }`
（`formId` 可选，缺失回退首形态），`MAP_JSON_VERSION` 4 → 5。第二阶段背景引用
也带上 `formId`（§6.3），`MAP_JSON_VERSION` 5 → 6。

## 1. 现状

### 1.1 资产行今天扛了三件事

| 职责 | 今天的落点 |
|---|---|
| 身份 | `code` / `name` / `type` |
| 行为 | `blocking`（背景恒 false，`blockingFor` 单点收口） |
| 外观 | `fit_mode`、`image_path/mime/size/width/height`、`bg_color` |
| 占格 | `width_cells` / `height_cells` |
| 状态 | `is_active` |

「外观」与「占格」都是**一份资源只有一套**——想让同一个资源有第二种样子或第二种
占位，只能整行复制（code、外观、阻挡全白复制一份）。

### 1.2 落位链路（宽高的流向）

```
调色板选中 asset → pendingAsset = assetsById.get(selectedAssetId)
  → EditorCanvas.pendingFootprint = { w: asset.widthCells, h: asset.heightCells }
  → 点击画布 → MapEditorPage.onPlaceItem
  → editorStore.placeItem({ id, widthCells, heightCells }, x, y)
  → cells["x,y"].item = { assetId, w, h }     ← 几何在此冻结
```

### 1.3 渲染链路（外观永远现查）

`DraftAnchorItem { assetId, formId?, w, h }` 只存**引用 + 几何**；图片、纯色、
填充方式是渲染时按 `assetId`（+ `formId`）从资源库现查（`assetsById.get(...)`，
见 `MapAssetLayers.tsx` / `AssetThumbnail.tsx`）。背景格更极端——
`DraftAssetRef { assetId, formId? }` 连宽高都没有（恒填 1 格）。

**这条事实是本设计的支点**：外观一直都是「现查」的，所以把外观搬到形态行之后，
渲染只需把「查谁」从 `assetsById` 换成「先按 formId 找形态、找不到回退首形态」，
五个渲染页的 `assetsById` 构建代码**一行不用改**。

### 1.4 快照 / 旧游戏：本版不引入回归

游戏页 `useAssets({})` **不过滤 `is_active`**，图片 URL 直指资源库文件。也就是说
**今天改一个资源的图片，已部署的旧游戏就会跟着变**；形态沿用同一套语义（形态行
在、外观就现查得到），因此「外观下沉到形态」**不是回归**，只是把同一个语义换了个
载体。快照自证外观（§12）明确不做。

## 2. 目标语义：asset → forms → 画布锚点

```
assets        一行一个资源：code / name / type / blocking / isActive
asset_forms   一行一个形态：name / w×h / 图片 / 纯色 / 填充方式
画布锚点      cells[k].item = { assetId, formId, w, h }   ← 引用 + 几何冻结
```

- **资源**回答「这是什么、能不能站上去」。
- **形态**回答「它以什么样子、占几格存在」。
- **锚点**回答「这一格放的是它的哪个形态」：冻结 `formId` 与 `w/h`。

## 3. 数据模型

### 3.1 `asset_forms`（新表）

```sql
CREATE TABLE asset_forms (
  id            bigserial PRIMARY KEY,
  asset_id      bigint      NOT NULL REFERENCES assets(id) ON DELETE CASCADE,
  name          varchar(32) NOT NULL,
  width_cells   integer     NOT NULL,
  height_cells  integer     NOT NULL,
  -- 外观（从 assets 搬来，列名与类型一字不改）
  fit_mode      varchar(16) NOT NULL DEFAULT 'cover',
  image_path    text,
  image_mime    varchar(64),
  image_size    integer,
  image_width   integer,
  image_height  integer,
  bg_color      varchar(7),
  -- 调色板顺序
  sort_order    integer     NOT NULL DEFAULT 0,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uq_asset_forms_asset_name  ON asset_forms(asset_id, name);
CREATE INDEX        asset_forms_asset_id_index ON asset_forms(asset_id);
```

| 决策 | 取值 | 理由 |
|---|---|---|
| 主键 | `bigserial` | 与全库一致（应用层从不预生成） |
| 外键 | `ON DELETE CASCADE` | 形态是资源的从属；资源硬删连带删形态 |
| 宽高约束 | **不建 DB CHECK**，沿用 zod（1~12） | 与今天的 `assets.width_cells` 一致——那两列也从无 CHECK |
| 形态名唯一 | `(asset_id, name)` 唯一索引 | 同一资源下「横放」只能一个；跨资源可重名 |
| 排序 | `sort_order`，插入取 `MAX+1`，响应按 `sort_order, id` | 调色板顺序；**不做拖拽排序 API**（§12） |
| `updated_at` | 应用层维护（`db.fn.now()`） | 与全库一致，无 DB trigger |
| `is_active` | **形态不带** | 启用/停用是资源级开关（§4.5），形态没有独立的可见性语义 |

新表由 PG 自动生成约束名（`asset_forms_*_not_null` 等），天然对齐表名，不存在
v0.6.0 收口过的历史前缀问题。

### 3.2 `assets` 删掉的十列

`width_cells`、`height_cells`、`fit_mode`、`image_path`、`image_mime`、
`image_size`、`image_width`、`image_height`、`bg_color`
——**九列**（`code`/`name`/`type`/`blocking`/`is_active`/时间戳保留）。

> 磁盘上的图片**不动**：形态只是把 `image_path` 这个字符串搬到自己行里，
> `assets/<assetId>/…` 的路径规则照旧。新上传的形态图片落在
> `assets/<assetId>/forms/<formId>/…`（§7.6）。

## 4. 行为规则（不变量）

1. **每个资源至少一个形态**：删除到最后一个 → 409「资源至少要保留一个形态」。
2. **背景资源也可以有多个形态**：`POST /forms`、`DELETE /forms/:formId` 与物品
   完全同规则——一个背景资源下面可以挂「草地 / 沙地 / 雪地」，各有自己的图。
   唯一保留的差别是**占格**：`PATCH /forms/:formId` 允许改外观，但**拒绝改
   `widthCells` / `heightCells`**（400「背景资源的形态占格恒为 1×1，不能修改」）
   ——背景恒填 1 格，占格字段对它不参与渲染，改它是个谎言。
3. **`item ↔ background` 切换**：双向放行，**保留全部形态**。切背景不删形态
   （用户的数据不该因为改个类型就静默消失），切物品也不给占格解锁以外的任何
   东西。**不做级联删除**。
4. **资源可启用的前提 = 至少一个形态有外观**：
   ```
   activatable = asset.forms.some(f => hasAppearance(Boolean(f.imageUrl), f.bgColor))
   ```
   沿用 v0.5.1 的 `hasAppearance`，与「删图后自动停用」是同一个谓词。
   删除某形态的图片后，若**所有形态都没有外观了** → 资源自动停用。
5. **形态的增删改不影响已放置的锚点几何**：放置是拷贝（形态的 w/h → 锚点 w/h）。
   但形态的**外观**是现查的——改形态图片，画布上所有引用它的格子立刻变，
   这与今天改资源图片的行为完全一致（§1.4）。
6. **删除形态前查占用**：若该形态被**草稿画布**引用（`cell.item.formId` 或
   `cell.background.formId` 命中）→ 409「该形态已被 N 张地图使用」。已发布版本
   与已部署游戏不查（快照是历史，删了也不回头改），渲染时走 §6.2 的回退。
7. **占用检查、联动目标仍是资源级**：`AssetUsage`、谜题联动指向资源（v0.6.0
   语义），形态无感知。

## 5. API

### 5.1 DTO（shared/types/domain.ts）

```ts
/** 外观字段组——形态是它唯一的宿主。 */
export interface AssetAppearance {
  fitMode: AssetFitMode;
  imagePath: string | null;
  imageUrl: string | null;
  imageThumbUrl: string | null;
  imageMime: string | null;
  imageSize: number | null;
  imageWidth: number | null;
  imageHeight: number | null;
  bgColor: string | null;
}

export interface AssetForm extends AssetAppearance {
  id: number;
  assetId: number;
  name: string;
  widthCells: number;
  heightCells: number;
  sortOrder: number;
  createdAt: string;
  updatedAt: string;
}

export interface Asset {
  id: number; code: string; name: string;
  type: AssetType;
  blocking: boolean;
  isActive: boolean;
  createdAt: string;
  updatedAt: string;
  /** 按 sort_order, id 排序；长度 ≥ 1。 */
  forms: AssetForm[];
}
```

`Asset` 删掉 `widthCells`/`heightCells`/`fitMode`/`image*`/`bgColor` 共 9 个字段。

配套的解析函数（放在 `shared/src/assetRules.ts`）：

```ts
/** 锚点 formId → 形态；缺失或找不到都回退首形态。 */
export function resolveAssetForm(asset: Asset, formId?: number | null): AssetForm | undefined;
```

### 5.2 资源端点（瘦身）

| 端点 | 变更 |
|---|---|
| `GET /api/assets`、`GET /api/assets/:id` | 响应内嵌 `forms`（一次 `WHERE asset_id IN (…)` 带出，按 `sort_order, id`）；去掉 9 个外观/占格字段 |
| `POST /api/assets` | 入参去掉 `widthCells` / `heightCells`；`bgColor`、`fitMode` **保留**，语义是「初始形态的外观」（§4/§8.4）。服务端一次事务插两行：资源 + 名为「默认」的 1×1 形态 |
| `PATCH /api/assets/:id` | 入参去掉 `widthCells` / `heightCells` / `fitMode` / `bgColor`（多形态下这些字段归属不明，一律走形态端点）；保留 `name` / `type` / `blocking` / `isActive` |
| `POST /api/assets/:id/image`、`DELETE /api/assets/:id/image` | **删除**，图片搬形态（§5.3） |
| 其余（启用/停用/删除/占用） | 不变 |

### 5.3 形态端点（新增，嵌套在资源下，与旧的 `/:id/image` 同风格）

```
POST   /api/assets/:assetId/forms                  { name, widthCells, heightCells }
PATCH  /api/assets/:assetId/forms/:formId          { name?, widthCells?, heightCells?, fitMode?, bgColor? }
DELETE /api/assets/:assetId/forms/:formId          204
POST   /api/assets/:assetId/forms/:formId/image    上传（multipart，字段名 image）
DELETE /api/assets/:assetId/forms/:formId/image    删图
```

- 三个非图片入口先校验资源存在（404）。
- 形态名：trim、1~32 字（`ASSET_FORM_NAME_MAX_LENGTH`）、同资源内不重名 → 409。
- 宽高：整数 1~12，复用 `assetSizeSchema`；背景资源的形态发宽高 → 400（§4.2）。
- `DELETE` 顺序：存在 → 非最后一个 → 未被草稿引用（§4.6）→ 204。
- `PATCH` / `POST` 返回更新后的 `AssetForm`；图片上传/删除返回**更新后的整个
  `Asset`**（沿用旧 `/image` 端点的返回习惯，前端直接拿去刷缓存）。

## 6. 画布 JSON 与快照（v4 → v5）

### 6.1 锚点加 `formId`

```ts
export const draftAnchorItemSchema = z.object({
  assetId: z.number().int().positive(),
  formId: z.number().int().positive().optional(),   // v0.6.1 新增
  w: z.number().int().min(1),
  h: z.number().int().min(1),
});
```

- `draftCellSchema` 是 `.strict()`，必须显式声明 `formId`，否则新数据写入会被拒。
- **可选**是关键：存量 v4 锚点缺字段照样过校验，渲染走回退。
- `MAP_JSON_VERSION` 4 → 5（只作戳记，`mapDraftSchema.version` 仍然是
  `positive()`，不校验相等，见 §1.4）。

### 6.2 渲染回退规则（唯一权威）

```
form = asset.forms.find(f => f.id === anchor.formId) ?? asset.forms[0]
```

三条分支都要能落地：

| 情况 | 结果 |
|---|---|
| 锚点有 `formId` 且形态在 | 用那个形态的外观 |
| 锚点无 `formId`（v4 存量） | 用首形态 |
| `formId` 指向的形态已删除（§4.7 只挡草稿引用，历史快照挡不住） | 用首形态 |

`MapBackgroundLayer` 同理：背景引用带 `formId` 时取那个形态，缺字段（存量）时
取 `asset.forms[0]`。

### 6.3 背景格也带 `formId`（v5 → v6）

背景资源放开多形态后，背景格必须能说自己刷的是哪个形态，否则同一片草地上
想混几种地表就办不到：

```ts
export const draftAssetRefSchema = z.object({
  assetId: z.number().int().positive(),
  formId: z.number().int().positive().optional(),   // v0.6.1 续新增
});
```

- 与物品锚点同一个口径：**可选**，缺字段走 §6.2 的回退。
- `MAP_JSON_VERSION` 5 → 6。迁移 `…00029` 给存量背景格补上 `formId`（§7.6）。
- 编辑器放置背景时把选中形态的 id 写进格子里（`editorStore.placeBackground`）。

## 7. 数据迁移 `20260101000028_v061_asset_forms.ts`

### 7.1 up（单事务）

1. `CREATE TABLE asset_forms`（§3.1 DDL + 两个索引）。
2. 逐行搬：
   ```sql
   INSERT INTO asset_forms (asset_id, name, width_cells, height_cells,
                            fit_mode, image_path, image_mime, image_size,
                            image_width, image_height, bg_color,
                            sort_order, created_at, updated_at)
   SELECT id, '默认', width_cells, height_cells,
          fit_mode, image_path, image_mime, image_size,
          image_width, image_height, bg_color,
          0, now(), now()
     FROM assets;
   ```
   **所有资源（含背景）各补一个「默认」形态**，宽高照搬旧列——背景行的宽高不参与
   渲染（§4.2），保原值只为 down 无损。
3. 改写画布：读 `asset_forms` 出「资源 → 首形态 id」映射，给 `maps.data` 与
   `games.snapshot.map` 的每个 `cells[k].item` 补 `formId`，并把 `version` 4 → 5
   （手法照抄 `…00025` 的 `rewriteMapCells`：逐行读 JSON → 就地改 → 回写）。
4. `ALTER TABLE assets DROP COLUMN` 九列。

### 7.2 down（单事务，严格反向）

1. `ALTER TABLE assets ADD COLUMN` 九列（宽高 `NOT NULL DEFAULT 1`，其余可空）。
2. 回填：取每个资源的首形态（`DISTINCT ON (asset_id) … ORDER BY asset_id,
   sort_order, id`）写回九列。
3. 改写画布：删掉 `item.formId`，`version` 5 → 4。
4. `DROP TABLE asset_forms`。

### 7.3 往返验收

- up → down → up，每一步 dump `assets` 全列与 `asset_forms` 全列逐字段比对。
- **已知的有损点（必须如实记录）**：up 第 3 步给锚点补的 `formId`，在 down 第 3 步
  被整列删掉——这是设计使然（v4 没有这个字段），不是缺陷。除此之外资产行与形态行
  **逐字段 0 差异**。
- 若某资源在形态表里被人为改了排序，down 回填取「首形态」，可能与 up 之前的原值
  不同——迁移路径上不会发生（up 之后没人改数据就 down），验收时不测这条。

### 7.4 与 `…00026` 的交互

`…00026`（v0.6.0 约束收口）把 `assets_width_cells_not_null` 等约束名统一了。本迁移
drop 九列时这些约束随之消失；down 重新加列时 PG 按 `表_列_not_null` 自动重建同名
约束，链式回滚对得上。

### 7.5 失败即整体回滚

单事务，任一步失败全回滚（与 `…00025` 同一手法）。

### 7.6 背景多形态迁移 `20260101000029_v061_background_forms.ts`

表结构不动（`asset_forms` 早就能容纳任意多个形态，限制一直在服务层代码里），
改的只有画布 JSON：

- up：给 `maps.data` / `games.snapshot.map` 的每个 `cells[k].background` 补
  `formId`（取「资源 → 首形态」，与 API 排序一致），`version` 5 → 6；
- down：摘掉 `formId`，`version` 6 → 5；
- 手法与 `…00028` 完全一致：逐行读 JSON → 就地改 → 回写，一个事务。

`formId` 是可选的，所以不补数据也能跑；补只是为了「v6 画布里背景格都显式带着
自己选的是哪个形态」，与 `…00028` 对物品锚点的处理同一个口径。

**往返实测**（up1 / down / up2 逐字段 dump 比对）：`maps` 14 行、`games` 4 行、
`asset_forms` 38 行，**0 差异**；up 后 284 个背景格全部带上 `formId`、9 张地图
落到 v6（其余 5 张是 v2/v3 存量，两次迁移都不碰），down 后背景格 `formId` 归零。

### 7.7 新上传的形态图片路径

`utils/image.ts` 加一个入口，复用 `processImage`：

```ts
export async function processAssetFormImage(
  assetId: number, formId: number, buffer: Buffer,
): Promise<ProcessedImage> {
  return processImage(`assets/${assetId}/forms`, formId, buffer, THUMBNAIL_MAX_DIMENSION);
}
```

→ `assets/<assetId>/forms/<formId>/<uuid>.<ext>`，目录仍归资源所有，uuid 防重名。

### 8.4 详情页形态管理区

```
资源区：名称 / 类型 / 阻挡                                    [保存]

形态区
  ┌ 形态 1 · 默认 ─────────────────────────────────┐
  │ [缩略图]  名称 [默认]  占格宽 [1] 高 [1]        │   ← 背景资源隐藏占格
  │          填充方式 [cover ▾]                     │
  │          外观 [图片 | 纯色]  + 上传/删除图片     │
  │                              [保存形态] [删除]   │
  └────────────────────────────────────────────────┘
  [+ 添加形态]
```

背景资源的形态卡只少两样：占格输入框（恒 1×1，不给改）和删除按钮的可用条件
与物品完全相同（形态数 ≤ 1 才禁用）。「添加形态」按钮两类资源都有。

- 资源区「保存」只提交 `name` / `type` / `blocking`。
- 每张形态卡一个「保存形态」，提交 `name` / `widthCells` / `heightCells` /
  `fitMode` / `bgColor`；图片上传/删除即时生效（与今天一致）。
- 删除按钮：形态数 ≤ 1 或被占用 → 禁用 + 提示（服务端 409 兜底）。

### 8.5 调色板

一张形态一张瓦片，**物品层与背景层同一套规则**：缩略图（形态自己的外观）+
资源名 + 形态名 + `w×h` 徽标。搜索匹配 资源名 / code / 形态名。背景瓦片的
`w×h` 恒显示 `1×1`——那不是省略，是事实。

> 评估过的替代方案：资产瓦片点击后展开形态 chips——平板网格空间放不下长形态名，
> 且「你放置的东西是形态」应当一眼可见，故选平铺。

## 11. 收益与代价

**收益**

- 一个资源可表达多个「样子 + 占位」（宝箱开/关、树大/小、家具横/竖），不再为换一
  种样子整行复制资源。
- 资源行回归「这是什么 + 能不能站」；外观与几何归形态；概念单一化。
- 五个渲染页的 `assetsById` 构建代码零改动——`Asset` 自带 `forms`，渲染只换
  「查谁」。

**代价**

- 多一张表、五个端点、一个详情页管理区。
- 画布 JSON 升到 v5，存量锚点要改写（§7.1 第 3 步）。
- 调色板从「资源瓦片」变「形态瓦片」，交互有一处小变化。
- 形态外观是现查的：改形态图片，所有引用它的画布（含已部署游戏）立刻变——
  与今天改资源图片的行为一致，但需要在文档里说清，避免误以为「改形态只影响新放置」。

## 12. 遗留（明确不做）

- **快照自证外观**：让已部署游戏冻结部署那一刻的形态图片（不随资源库编辑而变）。
  今天游戏页就是现查资源库的，本版不引入这个语义变更；要做得连快照一起扩，
  是独立专项。
- **形态拖拽排序 / 上调下调**：`sort_order` 已留，API 与 UI 不做。
- **画布上「换成另一形态」**：放置后只能擦除重放；不做就地变换（需锚点改写 +
  碰撞重算）。
- **形态级启用/停用**：启用是资源级开关（§4.5），形态不单独可见性。
- **批量占位预设模板**（L 形四格等）：形态已是通用机制，模板是上层快捷方式。

### 13.2 与设计的偏差（都是实施时才发现必须这么做）

1. **`bg_color` 保持 `text`，不用 `varchar(7)`**。新表本来可以收紧，但 `down` 要把这一列搬回
   `assets`，而它历史上就是 `text`——收紧会让「up → down」的列定义出现差异。
2. **搬迁 INSERT 必须 `ORDER BY id`**。`asset_forms` 的 `id` 由插入顺序决定，`sort_order`
   全是 0，「同资源的首形态」就依赖 id。第一次跑出来的 up→down→up 正是因为
   `SELECT … FROM assets` 的返回顺序在两次执行间不同，导致所有 `formId` 全变；加
   `ORDER BY id` 后往返 0 差异。
3. **`AssetThumbnail` 的入参从整个 `Asset` 换成 `appearance` + `name`**。外观不再挂在资源上，
   让组件自己去资源里取形态等于把「取哪个」的判断散到各处；现在调用点先 `resolveAssetForm`
   再传进来，判定只有一处（4 个调用点）。
4. **详情页拆出 `AssetFormCard`**。一个资源几个形态就有几张卡，卡片自己持有草稿状态与图片
   mutation，比塞进一个大表单好读。
5. **`PATCH /api/assets/:id` 不再接受 `fitMode` / `bgColor`**。多形态下「资源级填充方式」没有
   明确含义，一律走 `PATCH /forms/:formId`。

### 13.3 迁移往返实测

up → down → up，`assets` 全列、`asset_forms` 全业务字段、`maps.data` / `games.snapshot`
逐字段比对 **0 差异**；down 后 `assets` 的九列类型与原定义逐一吻合（`bg_color` text、
`fit_mode` varchar default `'cover'`、`image_path` text、宽高 integer default 1），
`asset_forms` 表消失、画布里的 `formId` 全部摘除、`version` 回到 4。

**唯一的有损点**：up 补进锚点的 `formId` 在 down 时整列删掉——v4 没有这个字段，这是设计
使然，不是缺陷。

### 13.4 第二阶段：背景资源也多形态（2026-10-19 续）

需求追加一句「背景资源也有多个形态」，把第一阶段设的最后一条限制取消。**没有升版本号**
——同一个专项的多阶段续写本文（项目约定）。

**改了什么**

| 层 | 改动 |
|---|---|
| shared | `DraftAssetRef` 加 `formId?: number`；`draftAssetRefSchema` 同步；`MAP_JSON_VERSION` 5 → 6；`AssetForm` / `assetForm.ts` 的注释去掉「背景只有一个形态」 |
| server | `assetFormService` 删掉 `assertItemType`（背景增删形态不再 400），保留「背景不能改占格」；`assetService.updateAsset` 删掉 `item → background` 的 409 |
| 迁移 | **新增** `20260101000029_v061_background_forms.ts`：给 `maps.data` / `games.snapshot.map` 的 `cells[k].background` 补 `formId`，`version` 5 → 6；down 严格反向。表结构不动 |

**两条判断，写下来免得下次重想**

1. **背景形态的占格仍然锁死 1×1，且不给改**。背景层是「一格一格刷」的层，一个背景格
   恒填 1 格；此时给背景形态一个可编辑的 `widthCells` 就是在 UI 上撒谎。所以只放开
   「多个外观」，不放「占格」——服务端保留 400，详情页隐藏输入框，调色板瓦片上照实
   显示 `1×1`。
2. **`item → background` 不再要求先删形态**。第一阶段的 409 是为了避免「切类型时静默
   丢掉用户建的形态」；但正确做法是根本不要丢，而不是逼用户手动删。现在切换类型保留
   全部形态，只是背景形态暂时不能改占格，切回物品即可编辑。

**迁移往返实测**：up1 / down / up2 三次 dump 逐字段比对（`maps` 14 行、`games` 4 行、
`asset_forms` 38 行）**0 差异**；up 后 284 个背景格全部带上 `formId`、9 张地图落到 v6
（另 5 张是 v2/v3 存量，两次迁移都不碰），down 后背景格 `formId` 归零、version 回 5。

**测试**：server 165 例（+1 背景迁移形状）、web 590 例（+5：调色板两层、背景层回退三分支、
`placeBackground` 无 formId 分支）；shared 135 例不变。三包 `tsc --noEmit` 0 错，build ✓。
