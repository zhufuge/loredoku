# 地图编辑器系统需求文档（v0.4.3）

**文档类型**：版本需求与验收（本文档只定义需求与验收口径，不含代码实现）
**修订记录**：2026-10-16 首版 —— 放置编号语义重定义（CLAR-J01 / SPEC-J02 / SPEC-J03）、编辑页位置条件丢失（BUG-J04）
**修订记录**：2026-10-16 增补 —— **编号可多次放置**、去掉「编号 N 已放置在 …」提示（SPEC-J05）
**适用范围**：游戏页面（`/games/:slug`）、编辑器（`/editor/:projectId`）
**前置版本**：v0.4.2（`docs/v0.4.2.md`）
**实现载体**：`packages/web`（本版**不涉及** `packages/shared` 类型与 `packages/server` 接口）

> 本版主题：**把「放置参与者」和「放置编号」拆成两个动作**。
> 点击参与者 = 进入放置状态；此时**点击格子放的是「编号」**（再点一次同一格就移除），
> **长按格子才是「放置参与者」**（放头像），也只有长按会触发同行同列的排除项。
> 增补：**编号是候选标记，同一位参与者的编号可以同时留在多个格子上**——唯一的是头像，
> 所以短按永远不再报「编号 N 已放置在 R{r} C{c}」。
> 另外修掉一个数据丢失缺陷：编辑器里给某人填了「位置条件」，保存后再去填第二个人，
> 切回来第一个人的条件就没了。

### 0.1 与 v0.4.2 的行为差异（改了什么）

| 场景 | v0.4.2 行为 | v0.4.3 行为 |
|---|---|---|
| 点击参与者 | 进入放置状态 | **不变**（只是明确写进文档） |
| 点击（短按）格子 | 往该格**追加**该参与者编号；随后**同行同列自动补 `×`**；并清除其它格子的同编号 | 往该格**切换**该参与者编号（有→删、无→加）；**不补 `×`**；**保留**其它格子的同编号（编号可多处） |
| 长按（≥500ms）格子 | 整格替换为该参与者头像，**同行同列自动补 `×`**，并清除其它格子的同编号 | **不变**（清除的仍是「其它格子的候选编号」） |
| 同一格再点一次同编号 | 无反应（`duplicate` 提示） | **删除该编号** |
| 短按点「该参与者已在别格」 | 拒绝 + toast「编号 N 已放置在 R{r} C{c}」 | **允许**，编号可以落在多个格子上；不再有这个 toast |
| 长按点「该参与者已在别格」 | 拒绝 + toast | 若别处只是**候选编号** → **允许**（这就是确认）；若别处已有**头像** → 仍拒绝 + toast「该参与者的头像已放置在 …」 |
| 编辑页位置条件 | 保存 A → 保存 B → 回到 A，**A 的条件丢失** | 三者都保留 |

## 1. CLAR-J01 放置参与者与编号说明

### 1.1 现状

- 游戏页面已有两个动作：**点击参与者卡片** → `mode = { kind: 'placing', participantId }`；**短按格子** → 放编号；**长按格子（≥500ms）** → 放头像。
- 但界面上只有一句概括性提示（`GamePage.tsx` 左栏），没有把「编号」与「参与者」的关系讲清，玩家容易把它理解成「点一下参与者，再点格子就把这个人放上去了」。

### 1.2 术语表（延续 CLAR-H13，本版再次确认）

| 术语 | 指什么 | 出现在哪里 | 唯一性对象 |
|---|---|---|---|
| **参与者** | 左侧参与者面板里的一张卡片（角色头像 + 序号 + 名称 + 线索） | 只在面板里 | **不适用**（卡片不进地图） |
| **参与者编号** | 格子里九宫格中的那个数字标记（1 起，与卡片左上角序号一致） | 地图格子上 | ❌ **可重复**（SPEC-J05：同一位参与者的编号可同时留在多个格子上，都是候选） |
| **参与者头像** | 整格替换成该参与者的头像（长按的结果） | 地图格子上 | ✅ **唯一**：每位参与者最多一个头像 |

> 口径：**编号 ≠ 参与者**。编号是「候选标记」，参与者是「面板里那个人」。
> 文档、注释、toast、测试命名一律用「编号」指代格子上的数字，用「参与者」指代面板卡片。
> **编号可以多处、头像只能一处**：短按是「标出可能」，长按是「确认答案」。

### 1.3 需求：左栏说明文案（逐字）

`GamePage` 左栏参与者面板上方的说明段（现 `GamePage.tsx` 约 628–635 行）替换为：

> 点击参与者进入放置状态：**点击格子放置的是该参与者的「编号」**（再次点击同一格即移除），
> **长按格子（≥500ms）放置的是该参与者的「头像」**。编号与参与者不是一个东西——编号只是候选标记，
> **同一位参与者的编号可以同时留在多个格子上**，点编号不会触发行 / 列的排除项；只有长按放头像时
> 才会自动在同行同列补上 ×，并把该参与者留在其它格子的编号清除。**每位参与者的头像只能有一个。**
> 需要手动排除时，用工具栏的「禁止符号」。已放置的参与者卡片会变淡。
> 提交前会校验行 / 列互斥与位置条件。

同时更新以下**代码注释**口径（不改逻辑）：

- `lib/gamePlacement.ts` 顶部与 `placeParticipant` 的 JSDoc：把「短按放标号」补上「**且不再补 `×`；再点一次同格即移除**」。
- `GamePage.tsx` 中 `startCellPress` / `endCellPress` / `dispatchCell` 的注释：把「短按（编号）」与「长按（头像）」并列写明，并注明只有长按补 `×`。

### 1.4 明确不改的

- 不改「长按 = 放头像」的判定阈值与实现方式（仍是 `GAME_LONG_PRESS_MS = 500` 的定时器 + `fired` 标记吞掉后续 `click`）。
- 不改工具栏、撤销 / 提交 / 校验的任何交互。
- 不改 `EditorTool` / `GameOperationMode` 的类型成员。

### 1.5 验收

- 源码断言：`GamePage.tsx` 含 §1.3 的关键短语（「进入放置状态」「再点一次」「长按」「排除项」
  「同一位参与者的编号可以同时留在多个格子上」「每位参与者的头像只能有一个」）。
- 文案中不再出现「短按格子放置编号、长按放置头像」这种与 §1.3 冲突的旧句，
  也不再出现「编号 / 头像仍只能出现在一个格子上」（SPEC-J05 收窄后的旧口径）。

## 2. SPEC-J02 放置编号不再自动补排除项

### 2.1 现状

`placeParticipant`（`lib/gamePlacement.ts`）在**两种** variant 落地之后**一律**调用 `autoForbiddenCells`，
把该格所在**行与列**的其余可站立格填上 `{ kind: 'forbidden' }`，并与本次放置合并为一个撤销步（SPEC-G06）。

### 2.2 需求

1. **`variant === 'number'`（短按放编号）时，不再调用 `autoForbiddenCells`** —— 不产生任何 `×`。
2. **`variant === 'image'`（长按放头像）时，保持现状** —— 仍然自动补同行同列的 `×`，仍与放置合并为一个撤销步。
3. `autoForbiddenCells` 这个纯函数**保留**（仍被长按路径使用），签名与行为不变。
4. `sweepParticipantNumbers`（SPEC-H01）**保留**：长按时执行；短按**加入**编号时也执行（见 §3）。
5. 撤销步数：短按放编号 = **1 步**（只含「加入编号 + 清除其它格子同编号」，不含 `×`）。

### 2.3 落点边界表（短按放编号）

| 落点情况 | 结果 |
|---|---|
| 空格 | 加入编号（九宫格第 1 格），**不产生 `×`** |
| 已有其它参与者的编号 | 追加为第 N 个编号，**不产生 `×`** |
| 已有本参与者的编号 | **删除该编号**（见 §3） |
| 已是 `×`（禁止格） | **拒绝** + toast「该格已标记为排除项，请先清除」 |
| 已是本参与者的头像 | **拒绝** + toast「该格已放置该参与者的头像」（不降级成编号） |
| 已是其它参与者的头像 | **加入**编号并整格降级为九宫格（既有行为）→ 见 §3.4 边界表 |
| 不可站立格 | **拒绝** + toast「该格有不可站立的物品，不能放置」 |
| 该参与者已在别格 | **加入**（SPEC-J05：编号可多处，短按不看唯一性，也不再有「已放置在 …」toast） |
| 九宫格已满 9 个 | **拒绝** + toast「该格编号已满（最多 9 个）」 |

### 2.4 与提交校验（FEAT-V01）的关系

**校验不放宽。** `validatePlacement` 仍然检查：

1. 每位参与者必须在盘上；
2. 行互斥；
3. 列互斥；
4. 位置条件（OR 列表）。

> 也就是说：**放编号是自由标记，提交校验是严格判卷**。玩家可以用编号自由试探、用工具栏的
> 「禁止符号」手动补 `×`，最终答案仍需满足行 / 列互斥。这是本版改动后的**预期体验**，
> 不是缺陷。

### 2.5 验收

- 纯函数：短按（`variant: 'number'`）落格后，`forbiddenCells(board)` **不新增任何 key**；长按（`variant: 'image'`）仍新增整行整列的 key。
- 纯函数：短按落格后，`past` 只增长 1 步。
- 既有 SPEC-G06 用例组改为**只对长按断言**（见 §7.1）。
- SPEC-J05：短按落格后，`sweepParticipantNumbers` **不执行** —— 该参与者在其它格子的编号原样保留（见 §3.6）。

## 3. SPEC-J03 放置编号改为「切换」

### 3.1 现状

`placeParticipant` 的 `number` 分支只做追加：

```ts
const numbers = previous ? [...numbersIn(previous), input.participantId] : [input.participantId];
```

该格已有该编号时，`placementBlockReason` 返回 `'duplicate'`，页面 toast「该格已有编号 N」，**什么都不发生**。

### 3.2 需求

短按（`variant: 'number'`）在一次手势内完成一次 **toggle**：

1. 该格**已有**该参与者编号 → **删除**这一个 entry；
   - 删除后该格仍有其它编号 → 保留 `{ kind: 'numbers', entries: [...] }`；
   - 删除后该格**没有任何内容** → **删除整个格子**（`delete board[key]`，回到空格，**不是** `×`）。
2. 该格**没有**该参与者编号 → **加入**（沿用 §2.3 的落点规则，仍做九宫格容量检查；
   SPEC-J05 后**不再**做唯一性检查）。
3. 加入路径**不执行** `sweepParticipantNumbers` —— 该参与者在其它格子的编号原样保留
   （SPEC-J05 取代了首版「一份编号只在一处」的口径，见 §3.3 / §3.6）。
4. 删除路径**不执行** `autoForbiddenCells`，也不执行 `sweepParticipantNumbers`。
5. `placementBlockReason` 中「该格已有该参与者编号 → `'duplicate'`」这一拒绝**取消**（改为允许），
   `PlacementBlock` 的 `'duplicate'` 成员**保留在类型里**（见 §9 Q6），只是短按路径不再返回它。
6. 撤销：加入 = 1 步；删除 = 1 步；不产生变化的点击 = **0 步**（`commit` 的结构比较兜底）。

### 3.3 与唯一性（SPEC-G05 / SPEC-H01）的关系

> **本节口径已被 SPEC-J05（§3.6，同版增补）取代。** 保留在此只为说明改成什么样、为什么改。

首版维持「同一位参与者的编号 / 头像只能出现在一个格子上」，短按落在「该参与者已在别格」
时拒绝 + toast。增补后**收窄为只约束头像**：

- **编号**：候选标记，**可以同时留在多个格子上** —— 短按不看唯一性，也没有「已放置在 …」toast。
- **头像**：唯一。长按落在「该参与者已在**别**格放过头像」时 → 仍**拒绝** + toast
  「该参与者的头像已放置在 R{r} C{c}，请先清除那一格」（不做「自动搬家」）；
  若别处只是候选编号 → **允许**（这一次长按就是确认），随后由 `sweepParticipantNumbers`
  把那些候选清掉。

### 3.4 落点边界表（toggle 两个方向）

| 该格现状 | 该格是否有本编号 | 结果 |
|---|---|---|
| 空格 | 否 | 加入 → `{ kind: 'numbers', entries: [n] }` |
| 有别人的编号 | 否 | 追加 → `entries: [..., n]` |
| 有本编号 + 别人的编号 | 是 | 删除本编号 → `entries: [别人]` |
| 只有本编号 | 是 | 删除本编号 → **整格删除（空格）** |
| `×` | 否 | 拒绝（toast） |
| `×` | — | 不可能（`×` 格不携带编号） |
| 本参与者的头像 | 是（头像即编号） | **拒绝**（toast「该格已放置该参与者的头像」），不删除头像 |
| 别人的头像 | 否 | **加入**：整格降级为九宫格编号（头像自带的编号留在里面），沿用既有行为（§9 Q4） |
| 不可站立格 | — | 拒绝（toast） |

### 3.5 验收

- 纯函数 `gamePlacement.test.ts` 新增一节 `placing a number toggles (SPEC-J03 §3)`：
  1. 空格点击 → 有编号；再点 → 空格（且 `forbiddenCells` 为空）；
  2. 两格各放一个不同参与者编号 → 同格 toggle 只增删自己的 entry；
  3. 删除最后一个 entry 后 `board[key] === undefined`（不是 `forbidden`）；
  4. 加入后再点 → 步数各 +1；第三次点到「删除最后一个 entry」→ 仍是 +1；
  5. 不产生变化的组合（不该出现）不增长 `past`。
- `placementBlockReason` 在「该格已有本编号 + `variant: 'number'`」时返回 `null`。

### 3.6 SPEC-J05 编号可多次放置（同版增补，取代 §3.3 的口径）

> 用户原话：「编号可多次放置，不要提示编号 x 已放置在 xx」。这是对 §3.3 首版口径的**推翻**。

#### 3.6.1 需求

1. **短按（`variant: 'number'`）完全不受唯一性约束**：同一位参与者的编号可以同时留在任意
   多个格子上；每一格都是独立候选，互不清理。
2. **「编号 N 已放置在 R{r} C{c}」这条 toast 消失** —— `PlacementBlock` 的 `'elsewhere'`
   语义收窄为「**头像**已在别处」。
3. **长按（`variant: 'image'`）**：
   - 该参与者已在**别格**放过头像 → 拒绝 + toast「该参与者的头像已放置在 R{r} C{c}，请先清除那一格」；
   - 该参与者只在别格留了**候选编号** → **允许**（这一次长按就是确认）。
4. **`sweepParticipantNumbers` 的调用点收进 `variant === 'image'` 守卫**（`placeParticipant`）：
   短按路径不再执行它；长按路径仍在种 × 之后执行，与放置合并为一个撤销步。
5. **`participantPlacementAt` 改为三步判定**（判卷与 toast 共用同一个「这位参与者在哪」）：
   1. 有头像 → 返回头像格；
   2. 无头像、该编号**恰好在一格** → 返回那一格（沿用 v0.4.1 的宽松判定）；
   3. 无头像、该编号在**多格** → 返回 `null`（没人确认过，不随机挑一个）。
6. **提交校验**：`participantPlacementAt` 返回 `null` 时仍记 `unplaced`，但文案分开讲：
   - 完全没动 → 「编号 N 尚未放置」（不变）；
   - 有候选未确认 → 「编号 N 尚未确认（K 格只有候选编号，长按格子放置头像才算放置）」。
7. **左栏说明文案**把「每位参与者的编号 / 头像仍只能出现在一个格子上」换成
   「同一位参与者的编号可以同时留在多个格子上 …… 每位参与者的头像只能有一个」（见 §1.3）。
8. **卡片淡化不变**：`placedParticipantIds` 仍按「盘上有任何标记」计算，单独一个候选编号
   也会让卡片变淡 —— 那是「这个人标过了」的提示，不是判卷结论。

#### 3.6.2 与 SPEC-H01（v0.4.2）的关系

SPEC-H01 的「清除该参与者在其它格子的编号」**保留但收窄**：只在**长按确认头像**时执行。
理由：编号是候选、头像才是答案；候选可以在多处待着，确认答案之后它们才成为过期数据。

#### 3.6.3 边界表

| 操作 | 该参与者头像在别处？ | 该参与者编号在别处？ | 结果 |
|---|---|---|---|
| 短按某格 | — | 有 | **加入**该格（候选可多处，互不影响） |
| 短按某格 | 有 | 无所谓 | **加入**该格（编号与头像不冲突，那个头像不动） |
| 长按某格 | **有** | 无所谓 | **拒绝** + toast「该参与者的头像已放置在 …」（头像唯一） |
| 长按某格 | 无 | 有（1 格或多格） | **允许**：放头像 + 同行同列补 `×` + 清掉别处候选（**1 个**撤销步） |
| 长按某格 | 无 | 无 | **允许**（普通放置） |

#### 3.6.4 验收

- 纯函数：同一参与者的编号连按 3 格 → `countPlacements === 3`、`candidateCellCount === 3`、
  `forbiddenCells` 为空；再点其中一格 → 只删那一格，其余两份保留。
- 纯函数：`placementBlockReason` 在「别处只有候选编号」时（短按与长按**都**）返回 `null`；
  在「别处已有头像」且长按时返回 `'elsewhere'`。

## 4. BUG-J04 编辑页「参与者信息」位置条件丢失

### 4.1 复现步骤（用户报告）

1. 打开编辑器 `/editor/:projectId`；
2. 点参与者 1 的卡片 → 抽屉打开 → 「位置条件」→「添加位置」→ 在画布点几个格 → **保存**；
3. 切到参与者 2 → 同样填位置条件 → **保存**；
4. 切回参与者 1 → **位置条件列表空了**（第 2 步填的没了）。

### 4.2 根因（已定位）

`packages/web/src/stores/editorStore.ts` 的归一化函数 `ensureEntry` **只复制四个字段**，
漏了 v0.4.1 新增的 `positionConditions`：

```ts
function ensureEntry(entry: CharacterSlotEntry | null): CharacterSlotEntry | null {
  if (!entry) return null;
  return {
    characterId: entry.characterId,
    themeColor: entry.themeColor ?? DEFAULT_THEME_COLOR,
    clue: entry.clue ?? '',
    linkages: (entry.linkages ?? []).map((linkage) => ({ ...linkage })),
    // ← 这里缺 positionConditions
  };
}
```

`ensureEntry` 被 **5 处**使用，全部都会把 `positionConditions` 抹掉：

| 位置 | 作用 | 用户可见后果 |
|---|---|---|
| `snapshot()`（第 207 行） | `commit()` 的副本与撤销栈来源 | **改任何东西都会清掉所有参与者的位置条件** —— 报告中的「保存另一个人后丢失」即此路径 |
| `init()`（第 252 行） | 载入草稿 | **刷新一次页面，位置条件就没了**（即使没做任何操作） |
| `setGridSize`（第 576 行） | 改画布尺寸 | 改尺寸后全部丢失 |
| `applyDraft`（第 592 行） | 应用草稿 | 撤销 / 重置后丢失 |
| `toDraft()`（第 681 行） | **写回服务端** | **保存到数据库的 JSON 本来就不含位置条件** |

另外 `setSlot`（第 527–541 行）内联构造槽位对象时同样没有 `positionConditions`
（该分支只用于「给空槽位分配角色」，语义上应保持空条件，见 §9 Q8）。

### 4.3 需求（修复）

1. `ensureEntry` 必须保留 `positionConditions`，并沿用既有约定：
   - **深拷贝**（新对象数组，元素 `{ x, y }` 也是新对象），避免历史快照与当前状态共享引用；
   - **空数组 / 缺省不落字段**（与 `setParticipantConfig` 的一致约定：草稿里不留死数组）。
2. 修复后，以下链路必须全部保住条件：
   `init` → 抽屉读 `slot.positionConditions` → 保存 → `snapshot` / `commit` → `toDraft` → 服务端 JSON → 重新 `init`。
3. **不动** `mapDraft` schema、不动 `setParticipantConfig` 的语义（它已正确）。
4. 顺带澄清：`ParticipantDrawer` 的 seed effect（`[open, slot]`）依赖 `slot` **对象引用**；
   修复后若 `ensureEntry` 仍每次返回新对象，则每次 `commit` 都会重 seed 抽屉本地草稿。
   见 §9 Q7 的默认取值。

### 4.4 影响面清单（修复后需回归）

- `packages/web/src/stores/editorStore.ts`（`ensureEntry`，必要时 `setSlot`）
- 依赖 store 的既有测试：`editorStore` 相关单测、`ParticipantDrawer.test.ts`、`EditorPage.*.test.ts`
- 端到端：编辑器保存 → 重新载入 → 位置条件仍在；`gamePlacement.validatePlacement` 的
  `condition` 分支在游戏页能读到条件（此前因 web 侧已丢，条件校验实际上从未生效过）

### 4.5 验收

- 新增单测 `stores/editorStore.test.ts` 一节 `positionConditions survives (BUG-J04 §4)`：
  1. `init` 载入带条件的草稿 → `characterSlots[0].positionConditions` 仍在；
  2. `setParticipantConfig(0, …)` 后 `setParticipantConfig(1, …)` → **槽位 0 的条件仍在**；
  3. `toDraft()` 输出里带 `positionConditions`；
  4. `snapshot` 深拷贝：改副本不污染原状态（引用不同）。
- 源码断言：`ensureEntry` 的函数体内出现 `positionConditions`。
