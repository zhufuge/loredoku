## 0. 一句话

**同一个仓库出第二份产物**：入口 `player.html`、`base: '/loredoku/'`、输出 `dist-player/`；
构建时把**一个**主题资源包 emit 到产物里的 `<code>/` 下，运行时不发一个 `/api` 请求。
游戏页的 1500 行渲染逻辑**一行没抄** —— 把「数据从哪来」抽成 `GameSource`，播放器只是换了一层
实现（`api` → `bundle`）。

## 1. 形状：与 v0.8.0 §11.6 那个草稿的对照

v0.8.0 就把这件事的形状写下来了（§11.6「本版不做：托管与播放」）。那一节的结论全部成立，
只有接口的**签名**改了：

| 当初写的 | 这一版落的 | 为什么 |
|---|---|---|
| `loadTheme(code): Promise<{ theme, games }>` | `useTheme()` + `useGame()` + `useAssets()` + `useCharacters()`，各自返回 `{ data, isLoading, isError }` | 渲染层里凡是碰数据的角落，要的就是 query 三件套。写成 `Promise` 还得再包一层 loading / error，等于在 `GamePage` 里重新发明一遍 `useQuery` |
| `loadGame(key)` 返回**这一关引用到的** assets / characters | `useGame(key)` 只给一关；assets / characters 是**全量** | 包本身就有全量两份（`assets.json` / `characters.json`），裁成「这一关用到的」要多写一遍引用收集，收益只有几百 KB —— 而两者都已经在产物里了 |
| `resolveFile(path)` | `fileUrl(path)` + `themeForbiddenSymbol()` + `themeToolIcons()` | 包里**已经**把 v0.8.7 那两层兜底（谜题 → 主题）在打包时解析完了（v0.8.7 §4 / §7），播放器不需要再查主题那一份；两个函数因此恒返回 `null`，游戏页的两条兜底分支在播放器里不可达 |
| （没写） | `storageId(key)` / `themeHref` / `listHref` / `gameHref` | 两个入口的路由前缀不同（`/play/…` 与 `/loredoku/:code/play`），存档键也不同（§4）。与其在 `GamePage` 里写「如果是播放器就……」，不如把这些差异全收进 source |

**「不要复制一份 GamePage」** 这条按 §11.6 的原话落地：`GamePage.tsx` 现在只剩一个 10 行的薄壳
（`packages/web/src/pages/GamePage.tsx` 顶部），本体改名 `GameView`，它的入参就是一个
`GameSource` —— 它不认识 axios，也不认识包。

## 2. GameSource：一个接口，两份实现，三个文件

```
src/lib/gameSource.tsx      接口 + GameSourceScope / useGameSource / useProvidedGameSource
src/lib/apiGameSource.ts    useApiGameSource()  —— 四个 query 委托给原来的 hook
src/player/PlayerBundleProvider.tsx   useBundleGameSource(code) —— 四个 query 读包
src/pages/ApiGamePage.tsx   <GameSourceScope source={api}>  <GameView/>   ← 工坊 / 线上
src/player/PlayerGamePage.tsx         <GameSourceScope source={bundle}><GamePage/>  ← 播放器
```

`GamePage` 自己**不再偷偷回退**到 api 分支：没有 scope 就抛错。

```ts
export function GamePage(): JSX.Element {
  const provided = useProvidedGameSource();
  if (!provided) throw new Error('GamePage 需要 GameSourceScope：工坊请用 ApiGamePage，播放器请用 PlayerGamePage');
  return <GameView source={provided} />;
}
```

为什么值得抛错而不是「默认走 api」：默认值等于把「忘了套 scope」这种错变成**运行时才发现的
一次请求失败**；而按 `GameSource` 的约定，没有来源本来就不该渲染这一页。工坊与播放器两条路
都显式给了 source，这条分支只在「有人把 GamePage 挂进新路由却忘了给数据」时触发。

### 2.1 axios 必须真的离开播放器的 chunk

`useApiGameSource` 一路 import 到 `@/api/*` → `axios`，而**模块的顶层 import 是执行即生效**的：
`gameSource.tsx` 里只要还留着这个函数，播放器 import 那个 context 就带着 axios 一起进产物。

第一次构建就撞上了：`vendor-ui` 里能 `grep` 到 `axios` 的 UA 字符串；dev 里进关卡页会额外拉
**7 个** `src/api/*.ts` 模块。拆成三个文件 + `React.lazy` 之后：

- `gameSource.tsx` 只剩「接口 + context」，**零依赖**；
- `ApiGamePage` 是独立 chunk（27.26 kB），在播放器里**永远不会被请求**（播放器给的 source 让
  `GamePage` 的门直接过了，根本走不到 lazy 那一层）；
- 实测产物里 `grep -l axios dist-player/assets/*.js` → 无；dev 里 `src/api/*` 请求 → 0。

## 3. 路由与地址

```tsx
createBrowserRouter([
  { path: '/',               element: <Navigate to={`/${BUNDLE_CODE}/play`} replace /> },
  { path: '/:code/play',     element: <PlayerHomePage /> },
  { path: '/:code/play/:key', element: <PlayerGamePage /> },
  { path: '*',               element: <Navigate to={`/${BUNDLE_CODE}/play`} replace /> },
], { basename: playerBasename() })
```

- `basename` = `BASE_URL` 去掉结尾斜杠（`/loredoku`）。代码里写 `/hlm/play`，浏览器里是
  `/loredoku/hlm/play` —— 换部署路径只改 `vite.player.config.ts` 的 `base` 一处。
- 根地址与 404 都跳到**构建时烤进去的那个主题**（`__PLAYER_BUNDLE_CODE__`，由插件在 `config`
  钩子里 `define`）。一个产物只装一个包，`/loredoku/` 没有第二个合理去处；`BUNDLE_CODE` 为空
  （绕过构建直接跑 vite）时退回 `/play`，让页面自己报「没有这个包」。
- `GameSource` 的三个地址函数返回的都是**站内路径**（不带 base）：工坊的 router 挂 `/`，播放器
  挂 `/loredoku`，各自由自己的 router 补前缀。所以 `GamePage` 里那句「返回主题」不用分情况。

## 4. 存档键：`bundle:<code>:<key>`

`localStorage` 里最终落成一枚键：

```
loredoku.game.progress.bundle:hlm:puzzle-hlm-sishan
```

（v0.8.0 §11.6 定的形状，这一版兑现。）`GamePage` 不再自己拼键，只问 `source.storageId(slug)`：

| | 键 | 为什么 |
|---|---|---|
| api（工坊 / 线上） | 游戏 slug 原样 | **线上已有进度不能作废**，这一份是历史包袱，必须保住 |
| bundle（播放器） | `bundle:<主题code>:<key>` | 离线包里的进度不该出现在线上，反之亦然；同机同时开着两者互不干扰 |

**实测**：在 `/loredoku/hlm/play/puzzle-hlm-sishan` 点一格（禁止符），`localStorage` 从
`["loredoku.gameview.ruler"]` 变成多出上面那枚键，值是
`{"v":2,"gridSize":4,"participantCount":4,"board":{"0,0":{"kind":"forbidden"}}}` —— 与工坊那边
同一份存档格式（`v: 2`），只是键的身份段换了。

## 5. 包怎么读

`src/player/bundleLoad.ts`：纯函数 + 两个 `fetch`，没有 React、不知道路由、不认识 axios。
「包长什么样」这一件事只在这里被解释一次。

```
manifest.json          身份 + 关卡清单 + 每个文件的校验和
assets.json            全量资源，URL 已换成包内相对路径
characters.json        全量角色，同上
puzzles/<key>.json     { key, summary, map, puzzle }，引用已重编号
files/**               图片、封面
```

| 函数 | 做什么 |
|---|---|
| `bundleRoot(code)` | `/loredoku/hlm/`（站点 base + 编码 + 斜杠） |
| `bundleFileUrl(root, path)` | 包内相对路径 → `<img src>`；空路径给 `null`（不是 `""`） |
| `loadManifest` | 取 `manifest.json` 并 `assertBundleFormat` |
| `loadGame` | `key` 必须出现在 `manifest.games` 里，否则直接报「没有这一关」——文件路径不必猜 |
| `loadAssets` / `loadCharacters` | 取全量并逐条改写 URL |
| `toGameCard` / `toGameDetail` | 摊成列表页 / 游戏页认识的形状 |

**格式不匹配就直说**（`assertBundleFormat`）：`format` 不是 `loredoku-theme`、或 `formatVersion`
不是当前版本，都抛错。包之间没有升级关系（v0.8.0 §11.4：身份是 `exportedAt` 不是版本号），
硬读只会得到一片空白画布 —— 那比一句「请用同一个版本重新导出」难查得多。

### 5.1 顺手修掉的一个包格式 bug（`map` 没重编号）

`buildBundlePuzzleFile` 从 v0.8.0 起写的是：

```ts
map: game.map,                       // 服务端 toDetail 给的就是 puzzle.map.data 的原始引用
puzzle: renumberPuzzleDraft(...),    // clone 一份再改引用 id
```

于是包里出现**两份画布**：`puzzle.map.data` 里的 `assetId` 是重编号后的 `1..N`，`map` 里的还是
数据库原 id。播放器第一眼看到的正是这个 —— **棋盘底色全黑、一张物品图都不出来**（实测截图：
4×4 空棋盘）。改成 `map: puzzle.map.data`（重编号之后的那份）就对了。

为什么到这一版才暴露：v0.8.0 到 v0.8.7 都没有消费方，没人真的读过这个字段。`bundle.test.ts`
补了一条断言（两份画布必须是同一份对象的引用），`shared` 因此 +1 条测试。

### 5.2 URL 改写要在「形态」那一层

图片挂在**形态（variant）**上，不在资源上（v0.6.1 §5.1：一个资源可以有几个样子）。只改资源
那一层会得到一个「名字都在、图全是破的」的画布 —— 所以 `resolveAssetFileUrls` 要下钻一层，
`resolveCharacterFileUrls` 同理（头像在里面一层）。

在**读包这一层**做而不是让渲染层每次拼：画布 / 名册 / 禁止符号三处的 `<img>` 都在深层组件里，
各拼一次前缀迟早漏一处；而且渲染层认的是「`imageUrl` 就是能用的地址」这条老约定
（v0.8.0 §11.2 的 `resolveFile` 就是干这个的）。

## 6. 列表页 `/loredoku/:code/play`

数据只有一处：`manifest` —— 关卡清单是 `games`，难度分级的名字与颜色是
`theme.difficultyLevels`（2026-11-09 补，见 §13）。没有「全部游戏」的上一级（这个产物只有一个
主题）、没有 `/themes` 查询（包本身就是那个主题，导出时分级已冻在里面）、没有接口。

卡片用**同一张** `GameCard`。为此把它的入参从 `MapGameSummary` 收窄成 `Pick` 五个字段：

```ts
export type GameCardData = Pick<MapGameSummary, 'slug' | 'name' | 'coverUrl' | 'difficulty' | 'gridSize'>;
```

卡片本来也没用过 id / 时间戳；`MapGameSummary` 结构上天然满足这个 `Pick`，线上那边的调用
**一行都没改**。所以在工坊里改卡片长什么样，播放器会跟着变 —— 两边不会各长一张脸。

四种状态（都不是「白屏」）：

| 看到什么 | 什么时候 |
|---|---|
| 四张方形骨架 | `manifest.json` 还在取 |
| 「这个播放器里没有「hlm」这个主题的资源包」+ 具体 HTTP 错误 + 一句怎么给包 | 包不存在 / 路径不对 |
| 「这个目录里装的不是「hlm」的包 —— 包里写的是「xxx」」 | 部署时目录名与主题编码不符 |
| 「这个主题还没有可玩的关卡」+ 重新加载 | `manifest.games` 为空 |

## 7. 关卡页 `/loredoku/:code/play/:key`

`PlayerGamePage` 只做**三道门**，然后把画布交给 `GamePage`：

1. 包在不在（`manifest` 取得到吗）；
2. 目录名与包的身份对不对得上（`/loredoku/hlm/` 里装的必须真是 `hlm`）；
3. 包里有没有这一关（`manifest.games` 是唯一清单，没有就是没有）。

三道门之后：

```tsx
<GameSourceScope source={useBundleGameSource(code)}>
  <GamePage />
</GameSourceScope>
```

三道门的错误页长得一样（对玩家都是「打不开」），差别只在第二行那句给作者看的说明；底部的
「回到关卡列表」用 `Link` 而不是 `<a href>` —— 地址是 basename 内的（`/hlm/play`），写死
`href` 会掉到站点根上去。

## 8. 构建与命令

```bash
npm run dev:player                                    # localhost:5174/loredoku/
npm run build:player                                  # → packages/web/dist-player/
npm run preview:player                                # localhost:4173/loredoku/（不要求包）
npm run build:player -- --bundle=/path/to/hlm.zip     # 临时换包，不改 .env
LOREDOKU_BUNDLE=/path/to/hlm.zip npm run build:player # 显式环境变量覆盖
```

**默认包路径写在仓库根 `.env` 的 `LOREDOKU_BUNDLE`**（模板见 `.env.example`，2026-11-09
补，详见 §14）。优先级 `--bundle` > 显式环境变量 > `.env`；相对路径按仓库根解析。
包可以是主题概览页导出的 `.zip`，也可以是**解压后的目录**（里面直接是 `manifest.json` /
`puzzles/` / `files/`）。

### 8.1 为什么包一层 `scripts/player.mjs`

vite 的 CLI 用 `cac`，**未知选项直接报错**（实测 `vite build --bundle=…` 抛
`CACError: Unknown option`）。这一层把 `--bundle` 摘出来、连同 `.env` 的默认值（§14）一起
解析成一个绝对路径塞进 `LOREDOKU_BUNDLE`，剩下参数原样递给 vite（`--host` / `--port` /
`--mode` 都还能用）。

三个细节：

- 相对路径先按**仓库根**试、再按当前目录试 —— `.env` 就在仓库根，写
  `./resources/themes/hlm.zip` 的人心里想的是那里，而 npm 把脚本的工作目录切到了
  `packages/web`；
- `preview` 不要求包（它服务的是已经烤好包的 `dist-player/`），`dev` / `build` 三处都没配
  时直接 `exit 2` 并打印三处给法（§14）；
- 路径解析与优先级收在 `scripts/playerEnv.mjs`，`vite.player.config.ts` 直接调同一个函数
  —— 不经过包装脚本、手工 `vite --config vite.player.config.ts` 也认 `.env`。

### 8.2 `scripts/readBundle.mjs`：自己解 zip，不引依赖

包里只有 `stored`(0) 与 `deflate`(8) 两种压缩方法，Node 的 `zlib.inflateRawSync` 就够了。
为一个构建期工具加一个解压库，比这 150 行贵（v0.8.0 §11.6 的取舍同一条：依赖只进不出）。

- **不支持 zip64**（> 4GB 或 > 65535 个条目）：主题包远到不了，真遇到就报错并让人先解压成
  目录 —— 明确失败好过悄悄读错；
- 解压后是一张 `Map<相对路径, Buffer>`，`build` 与 `dev` 共用同一个形状。

### 8.3 `scripts/bundleAssets.mjs`：把包烤进产物 / 在 dev 里递出去

| 钩子 | 做什么 |
|---|---|
| `config` | `define: { __PLAYER_BUNDLE_CODE__ }` —— 主题编码要在**模块求值之前**就位（`bundleCode.ts` 顶层读它）；放 `generateBundle` 就晚了 |
| `buildStart` | 打一行 `资源包：hlm（红楼梦）· 8 关 · 导出于 …`，构建日志第一行就知道对不对 |
| `generateBundle` | 包里每个文件 `emitFile` 成 `<code>/<相对路径>` |
| `configureServer` | dev 中间件：`<base><code>/<路径>` 直接从内存里递；顺手做 SPA fallback |
| `closeBundle` | 产物里的 `player.html` 改名 `index.html` |

改名那一步：Vite 按**源文件名**输出入口 HTML，产物里就是 `player.html`，而部署后访问的是
`/loredoku/` —— 静态服务器（含 `vite preview`）只认 `index.html`。改名比「入口文件就叫
index.html」干净：那个名字会让工坊与播放器两份入口在同名文件上打架。

**dev 的 SPA fallback 踩过一个坑**：`/loredoku/hlm/play` 也以 `/loredoku/hlm/` 开头，早期版本
里「不是包文件 → `next()`」让它落到 vite 自己的 fallback，拿到**工坊的** `index.html` —— dev 里
进关卡页会渲染成工坊的「正在加载工作台…」，还会顺手打出十个 `/api` 请求。现在包文件与页面
路由只靠「文件在不在」区分：包文件命中就递，没命中就走页面判定（无扩展名、非 `/@…`、非
`/src/` 才改写成 `player.html`）。

### 8.4 `vite.player.config.ts` 的三处不同

1. `base: '/loredoku/'` —— 产物里的资源地址、包地址、路由 basename 全由这一个值推导；
2. `input: player.html` —— 工坊的页面、编辑器、api 层都不会被这个产物间接触达；
3. `bundleAssets(bundlePath)` —— 见上；
4. `defineConfig` 用**函数形式**（§14）拿 `mode` / `isPreview`：`mode` 用来挑
   `.env.[mode]`，`isPreview` 时传 `null` —— preview 服务的是已烤好包的产物，
   包文件被删了也应该能预览上一次的构建。

外加 `server.port = 5174`（工坊在 5173，两个 dev server 同时开着是常态），**并且不配 `/api`
代理**：播放器不打接口，少了这层，任何漏网的请求在 dev 里立刻 404，而不是被悄悄代理到工坊后端
——「dev 里能跑、产物里 404」这类错就不会出现。

`emptyOutDir: false` 是有意的：包里几千个文件删一遍再写一遍纯属浪费，而且本机的文件系统 shim
对「递归删目录」会失败，第二次构建直接报错。代价见 §11.3。

## 9. 部署

产物是一个纯静态目录，**任何静态服务器**都行：

```
dist-player/                 → 部署到 https://<host>/loredoku/
├── index.html               （由 player.html 改名而来）
├── assets/                  js / css / 字体（构建期那一份）
└── hlm/                     ← 资源包原样摊在这里
    ├── manifest.json
    ├── assets.json
    ├── characters.json
    ├── puzzles/*.json
    └── files/**
```

需要一条 **SPA rewrite**：`/loredoku/<任意非文件路径>` → `/loredoku/index.html`（和工坊那条
一样）。缺了它，玩家刷新 `/loredoku/hlm/play/sishan` 会 404。

- **一个产物只装一个主题**。多主题 = 多份产物 + 各自部署到 `/<code>/` 下（见 §11.1）；
- `file://` 打不开 —— `fetch` 跨源（v0.8.0 §11.6 早就写过这条提醒）。想「双击就能玩」只能
  打一个单文件产物（内联 JSON + base64 图片），这一版不做。

## 11. 代价与没有做

1. **一个产物一个主题。** 包里 `manifest.theme.code` 必须等于目录名，否则列表页 / 关卡页都
   给「装的不是这个主题的包」。要让一个播放器服务 N 个主题，就得改成「运行时按 URL 去取」，
   那时产物与数据分离，部署也要多一步（这一步被 §9 的「拷走 dist 就能玩」换掉了）。
2. **换包要重建。** 包是构建期 `emitFile` 进去的，产物里没有「去别处找包」的代码路径。
   换主题 / 重新导出之后重跑 `build:player` 即可，但**不是**换个文件就生效。
3. **旧文件会残留。** `emptyOutDir: false`（§8.4）意味着换版本后上一次哈希过的
   `assets/*` 还躺在 `dist-player/assets/` 里。发布前手动清一次目录 —— 构建命令不替你决定。
4. **包里没有字体**（v0.8.0 §11.5）：字体是构建期资源，播放器自带与工坊同一份
   （`registerBundledFonts()`），所以字形一致；但**作者不能给主题配自定义字体** —— 真要支持
   得先做上传、裁字、授权那一整套。
5. **已经发出去的老包仍是内置五档。** 首发版把分级漏在包外、列表页也没传 `tiers`；
   2026-11-09 的 §13 修好了「新包 + 新播放器」，但**旧 zip 里没有那个键** —— 新播放器读到
   `undefined` 就按「没配过」处理（`resolveDifficultyTiers` 给内置五档），不会报错也不会空白。
   要显示作者配的名字，得重新导出一次包、再重跑 `build:player`。这是包格式加可选键换来的
   兼容边界，不做自动迁移。
6. **列表页只有「这一个主题的关卡」。** 没有分类、搜索、排序、合集、难度筛选 —— 工坊那些
   依赖接口与 `games` 表的能力都不在。
7. **两套存档键互不相通**（§4）。这是有意的，但也意味着「线上玩到第 3 关、下载包继续玩」
   不会继承进度。
8. **没有导入回工坊。** 包仍然只出不进（v0.8.0 §11.6 预留的 `originIds` + `code` 对账仍未
   实现）。
9. **zip64 不支持**（§8.2），且整包在内存里摊开再 emit —— 4.8 MB 的包没问题，几百 MB 的包
   会难受。真到那一天先解压成目录再指过来（`readBundle` 直接读目录，那一路不占额外内存）。
10. **`GameSource` 的 bundle 实现里那两个 `() => null`。** 它们靠的是「打包时已经把谜题 →
    主题的兜底解析完了」这条前提（v0.8.7 §4 / §7）。哪天包格式改成「只带谜题自己那份」，
    这两行就得重新变成真查询 —— 而游戏页那两条兜底分支会立刻复活。
11. **`PlayerGamePage` 仍没有页面级测试。** `bundleLoad` 的纯函数与 `PlayerHomePage` 的徽章
    （§13）都有单测，但关卡页的三道门只有真浏览器验过（§10）。要测它得 mock `fetch` +
    router + `GamePage` 三样，性价比不足以在这一版付。

## 13. 补（2026-11-09）：列表页难度徽章跟随主题

> **来源**：用户的一条 —— 「修复 player 的列表页的难度等级文字不按主题设置的问题」。
> 不新开版本号：这是对 §6 那张卡的修正，追加在当期文档里（§11.5 / §11.11 / §10 的旧结论
> 已就地改掉，见下面「改了哪些旧话」）。

### 13.1 症状与根因

`hlm` 主题在概览页配了五档 **初 / 平 / 通 / 灵 / 仙**，线上 `/play/theme/hlm` 的卡片写的是
「通」；同一个包打进播放器后，卡片写的是内置的「中等」。颜色也跟着错：内置坡按**档位在
五档里的位置**取色，主题若给某一档单独选过色，那颗色在包里更是无处可寻。

两层原因叠在一起：

| 层 | 问题 |
|---|---|
| 产出侧 | `manifest.theme` 只有 `code / name / description`，`theme.json` 只装身份；包里每关只带 `difficulty` **数字**。名字、颜色、有哪几档都是主题级配置（`themes.data.difficultyLevels`），导出时被整个漏掉 —— §11.5 当初把这条写成了「代价」，其实是个 bug |
| 消费侧 | `PlayerHomePage` 给 `GameCard` 没传 `tiers`。这一页在 `WorkspaceLayout` 外面，`DifficultyBadge` 的 `tiers ?? workspace?.theme.data.difficultyLevels` 两边都是 `null`，于是落到 `resolveDifficultyTiers(undefined)` 的内置五档 —— 与 v0.8.6 §3.6 修 `/play` 时撞的是同一堵墙，只是那次用 `useDifficultyTiersByCode()` 绕开了，播放器没有 `/themes` 可查 |

### 13.2 包格式：加一个可选键，不升版本

```jsonc
// manifest.json
"theme": {
  "code": "hlm",
  "name": "红楼梦",
  "description": "…",
  "difficultyLevels": [              // ← 新增，可选
    { "label": "初", "level": 1 },
    { "label": "平", "level": 2 },
    { "label": "通", "level": 3 },
    { "label": "灵", "level": 4 },
    { "label": "仙", "level": 5 }
  ]
}
```

三条取舍：

- **放 `manifest.theme`，不放 `theme.json`。** 列表页本来就要读 manifest（关卡清单在里面），
  再为五档名字多取一次文件不值；`manifest.theme` 早就把 theme.json 的 code / name /
  description 抄了一份，这里只是同一个做法。`theme.json` 仍是「只装身份」（v0.8.0 §11.2）。
  style 不能进包的理由是「会与关卡里那份不一致」，分级没有这个问题 —— 关卡里只有数字，
  名字与颜色只有主题这一份。
- **存原始配置，不排序、不补内置档。** 排序与兜底统一交给读包方的
  `resolveDifficultyTiers()`（与线上 `useDifficultyTiersByCode` 同一个函数），导出侧不发明第二套。
- **`BUNDLE_FORMAT_VERSION` 保持 1。** 新键是加法：新播放器读老包 → `undefined` → 内置五档
  （与修复前逐字节一致）；老播放器读新包 → 多一个不认识的键，忽略。升版会让所有存量 zip 在
  `assertBundleFormat` 那里直接被拒，为了五档名字不值得。代价写在 §11.5：**旧包要重新导出
  才能显示作者起的名字**。

## 14. 补（2026-11-09）：默认资源包路径进 `.env`

> **来源**：用户的一条 —— 「资源包默认路径 改放到 .env 中」。问定的两处：默认指向
> `./resources/themes/hlm.zip`（并把里面那份旧导出换成最新导出），以及**保留 `--bundle` 覆盖**。
> 不新开版本号，追加在当期文档里。

### 14.1 改了什么

首发版里「包在哪」是每次敲命令时给的：不带 `--bundle` 就 `exit 2`。现在把默认值放进
仓库根 `.env`（被 gitignore，模板是 `.env.example`）：

```dotenv
# .env / .env.example
LOREDOKU_BUNDLE=./resources/themes/hlm.zip
```

于是 `npm run dev:player` / `build:player` **不带任何参数**就能跑。优先级写在一处：

```
--bundle=<路径>  >  显式环境变量 LOREDOKU_BUNDLE  >  .env 的 LOREDOKU_BUNDLE  >  没有 → 报错
```

`.env` 里的相对路径按**仓库根**解析（`.env` 就在那儿），也接受绝对路径。`preview:player`
不需要包 —— 它服务的是已经烤好包的 `dist-player/`。

`resources/themes/` 本来就在 `.gitignore` 里，包不进仓库；这次把里面那份首发导出换成了
**最新导出的 `hlm` 包**（带 §13 的 `difficultyLevels`），所以默认路径看到的徽章是
初 / 平 / 通 / 灵 / 仙，不是内置五档。

| 首发版（没读 `.env`） | 205.72 KB | `Minified React error` |
| 用 `loadEnv` 之后 | **415.67 KB** | `react-dom.development` |

原因在 Vite 5 的源码：`loadEnv` 读到 `.env` 里的 `NODE_ENV` 会顺手写
`process.env.VITE_USER_NODE_ENV = 'development'`（本仓库 `.env` 就有这一行）。包装脚本在
spawn vite **之前**调它，这个值被继承进子进程，于是 React 走了 development 分支。

改成**零副作用的自己读**：`loadRootEnv()` 按 Vite 相同的文件顺序
（`.env` → `.env.local` → `.env.[mode]` → `.env.[mode].local`）扫一遍，只做注释 / `export` /
引号 / 行尾注释这点解析，不做变量展开，**一个字节都不写 `process.env`**。顺带不引新依赖、
不必在包装脚本里加载整个 vite。单测里有一条专门钉住 `process.env` 前后完全相等。

### 14.4 实测

### 16.2 实测（CDP + sharp 逐像素）

`/play/theme/hlm/puzzle-hlm-sishan`，1440×900，取画布下边界的竖线与右边界的横线，
按色块分段读像素。计算样式：

```
rgba(74, 63, 53, 0.3) 24px 24px 0px 0px
```

| 界面 | 纸面 | 外框线 | 影子带 | 页面底色 |
|---|---|---|---|---|
| 深色 | `184,173,156` | `107,98,87`（4px） | `43,38,32`（**21px**） | `31,28,24` / body `26,23,20` |
| 浅色 | `184,173,156` | `107,98,87`（4px） | `193,188,182`（**21px**） | `245,243,238` / body `248,246,242` |

右边界同样量到 21px。颜色与算式仍对得上：`0.3 × (74,63,53) + 0.7 × 底色` —— 深色
`(43.9, 38.5, 32.7)`、浅色 `(194.3, 189.0, 182.6)`，与量到的差 1 以内。

v0.8.7 §6 那条「写的 6px、看到 3px」的损耗**是常数不是比例**：外框 SVG 描边以画布边界
为中心画（`stroke-width` 5.6），外半边压掉 2.8px。所以 `6 − 2.8 ≈ 3`，现在
`24 − 2.8 ≈ 21`。5× 放大的右下角截图里，L 形硬影完整、没有被切断。

### 16.3 一个要报备的边界：下边的裁剪余量只剩 6px

画布外的影子画在 `main { overflow: hidden }` 里，能不能露出来取决于画布到 `main` 边界
的距离。实测两种窗口：

| 窗口 | 画布尺寸 | `main` 下边余量 | 影子 |
|---|---|---|---|
| 1440×900 | 672×672（`bottom=770`） | **30px** | 露出 21px；余量还剩 6px |
| 1280×720 | 672×672（`bottom=680`） | **−60px** | 完全看不到；画布底部本身已被裁 |

**1280×720 下看不到影子不是这次改坏的**：画布是固定 672×672、不随窗口高度缩放，窗口
一矮，`main` 的 `overflow: hidden` 先切掉画布底部，画在更下方的影子自然也一起消失
（`6px` 时同样如此）。右边界余量分别是 167 / 87px，一直宽裕；瓶颈只在下边。

这一版**没有动布局**：不擅自给 `main` 加 padding、不改 `overflow`、不引入自适应缩放 ——
那会牵动四张画布的适配与既有滚动行为，是独立的一件事。结论是：在常见的 1440×900 上
24px 是能完整看到的，但已经贴近上限；再往上加、或换更矮的窗口，就要先解决裁剪。
