## 1. 问题

导出弹窗给的是清单（v0.8.0 落地的「先给清单，再给文件」），但清单只是**看**，
点「导出 zip」仍然是把主题下所有在线关打进一个包。主题有十几关时，作者经常
只想归档**新上线的那几关**：旧关已经归档过，重打一遍只是让 zip 大一倍、
对自己的关卡目录做一次覆盖。

清单明明已经把每一关列出来了，勾选框是它的自然延伸。

## 2. 做法

### 2.1 接口：query 里带 `games`

`GET /api/themes/:code/bundle?games=7305,7629`。缺席 = 全部在线关
（v0.8.0 起的老行为，不动）。

- `packages/shared/src/schemas/theme.ts` 新增 `themeBundleQuerySchema`：
  `games` 是 `/^\d+(,\d+)*$/` 的字符串，transform 成 `number[]`。放在
  query 而不是 body——接口仍然是 GET，`downloadThemeBundle` 走 axios 的
  `params`。
- `packages/server/src/controller/themeController.ts` 的 `bundle` 多解析一次
  `ctx.query`，把 `gameIds` 透传给 `buildThemeBundle`。
- `packages/web/src/api/themes.ts` 的 `downloadThemeBundle(code, gameIds?)`：
  选中集为空时不带 `params`（与老请求一字不差）。

### 2.2 服务端：选中集对在线集做差

`packages/server/src/service/bundleService.ts` 的 `takeGames(themeId, gameIds?)`：

- `gameIds === undefined` 走老逻辑（0 行抛「这个主题还没有上线的关卡…」）。
- 给了就取出在线行的 id 集，然后：
  - 选中里有**不在线 / 不属于这个主题**的 id → 400，message 列出是哪几个
    （`选中的第 999999 关不在线或不属于这个主题`）；
  - 选中集为空 → 400（`没有选中任何关卡，先勾上至少一关`）；
  - 其余按选中集过滤行。
- `row.id` 在 knex 里可能是字符串（bigint），全程 `Number(row.id)` 再比，
  否则 `gameIds.includes(row.id)` 报 TS2345。

之前每一关的取数（map）抽成 `toTaken(row)`，`buildThemeBundle` 与
`takeGames` 都用同一份，不重复写「谜题读不出来」那段。

### 2.3 弹窗：勾选框 + 两个快捷键

`packages/web/src/components/theme/ExportBundleDialog.tsx`：

- `selected: Set<number>`，**默认全选**（`useState` 初始化 + 一个按
  `theme?.code` 重置的 effect，只在开 / 关这个节拍重置——games refetch
  回来不为所动，上一次的取舍也不该跟到下一次）。
- 每一行名字前面一个勾选框（`h-3.5 w-3.5 accent-primary`），难度与格数
 照旧在右边。
- 清单右上「全选 / 清空」两个 ghost 按钮，各自在该灰的时候灰
 （全选灰 = 已经全选；清空灰 = 已经空）。
- 底行从 `共 N 关` 改成 `已选 X / 共 Y 关`。
- 导出按钮多一个禁用条件：`selected.size === 0`。请求只带选中的 id。
- 完成屏不变（文件名 + 再导一次 / 完成）。

## 4. 同一份清单的两头

清单先有、勾选后有，但两者读的是同一个 `games` prop，没有第二份数据源：
服务端拿选中集对在线集做差（而不是对清单做差），弹窗里的行**一定**是在线
关，不会出现「勾了却导不出来」的行。作者从外部拼一个 id 进来才会撞上
400 那条。

## 5. 没做的

- 没做「记住上次选了哪几关」：每次打开都回到全选。导出是低频的归档动作，
  记忆反而更容易让作者漏打新关。
- 没加「按难度 / 按网格大小批量选」：主题目前最多 24 关，手动勾得动。
- 没把选中集写进文件名：文件名是主题 + 日期，与内容无关。
- 没加资源 / 角度的勾选：它们跟着关走，单选没意义。
- 字体补的五字没有单独的验证截图：裁字流程（`npm run fonts` 读
  `font-extra-chars.txt`）自 v0.9.8 起多次验证，产物 950736 → 951928 B。

## 6. 名册联动指向的淡金

用户反馈：游戏页面里一位参与者**联动其他参与者**时，被指向的那些参与者的高亮，
要从那道金框向头像蔓延一层金色透明色，**不要头像放大效果了**。

未指定版本号，按 AGENTS.md §3.5 并进本版文档。

### 6.1 问题

被联动指着的参与者本来有两重反馈叠在名册卡片上：

1. 一道 2px 的联动色外扩框（`ringLayers`，联动色由谜题的联动调色板解析，
   缺省 `HIGHLIGHT_BLUE = '#90CAF9'`）；
2. 头像 `transform: scale(1.08)`（v0.3.9 落地的反馈）。

放大读成「这位自己要干嘛」，而联动说的是「**别人**指着他」—— 动的是别人的手，
不是这张脸。金框留着（它标的是**哪一条联动**），放大撤掉，换成一层淡金
**从框往头像蔓延**：起点的颜色来自框，终点的边界是脸。

### 6.2 做法

三处改动，都在「参与者名册」这一侧（棋盘不画 character 联动，只有名册画）：

- `packages/web/src/index.css`：新增 `@property --link-hole`与
  `.participant-link-tint` / `[data-link-tint='on']` 两条规则。它与既有的
  `.participant-tint` 是**同一枚圆心、相反的方向**：主题色那层是「圆长大」
  （`--tint-r` 0.5 → 320），这层是「孔缩小」（`--link-hole` 260 → 32）——
  径向渐变写成「圆心内透明、孔外全是联动色」，孔从盖住整张卡缩到被头像盖住，
  金色就从四个角 / 框边退到头像边缘。色必须**从框开始**长，写不成「一个圆从某处
  长出来」（起点在四个角），只有孔缩小能让外圈先出现；软边（62% → 78%）沿用
  同一条规矩 —— 硬边扫过来读成「擦过去一圈」，不像蔓延。
- `packages/web/src/components/map-editor/ParticipantPanel.tsx`：
  - 卡片根节点在 `data-tint` 旁新增 `data-link-tint`（`isHighlighted` 门控），
    与触碰态**两条轴各开各的** —— 联动指着同时也可能正被碰着，两层 0.16
    叠一起就是了；
  - 新增 `linkTint(color)`：把联动色解析成 `rgba(r, g, b, 0.16)`（与 `themeTint`
    同一套解析、同一档透明度），解不出来落回联动蓝 —— 不能落主色，这不是
    「被选中」；
  - 淡金那层的 `--tint-x` / `--tint-y` 与主题色那层**逐字相同**：蔓延的终点
    必须落在头像边缘，圆心偏一点金色就从脸的侧面冒出来；
  - 头像删掉 `transform: scale(1.08)` 与对应 transition。
- 几何自查：基线孔 260 的色沿 ≈ 203px > 桌面卡对角线半径 151px 与竖屏横卡
  138px（静置不漏金）；终态孔 32 的色沿 ≈ 25px，被头像半径（桌面 47、
  竖屏 28）盖住。头像那枚圆在普通流里、画在 `z-index: -1` 这层之上，
  「染纸不染人」的底线不变。

### 6.3 验证

| 场景 | 结果 |
| --- | --- |
| 单测 `ParticipantPanel.test.tsx`（5 条） | 指向的卡挂 `data-link-tint`、未指向的不挂；2px 框颜色跟联动色走；`--link-color` = `rgba(170, 0, 0, 0.16)`、圆心 `--tint-y: 55px`；联动色缺省落回联动蓝；面板内无 `scale(1.08)` |
| 全量回归 | typecheck exit 0；web 1182（+5）；shared / server 不受影响 |
| 真浏览器（`/play/puzzle-hlm-kanposanchun-hard`，1280×900） | 点亮 card 1 后，被指向的 card 0 挂 `data-link-tint="on"`，`--link-hole` 从 260 收到 32（色沿 ≈ 25px < 头像半径 47 ⇒ 金色只铺纸不盖脸）；2px 框仍在，色为 `rgb(241, 171, 68) 0px 0px 0px 2px`；激活者 card 1 自己不挂 |

### 6.4 没做的

- 没把 `--link-hole` 的起止值按卡片实际对角线算：260 / 32 是按当前两种卡型
  （桌面竖卡 110×196、竖屏横卡 173×80）推的定值；卡型再变（v0.10.1 式的
  新布局）要回来核一遍阈值。
- 没改成「联动色与主题色互斥」：两者叠一起 = 0.16 + 0.16 的深一点，这是
  刻意保留的（两个状态同时为真）。
- 棋盘上的联动高亮没动（画在格子上那一套），本条只说名册。
- reduced-motion 不用单写：`index.css` 的 `@media (prefers-reduced-motion)`
  里 `*` 那条覆盖了自定义属性的 transition（与 `.participant-tint` 同理）。

## 7. 导出包漏掉背景修饰层

用户反馈：「主题包导出，是不是少了背景装饰层，player 打开没有看到」。
未指定版本号，按 AGENTS.md §3.5 并进本版文档。

### 7.1 问题

v0.10.9 加层的时候，**凡是「遍历单元格里两三个引用」的地方都只遍历了
两个**。导出链路因此漏掉整层：

- `collectMapThemeRefs`（`packages/shared/src/themeScope.ts`）只收
  `cell.background` / `cell.item` ⇒ 修饰层引用不进**引用闭包**，
  `buildBundleIdMaps` 发序号时见不到它；
- `renumberPuzzleDraft`（`packages/shared/src/bundle.ts`）只重编号
  background / item ⇒ 谜题 JSON 里修饰格仍写着**数据库原 id**。

真实数据实测（改前）：`GET /api/themes/hlm/bundle?games=7850`
（「一从二令三人木」，画布三格带 `decoration`，指向资源 13390「地毯」）
的 zip 里 `assets.json` 只有 14 个资源、没有地毯、也没有它的图；
谜题 JSON 的 `decoration` 还是 `13390` / `11920-11922`。播放器那一格
画不出任何东西。

### 7.2 做法

**两处源头（shared）**：

- `collectMapThemeRefs` 在 item 块后新增 decoration 块（资源 + 形态，
  `where` 写「单元格 x,y 的背景修饰[形态]」）。它同时是**主题边界检查**
  的数据源，所以那套检查也跟着补齐了；
- `renumberPuzzleDraft` 的单元格循环新增 decoration 重编号
  （`assetId` remap + `variantId` remapOptional）。

**同一把尺子的其它八处**（都是「遍历单元格取引用 / 计数」的地方，
漏一处就漏一种行为）：

| 位置 | 补上之后的口径 |
| --- | --- |
| `mapCanvasRepository.resizeDraft` | `ResizeRemoved` 新增 `decoration` 计数；越界的修饰格同样被裁掉 |
| `mapCanvasService.assertValidReferences` | 存图时校验修饰引用的资源存在（否则导出包会被它卡住） |
| `versionService.validateDraft` / `getVersion` | 发布校验与版本摘要的 `assetIds` |
| `versionRepository.summarizeData` | 版本摘要 `itemCount`（画布上用到的不同资源数） |
| `assetRepository.getUsages` | 资源占用检查（删除前的「正被 N 张地图使用」） |
| `assetVariantRepository.getUsages` | 形态占用检查（删除形态前的拦截）—— 只扫 `cell.item.variantId` 时，删掉一个修饰形态毫无阻拦 |
| `assetRepository.clearAssetFromDrafts` | 删资源时清掉指向它的修饰格，空格判断带上 `!next.decoration` |
| `useEditorResize` / `MapEditorPage.persistGridSize` | 缩画布的越界预警与「已移除越界内容」toast 加一段「背景修饰 N」 |

前六处都在服务端，彼此不知道对方存在 —— 它们能对齐，靠的是「单元格里有
三个引用键」这一条事实本身，不是共同的抽象。

`ResizeRemoved` 加的是**必填**字段 `decoration: number`——它只在服务端
内部流转（repository → route → 前端 toast），不像 `Asset` / `AssetVariant`
那些 DTO 要给旧导出包留余地。

**刻意不动的**：`findItemPlacements`（`packages/web/src/lib/highlight.ts`）
不扫修饰层——联动目标选择器（`PuzzleEditorPage` 的 `placedItems`）只列
**物品层**的 `cell.item`，装饰资源在 UI 里根本选不到，联动语义不该变。

### 7.4 没做的

- 没给修饰层做导出**体检**的单独提示：体检（`bundleService` 的

  之后体检自动覆盖它，没有第二条路径。
- 没把 `decoration` 加进联动目标选择器（见 7.2「刻意不动的」）。
- 没改 `docs/v0.10.9.md`（历史文档，禁改）；本条属 v0.10.9 实现的遗漏，

## 8. 联动淡金的退场也是金色

### 8.1 问题

v0.10.11 的那层淡金（§6）蔓延用「孔缩小」，撤回用「孔放大」，几何上是对称
的。但颜色不是：`--link-color` 取的是 `linkTint(highlightColor ?? HIGHLIGHT_BLUE)`，
而 `highlightColors` 在**撤掉高亮的那一帧就空了** —— `--link-hole` 要过完整条
`--motion-retract` 才缩回 260，这几百毫秒里渐变的颜色已经翻成了缺省蓝
`rgba(144, 202, 249, 0.16)`。用户看到的是「金色蔓延过来，换了个颜色溜走」。

### 8.2 做法

`ParticipantPanel` 加一个 `lastLinkColorsRef: Map<number, string>`：渲染时每一
格的联动色只要有值就写进这张表，取色时按 `highlightColor ?? 记忆里的那一支 ??
HIGHLIGHT_BLUE` 落值。

```ts
const linkColor = highlightColor ?? lastLinkColorsRef.current.get(index) ?? HIGHLIGHT_BLUE;
```

- **为什么在渲染期写 ref，不做 effect**：effect 晚一帧，退场的第一帧仍是蓝，
  闪一下再变金 —— 修的是「颜色跳变」，不能再引入一次跳变。写的是只增不改的
  缓存，渲染被丢弃也不会错。
- **记忆不会钉死**：下一次被指着若换了联动色（换了金的成色），那一帧就更新。
- **从没被指过的卡**：表里没有这一格，仍是缺省蓝 —— 反正孔是 260，看不见。

CSS 那侧没改（`.participant-link-tint` 的注释补了这段规矩）。

### 8.3 验证

| 场景 | 结果 |
| --- | --- |
| 单测 `ParticipantPanel.test.tsx`（+2） | 撤掉高亮后 `data-link-tint` 为 null 而 `--link-color` 仍是 `rgba(170, 0, 0, 0.16)`；再换 `#F1AB44` 联动色，记忆跟着更新为 `rgba(241, 171, 68, 0.16)`；从没被指过的卡仍是缺省蓝 |
| 真浏览器（`/play/puzzle-hlm-kanposanchun-hard`） | 改前：移开指针约 950ms 后（撤回动画跑完）`--link-color` 翻回 `rgba(144, 202, 249, 0.16)`；改后：同一时刻仍是 `rgba(241, 171, 68, 0.16)` |
| 全量回归 | typecheck exit 0；shared 291；web 1184；server 234；build 通过 |

### 8.4 没做的

- 没给 2px 金框做「颜色记忆」：框随 `box-shadow` 一起在 180ms 内渐隐，本身就
  是金色退场，不需要。
- 没把记忆写进 CSS（比如给 `--link-color` 注册 `<color>` 语法做过渡）：金 → 蓝
  会插值成一滩过渡色，不是「同色退场」。
