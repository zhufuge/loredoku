## §1 结果卡的出口

两张结算卡原来都没有「离开这一局」的直接动作：通过面是「关闭 / 再玩一次」（关闭
只是把弹窗收掉，人还站在棋盘前），未通过面是「继续游戏 / 重新开始」。要回列表得
去点左上角那个返回箭头 —— 一局刚结束时，玩家的注意力在卡上，不在角落。

| | 之前 | 现在 |
|---|---|---|
| 通过 | 关闭 / **再玩一次**（主） | 关闭 / 再玩一次 / **返回谜题列表** / **下一关**（主） |
| 未通过 | 继续游戏 / **重新开始**（主） | 继续游戏 / 返回谜题列表 / **重新开始**（主） |

- **返回谜题列表**在两面都有。地址是 `source.listHref()` —— 与左上角箭头同一个
  落点（线上 `/play`、播放器 `/loredoku/:code/play`），两个入口不必在页面里判
  「我是不是播放器」。
- **下一关只在通过时出现**。未通过时「换一关」是一句逃跑的邀请；通过之后它才是
  顺理成章的下一步。
- **一个面只留一枚实心按钮**。通过面：有「下一关」时它是实心的、「再玩一次」退成
  outline；后面没有没做过的关时反过来 —— 否则四枚全是描边，读不出「下一步建议做
  什么」。未通过面的实心按钮仍是「重新开始」（本版不动它），两枚新按钮都是 outline。
- `DialogFooter` 加了 `flex-wrap`：四枚按钮在窄窗里换行，而不是被压成四段等宽。

### 1.1 「下一关」= 列表顺序里的下一个未完成

```
当前这一关 → 往后找 → 找到第一个「还没通过」的 → 就是它
                     一个都没有 → 不画这枚按钮
```

三件必须成立的事：

1. **顺序 = 列表顺序**。两个入口给的清单本来就排好了：线上 `/api/games` 按
   `sort_weight, slug`，包里按导出时同一套顺序（`gameRepository.listGameRowsByTheme`）。
   所以「下一关」永远等于「列表里当前这张卡的下一个卡片」，不另存「关卡序号」——
   那个数字一眼看去像身份，其实只是位置，重排一次就全是错的。
2. **跳过已通过的**。已经结案的关卡再跳一次没有意义。
3. **不回头、不缠绕**。当前是最后一关、或者后面的全通过了 → `null`，按钮不画。
   指不到地方的按钮比没有更糟。

边界：当前这一关**不在清单里**（地址过时、那一关刚被取消部署）时，从清单开头找
第一关还没通过的。那不是「下一关」，是「下一个还没做的」，也是这一页唯一能给的
合理去处。

数据从 `GameSource.useCatalog()` 来（新增）。`api` 实现复用的就是列表页那个
`useGames()`（同一 `gameKeys.all`，react-query 去重，不多一个请求）；`bundle`
实现读已经取到的 `manifest.games`。`GameLevelRef` 只有 `key` + `gridSize` 两项 ——
算下一关只需要这两个，复刻一份完整卡片数据是第二份真相。

## §2 通过记录：用时 + 完成时刻 + 那枚印

存在 `localStorage`，键 `loredoku.game.completed.<存档键>`：

```ts
interface GameCompletion {
  elapsedMs: number;    // 这一局的用时（列表页写的就是它）
  completedAt: string;  // 通关那一刻的墙钟（ISO），只进 title
  stampUrl: string|null;// 通过时定案卡上盖的那枚印的地址
}
```

**为什么还是 localStorage**：玩家没有账号 —— 摆放存档（v0.6.2）、计时（v0.7.11）
都是这条理由，通过记录是同一份进度的第四段。键按**存档键**分，于是线上（裸 slug）
与播放器（`bundle:<code>:<key>`）两套记录互不相通，与 v0.8.0 §11.6 定下的规矩一致。

**指纹只有 `gridSize`**。同一存档键重新部署后网格变了，那就是另一道题，旧记录整条
作废。名单人数（`participantCount`）不进指纹 —— 列表页的两份数据（`MapSummary` /
播放器卡片）都只有 `gridSize` 可对，多存一个对不上的字段，只是让「读得回来吗」多
一个不确定的分支。

**首次为准，不覆盖**。已经有一条有效记录时 `recordGameCompletion` 原样返回它。
重玩再快也不改数字：卡片上那枚印是**凭证**，不是排行榜；数字随每次重玩来回跳，
会把一枚印读成一个计时器。想刷新成绩就清站点的 localStorage —— 这条与 v0.7.11
「提交不落盘」是同一种态度：界面不替玩家改成绩。

**什么时候写**：`submit()` 判卷通过的那一刻，不是结算卡弹出来的时候。读者是
「按下提交、答对了」这件事，与弹窗何时出现无关 —— 玩家中途刷新也不该丢掉结案。
`recordGameCompletion` 自己保证不重复写，这里不必再判一次。

### 2.1 为什么把「印的地址」一起存下来

列表页拿不到关卡级的工具图标：`MapGameSummary` 只有卡面那几项，播放器的
`manifest.games` 也只装清单。为了盖一枚印去逐关打开关卡 JSON 不划算 —— 而**通过
那一刻游戏页手里正好有它**（谜题 → 主题 → 内置，`lib/toolIcons.ts` 已经解析完）。
所以记地址，不记「去哪查」。

代价：作者事后换掉那枚图、或包重新导出过（`files/icons/` 里的文件名带关卡 key，
重新导出不一定同名），旧记录里的地址可能 404。卡片对加载失败的那张图**静默不画**
（`onError` → `setFailed`），不留破图标 —— 用时照常显示，完成这件事仍然说得清。

## §3 列表页：大面积覆盖 + 倾斜的印 + 完成用时

一个已完成的关，卡片上多两样东西，分两处放：

### 3.1 封面：整张压一层，再把印斜着盖上去

- 覆盖铺满**整张封面**（`absolute inset-0`，实测 291×290 覆盖 291×291 的封面，
  覆盖率 0.997 —— 差的 1px 是圆角抗锯齿）。颜色 `bg-background/55`：浅色下是
  `rgba(248,246,242,0.55)`、深色下 `rgba(26,23,20,0.55)`，**只有语义 token**，
  深色自然变暗（AGENTS §3.2）。实测通过卡封面平均亮度 199.6，同尺寸未覆盖的
  封面 237.7。
- 印取 `stampUrl`，`-rotate-[8deg]`、`opacity-90`、`shadow-lifted`、长宽各
  62%（实测 203px / 291px = 69.8%，长边被 `max-h` 收住）。**-8° 是定案卡那枚
  `stamp-press` 停下时的角度** —— 同一枚印在两处不会一正一歪。
- 为什么是整张覆盖而不是角标：卡片在网格里只有 291px，一个角标会被扫过去；
  一整片覆盖才让人在「挑下一关」时一眼看见哪些做完了。覆盖只压封面、不压卡片：
  标题与页脚仍要读得清。
- 深色翻一次（`dark:invert dark:hue-rotate-180`）—— 与工具栏那几枚同一条理由
  （图多半是深墨画在透明底上），只 `invert` 会把红印变青。实测深色 `filter` 是
  `hue-rotate(180deg) invert(1)`。

**没配印就不盖章**（与 v0.9.3 §3 定案卡同一条规矩）：内置 lucide 图标是界面图标，
盖上去像把按钮按进封面里。那一档**连覆盖一起不画** —— 一片没有印的空蒙版只会把
封面弄脏。只留用时。

### 3.2 页脚：`用时 03:07`

排在 `n × n` 左边（成绩比尺寸更该被看见）。写成「用时」而不是光一个 `03:07`：
不加字的数字挨着难度徽章，会被读成又一个字段而没有名字。`title` 里补一句
「完成于 2026-11-10」—— 时刻不占版面，但鼠标一停就能问出来。

未完成的卡页脚与改动前**逐字相同**。

### 3.3 谁来读记录

**页面读、按卡传**（`GameCard.completion`）。卡片是纯展示；「哪些关通过了」是
列表页要一次算清的一件事（它还顺手决定定案卡「下一关」跳哪儿），而两个列表页都
已经握着 `gridSize`。让二十几张卡各读一次 localStorage 就是二十几次同步序列化。

## §5 顺带修的两个真 bug：计时落盘抢跑

给计时加了 `hydrated` 闸门之后，两件**一直在那里、但 jsdom 看不出来**的问题露出来
了。两者都在 `GamePage` 的「计时落盘」那条 effect 上。

### 5.1 续计时从来没生效过（v0.7.11 的债）

真浏览器里 `gameQuery.data` 是异步来的，所以这一页先渲染一次「画布还没到」的形态
（`gridSize = 0`），再渲染一次真的。依赖一变，effect 的**清理函数**先跑 —— 那一刻
`elapsedRef` 还是 0，`persist()` 写进一个「0 毫秒」，而 `writeGameTimer` 对 0 的
处理是**删键**。它跑在水合 effect **之前**，删的正是水合要读的那条计时。

结果：关掉页面再回来，秒表总是从 `00:00` 重新开始。真浏览器实测（修之前）：
`timer key after reload: null`。

修法：`hydrated` 为假时这条 effect 直接返回（不挂定时器、也不注册卸载落盘），
水合读完存档才置真。回归用例「数据晚一拍才到时，存档里的计时不会被抢在读取之前
删掉」——**把闸门拿掉这条用例立刻红**（已实测）。

### 5.2 换关会把上一关的用时写进下一关

从定案卡点「下一关」时组件不重建：`slug` 变了、新一关的数据还在路上。旧版这里
会把上一关的累计毫秒连同**上一关的指纹**写进新一关的键。真浏览器实测（修之前）：

```
loredoku.game.timer.puzzle-outdoor-painting:
  {"gridSize":0,"participantCount":0,"elapsedMs":189244}
```

成绩串了关，留下的还是一条永远读不回来的垃圾（`readGameTimer` 的指纹对不上）。

修法两道：

- `draft` 为空 → 把 `hydrated` 打回 false，等新一关读完自己的存档；
- 指纹为 0 时**不写**（`gridSize <= 0` 直接返回）—— 那一条本来就永远读不回来。

修之后同一场景：新一关不产生计时键，上一关那条 `elapsedMs` 原样保留。

### 5.3 为什么要在这版修

用户这一版要「记录通过的时间」，而它是从同一条秒表读的。带着 5.1 的 bug，成绩会
被记成「打开页面到提交」这一小段；带着 5.2 的 bug，点「下一关」之后新一关会莫名
带着上一关的用时。两个都必须先修，否则新功能记下来的是错数。

## §6 改名：`禁止符号 → 标记`，数据键一起改

### 6.1 为什么连数据键一起改

界面上从 v0.8.6 起一直叫「禁止符号」，但玩家做的是**标记**这个动作（「这格排除」），
`forbidden` 是它落下去之后的语义。只改文案会让「界面说标记、数据说 forbidden」长期
并存 —— 下一个读代码的人得先在脑子里做一次翻译。所以这一版把键也改成 `mark`。

| 旧 | 新 |
|---|---|
| `PuzzleDraft.forbiddenSymbol` | `PuzzleDraft.mark` |
| `ThemeData.forbiddenSymbol` | `ThemeData.mark` |
| `ForbiddenSymbolImage` | `UploadedImage` |
| `forbiddenSymbolSchema` / `…ImageSchema` / `…PathSchema` | `optionalUploadedImageSchema` / `uploadedImageSchema` / `uploadedImagePathSchema` |
| `FORBIDDEN_SYMBOL_MAX_DIMENSION` / `…PATH_MAX_LENGTH` | `SYMBOL_IMAGE_MAX_DIMENSION` / `SYMBOL_IMAGE_PATH_MAX_LENGTH` |
| `POST/DELETE /api/themes/:code/forbidden-symbol` | `…/mark` |
| `POST /api/puzzles/:id/forbidden-symbol` | `…/mark` |
| 上传目录 `…/forbidden-symbol/` | `…/mark/`（**老图不搬**） |

`ForbiddenSymbolImage → UploadedImage` 是顺带的一刀：它服务的早就不止「禁止符号」
一种图（标记、三枚按钮图标、那一圈），名字里带着一种用途只会误导。

**老图片文件留在原目录**：数据里存的是完整相对路径，目录名只决定「新上传写到哪」。
搬文件要动 `storage/uploads`（gitignore 的运行时数据、DB 行引用着），换来的只是目录
好看一点 —— 不值。

### 6.2 旧数据怎么读

三处旧数据不可能同时改完：**冻结的谜题版本行**（部署时只读）、**v0.9.6 之前导出的
资源包**、以及迁移跑之前的库。所以读侧留了一条兜底：

```ts
// schemas/common.ts
export function withLegacyImageKeys(schema) { /* forbiddenSymbol → mark */ }
```

关键是它必须**套在对象那一层**，不能只套字段：`puzzleDraftSchema` / `themeDataSchema`
都是 `.strict()` 的，未知键会被判成「写错了名字」，字段级的 `preprocess` 看不到同级
的旧键。所以两个 schema 的最外层都是 `z.preprocess(moveLegacyImageKeys, z.object({…}).strict())`。

写出去时只写新键 —— 迁移之后库里不会有第二种形状。

### 6.3 迁移 `20260101000046_v096_mark_and_ring.ts`

改 JSON 键，不动表结构。`themes.data` 与 `puzzles.data` 各扫一遍：

```
themes：forbiddenSymbol → mark；pressRing / checkStyle.ring → ring.image；checkStyle 只剩颜色
puzzles：forbiddenSymbol → mark
```

**回退是有损的**，写在迁移注释里：合并后的 `ring.image` 只有一个，拆不回 `pressRing`
与 `checkStyle.ring` 两个位置。回退时写回 `pressRing`（先有的那个、玩家更常看到的那圈），
校验圈回到内置本色环。

`db:rollback` → `db:migrate` 往返实测通过（见 §9）。

## §7 圆环合并：长按计时环 + 提交校验圈 = 一圈

### 7.1 为什么

玩家看到的都是「一圈绕着一格走」：长按是等它装满（放头像）、校验是等它扫完（宣布这
一位对错）。同一种回应、同一个尺度、同一个世界的语言。分成两份配置的后果是作者要传
两次图，而且很难保证两张看起来是一家人。

```ts
export interface ThemeRing {
  /** 那一圈图。缺失 = 两处各画内置细弧。 */
  image?: UploadedImage | null;
}
```

形状是 `{ image }` 而不是直接 `{ path }`：那一圈将来可能不只「一张图」（速度、粗细），
先把「图」这一格留出名字，读点就不必写 `ring.path` 这种把结构焊死的样子。

### 7.2 端点与消费点

- 端点从两个合成一个：`POST|DELETE /api/themes/:code/ring`（原 `press-ring` 与
  `check-ring` 都删掉）。
- 游戏页只解析**一次**，两个图层共用同一个值：

```tsx
const ringImage = useMemo(() => resolveRingImage(source.themeRing(detail?.themeCode), source.fileUrl), …);
…
<MapGamePressRing imageUrl={ringImage} … />       // 长按那一圈
<MapGameCheckLayer ringUrl={ringImage} … />       // 校验那一圈
```

- 校验**颜色**保留（`ThemeCheckColors { passColor, failColor }`）：颜色是「对 / 错」的
  语义，和环长什么样是两件事。配图与配色各走各的端点，改一个颜色不会覆盖那一圈图。

### 7.3 资源包里怎么走

`manifest.theme.ring = { image: { path } }`，图装一份 `files/ring/ring.<ext>`（原来是
`files/ring/press-ring.*` 与 `files/check/check-ring.*` 两份）。

## §8 配置并入一个模块

### 8.1 谜题抽屉：`操作提示`

原来两节（「标记」+「工具按钮图标」）合成一节，四行：标记 / 清除 / 撤回 / 提交。
每行：预览（本图或内置）+ 名字 + 「自己的 / 跟随主题 / 都没有」的说明 + 上传 / 移除。

### 8.2 主题概览页：`操作提示`

原来四张卡（标记 / 工具按钮图标 / 长按计时环 / 提交校验）合成一张，五行：标记 /
清除 / 撤回 / 提交 / 圆环，外加紧跟其后的两档校验颜色。

为什么合成一张：五项回答的是同一个问题 —— **这个世界的操作手感长什么样**。分四张卡
会让人以为互不相干，而作者调的时候往往是一起调的。

两处都用 `data-testid`（`marks-row-<key>` / `mark-row` / `tool-icon-row-<icon>`）把
「这一行在不在」钉住 —— 那条是数据契约（哪一项有配置），不是排版。

## §10 换关 = 换一局：按关卡重建渲染层

### 10.1 问题

用户反馈：「进入下一关时，应该加载这一关的状态和数据，不要复用上一关的状态和数据。」

「下一关」是**同一个 router 内的地址变化**（`/play/a` → `/play/b`），React 复用的
是同一个组件实例，于是上一关的**逐关状态**全都留在原地。真浏览器实测（修复前）：

```
A 关（Fireside Beach 5×5）放大到 130%
→ 点「下一关」
B 关（Outdoor Painting 6×6）：zoom=130%，transform=translate(48.8px, -98.2px) scale(1.3)
```

B 是 6×6、格子更大，130% 之下那张纸直接被摆到了屏幕外 —— 玩家看到一片空白，
得自己点「重置视图」。同类的还有：点击瞬间弹窗里仍是上一关的标题（`gameQuery`
的新数据还没到，而 `result` / `diff` 的旧值还在）；放置模式、联动激活、长按进度环、
刚放下的脉冲表、结算卡与校验圈，都是同一类「上一关的东西」。

### 10.2 做法：`key` 换实例，不写「重置清单」

在**渲染层外面**套一层按关卡变化的 `key`：

```tsx
export function GameView({ source }: { source: GameSource }): JSX.Element {
  const params = useParams<{ slug?: string; key?: string }>();
  const levelKey = (params.slug ?? params.key) || '';
  return <GameViewForLevel key={levelKey} source={source} />;
}
```

`key` 变了 React 就卸载旧的 `GameViewForLevel`、挂一个新的 —— 它下面那二三十个
`useState` / `useRef` 全部回到初值，然后由新一关自己的数据重新水合。

**`key` 为什么必须加在 `GameView` 这一层**：`GameView` 是所有入口的汇合点 ——

```
线上 / 工坊： ApiGamePage → GameView
播放器：      PlayerGamePage → GamePage → GameView
```

第一版把 `key` 加在了 `GamePage` 上，只覆盖播放器那一条；真浏览器实测线上路径
**根本没经过它**，换关后缩放仍停在 130%。加在 `GameView` 上，两条入口自动都得到，
将来再接第三个入口也不会漏。

**为什么不是逐个重置**：这一页的逐关状态有二三十个（缩放 / 平移 / 用户调整过标记、
模式、联动激活、长按格、清除长按、脉冲表、计时器、结算状态、校验序列、悬停、
区域标签…）。写一份「换关时要清哪些」的清单，漏一个就是这一处 bug 的重演；而
`key` 是唯一一处能保证「全都归零」的写法。

`GamePage` 退回成「只负责供数据」，`GameView` 变成「按关卡分派」，渲染本体叫
`GameViewForLevel`（注释里写了不要直接用 —— 它带着上一次的状态）。

### 10.3 与 §5 的关系

§5 那两道闸（水合前不落盘、指纹为 0 不写）仍然需要：`key` 只保证「换关之后是新的
一局」，而**每一局自己**读存档 / 写存档的先后顺序是另一件事，两者不重叠。

## §11 没做的
- **不把通过记录做成服务端数据**。玩家没有账号（v0.6.2 起就是这条前提）；真有
  账号那天，「通过」应该是整份进度的一部分，不是单独一张表。
- **不做「已完成 3 / 8」的总数**。这次用户只要卡片上的时间与印；一个计数需要
  先回答「按什么分组」（主题？全站？播放器是单主题的），那是另一个问题。
- **不做成绩排行榜 / 取最快的一局**。印是凭证，见 §2。
- **不把覆盖做成半张 / 角标 / 描边**。用户要的是「大面积覆盖」；小面积标记在
  291px 的卡上会被扫过去。
- **不在没配印时用内置图标代替**。同 v0.9.3 §3。
- **不给「下一关」加「还有 N 关」之类的附注**。卡上已经写着按钮，数字需要一行
  解释才有意义。
- **不改定案卡「不报用时」那条**（v0.9.3 §3）。成绩现在写在**列表页**，弹窗里
  仍然不念 —— 两处不重复。
- **不把结果卡的四个按钮折进菜单**。一局结束只有这几个动作，摊开比藏起来快。
- **不在换关时逐个 `setXxx` 手动清状态**。见 §7：二三十个逐关状态靠清单维护，
  漏一个就是同一个 bug 的重演。

- **不搬老图片文件**。`storage/uploads` 下的 `forbidden-symbol/`、`press-ring/`、
  `check-ring/` 三个目录原样留着 —— 数据里存的是完整路径，改名不影响读。
- **不在资源包里兼容旧键**。包是导出时生成的，重新导出就是新形状；`manifest` 里
  没有留 `pressRing` 的位置（老包由播放器按「没配」处理）。
- **不把校验颜色也并进 `ring`**。颜色是语义（对 / 错），不是「那一圈长什么样」。
- **不保留旧端点做别名**。`/forbidden-symbol`、`/press-ring`、`/check-ring` 直接消失：
  它们只被本仓库自己的前端调用，留别名等于留一份没人用的接口。
- **不给五项做「一键全清」**。清空是五个独立决定，一个按钮会顺手抹掉作者挑过的图。
