## §1 问题：圆心横坐标写死在 `50%`

`index.css` 里那层色的渐变是：

```css
background-image: radial-gradient(
  circle calc(var(--tint-r) * 1px) at 50% var(--tint-y, 55px),
  ...
);
```

纵向那一半早就是活的 —— v0.7.14 就由组件按实际头像尺寸算出 `--tint-y`
（`AVATAR_PADDING + avatarSize / 2`，桌面 = 8 + 94/2 = 55px）。横向那一半一直是
字面量 `50%`，因为桌面竖卡里头像**就是这么摆的**（`items-center` 一列）。

v0.10.1 的横卡换了网格：头像占第一列（`grid-cols-[auto_minmax(0,1fr)]`）、
纵向跨两行，右边是名称与线索。头像的实际圆心在卡片宽的约 **23%** 处，而渐变仍
从 `50%` 起跳 —— 色团出现在名称与线索那一侧，随后才铺满整张卡。

| | 桌面竖卡 | 竖屏横卡（v0.10.1 起） |
|---|---|---|
| 卡片 | 110×196 | 172.5×80（线索两行时 98） |
| 头像 | 94×94，横向居中 | 56×56，贴左 |
| 头像圆心（卡内） | `50%` / 55px | **40px** / 39px（高卡 48px） |

实测（375×812，`/play/puzzle-hlm-kanposanchun-hard`，7 人）：tint 元素因 1px 边框
内缩成 170.5×78，头像圆心落在 `cx 40 / cy 39`；卡片高 98 那三张 `cy 48`
（= 96/2）—— 因为 `content-center` 让头像**始终在卡片纵向中线**，所以纵向用
`50%` 自适配任意卡片高度是对的。

## §2 做法：把横坐标也交给组件

两处改动，一个常量组：

1. **`index.css`** 渐变起点的横坐标改成变量，默认值保持桌面原样：

   ```css
   circle calc(var(--tint-r) * 1px) at var(--tint-x, 50%) var(--tint-y, 55px),
   ```

2. **`ParticipantPanel.tsx`** 按 `compactPortrait` 分两套圆心：

   | | `--tint-x` | `--tint-y` |
   |---|---|---|
   | 竖屏横卡 | `COMPACT_CARD_PADDING_X + COMPACT_AVATAR_SIZE / 2 + COMPACT_AVATAR_OFFSET_X` = 6 + 28 + 6 = **40px** | `50%` |
   | 桌面竖卡 | `50%` | `AVATAR_PADDING + avatarSize / 2` = 55px |

3. 新增两个常量，让「头像圆心」只有一处算式：

   - `COMPACT_CARD_PADDING_X = 6` —— 横卡网格那串类里的 `px-1.5`；
   - `COMPACT_AVATAR_OFFSET_X = 6` —— 头像那段行内样式里的 `translateX`。

   头像的右移原来直接写 `transform: 'translateX(6px)'`。它是**纯视觉位移**（网格
   第一列是 `auto` 宽，用内边距会把列撑宽、把右边那列挤窄，线索于是多折一行），
   但也正因为它不参与布局，算圆心时必须显式加进来 —— 提成常量之后，改头像位移
   与改扩散起点不会各走各的。

半径 320 不必跟着调：竖屏从 `(40, 39)` 到最远那个角只有约 136px，而渐变在
55% 处仍是实色（176px），铺满时整张卡仍是均一的一层，右下角不会留一块淡角。

## §3 验证

真浏览器量测（agent-browser，dev 5173 + 后端 3000）：

| 视口 | 页面 | 卡片 | 头像圆心在 tint 内 | `background-image` 的 at | 结论 |
|---|---|---|---|---|---|
| 375×812 | `/play/puzzle-hlm-kanposanchun-hard` | 172.5×80 | `(40, 39)` | `40px 50%` | 圆心正落在头像 |
| 375×812 | 同上，线索两行的三张 | 172.5×98 | `(40, 48)` | `40px 50%` | 纵向 50% 自适应 |
| 1280×800 | 同上 | 110×196 | `(50%, 26.8%)` = `54, 52` | `50% 55px` | 桌面口径未变 |

- 7 张卡的 `--tint-x` 全为 `40px`、`--tint-y` 全为 `50%`，与各自头像实测圆心一致
  （横坐标误差 0）。
- 把半径临时钉在 58px 截图：色团出现在**头像**上并向四周摊开；把 `--tint-x` 强行
  改回 `50%` 再截同一张，色团移到名称与线索那一侧 —— 这就是修掉的偏差。
- 悬停真实时序（`mouse move` 到卡片，100/220ms 各截一张）可见半径在长、起点在
  头像，不是整层淡入。
- 桌面 1280×800 的 7 张卡 `at` 全部仍是 `50% 55px`、卡片仍 110×196、`docW 1280`
  无横向溢出。

## §4 没做的

- **没加测试**。这是纯 CSS 起点 + 一个由 `compactPortrait` 分支的变量：jsdom 不做
  布局、算不出渐变的 `at`，而且 `portraitFit` 在测试环境恒为 `false`（窗口被桩成
  1024×768），竖屏分支根本走不到。按 AGENTS.md §4.2「界面外观不写断言」由真浏览器
  量测覆盖。既有的 `GamePage.press.test.tsx:347/356/378` 只断言根节点的 `data-tint`
  属性，未受影响（80 条全过）。
- **没动半径与时长**。`--tint-r` 320、`--motion-tint` 560ms、
  `--motion-ease-spread` 都是 v0.7.14 定的，本次只挪起点。
- **没改 `.press-glow` 一类棋盘上的光圈**。用户说的是名册卡片里那层色。
- **没把圆心改成 JS 实测**（`getBoundingClientRect` + `ResizeObserver`）。当前卡片
  结构是固定的两列网格，圆心由三个常量即可精确推出；上测量会把一次布局读数挂进
  每张卡的渲染路径，名册可以有 24 张。

## §5 问题：同一谜题发新版本，难度与顺序被清零

谜题列表页（`/hlm/puzzles`）里每一行版本都能「部署为游戏」。`GameDeployDialog`
原本只在**这一行版本自己**部署过时回填（`existingGame` / `activeExisting`）：
难度取 `activeExisting.difficulty`、顺序取 `activeExisting.sortWeight`。新版本行
还没有自己的部署，`activeExisting` 为 `null`，于是难度落回主题缺省档（内置五档
是第 3 档）、顺序落回 `0`。

但真实数据里「同一谜题连发十几版、只有最新版上线」是常态：红楼梦主题 24 关里，
`hlm-sishan` 有 18 个版本、`hlm-kanposanchun` 有 4 个版本，都只有最高那一版被
部署。每发一版就重设一次难度、列表里的先后也散掉一次 —— 而作者想改的往往
只是封面或题面，难度与顺序本来就该跟着这关走。

`MapGameSummary` 里 `sortWeight` 的注释本来就写着「为了让部署弹窗回填上一次设的
序号」。这次只是把「上一次」从**同一行**放宽到**同一条血统**。

## §6 做法：值 prop + 一支独立的补填 effect

### 6.1 不改数据层

考虑过给 `MapGameSummary` 加 `puzzleRootId`（服务端 `GAME_SELECT` 与 `toSummary`
透出），**否了**：要动 shared 类型、服务端、8 处测试夹具，而且新字段会随
`player/bundleLoad.ts:148` 的 `{ ...file.summary, ... }` 进资源包。而
`PuzzleEntrySummary` 本来就带 `rootId`，`puzzlesApi.listVersions(id)`（服务端
按 `owner.root_id` 取整条血统）与 `usePuzzleVersions` 都是现成的 —— 纯前端就够。

### 6.2 弹窗只收一个值

`GameDeployDialog` 新增一个可选 prop `siblingGame?: MapGameSummary | null`。
**中途否掉过 resolver 方案**（`resolveSiblingGame` + `siblingVersions` 两个 prop）：
resolver 为躲内联箭头导致的 effect 重跑必须放进 ref，可血统查询与 `useGames()` 是
两次独立请求 —— 若血统先到、`gamesQuery.data` 后到，`useMemo` 不会重算，就查不到
兄弟部署。改成**页面用 `useMemo` 算好的值**，React 按值重渲染，没有这个竞态。

`PuzzlesPage` 侧：

```ts
const bloodlineQuery = usePuzzleVersions(deployTarget?.id ?? null);
const siblingGame = useMemo<MapGameSummary | null>(() => {
  if (!deployTarget) return null;
  for (const entry of bloodlineQuery.data ?? []) {
    if (entry.id === deployTarget.id) continue;
    if (entry.rootId !== deployTarget.rootId) continue;
    const game = gameByPuzzle.get(entry.id);
    if (game) return game;
  }
  return null;
}, [deployTarget, bloodlineQuery.data, gameByPuzzle]);
```

取整条血统而不是列表页的 `versions`：后者只是**当前页 12 条**，兄弟版本常在别的
页。传 `deployTarget.id` 即可 —— 服务端 `listVersions(id)` 会先 `requireRow(id)`
再取 `owner.root_id`，血统里任意一行都能解析出整条。`DeploymentsPage.tsx` 完全
没动（`siblingGame` 缺省 `null`，行为不变）。

### 6.3 只借难度与顺序，不顶替 `activeExisting`

`activeExisting` 还驱动封面三态、`slugReplaced`、「原访问路径将失效」、中段反解 ——
这些都是**这一版自己的内容**。所以兄弟部署走一支**独立**的 effect，声明在整表
回填之后，只在 `!activeExisting && siblingGame` 时补两个 `setState`：

```ts
useEffect(() => {
  if (!open || !activePuzzle || activeExisting || !siblingGame) return;
  if (!difficultyTouchedRef.current) setDifficulty(siblingGame.difficulty);
  if (!weightTouchedRef.current) setSortWeight(String(siblingGame.sortWeight));
}, [open, activePuzzle, activeExisting, siblingGame]);
```

血统查询是异步的，可能**晚到**，所以不能塞进整表回填那支 effect（否则会把作者
刚打的名称与路径冲掉）。两个 `useRef(false)` 记录作者有没有动过难度 / 顺序；
整表回填时清零，难度按钮与顺序输入的 `onChange` 置 `true` —— 默认值只是「默认」，
作者一动手就以他为准。

## §8 没做的

- **没给 `MapGameSummary` 加字段**。理由见 §6.1：一条纯前端通道已经够，动 shared
  与服务端会波及 8 处夹具和资源包。
- **没改服务端 `upsertGame`**。它仍只认同一 `puzzle_id` 的上一行
  （`data.sortWeight ?? previous?.sort_weight ?? 0`）；本次要的是**弹窗默认值**，
  服务端语义不动。
- **没动顺序的三态**。空串 = 这次不提、整数 = 该值、越界报错，全部保持。
- **没动 `DeploymentsPage.tsx`**。那里弹窗是「挑一个版本部署」，没有
  「当前正在看哪一行」的概念，兄弟回填不适用。
