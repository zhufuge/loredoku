# 需求 + 设计：谜题基本信息补名称 / 封面 + 引入新地图（v0.7.3）

> **状态**：**已实施**（2026-10-21）。需求即本文，设计即本文；实施记录见 §9。
>
> 需求原文：
> ```
> v0.7.3
> 添加谜题引入新的版本地图的功能，在谜题编辑页面
> - 添加名称和封面到基本信息框中
> - 顶部工具栏添加引入新地图按钮和功能，点击弹窗选择已发布的地图版本，
>   仅展示gridsize和当前谜题地图的gridsize相同的；选择后仅替换地图信息
> ```

## 0. 一句话

两件事：

1. **谜题「基本信息」抽屉补上名称与封面** —— 名称进草稿（可撤销、随保存落库），
   封面是行字段，和地图编辑器一样先留在本地、等「保存」时上传。
2. **顶部工具栏加「引入新地图」** —— 弹窗只列**方格尺寸相同**的已发布地图版本，
   选中后只换底图（`data.map`），参与者 / 联动 / 调色板 / 描述一概不动。

## 1. 改之前是什么样

- **谜题基本信息抽屉**只装三块：描述、参与者布局、联动主题色。名称与封面只能回到
  谜题列表用「编辑谜题」对话框改 —— 在编辑器里改个名字要离开当前页面。
- **底图创建时固定**：`createPuzzle` 把所选地图版本的画布整份复制进 `data.map.data`，
  之后再也不问地图要数据（v0.7.1 §5 的「谜题自带底图」）。好处是谜题可独立发布 /
  冻结，代价是**换底图只能新建谜题**，参与者配置、联动、描述全部重做。
- **保存的护栏**：`puzzleService.savePuzzle` 会把客户端送来的 `map` **无视**，一律用
  存量覆盖（`map: stored.map`）。画布是服务端资产，客户端伪造不了 —— 这条护栏也是
  「引入新地图」必须先解决的那件事。

## 2. 基本信息补名称与封面

### 2.1 抽屉结构

| 区块 | 字段 | 落点 |
|---|---|---|
| 名称 | 必填，`PUZZLE_NAME_MAX_LENGTH` | store `name`（进撤销栈，随草稿保存写回 `puzzles.name`） |
| 描述 | 选填，`PUZZLE_DESCRIPTION_MAX_LENGTH` | store `description`（同前） |
| 封面 | 选填图片，`CoverPicker`（`layout="stack"`、`noun="谜题"`） | 行字段 `cover_path`，**不进草稿** |
| 参与者布局 | 列数 | store `rosterCols` |
| 联动主题色 | 2~12 项 | store `linkageColors` |

### 2.2 名称为什么进 store，封面为什么不进

- 名称本来就在 `PuzzleDraft.name` 里，也是 `savePuzzleDraft` 回写 `puzzles.name` 的来源；
  放进 store 顺带就拿到了**撤销**与「保存后才落库」的语义，不需要额外的 PATCH。
- 封面没有 JSON 通道（`cover_path` + multipart 上传），且 **fork 态（`?v=`）下还没有
  可写的行**——那一屏落库之前，任何上传都无处可去。所以封面跟地图编辑器同一套：
  抽屉只产出 `{ file, removed }`，页面收在 `pendingCover` 里算作 dirty，等
  **草稿保存成功之后**（`onSaved` 拿到的行 id，fork 态就是新行 id）再上传 / 删除。

### 2.3 脏标记与「保存」

- 抽屉的 `isDirty()` 把名称 / 封面也算进去（`coverFile`、`coverRemoved` 参与比较）。
- 名称为空或描述超长时「保存」禁用、`save()` 返回 `false`（页面据此拒绝切抽屉）。
- 页面的 `canSave` 与离开拦截从 `puzzle.dirty` 扩成
  `puzzle.dirty || coverDirty || forkFrom !== null` —— 只换封面也必须能点保存。

## 3. 引入新地图

### 3.1 入口

`EditorToolbar` 新增可选 `onImportMap?: () => void`，**不传即不渲染**（地图编辑器没这个
动作）。按钮排在「导入 JSON / 导出 JSON」右侧、`基本信息` 左侧，图标 `Map`，
标题「引入新地图（只替换底图画布）」。

### 3.2 弹窗

`PuzzleMapSwapDialog`：

- 数据源 `usePublishedVersions()`（`GET /api/maps/versions`，已带 `gridSize`）。
- **过滤**：`gridSize === 当前谜题的 gridSize`，并**排除当前这一份**（`mapId + versionNo`）。
- 头部写明当前底图：「当前底图：午夜花园 v3 · 9×9」。
- 列表项与「新建谜题」的版本选择器同款（地图名 + `v{n}` + `n×n · 发布于…`）。
- 空态：「没有其他 9×9 的已发布地图版本」+ 「前往地图」。
- 底部说明：「只替换底图画布与地图名称；参与者、联动、主题色、描述保持不变。
  新地图上不存在的联动目标会被移除。」

### 3.3 选中之后做什么

1. 取该版本的画布：`versionKeys.detail(mapId, versionNo)`（`GET /api/maps/:id/versions/:n`，
   返回 `MapVersionDetail.data`），走 `queryClient.fetchQuery` 复用缓存。
2. 拼成 `PuzzleMapContext`（`mapId` / `versionNo` / `mapName` / `gridSize` / `cells` /
   `regions` / `style`）。
3. `puzzle.replaceMapContext(context)` —— 一个撤销步：换 `mapContext`、标脏、清掉格子与
   区域选择、清掉参与者激活。
4. **失效联动**：用 `prunePuzzleReferences(slots, context)`（shared，与
   `validatePuzzleReferences` 同一份判定）把「新地图上不存在的 `asset` / `region`
   目标」从各参与者的 `linkages` 里摘掉，并 toast 报告数量。理由见 §3.5。
5. 关弹窗、关参与者抽屉（它的配置草稿是按旧画布 seed 的，必须重新读）。

### 3.4 保存时怎么把新底图交上去

客户端**不**直接送画布（送也没用，见 §1 的护栏）。改送来源三元组的两个：

```ts
SavePuzzlePayload = { data: PuzzleDraft, updatedAt?, mapSource?: { mapId, versionNo } }
```

`mapSource` 恒等于 store 当前 `mapContext` 的来源。服务端：

```
若 mapSource 缺省，或与存量快照的 (mapId, versionNo) 相同 → 用存量（零查询，老行为）
否则 → 读该已发布版本（过滤软删）→ 拿它的画布 → 校验尺寸相同 → 替换 data.map
```

- **为什么恒发而不是只在换过的时候发**：服务端按「与存量是否相同」短路，等价于
  「只在换了的时候查库」，客户端不需要维护「这次换没换」这个额外状态；而换完之后
  存量就是新的，后续保存继续短路，**地图版本后来被删也不影响谜题**（谜题拿的是副本）。
- **尺寸必须是同一个**：不是 UI 的客气，是硬约束 —— 底图尺寸决定名册长度与所有格子
  坐标，换尺寸等于把谜题的坐标系换掉（那是「新建谜题」的事）。服务端 400：
  「只能引入方格尺寸相同的地图版本（当前 9×9）」。
- fork 态同构：`forkPuzzleVersionBodySchema` 也收 `mapSource`，落库时同样解析。

### 3.5 为什么「仅替换地图信息」还要动联动

需求说「仅替换地图信息」，指的是参与者、线索、主题色、描述这些**谜题自己的东西**不
跟着变 —— 这一点严格守住。但联动里有一类目标是**指向底图**的：`asset`（画布上的物品）
与 `region`（区域）。旧画布上的区域 id 在新画布上不存在时，这份草稿就**存不进去**
（`assertReferenceIssues` 会 400），变成「换完底图就再也保存不了」的死局。

所以这类目标必须一起摘掉，且**同一个撤销步**：对话框底部先写明这条规则，替换后
toast 报「N 项联动目标在新地图上不存在，已一并移除（可撤销）」。没换底图的场景
（§2 的名称 / 封面）不受影响。

## 4. 撤销：`mapContext` 进快照

原来 `mapContext` 明确**不进撤销栈**（「只读画布」）。换底图之后这条不成立了：
撤销如果不把底图换回来，就会出现「底图是新的、联动是旧的」这种半截状态。

因此 `Snapshot` 增加 `mapContext`（引用级，不做深拷贝）。影响面：

- `commit()` / `undo()` / `redo()` 自动带上，一个撤销步换回底图 + 被摘掉的联动；
- `toDraft()` 读 `state.mapContext`，撤销后写回的自然是旧底图；
- `init()` 仍然重置 `past` / `future`，换谜题时不受影响。

## 5. 服务端改动

| 位置 | 改动 |
|---|---|
| `shared/schemas/puzzle.ts` | 新增 `puzzleMapSourceSchema = { mapId, versionNo }`（`.strict()`）；`savePuzzleDraftSchema` / `forkPuzzleVersionBodySchema` 各加可选 `mapSource` |
| `shared/puzzleRefs.ts` | 抽出 `collectReferenceIssues(slots, context)`；`validatePuzzleReferences` 保持签名；新增 `prunePuzzleReferences(slots, context)` → `{ slots, removed }` |
| `service/puzzleService.ts` | `resolveMapSnapshot(current, mapSource)`；`savePuzzle` / `forkVersion` 各用一次 |
| `controller/puzzleController.ts` / `puzzleVersionController.ts` | 把 `body.mapSource` 透传 |

## 6. 明确不做

- 不换方格尺寸（尺寸不同根本不出现在列表里）。
- 不支持「引入草稿中的地图」—— 只有已发布版本才是冻结快照。
- 不改「新建谜题」时的底图选择（还是 `usePublishedVersions()` 全量）。
- 不做底图切换历史 / 一键切回。
- 不在编辑器头部常驻显示底图名（弹窗里写清当前底图即可）。

## 8. 接口与数据变更

无迁移。`puzzles.data` 的形状不变（还是 `PuzzleDraft` v2），变的只是**谁可以换掉
`data.map`**：以前只有创建时那一次，现在保存时可以带 `mapSource` 换一次（同样只接受
服务端从已发布版本读出来的画布）。

### 9.1 落地清单

| 包 | 改动 |

| shared | `puzzleRefs.ts` 抽出 `collectReferenceIssues(slots, ctx)`（`validatePuzzleReferences` 签名不变）+ 新增 `prunePuzzleReferences(slots, ctx) → { slots, removed }`；`schemas/puzzle.ts` 新增 `puzzleMapSourceSchema`，`savePuzzleDraftSchema` / `forkPuzzleVersionBodySchema` 各加可选 `mapSource` |
| server | `puzzleService.resolveMapSnapshot(current, mapSource)`；`savePuzzle` / `forkVersion` 各用一次；fork 的落库名尊重作者改过的名称；`puzzleVersionController.fork` 透传 `body.mapSource` |
| web | `PuzzleInfoDrawer` 补 名称 + 封面（`PuzzleBasicInfo` 加 `name` / `coverFile` / `coverRemoved`，`save()` 改回 `boolean`）；新增 `PuzzleMapSwapDialog`；`EditorToolbar` 加可选 `onImportMap`；`puzzleStore` 的 `Snapshot` 收录 `mapContext` + 新增 `replaceMapContext(ctx, slots?)`；`PuzzleEditorPage` 接封面 pending 与换底图流程 |

### 9.2 基本信息（§2）

- 抽屉的 名称 / 描述 / 封面 合成一块「基本」，与 `MapInfoDrawer` 同一个排版；名称与描述进
  store（一个撤销步），封面进页面的 `pendingCover`。
- `save()` 从 `void` 改回 `boolean`（与 `MapInfoDrawer` 一致）：名称为空时返回 `false`，
  页面据此把用户留在抽屉里补完，而不是顺手切走。
- 页面的 `canSave` / 离开拦截改成 `puzzle.dirty || coverDirty || forkFrom !== null` ——
  **只换封面**也必须能点保存，否则那个文件永远传不上去。

### 9.3 引入新地图（§3）

- 入口是工具栏「导入 / 导出 JSON」右侧的图标按钮（不传 `onImportMap` 即不渲染，地图编辑器
  因此没有它）。
- 弹窗只列 `gridSize` 相同、且不是当前这一份的已发布版本；选中后 `queryClient.fetchQuery`
  取版本快照（缓存键与版本预览页共用，看过就是命中），再拼成 `PuzzleMapContext`。
- `replaceMapContext(ctx, prunedSlots)` 一个状态更新：换底图 + 摘掉失效联动 + 清选择 /
  参与者激活，**一个撤销步**。
- 失效联动用 `prunePuzzleReferences` 算，数量非 0 时用 `toast.message` 明说「已一并移除
  （可撤销）」；为 0 时普通 `toast.success`。

### 9.4 保存链路（§3.4）

- `buildPayload` 恒带 `mapSource`（取自 `puzzle.mapContext`）。服务端见「与存量相同」就短路，
  所以老数据的保存行为、查询次数都没变。
- fork 态同样带 `mapSource`（`forkSaveMutation`），所以「换底图 + 点保存 → 生成新草稿」
  一步到位。
- 封面在 `onSaved` 里上传：那一刻 `data.id` 一定是可写的行（普通保存是原行，fork 态是新行）。

### 9.5 顺手修掉的一处

`puzzleVersionRepository.forkVersion` 会拿服务端生成的 `{版本名} (自 vN)` **覆盖**草稿里的
`name`。名称搬进「基本信息」之后这就成了 bug：作者在 fork 态里改名 → 保存 → 名字被换回去。
现在：作者改过（且与版本名不同）就用他的，否则仍走 `uniqueName` 的自动命名。
