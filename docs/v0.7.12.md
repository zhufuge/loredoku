# v0.7.12 — 加载：全部换成 LOREDOKU 字标

> **状态**：已实施（2026-10-27）。
> **来源**：`/impeccable critique 全部loading的设计，掺入LOREDOKU字符动效，活泼灵动，0.7.12`
> **范围**：`packages/web`。只重做「等待」这件事的表达，取数逻辑、骨架屏的形状、
> 错误态与空状态都不动。

## 0. 一句话结论

这套界面里出现次数最多、也最像模板的一笔，是**每一个加载点都在转同一个 Lucide 圈**：
25 处 `<Loader2>` 散在 19 个文件里。它们全都正确，也全都没有身份 —— 而现在「等待」
这个时刻由产品自己的名字来说明，用与页标题同一支笔（霞鹜文楷）逐字盖上。

改完之后加载的表达收敛成**一种语言、五个尺度**（字标 / 一格翻牌 / 行内 / 整块 / 整屏），
由 `components/common/LoredokuLoader.tsx` 一处定义。

五个加载场景、五种写法、一个图标。用户看不出这是同一个应用在等同一件事，也看不出
这是哪个应用。

### 1.2 AI 味判定

**这一项改前不合格，而且它是全站唯一一处能让人一眼断定「这是生成的」的地方。**

判据很朴素：把界面里所有非文字的元素抹掉，剩下什么？剩下的是一排排转圈的
`Loader2`。它出现在全世界每一份 shadcn 模板里，而它恰恰是用户**唯一盯着看**的那几秒。

改后仍然不合格的是 `Skeleton` 的 `animate-pulse` —— 但那条**不改**，理由在 §3。

## 2. 三条判据（本次新增的设计规则）

加载不是一个组件，是三种不同的处境。此前它们共用一颗图标，现在按**用户此刻缺什么**分：

| 处境 | 用户缺什么 | 用什么 | 长什么样 |
|---|---|---|---|
| 整屏 / 弹窗正文 / 一大块空白 | 缺「有事在发生」 | `LoredokuLoader`（字标） | LOREDOKU，22 / 14 / 11px |
| 一行文字里的状态位（页头、按钮） | 缺一个节拍，不缺点缀 | `LoredokuTick`（一格） | 一格 8 帧翻牌 |
| 内容就在路上、形状可猜 | 缺「马上就有东西」 | `Skeleton`（骨架） | 保持原样 |

**为什么骨架屏不加字标**：骨架的职责是**预告内容的形状**，它已经在说「这一行马上会
出现一条 64px 的记录」—— 比「正在加载」具体得多。再叠一个字标，是同一句话说两遍，
而且会把「形状」这条信息盖掉。**骨架屏不动，是本次的结论，不是遗漏。**

**为什么页头那两处必须改**：它们不是加载组件，是一句话的位置。此前那句话写的是
「正在加载…」，等于告诉用户「这条描述暂时没有内容」。现在同一格换成翻牌格 + 一句
说得更具体的「正在加载部署…」—— 位置没变，信息量变了。

## 3. 字标本身

### 3.1 字形：为什么是这八个字母

LOREDOKU 就是「格物」。用产品自己的名字当状态指示，是这套界面里唯一**不需要教会
用户**的图形；换成任何抽象符号（三点、环形、墨滴）都得先解释一次「这是什么」。

字体走 `.font-kai` 那一支（霞鹜文楷的拉丁，手写衬线，与页标题同一支笔）。代价要在
这里记清楚：

- 这份 woff2 约 **800 KB**（GB2312 一级 + ASCII），`font-display: swap`；
- 它在工坊页的页标题上本来就要下载，且服务端对 `dist/assets/` 是 `immutable` +
  一年缓存 —— 所以**只在玩家侧第一次进入时**会有一次额外请求；
- 首帧若字体未就绪，退回 `ui-serif`：字形变了，但字号是 px 定的，**布局不跳**。

这也是它只在三个地方缺席的原因：`GamesPage` 底部紧挨着 `BrandLogo withWordmark`，
再加一串字标会**把品牌名写两遍**（那里用一格翻牌）；`Skeleton` 那八处见 §2。

### 3.2 节奏：一道光走过去，不是一个开关

周期 1500ms，八个字母依次错开 100ms（`animation-delay: calc(var(--i) * 100ms)`）：

```
0%   不透明度 .3，下沉 1px，缩到 97%
7%   盖上：不透明度 1，抬起 1px，涨到 105%
14%  落定：不透明 1，位置 0，尺寸 100%
64%  保持
74%  退下去（回到 0% 的样子）
```

两条刻意的取舍：

- **暗底是 .3，不是 0**。全暗会让整串字在闪烁与静止之间跳；留住三成，字母的轮廓
  始终在，动的只是明暗边界。读起来是「一道光走过去」。
- **幅度都压在个位数**：1px、5%、3%。这条动效一屏会看几十次，前三次叫活泼，
  第三十次叫抖。落到「看得出在动、不催人」这一档就停。

盖上那一下用的是 `place-pop` 的同一套（0.97 → 1.05 → 1）—— 与游戏页落子同一支动作。
不是巧合：两者都在把一枚字按进格子里。

### 3.3 一格翻牌：按钮里的那个尺寸

按钮里塞不下八个字母，于是同一个动作压成**一格**：L→O→R→…→U 每 180ms 换一个，
八帧走完 1440ms，`linear`（翻牌要读成「咔、咔、咔」，缓动会让它融化成一颗跳动的点）。

- 宽高 `1.15em`，跟着按钮字号走 —— `text-sm` 的按钮里约 16px，与它替换掉的
  `h-4 w-4` 图标**等宽**，pending 前后按钮不跳。
- 它**不带** `role="status"`，是 `aria-hidden`：它永远和「保存中… / 部署中…」同时出现，
  文案已经把状态说完了；再挂一个 live region 只会在同一句话上叠一层「处理中」。

### 3.4 为什么没有描线、扫描线、进度条

三个都被想过，都没做：

- **描线 / 描边文字**：为了「灵动」把字母描一遍，是纯装饰，违反 `.impeccable.md` 原则 1。
- **扫描线**（一行格子被扫过去）：读起来更像进度条，而这里**没有进度可言** ——
  假装有，是骗人。
- **进度条**：加载不可测（查询耗时未知），一条假进度会让用户等着它到 100%，然后发现
  还没好。

## 4. 减少动态：不是调慢，是换一种表达

`index.css` 末尾那条 `*` 规则会把所有动画压成 `0.01ms` 且只播一次。对字标来说这意味着
**每个字母停在关键帧的最后一帧** —— `opacity: .3`，整串几乎看不见；翻牌格更糟，
八格全停在 `opacity: 0`，按钮里剩下一个空洞。

这一类坑在这个仓库里已经记过两次（`.paper-light` 的 `--glow-w`、`.press-ring-arc` 的
时长），所以这里明写两条替代：

| 元素 | 减少动态下的样子 | 为什么 |
|---|---|---|
| 字标 | 八个字母全亮、静止 | 它本来就是品牌名，静止也说得通 |
| 翻牌格 | 整个收起（`display: none`） | 一个不动的单字没有意义，而旁边的「保存中…」已经说完了状态 |

### 6.1 一个只能靠产物验证的坑

三档尺寸的类名必须写成**字面量表**（`SIZE_CLASS: { sm: 'loredoku-word--sm', … }`）。
写成 `loredoku-word--${size}` 的话，Tailwind 的扫描器只看到 `loredoku-word--`，
三档 `font-size` 会被当作「未使用的自定义工具类」**整段删掉** —— 构建不报错、
类型检查不报错，运行时全部退回 16px。同类静默失败在仓库里已经两次
（v0.7.9 的 `shadow-[var(--x)]`、v0.7.10 的 `animate-in` 时长压不动），
所以这次直接在测试里断言类名，并在构建产物里 grep 了一遍。

`--i` 节拍、屏幕阅读器只读「加载中」、三档尺寸类名、翻牌格不自报状态、行内状态、

1. **慢加载仍然没有解释**（评分 10 的 2 分）。超过 3–5 秒的请求应该有第二句话

2. **`Skeleton` 的脉冲没改**（§2）。若哪天要改，方向是方向性微光而不是调时长。
3. **字标的「活泼」能撑多久**：一屏几十次的动效，前三次是惊喜，第三十次是延迟 ——

## 8. 追加：字标里的 R-E-D

LOREDOKU 的第 3–5 个字母正好拼出 **RED**。品牌资产（`assets/LOREDOKU-logo.svg`）
是**黑 + 朱双色墨迹**（`#000000` ×5 路径、`#5C2223` ×3 路径），左上角的图标就是
这两色画的；字标此前是一串均匀的 `--muted-foreground` 灰字，与图标没有血缘。

现在这三个字母上同一支朱，其余五个仍是灰字 —— 一串灰字里多一个落点，字标和
图标对得上，而且不需要第二个图形来解释「这是同一个牌子」。

| 主题 | 取值 | 来源 |
|---|---|---|
| 日间 | `#5C2223` | 资产里的朱，逐字节同一个值 |
| 夜间 | `#FEC4C5`（等效） | 不是手挑的浅红，而是对同一支朱跑同一条工序 |

**夜间为什么不是手写一个浅红。** 图标在深色里从来不是一个色值，而是一道工序：
`invert(1) hue-rotate(180deg)`（`BrandLogo` 的 `dark:invert dark:hue-rotate-180`，
来历见 v0.5.7 §2 —— 双色墨迹纯反色会把朱翻成青，转 180° 色相才还原成亮红）。
这里照抄**同一条 filter、同一个顺序**，而不是把结果 `#FEC4C5` 抄进代码：同一支墨过
同一条流水线，结果必然一致；抄一个值当下也对得上，但图标哪天调了色，字标就会
先走散 —— 而没人会去 grep 一个十六进制值找它是否还准。

实现只有一处：

```css
.loredoku-ink-red { color: #5c2223; }
.dark .loredoku-ink-red { filter: invert(1) hue-rotate(180deg); }
```

**位置从 `indexOf('RED')` 算**（`LoredokuLoader.tsx` 的 `BRAND_RED_AT`），不写死
`[2, 3, 4]`：名字若改，红自然跟着走；改完拼不出 RED 时 `indexOf` 返回 `-1`，
三个字母一个都不染 —— 宁可没有红，也不要红在错的位置上。

**翻牌格（`LoredokuTick`）不染。** 它落在按钮里，颜色是 `currentColor`：实底按钮上
意味着「靛蓝底上的米白字」，换成朱墨在靛蓝上直接消失（对比度 2:1 不到）。按钮的
对比度该由按钮自己的配色负责，字标那三个红字只在纸面上说话。

对比度（满不透明那一帧）：日间 `#5C2223` 在纸底 `40 30% 96%` 上 **11.4:1**；夜间
`#FEC4C5` 在墨底 `28 12% 9%` 上 **11.8:1**。都远超 AA —— 它还是装饰（`aria-hidden`），
但装饰也不该在某个主题里糊掉。字母自己的 `opacity` 会在 1 ↔ 0.3 之间呼吸，暗到
0.3 的那一帧自然凑不满这个比值；同一串字一起呼吸，读起来仍是「在动」，不是
「看不清」。

验证：`LoredokuLoader.test.tsx` 增 2 例（**哪三个字母**被点名、翻牌格一个都不染；
颜色本身在 `index.css`，由构建产物 grep `.dark .loredoku-ink-red{filter:invert(1)
hue-rotate(180deg)}` 核对）。

## 9. 追加：短加载不出现（迟到的淡入）

本地接口多数 20–80ms 就回来了。这种加载画出来只是一帧闪现 —— 用户看到的不是
「正在取」，是「画面抖了一下」。**这种闪烁比没有提示更糟**：每一次都让人以为
是自己点错了（点重了、按钮没反应、页面刷新了）。

做法是纯 CSS 的**迟到淡入**：

```css
@keyframes load-appear { from { opacity: 0 } to { opacity: 1 } }
.load-delayed { animation: load-appear 160ms var(--motion-ease-out) 200ms both; }
```

`animation-fill-mode: both` 是关键那一个词：延迟期间元素停在第一个关键帧
（`opacity: 0`），所以 200ms 内结束的加载**一帧都没被画出来过**；超过 200ms 才用
160ms 淡上来。不是「半透明地先露个脸」，是真的不出现。

| 数字 | 取值 | 理由 |
|---|---|---|
| 门槛 | 200ms | 低于它，人还没意识到「在等」。不取 300ms（业界常用上限）：这里多数请求本来就快，门槛再高等于白加延迟 |
| 淡入 | 160ms | 掐掉「一帧闪过」之后，剩下的边缘是 200–400ms 到达的加载：这段时间字标只淡到四五成，读起来是「刚浮上来又走了」。淡入再快就成了硬切，再慢就成了拖 |

**挂在哪**：`LoredokuLoader` / `LoadingBlock` / `InlineLoading` / `LoadingScreen`
四个出口的根节点。三层嵌套（屏幕 → 块 → 字标）各挂一次，但只有最外层真正跑动画：

```css
.load-delayed .load-delayed { animation: none; }
```

两层同节奏的 `opacity` 相乘，中段会明显偏慢，看着像没对齐。

**翻牌格不挂**。它出现的那一刻，按钮文案已经同时变成「保存中…」了 —— 这一格晚
200ms 再冒出来，只会让标签先短后长地跳一下，比闪一下更难解释。按钮的防闪若要做，
该做在「文案换不换」那一层，不是在这一格的样式上。

**骨架屏同样迟到**（`ui/skeleton.tsx`）。它不能直接叠 `.load-delayed`：呼吸动画也
占着 `animation` 这一条属性，后写的会整个顶掉前一条。于是两条写成一串：

```css
.load-skeleton {
  animation:
    load-appear 160ms var(--motion-ease-out) 200ms both,
    load-skeleton-pulse 2s cubic-bezier(0.4, 0, 0.6, 1) infinite;
}
```

呼吸照抄 `animate-pulse` 的曲线，但换成本地关键帧 —— 最后一处 `animate-pulse` 删掉
之后，Tailwind 连 `@keyframes pulse` 都不会生成，而这里失效是看不出来的。

**减少动态**下只剩「迟到」：全局 `*` 规则已经把时长压到 0.01ms，于是元素在 200ms
处直接出现（别闪这件事与是否要动无关）。骨架屏要单独把第二条动画恢复到 2.4s /
无限，否则它会停在半透明处一动不动 —— 那是「坏了」的样子。

同一类闪烁还剩一处刻意没动：**编辑器保存蒙版**（`EditorShell`）。它是 `opacity`
过渡而不是动画，压延迟要写成非对称的 `transition-delay`；而它同时是「挡住画布继续
操作」的信号，150ms 的空白会让人以为保存没开始。等真的听到反馈再说。

验证：`LoredokuLoader.test.tsx` 增 1 例（四个出口都挂 `.load-delayed`、翻牌格不挂）；
两处只能靠产物 + 浏览器核对 —— 构建后 grep 到 `load-delayed{animation:load-appear
.16s var(--motion-ease-out) .2s both}`、`.load-skeleton` 的两条动画与 reduced-motion
覆盖；无头 Chrome 对照渲了两行（延迟版 / 立即版），截图里只有立即版被画出来。

## 10. 追加：进编辑器为什么「有时候」在加载画布

因为它有**两道门**，而且两道门都可能被你撞见：

| 顺序 | 等什么 | 在哪 | 提示 |
|---|---|---|---|
| ① 分包 | `MapEditorPage` / `PuzzleEditorPage` 的 JS 还没下载（49KB / 57KB） | `router.tsx` 的 `Suspense` | 改前：`min-h-[60vh]` 居中一个**没有文案**的字标 |
| ② 画布数据 | `useMapCanvas(id)`（地图）/ `usePuzzleDetail` + `useMapCanvas`（谜题） | 页面里的 `mapQuery.isLoading` | 整屏 `正在加载画布…` |

于是「有时候」有四种结果，取决于**哪一道门在 200ms 之外**（§9 的门槛）：

| 处境 | 看到什么 |
|---|---|
| 同一个会话第二次进**同一张**图 | chunk 已下载 + `staleTime: Infinity` 的数据还在缓存 → 两道门都不亮，直接进编辑器 |
| 先进 A 图、再进 B 图 | chunk 命中（门①不出现），B 的画布没缓存 → 只有「正在加载画布…」 |
| 刷新页面后第一次进 | chunk 冷 + 数据冷 → 可能连着看到两道（这就是「有时候」） |
| 网络慢 | 门①先亮（没文案、位置还偏上 20vh），门②再亮（有文案、整屏） |

第三、四种情况的问题不是文案写错，是**同一段等待被讲了两遍，而且长得不一样**。

**改法一：整屏路由的 fallback 借用页面自己的那句话。** `lazyPage` 多了第二个参数，
编辑器 / 查看页 / 游戏五个整屏路由各自传 `screenFallback('正在加载画布…' / '地图…' /
'谜题…' / '游戏…')`。这样不管卡在哪道门，屏幕上永远是同一句、同一个位置（`h-screen`
居中）。外壳里的页（列表 / 资源 / 角色）仍用 `min-h-[60vh]` 那份 —— 它们的等待发生在
`AppShell` 里面，不该占满整屏。

**改法二：第二道门不重新迟到。** 两道门画的是同一个东西，却是两个组件实例：门①的字标
刚淡上来，门②一挂载又从头数 200ms，中间空出一次闪烁 —— 看着像「加载失败重来了」。
`LoredokuLoader.tsx` 里的 `useLoadDelayed` 记一个模块级时间戳（`lastVisibleAt`，只在
「真的亮了」之后写），800ms 内出现的下一件加载件直接以成品出现。

- **为什么是模块变量**：这个记忆要跨 **Suspense 边界**（门①在边界外、门②在页面里），
  而 context 也是被边界切开的普通树 —— 只能记在模块作用域。
- **为什么在 200ms 后才写**：200ms 内就结束的加载从头到尾没被画出来过，它不该算进
  「刚才已经在等」。
- **测试**：`LoredokuLoader.test.tsx` 的「接力」用例把假时钟**往回拨一分钟**再跑，
  跑完切回真时钟时时间戳停在过去，同文件后续用例不受影响（否则它会落在未来，
  后面的用例全部被判成「刚亮过」）。

剩下的边界：门①和门②之间如果隔着一次路由重挂载（从一张图直接跳到另一张图的编辑器），
接力窗口只有 800ms —— 超过就重新迟到一次。这是有意的：真的等了一会儿的东西，值得
重新淡上来。

## 11. 追加：纸背光那支墨太深

反馈只有五个字：「paper-shade 颜色太深了」。查下来，深的那一帧不在静止时 ——
在**光圈还没张开**的头一百多毫秒。

`.paper-shade` 的渐变半径是 `146% × --glow-r`。悬停时 `--glow-r` 从 `0.32` 长到 `1`，
而 `146% × 0.32 = 47%` 已经够不到四角（四角在 `71%` 处）—— 也就是说，光的圆圈还没
铺开时，**整张封面都落在渐变的满强度那一端**。淡入只要 120ms，比张开（700ms）快得多，
所以那一下是「整张纸变成深褐」，然后才慢慢亮回来。

在奶油纸底（`hsl(40 30% 96%)`）上取样，旧配方 `hsl(26 46% 25% / .72)`：

| 状态 | 四角像素 | L* |
|---|---|---|
| 没有暗角 | `248,246,242` | 96.9 |
| 悬停静止（`--glow-r: 1`） | `209,199,191` | 80.8 |
| 刚悬停（`--glow-r: .32`） | `134,110,90` | **47.6** |

静止时只掉 16 个 L*，所以前几版「静态截图并排比对」怎么调都抓不到问题 —— 那几次
调参（0.56 / 0.66 / 0.72）比的是**静止帧**，而难看的帧只在过渡里出现。

**改法：减墨，不减范围。** 色相 `26`、饱和 `46%`、`transparent 18%` 的透明芯全部
不动 —— 那两样决定的是「影子该有的形状与温度」。只把亮度从 25% 抬到 30%、不透明度
从 .72 收到 .55：

```css
hsl(26 46% 30% / 0.55)   /* 原 hsl(26 46% 25% / 0.72) */
```

同一处取样：

| 状态 | 旧 | 新 |
|---|---|---|
| 悬停静止四角 | `209,199,191`（L* 80.8） | `219,211,202`（L* 85.1） |
| 刚悬停四角 | `134,110,90`（L* 47.6） | `166,143,123`（L* 59.6） |
| 整卡平均 | `239,235,230` | `242,238,233` |

（最后一行是换完 CSS 后用真实规则复测的：静止 `221,213,204` / L* 85.7，进场
`171,148,130` / L* 62.9，整卡平均 `240,235,230` —— 与上表同量级，差异来自取样网格。）

静止时那 5 个 L* 几乎看不出，进场时那 12 个 L* 一眼能看出：**这就是「太深」的正确
着力点**。整卡平均只浅 3–5 个色阶，所以「纸上有一盏灯」这件事没被削弱 —— 对面是
一片 97% 亮的纸，暗角弱一点点，光心反而更突出。

**为什么不是把 `--glow-r` 的起点抬高。** 起点从 .32 抬到 .45，满强度的边界只从
`47%` 挪到 `66%`，四角（`71%`）仍在满强度区里 —— 改变的是过渡手感，不是那一帧的
深度。真正决定深度的是 α，不是半径。

**没动的：** `.paper-core`（近白热斑 `42 100% 95% / .42`）、`transparent 18%`、
进出场时长与曲线。这次只碰一个数。

验证：web 全量 **906 例**通过（`GameCard.test.tsx` 只断言 `paper-shade` 在类名里，
不含色值 —— 深浅由产物 CSS 与本节的取样表负责）；`vite build` ✓；产物里
`.paper-shade` 的末色为 `hsl(26 46% 30% / .55)`。取样方式：无头 Chrome 渲染
（真实类名 + 真实 `--glow-r`）→ `sharp` 读像素 → 算 L*。

## 12. 追加：收回再慢一点（340ms → 520ms）

「离开时收起的速度再慢一些」。改的是 `--motion-retract`，只有光圈在用：

```css
--motion-retract: 520ms;   /* 原 340ms */
```

**为什么原来那么短。** v0.7.10 §10.11 定这个数的时候用的是「退出不该让人等」这条准则，直接取了
进入时长（700ms）的一半 —— 340ms 确实「看得出在收」，逐帧采样也证明两条轨（半径、
取景框）同步衰减、`opacity` 冻到最后一刻才落。

**但那套采样只证明了「都动了」，没证明「看完了」。** 收回是**三件事叠在一起**：半径从
`1` 收窄到 `0.32`（光池收紧）、遮罩 `--glow-w` 从 `1` 关到 `0`（外圈裁掉）、最后 `opacity`
落 0。340ms 摊给三步，每一步都只走了个开头 —— 观感不是「缩回光心」，是光还没收拢就被
掐掉。所谓「收回」这件事，只有在收缩**看得完整**时才成立。

| 项 | 值 | 依据 |
|---|---|---|
| 新时长 | 520ms | 进入的 74%：仍是离开更快（这条不能破，否则退出比进入还隆重，读成卡住），但整套收缩能走完 |
| 上限 | `< 700ms` | 等于进入会失去「退出更快」的方向感；超过就变成「慢动作回放」 |
| 曲线 | 不变（`--motion-ease-retract`） | 问题只在长度。这条曲线本来就是「起步轻、收尾缓慢停住」，拉长之后收尾那段正好落在遮罩关到底的位置 |

**没有跟着改的：**

- 进入（`--motion-glow` 700ms / `--motion-ease-spread`）—— 两个方向本来就该不对称，
  这次只是把不对称的**比例**从 1 : 0.49 收到 1 : 0.74。
- `opacity 1ms linear var(--motion-retract)` 那条延迟 —— 它引用的是同一个 token，
  时长改了它自动跟着走（这也是当初不写字面量的原因）。冻结窗口变长到 520ms 是**必须**
  的：淡出早于收缩，收回就白做了。
- 封面缩放（`--motion-image` 360ms）—— 它和光同时退，如果跟着拉长，卡片会显得「不肯走」。

验证：`npm run typecheck` 三包 0 错；web 全量 **906 例**通过（没有用例断言这个时长，
光圈的进出由产物 CSS 与本节的比值负责）；`vite build` ✓，产物里 `--motion-retract: .52s`，
`.paper-light` 的三条退出过渡都指向它，进入侧仍是 `.7s`。

## 13. 追加：暗角铺得更开、更薄

「`.paper-shade` 向外扩散更大，过渡更多一点」。这两句话指的是同一件事 —— 把渐变
**场**放大：半径 146% → 200%，透明芯 18% → 12%。

```css
ellipse calc(var(--glow-r) * 200%) calc(var(--glow-r) * 200%) at 光心,
transparent 12%,
hsl(26 46% 30% / .55)
```

**为什么「放大半径」等于「扩散更大 + 过渡更多」。** 暗角的强度是「这个像素在渐变
全程里走了几成」的函数。半径从 438px（146% × 300px）拉到 600px，同样的像素距离就
只分到更少的路程 —— 影子整体摊薄、往封面之外延伸。而过渡带（透明芯到满强度之间
那段）从 `0.82 × 438 ≈ 359px` 变成 `0.88 × 600 ≈ 528px`，长了 47%。一个动作，两个
反馈都吃到了。

**透明芯的百分数为什么跟着降。** 300px 见方时，被照亮的芯的像素半径是
`0.18 × 438 ≈ 79px`，改成 `0.12 × 600 ≈ 72px` —— 几乎不动。芯不动、坡变长，读起来
才是「光还是那一盏，纸往外更暗得慢」；如果芯也一起放大，就成了「灯变亮了」，那是
另一回事。

**一个必须说清楚的代价：静止时这张卡上不再有「满强度」的暗角。** 满强度落在 600px，
已经在封面之外；四角（212px）只走到全程的 35%，那一段的 α 是 `0.55 × 0.27 ≈ 0.15`。
实测（奶油底）：

| 取样 | 旧（146 / 18） | 新（200 / 12） |
|---|---|---|
| 静止四角 | `221,213,204`（L* 85.7） | `228,222,214`（L* 88.7） |
| 静止上边中 | `238,233,227`（L* 92.6） | `238,233,227`（L* 92.6） |
| 静止整卡平均 | `239,234,229` | `241,238,233` |
| 进场四角（`--glow-r: .32`） | `171,148,130`（L* 62.9） | `171,148,130`（L* 62.9） |
| 进场上边中 | `178,157,140`（L* 66.1） | `194,177,164`（L* 73.3） |
| 进场整卡平均 | `203,190,178` | `208,196,185` |

四角那一行没变，是因为进场时 `200% × 0.32 = 64%` 仍然够不到四角（71% 处）—— 那一
小块仍是满强度。变的是中段：一片原本已经压到 L* 66 的区域，现在只到 73。**「太深」
的最后一点残余就在这 7 个 L\* 里**，而它恰好落在视觉重心（封面中部）。

**没动的：** α 与色相（`.55` / `26 46% 30%`，§11 的结论）、`.paper-core` 的 150px
热斑、`--glow-r` 的 0.32 → 1、进入 700ms / 退出 520ms 两条时长。

> §11 里那句「`146% × 0.32 = 47%` 够不到四角」是**当时**的几何；现在写的是 200%，
> 结论不变（`64%` 仍够不到 `71%`），只是数字换了。

验证：`npm run typecheck` 三包 0 错；web 全量 **906 例**通过；`vite build` ✓；产物里
`.paper-shade` 的半径为 `calc(var(--glow-r) * 200%)`、透明芯 `12%`、末色
`hsl(26 46% 30% / .55)`。上表由无头 Chrome 渲染真实类名 + `sharp` 读像素得到。

## 14. 追加：夜间模式里那行「参与者 4/4」

谜题编辑页左面板的标题栏，日间好好的，切到夜里几乎读不出字。

原因很朴素：那行颜色是**内联写死的**

```tsx
style={{ ..., color: '#1F2937' }}
```

`#1F2937` 是 slate-800 —— 为纸底挑的深灰。纸底（`40 30% 96%`）上它 13.60:1，毫无问题，
所以从 v0.6.x 定这个 40px 标题栏起，它在任何一次日间走查里都不会露馅。落在夜墨
（`28 12% 9%`）上则是 **1.22:1** —— 比 `--border` 还淡，等于那行字不存在。

| 主题 | 旧 `#1F2937` | 新 `text-foreground` |
|---|---|---|
| 日间（纸底 `#F8F6F2`） | 13.60:1 | **15.29:1** |
| 夜间（夜墨 `#1A1714`） | **1.22:1** | **15.15:1** |

**为什么是 `text-foreground` 而不是 `text-muted-foreground`。** 它是一行标题，不是说明
文字。全站标题这一层（`EditorLeftPanel` 的两个 tab、抽屉标题、卡片标题）都用
`foreground`；muted 在夜间是 7.25:1，够读，但它表达的是「次要」，而这行是这块面板的
名字加进度，不该自降一格。

**加 class 不够，必须删掉 inline。** 内联 `color` 的优先级高于类选择器 —— 只把
`text-foreground` 添上去，`#1F2937` 仍然赢，症状一模一样，而且看代码像是已经修了。
所以那一次编辑是「删一个属性 + 加一个类」，两件事一起做。

**顺带把数字包成 `tabular-nums`。** `4/4` 会变成 `10/10`，等宽数字让这一行不随进度
左右微跳；`{' '}` 那半个空格保持「参与者 4/4」里那个原有间距（也保住了
`textContent` 断言里的那串字面量）。

**全站扫描：只此一处。** `grep "color: '#"` / `text-[#` 在 `src/**/*.tsx` 里只剩
`PuzzleInfoDrawer` 的 `color: '#888888'` —— 那是新建联动调色板条目的**默认值**，
是数据不是样式。其余写死的 hex 全在 `MapGameLayers` / `StyleFields` / `ParticipantDrawer`
里，都是画布内容色（作者的作品，按 `design-system.md` §1.1 末的判据不随主题变）。
也就是说，这一行是唯一一处「用内联色值做 UI 文字」的地方。

**测试**：`ParticipantPanel.selected.test.tsx` 增 1 例 —— 断言那行同时满足「有
`text-foreground`」与「没有内联 `color`」。两半都要断言，理由就是上面那条：只检查
class 的用例，在有人重新塞回 inline 时会照样绿。已经反向验过一次（把 class 去掉 +
塞回 `#1F2937`，该例转红）。

**没动的：** 40px 行高、13px / 600、居中、`border-b` 的下边框色。日间观感只有极细微的
变化 —— 旧值偏冷（slate），新值偏暖（纸墨），正好是全站调色板的方向。

## 15. 追加：角色列收起后不留边、按钮上标题行

谜题编辑器左面板收起时原来是**一条 40px 的竖条**：上面一个 `›` 箭头，下面竖排两个字
「角色」。它的全部作用就是「把自己展开」，而代价是一条常驻的边 —— 画布少 40px，而且
这条竖条和参与者标题行并排时，两行「标题」中间夹着一列竖排字，读起来是乱的。

现在收起等于**这一列不存在**：`PuzzleEditorLeftPanel` 直接 `return null`，画布拿到
40px。展开入口挪到紧邻的参与者面板标题行左侧 —— 那一行是它唯一还站着的邻居。

**状态没有搬家，只多了一根线。** `collapsed` 与 `userTookOverRef` 仍然只在这个组件里
（自动收起是面板自己的知识：名册满了、所有「加入」都灰了，它比页面更清楚）。页面只拿
两样东西：

| 需要什么 | 通道 |
|---|---|
| 「现在收起了吗」—— 决定要不要挂那颗箭头 | `onCollapsedChange`（`useEffect` 里报 `collapsed`） |
| 「把面板叫回来」 | `ref.expand()`（`useImperativeHandle`，与面板内部那颗「收起」共用 `takeOver`） |

**这里有个必须留意的坑：收起后组件仍然挂载，只是渲染 `null`。** 如果为了省事写成
`{collapsed ? null : <PuzzleEditorLeftPanel />}`，一旦收起组件就卸载了，`userTookOverRef`
跟着重置；下次展开重新挂载时，自动收起那条 effect 又按「名册已满」把它收回去 ——
用户会看到面板自己弹回一条缝。返回 `null` 而不是不渲染，保住的正是这条记忆。

**箭头为什么用绝对定位，而不是在标题行里分一格。**

```tsx
<div className="relative shrink-0 border-b px-3 text-center text-foreground">
  <span className="absolute left-0.5 top-1/2 flex -translate-y-1/2 leading-none">
    {headerLeading}
  </span>
  参与者 <span className="tabular-nums">4/4</span>
</div>
```

分格（`flex` + 按钮 28px + `flex-1 text-center`）会让标题只在「面板宽 − 28px」里居中，
**往右偏 14px**。这一行只有三个字加一个分数，偏一点点就看得出来；而整块面板的居中，
一直是这行标题唯一在表达的排版事实。

无头 Chrome 渲染 + 像素量（浅底、13px/600）：

| 面板宽 | 箭头墨迹 | 标题墨迹 | 标题中心 vs 面板中心 |
|---|---|---|---|
| 250px，无按钮 | — | 92–156 | 124 / 125 |
| 250px，有按钮 | 13–18 | 92–156（**一格没动**） | 124 / 125 |
| 126px，有按钮（单列最窄） | 13–18 | 30–94 | 62 / 63 |

最窄那一档箭头右缘（18）到标题左缘（30）还有 12px，不碰。夜间同样成立 —— 箭头吃
`text-muted-foreground`（夜墨上 7.25:1），标题吃 `text-foreground`（15.15:1）。

**箭头单独导出成 `RosterExpandButton`**，而不是让页面自己写一遍 `<button>`：`title` /
`aria-label` / `aria-expanded` 这三行是「面板的一个出口」，与面板内部那颗「收起」是一对，
散在页面里迟早改一处忘一处。
