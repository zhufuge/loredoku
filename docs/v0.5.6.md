# v0.5.6 · 前端结构版：懒加载、flow hooks、图层拆分与共性上移

> 版本定位：**不新增任何功能**，不碰 JSON 结构、shared schema 与数据库，只做前端代码结构。四步按风险从低到高排列，每步独立可回滚；本版执行调研给出的五步中的前四步（§1）。

---

## 1. 需求原文

用户在此前「前端代码结构优化建议」调研之后给出的指令：

```
做1，2，3，4步，并整理到v0.5.6
```

「1，2，3，4 步」指该调研给出的五步计划（按风险从低到高，每步独立可回滚）的前四步，原文照录：

> **① 路由级懒加载 —— 零行为风险，先做**
> `router.tsx` 现在静态导入全部 11 个页面，首屏要下载编辑器全家桶（EditorPage + EditorCanvas + MapLayers + 两个 store + 5 个大抽屉）。改成 `React.lazy` + `Suspense` 后，进 `/play` 的玩家再也不下载编辑器代码。注意：fallback 复用现有加载样式别白屏；AppShell 保持静态；NotFoundPage 只有 14 行不值得懒加载。我已验证**没有测试渲染路由**，这步碰不到任何测试。
>
> **② 抽 flow hooks —— 治 God 页面**
> EditorPage 的 `return (` 在第 646 行，前 565 行全是 37 个 hook。按流程切开放进 `hooks/`（仓库已有先例：`useSaveMap` / `usePublishProject`）：`useEditorSave`（保存+自动保存+蒙版）、`useEditorPublish`（发布+ violations）、`useEditorResize`（改尺寸影响面）、`useEditorShortcuts`（PuzzleEditorPage 有**三个** keydown effect，正好合并成一个）。注意：hook 返回带名字的对象，不要 15 个值的数组；跨流程共享的 ref（canvasRef / mapInfoRef）留在页面里。
>
> **③ 拆 MapLayers（1022 行纯渲染）**
> 按层组拆成 5 个子组件（背景 / 物体 / 标尺 / 区域 / 高亮）。注意：`canvasLayers.test.ts` 41 个用例断言层序与 `MAP_LAYER_ORDER` 一致——**层序常量是唯一真相，拆文件不动层序**，导出 API 保持不变让测试原样通过。

> **④ 两个编辑器页共性上移**
> 已验证的共性：`useUnsavedChangesGuard`（已抽）、快捷键监听（EditorPage 1 处 vs PuzzleEditorPage 3 处）、保存/发布流程形态。抽 `useEditorShortcuts` + `EditorShell` 布局。**只抽不变式**——地图可写、谜题画布只读是实质差异，强行统一会造出带 6 个 flag 的通用组件，比留 20 行重复更糟。

## 2. 总体思路

调研的核心判断：**仓库的分层是干净的，要保护；问题在体积和打包，不在架构方向**。所以本版主线是「拆大到小 + 拆包」，而不是换架构。

| 症状（调研实测） | 本版对策 |
|---|---|
| 3 个页面占页面代码 56%；大组件 6 个 500~1000 行（MapLayers 1022、MapInfoDrawer 872、EditorCanvas 813、ParticipantDrawer 635、LinkageDialog 588、ParticipantPanel 519） | 第③步拆最大的 MapLayers；第②④步拆两个编辑器页 |
| 打包未切分：单 chunk 805 kB / gzip 250 kB | 第①步路由级懒加载 |
| PuzzleEditorPage 有 3 个 window keydown effect（EditorPage 1 个）——重复且有合并空间 | 第②步 `useEditorShortcuts` 合并成一个 |

调研同时给出七条本仓库特有的注意点，本版全程遵守：

1. **源码级测试锚点**：30 个测试文件用 `readSource/codeOf` 断言源码文本，移动文件会让它们**恒真或恒假而不报错**（v0.5.5 踩过三次）。每拆一个文件立刻逐文件跑测试，别只靠 typecheck。
2. **行为零变更是硬约束**：动手前记基线（web 55 文件 / 785 用例全绿），每步对比，任何一步能单独回滚。
3. **别建 barrel 文件**：拆文件夹时每层一个 `index.ts` 会引入循环依赖、拖垮 tree-shaking。
4. **空间约束是拆组件时的雷**：参与者抽屉必须挂在带 `relative` 的头部栏兄弟容器（FIX-N10），浮层层级只用 `UI_Z`。
5. **JSON 结构不碰**：只动 web 表现层。
6. **撤销栈不变量**：50 步上限、`mapContext` 永不进 undo 栈。
7. **行数不是判据**：拆分看「变化是否局部」「能否单独测」。

第二轮指令把「收敛」提到了台面：懒加载按页切分之后，rollup 又自动切出 20 余个 2~40 kB 的依赖 / 共享碎块，`dist` 达到 45 个文件——「按路由分割」的收益还在，但「每个 lucide 图标一个文件」显然是过度切分。收敛手段是 `manualChunks` 手动分组（§3.4），**总下载量不变、文件数减半**；同时借用户第二个诉求，把「npm start 单端口托管前端」补上（§7），这是这个 monorepo 一直缺的最后一块生产拼图。

## 3. 第①步 路由级 React.lazy 懒加载

### 3.1 做法：`lazyPage` 包装器

`router.tsx` 重写（77 → 114 行）。核心是一个包装器，把「懒加载」和「加载态」合成一件事：

```tsx
function lazyPage(load: () => Promise<{ default: ComponentType }>): ComponentType {
  const Lazy = lazy(load);
  return function LazyPage(): JSX.Element {
    return (
      <Suspense
        fallback={
          <div className="flex min-h-[60vh] items-center justify-center gap-2 text-sm text-muted-foreground">
            <Loader2 className="h-4 w-4 animate-spin" />
            正在加载…
          </div>
        }
      >
        <Lazy />
      </Suspense>
    );
  };
}

const GamePage = lazyPage(() => import('@/pages/GamePage').then((m) => ({ default: m.GamePage })));
```

10 个页面全部懒加载；`AppShell`（布局外壳，首屏必需）与 `NotFoundPage`（14 行，懒加载的包装成本大于收益）保持静态导入。fallback 复用现有加载样式（`Loader2` + `text-muted-foreground`），不白屏。

### 3.2 关键设计：路由数组逐字不变

`element: <GamePage />` 一行不改——只把 import 行从静态改成 `lazyPage(() => import(...))`。这样做的直接收益是**测试零风险**：调研已验证「没有测试渲染路由」，路由断言只查 `routerSource` 文本。

唯一需要同步的锚点是 `GamesPage.test.ts` 里一条 import 断言：

```ts
// v0.5.6: pages are lazy-loaded now
expect(routerSource).toContain("import('@/pages/GamesPage')")
```

`GamePage.test.ts` 的全部路由断言零改动通过。

### 3.3 效果（第一轮交付时）

| | 前（v0.5.5） | 后（第①步完成） |
|---|---|---|
| 入口 chunk | 805.74 kB / gzip 250.18 kB | **433.24 kB / gzip 137.60 kB** |
| EditorPage | 打进入口 | 独立 chunk 51.83 kB |
| PuzzleEditorPage | 打进入口 | 独立 chunk 46.65 kB |

进 `/play` 的玩家不再下载编辑器全家桶（EditorPage + EditorCanvas + MapLayers + 两个 store + 5 个大抽屉）。

### 3.4 打包收敛（第二轮：manualChunks）

第一轮交付后用户反馈「拆得太零散，太多小文件」。彼时 `dist/assets` 有 **45 个文件**：10 个页面 chunk 之外，rollup 自动切出了 20 余个 2~40 kB 的碎块——每个 TanStack Query hook（`useItems` 2.09、`useMaps` 2.14……）、每个共享 lib（`grid` 23.07、`editorFocus` 28.98）、**每个 lucide 图标各一份**（`minus` / `plus` / `x` / `search` / `eye` / `pencil` / `eraser` / `rotate-ccw` / `undo`……）。

`vite.config.ts` 增加 `build.rollupOptions.output.manualChunks`（函数形式），**总下载量不变，文件数 45 → 25**：

| 分组 | 内容 | 体积 |
|---|---|---|
| `vendor-react` | react / react-dom / react-router / scheduler / **@remix-run/router** | 208.46 kB / gzip 67.87 |
| `vendor-ui` | radix / lucide / zod / sonner 等其余依赖 | 268.79 kB / gzip 82.52 |
| `vendor-query` | `@tanstack/*` | 40.63 kB / gzip 12.05 |
| `shared` | `src/lib` + `src/api` + `src/components/ui`（shadcn 基础件）+ 数据 hooks | 63.18 kB / gzip 21.67 |
| `index` | 入口（router / AppShell / main） | 8.50 kB |
| 页面 chunk ×10 | 按路由懒加载，边界不变 | 3.32 ~ 48.78 kB |
| `useEditorShortcuts` 等 | 编辑器流程 hook（两个编辑器页共享，rollup 自动切分） | 20.16 kB |
| 域共享组件 ×6 | GenderBadge / ItemThumbnail / CharacterThumbnail / PendingImageField / ParticipantPanel / MapRulerStrips | 0.50 ~ 9.50 kB |

三条实现期细节（都踩过，见 §12 R14~R16）：

1. **`@remix-run/router` 必须与 react-router 同组**：它默认落进 `vendor-ui`，而 react-router-dom（vendor-react）引用它，构成 `ui → react → ui` 循环 chunk 警告。
2. **`components/ui` 并入 `shared` 而不是独立成组**：ui 组件引用 `@/lib/utils` 的 `cn`，两个手动 chunk 之间形成 `ui → shared -> ui` 环（rollup 会告警）；合成一组后组内无边。这些件全站共用，每个页面本来就要下载，合并没有引入浪费。
3. **`useEditor*` 四个流程 hook 排除出 `shared`**：它们只被两个编辑器页使用，进基础层会让 `/play` 的玩家白下载约 12 kB；排除后由 rollup 按动态入口自动切分（`useEditorShortcuts` 20.16 kB 独立成 chunk）。

最终 build：**3.56s，25 个文件**；首屏总量与收敛前持平（vendor 系 + shared + index + css ≈ 582 kB / gzip 181 kB，懒加载按需部分不变）。

这是全版唯一一处刻意统一的微观行为差异，已在 `useEditorShortcuts` 的文档注释中说明；无测试钉它，UI 上三个 Esc 出口的级联顺序本身有测试守护（`ParticipantDrawer.test.ts`，见 4.4）。

## 6. 第④步 EditorShell 共性上移

### 6.1 六个共用件（`components/editor/EditorShell.tsx`，169 行）

调研结论「已验证的共性」具体化为六个零判断的展示件，两个编辑器页分别用它们替换逐字重复的 JSX：

| `EditorUnsavedLeaveDialog({ guard })` | 两页各自一份的 `useUnsavedChangesGuard` 弹窗 |
| `EditorPendingInfoActionDialog({ open, onOpenChange, onResolve })` | 基本信息未保存确认弹窗 |

| `EditorErrorState({ message, backLabel, onBack })` | 错误态 |
| `EditorImportInput({ inputRef, onChange })` | 隐藏文件 input |

### 6.2 `UI_Z.saveMask`

保存蒙版原先在页面里写死 `z-50`。上移为共享件时不能把字面量带进组件——收进 `packages/shared/src/constants.ts` 的 `UI_Z`：

```ts
saveMask: 40, // covers every panel while the save request flies
```

### 7.1 落点

`app.ts` 在 apiRouter 之后的最终顺序：

```ts
app.use(mount('/assets', serve(distAssets, { maxage: 31536000000, immutable: true, defer: false })));
app.use(serve(webDistRoot, { maxage: 0, setHeaders: (res, path) => html → no-cache }));

app.use(spaFallback);     // 链尾（顺序是刻意的，见 7.2）
```

缓存策略分三类：**带 hash 的 `/assets/*` 一年 immutable**（与上传文件 `FILES_ROUTE_PREFIX` 同配置）；**`index.html` no-cache**（SPA 入口每次验证，否则发版后旧 HTML 会继续引用旧 chunk）；**fallback 响应同样 no-cache**。

### 7.2 SPA fallback 与「洋葱模型」坑

`spaFallback` 是未命中请求的统一出口：

- **GET/HEAD 导航**（路径不以 `/api`、`/assets` 开头）→ `index.html`（200 + no-cache），客户端路由接管 `/play/:slug`、`/puzzles/:id/edit` 等深层链接；
- **其余未命中**（缺失的 asset、POST 到未知路径）→ 标记 404，交给 notFoundHandler 输出 JSON。

三个边界是刻意的：`/assets` 下的 miss **不回退 HTML**（否则浏览器报 MIME 错误而不是清晰的 404）；`/api/*` 保持 JSON 404；**dev 未 build 时整体退化为 JSON 404**（`existsSync` 检查，与 v0.5.5 行为一致）。

> **踩坑记录（R17）**：spaFallback 最初注册在 notFoundHandler **之前**，结果 6/7 用例通过、唯独深层路由 fallback 失效。根因是 Koa 的洋葱模型——fallback 的 `await next()` 会先执行下游的 notFoundHandler，后者当场把 body 设成 JSON 404；等控制流回到 fallback，`ctx.body != null` 已成立，永远接不到盘。插桩诊断还顺带发现：未命中请求的 `ctx.status` 在中间件链里是 Node 默认的 **200**（404 是 respond 阶段对空 body 的兜底），所以一切「等 status 变 404 再处理」的后置中间件都不可靠——这也是第一版用 `ctx.status !== 404` 判断失败的原因。**解法是把 fallback 注册到链尾**（notFound 之后）：notFound 的 `next()` 进入它，它接盘后 notFound 看到 body 自然收手；它标记的 404 又正好让 notFound 输出 JSON——两者协同。

## 14. 追加改动（第四轮）：品牌文案与字标对齐

### 14.1 需求原文

### 14.3 字标对齐：先量，再改

最初按「放大字体」直接给了 `fontSize = 1.05 × height`（22 → 23px），截图一看「格物」明显压过 logo —— 方向对、量级错。改用 CDP 量真值：

| 量 | 结果 |
|---|---|
| logo 资产墨迹（canvas 量 alpha） | 22px 框内 **16.19px**（上下各留约 13%，居中） |
| CJK 墨迹 | 约 **1.0em**（canvas `actualBoundingBox` 实测 16px→16、18px→17、20px→18） |
| 原状（16px / 默认 `line-height:1.5`） | 墨迹高度其实**基本相等**，问题出在**位置**：1.5 行高把墨迹挤出 box 中线，看起来比 logo 低半格 |

两个根因分别对症：

1. **高度**：`0.82 × height` —— 22 → 18px（墨迹 17，比 logo 的 16.2 略大一档，CJK 视觉重量轻，等值反而显小）；20（控制台头部）→ 16px。
2. **位置**：`lineHeight: 1`。行高等于字号后，行盒中线 ≈ 墨迹中线，flex `items-center` 才能让「格物」与 logo 的墨迹上下沿真正齐平。

A/B 过的四档（16/1.5、17/1、18/1、20/1），18/1 与 logo 齐平且不压字标，取之。字重 normal 后笔画变细，视觉上比原来的 600 更像「辅助标识」而非第二品牌。
