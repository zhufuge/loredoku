# 需求 + 设计：参与者布局归谜题（v0.6.3）

> **状态**：**已实施**（2026-10-20）。设计即本文；落地记录见 §8。
> 需求原文：
> ```
> 修改谜题的参与者布局，在基本信息中添加行列数参数，填入列数，实时计算行数，
> 展示 [列数] x 行数，基本信息保存后，调整布局。参与者槽框大小固定，
> 根据行列调整整体宽度。发布后的游戏的参与者布局按填写的行列信息展示。
> ```

## 0. 一句话

谜题「基本信息」里多一个**列数**输入框，行数由 `ceil(参与者数 / 列数)` 实时算出并
一起展示；值存在 `PuzzleDraft.rosterCols`（`null` = 自动）。槽框尺寸恒定 110px，
**面板整体宽度随列数变**；发布时列数随整个谜题冻结进快照，游戏页照它排版。

## 1. 改之前是什么样

参与者矩阵（`ParticipantPanel`）是个**自作主张**的组件：

1. `computeParticipantLayout(n)` 按黄金比例 `|cols/rows − 1/φ|` 挑列数（CLAR-602）；
2. `fitColumns(panelWidth − 16, …)` 再按容器宽度把列数往回收（MOD-803）；
3. 最后一行不满时居中（`leadingOffset`）。

也就是说列数是**面板自己算出来的**：作者看着 6 个人的花名册被排成 2×3，只能接受。
面板宽度恒为 256px，槽框 110px 固定，能挤就挤。

这在花名册是「附加信息」时够用。但它同时出现在**谜题编辑器**和**游戏页**——玩家看到的
第一样东西就是它，而作者对它没有任何控制权。

## 2. 目标

| # | 目标 | 怎么算达成 |
|---|---|---|
| 1 | 作者能定排几列 | 谜题「基本信息」加「参与者布局」区，一个**列数**输入框 |
| 2 | 行数不用填，自己算 | `rows = ceil(参与者数 / 列数)`，随每次输入实时更新并展示 `列数 × 行数` |
| 3 | 保存后才生效 | 抽屉是 draft → 保存 的窗体，列数跟着描述/调色板一起提交，一次撤销一步 |
| 4 | 槽框尺寸不变，宽度跟着列数变 | 槽框恒 110px；面板宽度 = 列数驱动：≤6 列取自然宽度（下限 256），>6 列封顶 512 并横向滚动（v0.6.3 fix，见 §9.2） |
| 5 | 已发布的游戏照此排版 | 列数随谜题冻结进 `games.snapshot.puzzle`，游戏页直接读 |

## 3. 设计

### 3.1 存什么：只存列数

`PuzzleDraft` 加一个字段：

```ts
/** `null` / 缺席 = 自动 */
rosterCols?: number | null;
```

**行数不存**。它是 `ceil(slots / cols)`，存进去就是第二个真源——改列数时还得记得改行数，
忘了就自相矛盾。所以只存列数，行数永远现算（`rosterRows`）。

**为什么不用 `PUZZLE_JSON_VERSION` 升到 2**：

- 字段是**可选**的，且「缺席」的含义（自动）与缺席时该有的表现（旧的自动排版）完全一致；
- 也就是说存量谜题**一行都不用改**，v0.6.1 那种 `…00029` 迁移在这里是纯负担；
- 版本号的意义是「读到 v1 得先兼容处理」，而这里没有要兼容的东西。

schema 侧（`puzzleDraftSchema` 是 `.strict()`）声明即收：

```ts
rosterCols: z.number().int().min(1).max(GRID_SIZE_MAX).nullable().optional(),
```

上限用**棋盘**的 `GRID_SIZE_MAX`（24）而不是参与者数：列数是个排版意图，导入的文件
带着 8 而棋盘只有 6 个人时，正确做法是渲染时夹到 6，而不是拒绝整份文件。夹的动作在
`resolveRosterCols(cols, total)` 一个地方。

### 3.2 实时行数

抽屉里的控件就一个输入框加一段行数（v0.6.3 fix 后，见 §9）：

```
[ 3 ]        × 2
```

- 输入 → `resolveRosterCols(值, min(参与者数, ROSTER_COLS_MAX))` → `rosterRows(参与者数, 列数)` → 展示；
- 输入 `99` → 夹到 **6**（列数最大值，先于参与者数生效），展示 `× 2`；输入 `0` → 夹到 1，展示 `× 7`；
- **清空 = 自动**：字段存 `null`，展示退化成 `2 × 4（自动）`——此时显示的是
  `computeParticipantLayout` 会给的排版，所以用户在按下保存之前就知道会得到什么。

「列数」文字标签与「共 x 位参与者」提示段都不要：输入框自己带着数，标签只是重复它；
提示段讲的是保存生效时机，而抽屉本身就是「保存才生效」的窗体，footer 已经说清了。

自动这个口子必须留：它是所有存量谜题的状态，也是唯一的「撤回」路径。

### 3.3 槽框固定，宽度随列数

```
宽度(cols) = cols × 110 + (cols − 1) × 14 + 8 × 2      ← 槽框 110 恒定、间距 14、内边距 8
面板宽度   = cols ≤ 6 ? max(256, 宽度(cols)) : min(宽度(cols), 512)
```

| 列数 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 算出来 | 126 | 250 | 374 | 498 | 622 | 746 |
| 实际 | 256 | 256 | 374 | 498 | 622 | 746 |

两个夹子的理由：

- **下限 256**：1 列只需要 126px，但「参与者 3/6」这个标题行活不下来；下限也让
  1~2 列的面板和改版前一模一样。
- **上限 512 只对 6 列以上生效**（v0.6.3 fix 后）：编辑器最多让填 6 列，6 列以内面板
  宽度 = 矩阵自然宽度，与滚动容器内容盒严丝合缝，**横向滚动条不可能出现**；只有导入
  或旧数据带来 7 列以上时才封顶 512，矩阵在面板内横向滚动——槽框既不缩小也不换行。

滚动要能用：`overflow: auto` 之外，矩阵自身还得有 `min-width: max-content`。否则
`justify-content: center` 会把超宽的矩阵两边各切一半，左边那半是滚动条永远滚不到的。
6 列以内时两者宽度相等，这条只管 > 6 的兜底路径。

自动模式**不参与**这套：宽度恒 256（与改版前一致），列数仍走「黄金比例 + 按容器收窄」，
`ResizeObserver` 也只在自动模式下开——有列数时，被测量的那一侧正是我们自己刚设的宽。

### 3.4 发布后的游戏

`gameService.deployGame` 把整个 `puzzle.data` 拷进 `MapGameSnapshot.puzzle`
（`isPuzzleDraft` 为真时），所以列数是**搭车**进快照的，发布链路一处都不用改。

游戏页读 `snapshot.puzzle.rosterCols`，用同一个 `rosterPanelWidthFor` 撑左栏。

由此确定一条语义（与快照的其他部分一致）：

> 改谜题**不会**改动已上线的棋盘。要换排版，重新发布一次。
>
> 老快照没有这个字段 → 自动。部署过的游戏不会因为在谜题里填了列数而变样。

## 6. 收益与代价

**收益**

- 作者第一次能决定玩家看到的排版；
- 只存列数，行数无处可漂移；
- 存量数据零改动——没有迁移，也就没有迁移可能带来的损失。

**代价**

- 多了一个作者可能填错的数（虽然有夹取兜底，且最多填到 6 列）；
- 6 列的面板会宽到 746px，画布让位（自适应格子兜底）；7 列以上——只有导入或旧数据
  能带到——才在面板内横向滚动；
- 自动与显式两套排版逻辑并存，`ParticipantPanel` 里多一条分支。

## 7. 遗留（明确不做）

- **行数不开放手填**：列数 + 人数已经唯一决定行数，再让填一次就是两个真源。
- **不做「按面板宽度自适应列数」与显式列数的混合**：有列数就听列数的，不缩。
- **已发布的游戏不跟随谜题改动**：快照语义如此，改排版要重新发布。
- **不记忆视图状态**（缩放 / 平移也不存）：与 v0.6.2 §8 一致，本版不涉及。

## 9. 修复记录（2026-10-20，v0.6.3 fix）

三项都是同一批试用反馈，**不升版本号、不加迁移**——前两项是纯 UI 口径，第三项是 bug。

### 9.1 基本信息面板的控件瘦身

- 删掉「共 x 位参与者，保存后参与者面板按此排列。」提示段；
- 删掉「列数」文字标签——输入框自己带着数，标签只是重复它；
- 控件收敛为 `[列数输入] × 行数`：有列数时只显示 `× 行数`（列数在框里），
  自动（空框）时显示自动排版 `列 × 行（自动）`，让用户在保存前就知道会得到什么；
- **列数最大值 6**：新增 `ROSTER_COLS_MAX = 6`，输入 `max=6` 且键入值夹到
  `min(6, resolveRosterCols(值, 参与者数))`。存量的 schema 上界不动（`GRID_SIZE_MAX`）——
  夹取是 UI 口径，导入带 8 列的旧文件仍要能渲染（见 9.2 的 > 6 兜底）。

### 9.2 参与者面板：6 列以内不出现横向滚动条

`rosterPanelWidth(cols)` 改成两段：

```
cols ≤ 6 → max(256, 宽度(cols))      宽度 = 矩阵 max-content，与滚动容器内容盒相等
cols > 6 → min(宽度(cols), 512)      封顶 + 横向滚动（只有导入 / 旧数据能到这）
```

6 列 = 746px 的面板确实宽，但这是「槽框恒定 110px + 不要滚动条」的必然代价；
画布是自适应格子，仍然有地方可去。`min-width: max-content` 保留，只管 > 6 的兜底路径。

### 9.3 编辑器缩放按钮不生效（地图 + 谜题）

**现象**：进编辑器点底部工具条的 ± 没反应；用 Ctrl+滚轮缩过一次之后，按钮又好了。

**根因**：缩放一步会改 `rulerStrip`（`rulerStripSize` 的 `maxFontSize` 含 `zoom`），
而 `rulerStrip` 是 `centerView` 的依赖——于是 `centerView` 换身份、自适应居中的
effect 重跑。该 effect 在 `userPannedRef` 为 false 时调用 `centerView()`，把 zoom
打回 1 并重新居中。滚轮路径（`EditorCanvas` 的 wheel handler）在改 zoom **之前**就置了
`userPannedRef = true`，所以滚轮缩放粘得住；按钮路径（两个页面各自的 `zoomBy`）只写
store，没置这个 flag，于是新 zoom 只活一代渲染就被居中掉。第一次滚轮缩放把 flag 置上
之后按钮自然「恢复」——正是反馈里「用过快捷键后才生效」。

预览页（`MapViewPage` / `PuzzleViewPage`）没有这个问题：它们的适配 effect 只依赖
`[gridSize]`，缩放不触发重跑。游戏页的缩放是纯本地 state，同样无辜。

**修法**：把按钮路径搬进画布，成为 `EditorCanvasHandle.zoomByStep(direction)`——
与滚轮路径同源（都走 `viewRef`、都置 `userPannedRef`、都是 `clampZoom` 一步），
差别只有锚点：滚轮认指针，按钮认视口中心。两个编辑器页面的 `zoomBy` 改成一行委托，
页面里不再有第二套缩放数学（`clampZoom` / `zoomAtPoint` / `ZOOM_STEP` 的导入随之删除）。

**回归测试**：`components/map-editor/EditorCanvas.zoom.test.tsx` 三例——按钮一步到位
（含 pan 重锚）、按钮缩放逃过紧接着重跑的自适应居中（把 flag 注释掉即失败）、
`centerView`（适应画布）照旧重置并重新武装该 pass。

## 10. 修复记录 · 第二轮（2026-10-20，v0.6.3 fix）

三项同样**不升版本号、不加迁移**：第一项是上一轮宽度改装的漏算，第二、三项是 UI 口径。

### 10.1 参与者面板：列数 ≥ 3 又出现横向滚动条（漏算的 1px）

**现象**：9.2 修完之后，3 列及以上仍然带一条横向滚动条。

**根因**：9.2 把面板宽度算成「矩阵 max-content + 左右 padding」，两边正好相等——
但 `<aside>` 自己是 `border-box` 且带着 `border-r`（与画布之间的 1px 分隔线），
这 1px 要从计算宽度里扣。于是滚动容器的内容盒比矩阵窄 1px，而 **1px 的溢出就足够**
唤出 `overflow-auto` 的横向滚动条。1~2 列时面板被 `max(256, …)` 抬到 256px，
冗余吃掉了这 1px，所以症状从第 3 列才开始——正好是反馈里的「≥ 3 列」。

**修法**：shared 新增 `ROSTER_PANEL_BORDER_WIDTH = 1`，`rosterPanelWidth` 的
natural 宽把它算进去：

```
宽度(cols) = cols×110 + (cols-1)×14 + 2×8 + 1
```

3 / 4 / 5 / 6 列的面板因此各宽 1px（375 / 499 / 623 / 747）。游戏页外层 aside
用的是同一个数字，面板自己的 `border-r` 与外层的重合在同一位置，视觉上仍是一条
1px 线。`> 6` 的封顶路径不受影响（照旧 512 + 滚动）。

### 10.2 参与者满时，默认收起角色框

`PuzzleEditorLeftPanel`（谜题编辑器左侧「角色」列表）新增默认收起：
名册非空且每个槽位都有参与者时收起成 40px 细条——此时所有「加入」按钮都已禁用，
列表没有可贡献的东西，宽度让给画布。

- 判定：`rosterFull = 名册非空 && 每槽位非 null`；
- 同步：effect 把 `collapsed` 置成 `rosterFull`，覆盖两种时机——进编辑器时名册
  已经满了（含 `puzzle.init` 在 effect 里 seed、面板先挂载的那一帧），以及会话
  中填满最后一格；
- 接管：用户点过「展开 / 收起」之后（`userTookOverRef`），自动逻辑永久退场，
  状态归用户。这是「默认」而不是「锁定」。

地图编辑器没有这个面板（SPEC-K04：角色只在谜题编辑器），游戏页是可读名册，均不涉及。

### 10.3 槽位标号背景探出槽位框

标号按 FEAT-O13 贴在卡片左上角（inset 0，且不画自己的上 / 左边，用卡片的框线），
而卡片是 `rounded-md`（6px 圆角）：标号的方角在圆角处探出框外。

**修法**：shared 新增 `PARTICIPANT_SLOT_RADIUS = 6` 作为唯一真源——卡片的圆角
从 Tailwind 类改成内联值，标号左上角按同一半径圆角（`'6px 0 6px 0'`，右下角保持
FEAT-O13 的 6px）。标号与卡片的圆角从此不可能漂移。
