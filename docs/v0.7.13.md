# v0.7.13 — 停一秒，物品报出自己的名字

> **状态**：已实施（2026-10-27）。
> **来源**：`添加地图上物品，hover1s时，出现名称的提示`
> **范围**：`packages/shared`（一个时序常量）+ `packages/web`（物品层、提示外壳）。
> 数据结构、保存逻辑、命中判定都不动 —— 这轮只改「鼠标停在一件物品上会发生什么」。

## 0. 一句话

物品层本来就带着一句 `title={asset?.name}`，但它在五个画布里只有**一个**看得见，
而且长相与节奏都不归我们管。这一版把它做成画布自己的一个动作：**同一件物品上停满
1 秒**，一张纸片从它上方浮出来 —— 地图编辑、谜题编辑、游戏、地图查看、谜题查看，
五处一致。

## 1. 原来的 `title` 三个不够

| # | 问题 | 实情 |
|---|---|---|
| 1 | **只有编辑器里能看见** | 物品层在游戏 / 地图查看 / 谜题查看三处是 `pointerEvents: 'none'`（点击要留给格子），而原生 `title` 依赖鼠标真正命中那个 DOM 节点 —— 它在那些页面**从来不弹**。五处画布，一处有名字。 |
| 2 | **节奏不归我们管** | Chrome 约 1s、Safari 更快、Firefox 更慢，没有可调的 API。「全站提示要么 320ms 要么 1s」这条约定，原生属性做不到。 |
| 3 | **长相不归我们管** | 深色下是系统气泡：白底、黑框、系统字体。v0.7.9 §5 已经定过规矩 —— 工坊里只该有一种提示长相，就是那张纸片。 |

于是「让物品报名字」这件事，实际要做的是**把悬停命中从 DOM 挪回画布坐标**。
画布本来就在算它（`resolveHoverEffects` → `hover`，物品抬手 `lift` 用的就是这份数据），
只是从来没拿去查表。

## 2. 为什么是 1s，而不是 Tooltip 的 320ms

全站提示是 320ms（`components/ui/tooltip.tsx`），因为那是在**找按钮** —— 目标明确，
提示是顺手给的一行字。

物品不是按钮。墙面上的物品是按格密排的，鼠标从左上走到右下会扫过十几件，320ms
会让一次扫视变成**提示雨**：纸片此起彼伏，每一张都在你走开之后才长出来。

1s 恰好把两种动作分开：**路过**（不停留，什么都不发生）和**在看**（停下来了，
说明你真想知道这个画的是什么东西）。这个数字也是需求方指定的，与手感的结论一致。

常量放在 `packages/shared/src/constants.ts` 的 `ITEM_HOVER_*` 旁边：

```ts
export const ITEM_NAME_TIP_DELAY_MS = 1000;
```

## 3. 不套 Radix Tooltip：命中本来就已经算好了

`TooltipTrigger` 要求 trigger 节点能收到指针事件。给物品层开 `pointer-events: auto`
是最省事的写法，代价是**游戏页的点击会被物品吃掉** —— 那里点格子是落子，物品层
盖在格子上，一旦可交互就要重新设计一整条打点链路（`stopPropagation`、shift 多选、
画笔穿透……）。

为了一个提示去改打点，是把便宜的事做贵。反过来做才顺：**命中用坐标算，
位置用几何算，只从 Tooltip 借一层皮**。

```ts
// components/ui/tooltip.tsx
export const TOOLTIP_SURFACE_CLASS =
  'max-w-xs rounded-sm border bg-popover px-2 py-1 text-2xs text-popover-foreground shadow-lifted';
```

`TooltipContent` 与物品名称提示都从这一处取类名。将来改纸片的圆角 / 字号 / 阴影，
两个提醒**一起**变 —— 长相的一致性不因为实现方式而破例。

## 4. 计时按物品算，不按鼠标算

一个 `hoveredKey`（当前指针落在哪件物品的脚位上）+ 一个 `tipKey`（谁已经停满了
1 秒），渲染时两个 key 必须**相等**才出提示。

单靠 `setTimeout` 是不行的：鼠标从宝箱划到木桶时，宝箱的定时器被清掉，但宝箱的
**名字**还挂在 state 里，会有一帧错挂在木桶头上。多对一次 key，这一帧就没了。

| 情形 | 行为 |
|---|---|
| 停在同一件物品上满 1s | 出提示 |
| 500ms 后划走 | 什么也没发生，计时作废 |
| 停满 1s，再划到旁边那件 | 旧提示**当场**消失，新的重新数 1s |
| 停 800ms，移出画布，又移回来 | 重新数满 1s（不接着用剩下的 200ms） |
| 停在空格 / 阻挡遮罩上 | 不出提示 |
| 物品在 `assetsById` 里找不到（资源被删） | 不出提示 —— 名字来自资源，纸片画不出来 |

判定用的是**脚位**（`w` × `h`），不是被 `scale` 撑出去的那圈画。这条跟抬手
（`lift`）用的是同一个规矩：悬停邻居格上那截溢出的画，不该让这件物品亮起来。

## 5. 位置：浮在上方；头顶不够就翻下来；贴边就换对齐

提示挂在物品的**显示框**上（`itemRectStyle` 的结果），不是脚位 —— 作者把一盏灯
缩到 0.5 倍、往右挪了一格，名字要跟着那盏灯走。

三档判断，都是几何，不需要测量：

| 场景 | 做法 | 数值 |
|---|---|---|
| 头顶空间够 | 浮在显示框上方 | 间隙 `6px`（与 `TooltipContent` 的 `sideOffset` 一致） |
| 物品在第一行（`top < 32`） | 翻到**下方** | 画布外层是 `overflow-hidden`，往上浮会被切掉半个纸片 |
| 离画布左右边不足 56px | 不再居中，改为贴边对齐 | 贴的是**画布**的边 —— 物品自己可能被 `offset` 推出去了，用画布边界兜住 |

翻转阈值用**画布像素**（32）而不是屏幕像素，是因为提示和画布一起被 zoom 缩放：
`32 × zoom` 的屏幕空间对应 `28 × zoom` 的纸片高度，任意缩放级别都成立。

水平方向用**百分比**而不是 `rect.width / 2`：绝对定位的包含块是**padding box**，
而 `rect` 是 border box —— 照像素算会差出一个 `padding`（编辑器里 2~12px，
随 `cellSize` 变）。这个偏差在静态审查里看不出来，只有渲染出来才会发现纸片
比中线偏了 4px（第一次截图就是这么抓到的）。

宽的那一头：`w-max` 让纸片跟着名字长，`max-w-48`（12rem）兜住离谱的长名字，
`truncate` 收尾。中文 11px 字装得下十几个字，够用。

## 6. 顺手的两件小事

- **`z-index` 39**：提示比一格宽，会盖到旁边那件物品上，而同一图层内谁在上由
  DOM 顺序决定 —— 后渲染的压住先渲染的，跟鼠标停在哪件无关。被悬停的那件临时
  提到 39（`MAP_LAYER_Z.itemLayer` 是 38，40 是游戏放置层，中间空着）。
- **`overflow: visible`**：物品框平时 `overflow: hidden`（图片溢出不外漏），
  抬手（`lift`）时已经临时打开；提示同样需要它，否则会被自己的框切掉。

## 9. 看过没做

- **提示里加一句尺寸 / 形态**（比如「宝箱 · 2×2」）。名字只回答「这是什么」，
  多一行会让它变成一块小卡片，卡片的时机和位置都得更讲究。等真的有人问「这是几格」
  再说 —— 编辑器右侧抽屉里本来就有。
- **双击锁定**（点一下就让名字常驻）。会和「点物品 = 选中」打架，得先决定
  选中是否要变成双击。
- **触摸端**：没有悬停这一说，长按 1s 已经有别的含义（物品搬家 / 画笔清除）。

## 10. 追加：传完头像，外观不该跳回纯色块

> 需求原文：`角色页面，原来角色是使用纯色外观，在上传图片成功后，提示成功，但是此时外观却切回到纯色块上了。上传成功后，应该自动切到图片上，等待用户下一步操作（比如保存）`

### 10.1 根因不在上传

复现路径很短：一个纯色角色 → 点「外观」里的「图片」→ 上传 → toast 说「头像已上传」
→ **分段控件跳回「纯色」**，刚传的图看不见。

上传本身完全正确，问题出在它**顺带引发的那次重取**：

| 步 | 发生的事 |
|---|---|
| 1 | `useUploadCharacterAvatar` 成功后 `toast.success` + `invalidate()` |
| 2 | 角色列表重取，`character` 换成新对象，`updatedAt` 变了 |
| 3 | 表单的同步 effect 依赖 `[character.id, character.updatedAt]`，于是又跑了一遍 |
| 4 | 它写 `setAppearanceMode(character.bgColor ? 'color' : 'image')` |
| 5 | 而库里 `bgColor` 还在 —— 外观模式的落库发生在按「保存」那一刻 |

于是第 4 步把用户刚做的选择按回了服务器值。**这跟「上传」没有因果关系**：
启用、停用、改名都会触发同一条链，只是上传的后果最刺眼 —— 它让一个刚刚成功的
动作当场看起来像失败了。

### 10.2 表单是草稿，不该被后台刷新写

`updatedAt` 放进依赖的本意是「保存后以服务器为准」。代价是**任何一次重取都算
保存**：同一条记录上别人的按钮（停用、添加形态）也能把你没提交的输入冲掉。
「改了名字 → 顺手点了停用 → 名字自己变回去」是同一个 bug 的另一个面孔，只是
没人报。

修法是把边界从「记录变了」改成「**换了一条记录**」：

```ts
useEffect(() => { /* 用服务器值重置表单 */ }, [character.id]);   // 不是 [id, updatedAt]
```

换角色 = 换内容，重置是对的；同一条记录刷新 = 别的按钮干的活，跟这张表单无关。

为什么不加一个 `touched` 标志（「用户动过模式就别覆盖」）？那等于给每个字段配一个
开关，而 `updatedAt` 依赖本身就是错的 —— 修边界比加豁免干净。

### 10.3 上传成功再补一手显式切换

```ts
uploadMutation.mutate({ id: character.id, file }, {
  onSuccess: () => setAppearanceMode('image'),
});
```

严格说这一行是冗余的（能点到上传，说明当前已经是图片模式），但它写清了意图：
**传图就是想用图**。将来若在纯色模式下也提供上传入口（比如拖一张图到色块上），
这一行就是那条接缝，而不是又要去改 effect。

落库仍旧等「保存」：`bgColor` 在按保存之前不被清空，所以用户反悔点回「纯色」时，
原来的颜色还在（v0.5.1 §1.2 的既有语义）。

### 10.4 同样的两处也修了

| 位置 | 症状 |
|---|---|
| `components/asset/AssetVariantCard.tsx` | 纯色形态传图后同样被按回色块 —— 一模一样的 effect 形状 |
| `components/asset/AssetDetailForm.tsx` | 改名 / 改类型后，点启用或增删形态会把输入冲掉（没有外观模式的病灶，但同一条错误依赖） |

三处都只改了依赖列表，没有动字段与保存逻辑。

### 10.5 验证

  改名不被刷新冲掉、换角色仍然重置。

  改回来全绿。这几条断言确实咬在病灶上，不是摆设。

## 11. 追加：角色的默认主题色与默认编号

> 需求原文：`添加角色的默认主题色和默认编号功能，添加可选字段color，display_name，在被选中到参与者时，如果字段有值，则使用该值`

### 11.1 每个角色都要重填一遍的东西

一个角色被「加入」到谜题的参与者区时，槽位要填主题色与编号展示。此前两者恒为
`DEFAULT_THEME_COLOR`（白）与序号 —— 同一个角色在一批谜题里反复出现，就得一遍遍
在参与者抽屉里重填。

这两项其实是**角色的属性**（这个角色习惯用什么颜色、习惯叫什么代号），只是之前
没地方写。所以放两条列在 `characters` 上：

| 列 | 类型 | 语义 |
|---|---|---|
| `color` | `text`，可空 | 加入时的**主题色**；`NULL` = 不指定，槽位照旧用白色 |
| `display_name` | `text`，可空 | 加入时角标上的**编号**；`NULL` = 不指定，槽位照旧显示序号 |

**它们不是 `bgColor`**。`bgColor` 是角色自己的长相（纯色块模式），`color` 是它给
槽位的主题色 —— 一个角色完全可以是红色色块、却带着蓝色主题色。所以是两列而不是
复用一列：混在一起会让人以为改外观就改了参与者配色。

### 11.2 「空」的三张脸必须收敛成一个值

麻烦全在「空」。三种写法都会出现：

- 老客户端/老数据**压根不发这个键**（列是后加的，库里老行为 `NULL`）；
- 前端显式发 `null`（主题色改回白、编号清空）；
- 服务端收到一个空白串也得认（手写 JSON、老表单）。

所以 schema 里「空」的写法塌成同一个 `null`，缺席则**不产生这个键**：

```ts
characterDisplayNameSchema = z.string().trim().max(CHARACTER_DISPLAY_NAME_MAX)
  .transform((v) => (v === '' ? null : v)).nullable().optional()

characterColorSchema = z.string().trim().regex(CHARACTER_COLOR_PATTERN)
  .transform((v) => (v.toUpperCase() === DEFAULT_THEME_COLOR ? null : v.toUpperCase()))
  .nullable().optional()
```

`null` 在 `update` 里算**有效补丁**（`toHaveProperty` 断言过），不是「没改」——
否则「清除默认值」这个动作永远发不出去。

两个字段的「空」长相不同，schema 因而不是同一个：编号是**空串**，主题色是
**白色**（§11.4）。共用的只有「`null` 是有效补丁」这条。

### 11.3 只在「加入」这一刻抄一次

```
角色.color / display_name  ──加入──▶  槽位的 themeColor / displayNumber（副本）
                                        ↑ 之后两边互不影响
```

`puzzleStore.assignSlot(characterId, defaults)` 多收一个可选参数，页面从
`charactersById` 取出角色默认值传进去。**之后改角色不再影响已加入的槽位，改槽位
也不回写角色** —— 槽位存的是副本，跟它本来就自己存 `themeColor` / `displayNumber`
是一个道理。角色改名 / 换头像仍然实时反映（那些是渲染时从 `characters` 读的），
只有这两项参与者配置是快照。

不这么做（比如渲染时用 `character.color ?? slot.themeColor`）会让「抽屉里改成黑的、
结果还是角色那个色」—— 一个用户明确的操作被一条隐式规则吃掉。

有值才覆盖：`null` / 空白一律走缺省，于是**所有老角色的行为一个像素不变**。

### 11.4 主题色没有开关：白色就是「未指定」

> 改过。最初做成了「复选框 + 取色器」：理由是取色器必须显示一个颜色，「未指定」
> 没有可显示的值。实际用下来多了一次判断 —— 而槽位本来就是白的，那个复选框其实
> 在问一个不影响结果的问题。

现在是常驻的一对控件，`[取色器][hex 文本框]`，默认值 `#FFFFFF`：

```
默认主题色  ▉ #FFFFFF
默认编号    []
```

**白色不落库。** `#FFFFFF` 与 `null` 是同一个意思：加入参与者时槽位用
`DEFAULT_THEME_COLOR`，库里存 `NULL`。塌缩写在 shared 的
`characterColorSchema` 里（trim → hex 校验 → 归一成大写 → 白转 `null`），
不是写在表单里 —— 这样 API 客户端、脚本、以后的第二个界面走的都是同一条规则。

代价说清楚：**一个角色无法要求「白色槽位」**。这不是损失 —— 白色槽位和「没指定」
本来就长得一模一样，能区分的只有数据库里那一行，而没有任何界面把那一行显示出来。

编号那边没有这个问题：文本框的「留空」天然就是空值，不需要哨兵。

### 11.7 看过没做

- **已加入的槽位不回填**。角色后来才配默认值，之前加入的槽位不会变 —— 这是
  §11.3 那条「副本」规则的直接后果，硬要回填就得定义「哪个值算用户改过」。
- **创建角色的弹窗里不填这两项**（schema 收，界面没收）：新建角色时还不知道它
  会出现在哪张谜题里。
