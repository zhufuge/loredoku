# v0.8.0 — 主题：先划一个边界，再把它装进一个包

> **状态**：已实施。设计写于 2026-10-29 白天，实施与两次改口都在同一天 —— §17 是第一次
> 对账，§18 是上手之后把「主题」重新理解成「工作空间」的那次改口。**本文只记裁定与理由**，
> 每节末尾的「代价」是它换来的东西要付的钱。
> **来源**：`添加主题功能（限定与打包）/ 主题级风格配置 / 主题模块页面 / 资源包（可独立部署、不依赖数据库）`
> **范围**：`packages/shared`（类型 + schema + 常量）、`packages/server`（一次迁移 + themes/bundle 模块）、
> `packages/web`（工作空间路由与两种外壳 + 各列表的主题边界 + 资源包导出）。

## 0. 一句话

主题不是一层新的「内容类型」，它是**给已有四个作品模块划的一条边界** —— 边界内互相可见、可复用，
边界外一概不可见；边界一旦划好，同一主题的风格只需配一次、已上线的关卡可以整体打包成一个**不依赖数据库的离线包**。
所以这一版真正的工作量不在「加一个 themes 表」，而在两件更难的事：**把隔离做成服务端的约束**，
和**让「已经能玩的那几关」成为一个可以被整体拿走的东西**（§11 的口径改口）。

## 1. 现在没有主题，隔离是怎么维持的

先把事实摆出来，因为设计要贴着它做。实测本地库（2026-10-29）：

| 表 | 总数 | 红楼梦（`hlm_` 前缀） | 其余 |
|---|---:|---:|---:|
| `assets` | 90 | 49 | 41 |
| `asset_variants` | 113 | 61 | 52 |
| `characters` | 72 | 32 | 40 |
| `maps`（血统） | 13 | 8 | 5 |
| `puzzles`（血统） | 13 | 8 | 5 |
| `games` | 38 行（其中活跃 12） | 8（活跃） | 4（活跃） |

红楼梦的 8 个谜题（撕扇 / 因麒麟伏白首双星 / 玉带林中挂 / 一从二令三人木 / 蕉下客 /
槛外人 / 勘破三春 / 芦雪庵联句）与另外 5 个（Fireside Beach / 道生一 / Outdoor Painting /
The Treasure Hunt / A）在数据上**已经是两个互不相交的世界**。逐条核对每个已发布谜题
引用到的资源与角色：

```
撕扇            assets 13  非 hlm 0     chars 4   非 hlm 0
芦雪庵联句      assets 11  非 hlm 0     chars 7   非 hlm 0
Fireside Beach  assets 8   非 hlm 8     chars 5   非 hlm 5
The Treasure Hunt assets 24 非 hlm 24   chars 24  非 hlm 24
…（8 个 hlm 谜题全部 0 越界，5 个默认谜题全部 0 越界）
```

**结论：主题这件事已经在发生了，只是靠命名约定（`hlm_`）和作者的自觉维持。**
这条实测有两个用处：①「主题」不是发明一个概念，而是把一条既有的隐性约定变成显式的数据结构；
② 迁移的 backfill 可以按**引用闭包**判定归属，而这批真实数据上它是 100% 干净的 —— 迁移零风险。

反过来看现在缺什么：`assets.code` 是**全局唯一**（`assets_code_unique`），所以第二个主题想用一个
叫 `grass` 的资源就必须改名叫 `hlm_grass`。前缀不是设计，是**约束逼出来的补丁**。这一点直接决定了 §3。

## 2. 主题是什么，不是什么

三件事，缺一件这个功能就不成立：

| 职责 | 含义 | 落在哪 |
|---|---|---|
| **命名空间** | 资源 / 角色 / 地图 / 谜题各自归属唯一主题，引用不得跨界；`code` 在主题内唯一 | `theme_id` 列 + 唯一约束 |
| **风格缺省** | 同一主题的地图从同一份样式出发，不必每张图重配 15 个线宽颜色 | `themes.data.style` |
| **打包边界** | 一个主题的**已上线关卡** = 一个合辑 = 一个可独立分发的离线包 | `theme_deployments` / 导出的 zip |

同时要说清三件**不是**：

- **不是皮肤。** 浅色 / 深色 / 跟随系统是界面外观；主题是作品内容（`docs/design-system.md` §0 第 4、5 条
  已经把这条线划过一次了 —— 画布不随外观变，同理，主题是画布那一侧的东西）。
- **不是版本。** 地图和谜题已经有一套 `draft` / `version` 的冻结机制。主题若也版本化，就得把
  资源、地图、谜题全部快照一遍 —— 等于把版本化做两遍，而且第二遍没有真相（`docs/map-management-and-editor.md` §1 不变式 3）。
- **不是权限。** 单用户本地工具，主题是**整理**手段，不是访问控制。别在它上面挂 ACL。

```
主题（themes）
├── 风格      themes.data.style（MapStyle 的缺省模板）
├── 资源      assets → asset_variants（图片 / 纯色）
├── 角色      characters（头像 / 参与者默认值）
├── 地图      maps（draft + 版本行，引用本主题资源）
├── 谜题      puzzles（画布副本 + 名册 + 调色板，引用本主题资源与角色）
│   └── 部署  games（一条谜题版本行 → 一局可玩的游戏）
└── 交付      主题合辑（在线）/ 资源包（离线数据包）
```

## 3. 数据层：列，还是关联表（问题 4）

| | A. 每表加 `theme_id` 列 | B. 关联表 `theme_items(theme_id, kind, item_id)` |
|---|---|---|
| 隔离能否兜底 | ✅ `FK ON DELETE RESTRICT` + 查询天然带列 | ❌ 多态外键（kind + id）无法建约束，只能应用层自己记得 |
| 列表查询 | `WHERE theme_id = ?`，走索引 | 每次 `JOIN` 或 `IN (子查询)` |
| `code` 主题内唯一 | ✅ `UNIQUE (theme_id, code)` 直接可建 | ❌ `code` 在 `assets` 上，关联表上建不了这个约束 |
| 一个对象属多主题 | ❌ 不可能 | ✅ 可能 |
| 删除主题时 | 数据库直接拒绝 | 得先清关联行，漏清就是悬挂引用 |

**裁定：A。** 决定性的一条是第三行 —— 需求要的是「主题内可复用、主题间不可复用」，多对多在语义上就是错的；
而只要承认这一点，`code` 的唯一性就必须从全局收紧到主题内，这件事**只有列能做到**。
第二决定性的是第一行：隔离必须能被数据库拒绝，否则它只是一串 `if`。

### 3.1 加列的范围：四张表，不是五张

| 表 | 加 `theme_id` | 理由 |
|---|---|---|
| `assets` | ✅ | 边界的第一公民 |
| `characters` | ✅ | 同上 |
| `maps` | ✅ | 地图引用资源，必须同界 |
| `puzzles` | ✅ | 谜题引用地图副本 + 角色 + 资源，必须同界 |
| `asset_variants` | ❌ | 形态跟随资源（`asset_id` 已级联），再加一列就有两个真源 |
| `games` | ❌ | 游戏的主题 = 它引用的谜题行的主题。冗余一列就要维护两处一致，而这只是一次 `JOIN` |

`games` 那条是刻意的克制：38 行的表，`JOIN` 的成本是零，而「两处 must agree」的成本会一直存在。

### 3.2 唯一约束：`(theme_id, code)`，一次改两个表

```sql
-- assets / characters 各一次
ALTER TABLE assets DROP CONSTRAINT assets_code_unique;
ALTER TABLE assets ADD  CONSTRAINT assets_theme_code_unique UNIQUE (theme_id, code);
```

三件事要一起做，否则中途数据不合法：

1. 先建 `themes` 并写入两条（默认 + 红楼梦），拿到 id；
2. 加 `theme_id`（**nullable**）→ backfill（§12）→ 再 `SET NOT NULL` + 建索引 + 换唯一约束；
3. 回滚严格反向：先恢复全局唯一约束（此时 `(theme_id, code)` 唯一 ⇒ 全局唯一必然成立，反过来不成立，
   所以回滚是安全的），再删列。

**老数据零冲突**：现有 `code` 全局唯一，天然满足「主题内唯一」。这一步不需要人工介入。

### 3.3 代价

- `assets` / `characters` 的 `code` 撞车从「保存时就报错」变成「仅在同一主题内报错」。这是**放宽**，
  所以老前端（不带 theme 上下文的后台脚本 / 导入）需要显式给出主题；没有默认值可推。
- 「把资源挪到另一个主题」变成不可能的操作（§8 护栏 2）。跨主题复用只能走**复制**（新 code，
  撞了加 `-2` 后缀），而复制本版不做（§15）—— 所以这一版的行为是：**建错主题 = 删了重建**，
  这也是 §7.1 要求新建时就选主题的原因。

## 4. `themes` 表

```ts
// packages/server/src/db/migrations/20260101000037_v080_themes.ts
themes: {
  id            bigserial primary key,
  code          varchar(64)  not null unique,   // 稳定标识：URL、资源包 manifest、导入对账
  name          varchar(100) not null,          // 显示名，不要求唯一（与 maps / puzzles 一致）
  description   varchar(500),
  data          jsonb        not null default '{}',  // 主题风格，见 §5
  is_default    boolean      not null default false,
  deleted_at    timestamptz,
  created_at    timestamptz  not null default now(),
  updated_at    timestamptz  not null default now(),
}
```

三条补充约束：

- **恰好一个默认主题**：`CREATE UNIQUE INDEX themes_default_unique ON themes (is_default) WHERE is_default`。
  默认主题不可删、不可 `deleted_at`，`code` 固定为 `default`。
  > **§19 起作废**：`is_default` 这一列和那条部分唯一索引都已删除 —— 没有「默认主题」，
  > 也没有「恰好一个」的约束。下面两条补充约束不受影响。
- **主题不做软删以外的版本化**（§2）。改名 / 改风格只影响**之后新建**的东西与 `themes` 详情页；
  已发布的谜题版本行、已导出的资源包都不受影响（前者自带快照，后者自带全量内容）。
- **`code` 与 `name` 分开**的理由和地图的 slug 一样：作者会想改显示名，但 URL 和包 manifest 不能跟着变。

`themes.data` 的形状：

```jsonc
{
  "version": 1,
  "style": { /* 完整 MapStyle，缺键按 DEFAULT_MAP_STYLE 补齐 */ },
  "linkageColors": [ { "key": "red", "label": "红", "color": "#B93A32" } ]
}
```

`linkageColors` 一并收进来，因为它是**同一主题的视觉语言**，现在住在每个谜题的 `data` 里，
同一主题的 8 个谜题各存一份、改一次要改八处 —— 和「地图样式重复配置」是同一个病。

## 5. 主题风格：三种做法，选第三种（问题 2 的前半）

| | S1 引用式（地图不存 style，读主题的） | S2 继承式（地图只存与主题的**差异**） | S3 快照式（新建时拷贝一次 + 显式同步） |
|---|---|---|---|
| 改主题风格，存量地图 | 立刻全变 | 未偏离的字段跟着变 | **不变**，需手动「同步」 |
| 地图能否独立渲染（导出 JSON / 资源包） | ❌ 不行 | ⚠️ 要连带主题 | ✅ 行 |
| `MapStyle` 形状 | 不用改 | 要改成 deep partial（新键 + 合并点） | 不用改 |
| 改动面 | 编辑器抽屉 / 导出 / 发布校验 / 渲染全部受影响 | 同上 + 新增 `resolveMapStyle` 合并点 | **只影响「新建地图」一处取值** |
| 违背既有原则 | 违背「地图是自包含作品」 | 部分违背 | 不违背 |

**裁定：S3。** 三条理由，按分量排：

1. **高压线**。`MapDraft` 从 v0.7.4 起就是可以导出 / 导入的独立文件，谜题从 v0.7.1 起自带画布副本。
   S1 会让一份导出的 JSON 失去渲染依据 —— 这不是「要不要多写一个合并函数」的问题，是把作品的
   可携带性换掉。S2 稍好，但仍要求「读这份 JSON 的人也知道主题风格」。
2. **真正的痛点被解决了**。「同一主题地图重复配置」的痛点是**新建一张图要从二十几个线宽 / 颜色 / 字号开始调**。
   S3 在新建那一刻把主题风格深拷贝进去，这个痛点消失。「主题改了我希望八张图全跟着变」是**另一个需求**，
   它和「我这张图想有点不同」天然冲突；用一次显式动作（`同步为主题风格`，逐项确认）比隐式追溯更可控，
   而且不会在「作者正好在改图」的时候把它脚下的地板换掉。
3. **改动面最小**。`MapStyle`、渲染层、编辑抽屉、导入导出、发布校验——**一处都不用改**。
   主题风格只作为「新建地图时的初始值」和「同步按钮的取值来源」。

具体落点：

- `POST /api/maps` 时若带 `themeId`，服务端把 `themes.data.style` 解析成完整 `MapStyle` 写进初始草稿。
  但注意 v0.5.8 起**创建地图不带画布尺寸**（`draft = null`），所以这里不能写草稿 —— 改为
  **初始化那一刻**（`PATCH /grid-size` 或首次导入）再由前端把主题风格填进 draft。这是既有流程的
  一个空隙，要单独处理，不能想当然。
- 地图编辑器的「基本信息」抽屉底部加一行小字：`风格来自主题「红楼梦」· 同步`（仅当与主题风格有差异时出现，
  点击弹逐项差异确认）。差异判定用深比较，和 `RegionStyleOverride`「只记差异」的判定同构。
  → 复查改成**常态可见**（无差异也写一行）并补「设为主题风格」的反向动作（§16.8）。
- 新建谜题时，`linkageColors` 也从主题拷贝（与地图副本同一时刻）。

## 6. 术语：主题 / 皮肤 / 参与者主题色

这是一个必须先解决的坑，否则代码里会出现三个 `theme`。

| 现在叫什么 | 指什么 | 落点 | 本版之后 |
|---|---|---|---|
| 主题开关（三态） | 浅色 / 深色 / 跟随系统 | `lib/theme.ts`、`ThemeToggle`、`html.dark` | **文案**统一为「外观」，代码**不改名**（改了要动 30+ 处，零收益） |
| 参与者主题色 | 名册卡片那个人自己的颜色 | `CharacterSlotEntry.themeColor`、`themeTint()` | 文案改称「参与者色」，代码不动 |
| **主题** | 本版的新概念 | `themes` 表、`/themes` | 唯一叫「主题」的东西 |

规则：**会话和文案里，「主题」只指作品主题；界面外观一律说「外观」。** 代码层面新增的标识符
一律带 `Theme` 前缀时先问一句「这是作品主题吗」，不是就换词（`AppearanceToggle`、`participantColor`）。
这条不写进文档就会在三个月后出现 `theme.themeColor`。

## 7. 展现方式：平铺之后怎么长出层级（问题 1）

现在五个模块各自平铺。三种候选：

| | V1 全局主题作用域 | V2 主题是第六个模块 | V3 完全替换（只剩主题） |
|---|---|---|---|
| 层级清晰度 | 中（「我总在某个主题里」） | 高（两套入口各司其职） | 最高 |
| 五个列表页改动 | 小（加个参数 + 下拉） | 小（同上，且可选） | 全部重写 |
| 跨主题找东西 | 要切来切去 | ✅ 原模块就是并集 | ❌ 没了 |
| 破坏既有导航 | 中 | 无 | 大（v0.7.1 刚定的顺序） |

**裁定：V2 为主，V1 的轻量版为辅。**

- **主结构**：导航第 1 项插入「主题」（`Layers` 图标），`/themes` 是卡片网格，点进 `/themes/:id` 是
  这个主题的**工作台**：一条主题横幅 + 四个 tab（资源 / 地图 / 角色 / 谜题）+ 三个动作（风格 / 打包 / 部署）。
  → 复查把这三层压成一行、把「打包 / 部署」改称「导出资源包 / 上线」（§16.2、§16.3）。
- **辅结构**：五个既有列表页保留，工具栏左端多一个 `主题筛选` 下拉（默认「全部」，
  记住上次选择）。这样「我只想改一个资源」的动线一点没变。
  → 复查改成页头下的**作用域条**，且筛选不跨页继承（§16.1、§16.12）。
- **重点：不做三层嵌套。** 层级只体现在**路由**上（`/themes` → `/themes/:id`），不体现在
  列表内部的分组标题里。既有列表已经有「草稿 / 版本」两块，再套一层组会把页面切成四段，
  扫描成本翻倍。

```
工坊
├── 主题            /themes            卡片：封面色带 + 名称 + 描述 + 计数（49 资源 · 8 地图 · 32 角色 · 8 谜题 · 6 已部署）
│   └── 红楼梦      /themes/:id        横幅（吸顶）+ [资源|地图|角色|谜题] + [风格 · 打包 · 部署]
├── 资源            /assets            + 主题筛选
├── 地图            /maps              + 主题筛选
├── 角色            /characters        + 主题筛选
├── 谜题            /puzzles           + 主题筛选
└── 部署            /deployments       按主题分组：合辑 + 该主题的单局（§16.4）
```

主题横幅为什么要吸顶：此后这一屏的每一条内容都属于它，「我在哪个主题里」必须随时可见 ——
这正是 V1 方案最大的缺点（容易忘记上下文），用一条 56px 的横幅解决掉。

`/themes` 的卡片不显示「版本号」——主题不版本化（§4）。显示的是**内容计数 + 最近一次打包时间**。

### 7.1 新建时必须能选主题（否则会建错，且改不了）

因为 `theme_id` 建行后不可改（§8 护栏 2），「建错主题」的代价是**删了重建**。所以主题的选择
必须在新建的**那一刻**就可见，而不是事后补：

- 四个新建对话框（资源 / 地图 / 角色 / 谜题）各加一个 `主题` 选择器，位置在名称之前。
- 默认值 = **当前列表的主题筛选值**；筛选是「全部」时 = 默认主题。
  > **§19 起**：第二句作废 —— 没有默认主题可退，新建必须明确带上 `themeCode`，
  > 不带就是 400。第一句仍然成立（筛选值就是答案，不做第二层兜底）。
- 在 `/themes/:id` 详情页里新建 → 选择器**锁定**为当前主题（这一屏不该出现别的主题），
  想换主题就回 `/themes` 或带筛选的列表页。
- 谜题的新建对话框原本就要选「地图版本」，那份地图的主题**决定**了谜题的主题 —— 所以这里的
  选择器是只读的提示（`将归入主题「红楼梦」（来自地图）`），不是可选项。这条不写清就会做出
  「谜题选主题 A、底图来自主题 B」这种自相矛盾的组合。

## 8. 隔离的三道护栏（不能只靠筛选下拉）

需求说「互相不可见和复用」。如果只在列表上加 `WHERE theme_id = ?`，那么一次手工改 URL、
一次导入旧 JSON、一次脚本调用就能把引用写穿。三道护栏都必须在**服务端**：

| # | 护栏 | 位置 | 行为 |
|---|---|---|---|
| 1 | **引用同界** | `mapService.save` / `puzzleService.save` / 发布校验 | 收集草稿里所有 `assetId` / `variantId` / `characterId`，逐个校验 `theme_id` 与本行一致；越界 400，逐条列出「资源 #4165（石板地）属于主题「红楼梦」」 |
| 2 | **不可搬迁** | 所有写入口 | `theme_id` 建行后不可改。改主题 = 复制一份到目标主题（新 code，撞名加 `-2`） |
| 3 | **删除兜底** | `DELETE /api/themes/:id` | `FK ON DELETE RESTRICT` 兜底；应用层先说人话：「主题下还有 49 个资源、8 张地图、32 个角色、8 个谜题，请先移空」；默认主题一律拒绝 |

> **§19 起**：这一条的地址变成 `DELETE /api/themes/:code`，「默认主题一律拒绝」作废（不再有默认主题）。

护栏 1 的实现可以复用 v0.7.3 的 `collectReferenceIssues` 的遍历骨架 —— 它已经在做「收集草稿里的
asset 引用」这件事，只是判据从「存在吗」换成「同主题吗」。新增 `collectThemeRefs(draft)` 与
`assertThemeScope(themeId, refs)`，放 `packages/shared`，前端在保存前也调一次（一致的前置提示）。
报错的呈现方式（说名字不说 id、多条按类型聚合、编辑器里画成行内标记）见 §16.11。

一条**例外**要写清：谜题的 `data.map.mapId` / `versionNo` 不校验。那是「画布从哪来」的追溯字段，
画布本身是副本（v0.7.1 §5.3），跨主题引用一份画布副本不会破坏隔离。但「引入新地图」对话框
只列出**同主题**的已发布地图 —— 这是体验层的一致性，不是约束。

## 9. 部署：单谜题还是整主题（问题 2 的后半）

现状很清楚：部署单元是**一条已发布的谜题版本行**，`games.puzzle_id` 活跃行唯一，`/play/:slug` 单局。

| | D1 只允许整主题 | D2 只允许单谜题（现状） | D3 两级：单局 + 主题合辑 |
|---|---|---|---|
| 玩家拿到的是什么 | 一个故事 | 一关 | 一个故事，也能单独玩一关 |
| 改一关要做什么 | 重新部署整个主题 | 重部署那一关 | 重部署那一关（合辑自动指向新版本） |
| 分享单关 | ❌ | ✅ | ✅ |
| 新引入的冻结机制 | 需要（一组版本号） | 无 | **无** |
| 与资源包的关系 | 一一对应 | 脱节 | 一一对应 |

**裁定：D3。** 核心是让「整主题部署」**不引入第二套冻结语义**：

- **合辑不是内容，是目录。** `theme_deployments` 一行只记 `{ theme_id, slug, name, description, cover_path }`，
  成员表 `theme_deployment_puzzles(deployment_id, puzzle_id, sort_order)` 按 **`puzzle_id`** 记录成员。
  于是「冻结」这件事仍然只有一处真相：谜题版本行。合辑里的某一关重新部署了新版本，合辑自动指向它，
  不需要重建合辑。
  成员键必须是 `puzzle_id` 而不是 `game_id`：`upsertGame` 是 delete-then-insert（v0.7.1 §7.6），
  同一谜题重新部署一次 **game id 就变了**，挂 game id 的成员会全部悬空。`puzzle_id` 不变，
  所以它是唯一稳定的挂点；玩家页再 `JOIN games ... WHERE deleted_at IS NULL` 取活跃的那条
  —— 取消部署时该关自动从合辑里消失，不需要清理成员行。
- **一键整主题部署**是动作，不是新状态：`POST /api/themes/:id/deploy` 对主题内每个谜题血统的
  **最新已发布版本**执行一次 `deployGame`（已有 game 的复用），再 upsert 合辑成员与顺序。
- URL：合辑 `/play/theme/:slug`，单局仍是 `/play/:slug`。`theme` 要加进 `slugError` 的保留字
  （`GAME_SLUG_PATTERN` 允许它，实测库里也没有这条 slug，但保留字必须显式拦，否则将来某个作者
  把自己那关命名成 `theme` 就撞了）。
- 合辑的 slug 与游戏的 slug 各自唯一，命名空间不同（`/play/theme/` vs `/play/`），不共享。
- 合辑是**活目录**，资源包是**快照**：重部署某一关，合辑自动指向新版本，但已经下载的包不会跟着变（§11.1）。

**代价**：`theme_deployments` + 成员表两张表，一个页面（部署页第一段），一个「勾选哪些关卡上架」的对话框。
换来的是「单关仍可分享」和「零新冻结机制」。

## 10. 游戏侧怎么展示（问题 3）

`/play` 从「一屏平铺全部游戏」改成两段：

```
┌ 主题 ──────────────────────────────────────┐
│ ┌──────────────────┐ ┌──────────────────┐ │
│ │ 红楼梦            │ │ 默认              │ │   ← 大卡片：封面 + 名称 + 8 关
│ │ 8 关 · 已部署 6 关 │ │ 5 关 · 已部署 2 关 │ │
│ └──────────────────┘ └──────────────────┘ │
├ 单个游戏 ───────────────────────────────────┤
│ （现有列表，不变）                            │
└────────────────────────────────────────────┘
```

`/play/theme/:slug` 主题页：封面横幅 + 描述 + 关卡列表（按 `sort_order`，卡片沿用 `GameCard`），
每张卡显示 `v{n}` 与难度。没有「下一关」这类强制串联 —— 推理游戏允许玩家随便挑一关。

→ 复查两处：单局段只列**不属于任何已上线合辑**的游戏（§16.5）；主题内关卡走
`/play/theme/:slug/:key` 并在游戏页给出返回主题的入口（§16.6）。

**一条不能忘的细节：存档键。** 现在 `readGameProgress(slug)` 按游戏的 slug 分键
（`docs/v0.4.1.md` §4.7）。合辑页里的关卡同时存在两条 URL（`/play/:slug` 与 `/play/theme/:slug`），
若按 URL 分键，同一个人在两条路上玩同一关会有两份进度。裁定：**进度键仍是游戏的 `slug`**，
路由参数只用于寻址。资源包模式也按游戏的 slug 分键（`bundle:{themeCode}:{gameSlug}`），
但那是下一版的事（§11.6）。

## 11. 资源包：只打「已经能玩的那几关」

需求原文：**一个主题打成包，包里自带谜题需要的一切 —— JSON、结构里 id 关联的资源、图片、字体；
部署页能部署包；游戏页能加载包玩，不碰数据库。**

**2026-10-29 改口（用户裁定）**：

1. 包的取材单位从「主题里的谜题」改为「**已部署的游戏**」；
2. **本版只做打包**：导入下一版再做；「部署资源包 / 在游戏页里加载包」也不在本版 ——
   下一版单独抽一个**能加载包的纯前端播放页**，那时再谈托管与播放。

这个改口不只是收窄范围，它把**取材口径**从「作者手上的内容」换成了「玩家已经能玩到的东西」，
顺手消掉原来三个难点：草稿要不要打、包内 key 怎么生成、包和线上是否一致。

### 11.1 为什么取材「已部署的游戏」

| | 从谜题打（原设计） | 从已部署游戏打（本版） |
|---|---|---|
| 取材 | `puzzles` 里挑已发布版本行 | `games` 的活跃行 |
| 草稿 | 要判断、要在报告里说「跳过了 2 关」 | **不存在这个概念** —— 没上线的游戏根本不在列表里 |
| 与线上是否一致 | 要人工核对 | **同一份数据**：包里那一关就是把 `getGameDetail` 的结果搬走 |
| 包内 key | 谜题名 slugify，中文名全空 → 兜底 `puzzle-1` | 直接用 `game.slug`（`GAME_SLUG_PATTERN` 的 ASCII 串，已唯一） |
| 关卡顺序 | 自己排 | 合辑的 `sort_order`；没有合辑时按部署时间 |

三条落地口径：

- **包里的一关 = 一次 `MapGameDetail`**（`MapGameSummary` + `map` + `puzzle`），减去绝对 URL、
  引用 id 重编号（§11.3）。包里没有第二套序列化格式 —— 这一点决定了将来播放器的渲染层不用重写。
- **包不依赖合辑存在**：主题里只单独部署过、没进合辑的关照样进包（顺序按部署时间）。有合辑时以
  `sort_order` 为准，因为那就是作者给玩家排的阅读顺序。
- **0 关已部署的主题**：导出按钮禁用，提示「先至少上线一关」。不导出空包 —— 那是零字节的谜题。

### 11.2 包里装什么

```
theme-bundle/
├── manifest.json            # 格式版本、主题、关卡清单、文件清单 + 校验
├── theme.json               # 主题身份：code / name / description / exportedAt
├── assets.json              # 这 N 关引用到的资源（形态 / 图片相对路径 / 纯色）
├── characters.json          # 这 N 关引用到的角色（头像相对路径 / 参与者默认值）
├── puzzles/
│   ├── sishan.json          # 一关 = 一次 MapGameDetail，id 已重编号
│   └── yin-qilin.json
└── files/
    ├── assets/1-stone-paving.webp          # 512px 缩略图（不是原图，见下）
    ├── covers/1.webp
    └── avatars/3-daiyu.webp
```

几条取舍：

- **没有 `maps/`，也没有 `theme.json.style`。** 谜题版本行**自带画布副本**（`PuzzleDraft.map.data`，
  v0.7.1 §5.3，含 `MapStyle`），`linkageColors` 也在 `PuzzleDraft` 里。风格跟着每一关走，
  包里不需要第二份「主题风格」—— 有第二份就会和关卡里那份不一致，而关卡里那份才是玩家看到的。
  `theme.json` 因此只装身份，供将来的播放页首页做标题。
- **没有 `player/`，没有 `index.html`。** 本版产物是**数据包**，不是站点（§11.6）。
- **只装被引用的**：一个主题 49 个资源，8 关实际用到约 30 个，不把主题库整个搬走。
  收集方式：遍历 `puzzle.map.data.cells`（`background` / `item`）+ `characterSlots[].characterId` +
  `linkages[type=asset]`，得到 id 闭包（`collectReferenceIssues` 已经在走同一条路）。
- **只带缩略图，缺了才退回原图** —— 这一条是 2026-10-29 在真实数据上量完之后改的，不是先前的估计：

  | | 原图 | 缩略图（`_thumb.webp`，512px） |
  |---|---|---|
  | 单张 | 平均 450 KB，最大 2 MB | 平均 12 KB |
  | 红楼梦 8 关整包 | **111 MB** | **2.26 MB**（小 49 倍） |

  画布层本来就优先用 `imageThumbUrl`（`MapAssetLayers.tsx`），512px 对几十像素的格子绰绰有余。
  先前的写法是「缩略图一起带」（两者都带），实测后发现那等于让作者下载 111 MB 的 zip 去玩
  一张 8×8 的棋盘，于是改成**只带缩略图**：包里 `imagePath` / `imageUrl` / `imageThumbUrl`
  三个字段填同一个包内相对路径，既有渲染代码一行不改。
- **关卡封面带**（卡片要），**地图封面不带**（游戏页不显示地图封面）。
- **文件按路径去重**：同一个 `image_path` 被多关引用时只存一份（红楼梦 8 关共用 13 个资源，
  不先去重会把它复制八遍）。文件名里的 `n` 是包内序号，`code` 只是给人读，冲突由 `n` 保证。
- **`sha256` 写进 manifest**：本版没有播放器来校验它，此刻它的作用是「传输损坏可查」；
  真正的校验点在下一版的播放器（失败就拒绝进入关卡 —— 宁可报「包不完整」也不要半张画布）。
  实测 8 关包：`manifest.files` 里每一条都在 zip 里存在，`sha256` 与 `bytes` 全部对得上，
  悬空引用（资源 / 形态 / 角色）0 条。
- **打包前先体检**：引用闭包里的每一行（资源 / 变体 / 角色）与每一个文件都必须存在，缺一个就**中止**
  并列清「哪一关的哪个引用缺了什么」。宁可一个包都不产出，也不要交付一个少一张图的包。
- **体积**：8 关约 30 个资源（含缩略图）+ 8 张封面，实测 **2.26 MB** —— 这是纯数据的重量，
  播放器不在这里面。

### 11.3 id 重编号：包里用本地序号，不是数据库 id

`PuzzleDraft` 里的引用全是数据库自增 id：`cells.*.background.assetId`、`characterSlots[].characterId`、
`linkages[].id`。这些 id 出了这个库就没有意义，导入另一个库还可能撞。

| | 包内保留原 id | 包内改用 `code` / `key` 字符串 | **包内重新编号（1..N）** |
|---|---|---|---|
| 渲染层 `assetsById: Map<number, Asset>` | ✅ 不用改 | ❌ 要改成 `Map<string, Asset>`，波及画布层 / schema / 校验 / 导入导出 | ✅ 不用改 |
| 跨库可移植 | ⚠️ 撞 id | ✅ | ✅ |
| 人可读 | ❌ | ✅ | ⚠️（`assets.json` 里同时给 `code`） |

**裁定：重新编号。** 按「首次出现顺序」给引用分配 `1..N`，原 id 只写进 manifest 的 `originIds`
（对账用，不参与渲染）。好处是：**下一版的播放器可以直接复用今天游戏页那套渲染代码，一行不用改。**

导出时的改写只有三处（都是纯函数，放 `shared/src/bundle.ts`）：

```
cells["3,5"].item.assetId:      4165     →  1
cells["3,5"].item.variantId:    4934     →  1
characterSlots[0].characterId:  3062     →  3
linkages[0].id (type=asset)     4986     →  7
```

`assets.json` 里同时保留 `code`（`hlm_stone_paving`）—— 下一版「导入回工坊」时用它匹配已有资源，
而不是靠 id。这也正是 §3.2 把 `code` 收紧到主题内唯一的第二个理由：**包里需要一个稳定的人读键**。

### 11.4 manifest

```jsonc
{
  "format": "loredoku-theme",
  "formatVersion": 1,
  "exportedAt": "2026-10-29T11:20:00+08:00",
  "theme": { "code": "hlm", "name": "红楼梦", "description": "…" },
  "games": [
    { "key": "sishan", "file": "puzzles/sishan.json", "name": "撕扇",
      "gridSize": 4, "difficulty": "medium", "cover": "files/covers/1.webp" },
    { "key": "yin-qilin", "file": "puzzles/yin-qilin.json", "name": "因麒麟伏白首双星",
      "gridSize": 5, "difficulty": "hard", "cover": "files/covers/2.webp" }
  ],
  "assets": "assets.json",
  "characters": "characters.json",
  "fonts": [{ "family": "霞鹜文楷", "builtin": true }],
  "files": [{ "path": "files/assets/1-stone-paving.webp", "bytes": 48213, "sha256": "…" }],
  "originIds": { "assets": { "1": 4165 }, "characters": { "3": 3062 }, "games": { "sishan": 271 } }
}
```

- `key` = `game.slug`，**不再由谜题名生成**。上一版草稿里「中文谜题名 slugify 全空 → 8 个 `""`」
  那个坑因此不存在了：红楼梦 8 个关名全是中文，但它们的 slug 是 ASCII，且已唯一。
  也正因为 key 就是访问路径，打包对话框里**不允许改 key** —— 要改去部署页改。
- `games[]` 里放的是卡片要的字段（`name` / `gridSize` / `difficulty` / `cover`），下一版播放页首页
  不用再打开关卡文件就能画出列表。
- 不引入「主题版本号」。包的身份是 `exportedAt`，因为主题不版本化（§4）；给一个假版本号只会让人
  以为「v2 的包能升级 v1 的包」—— 包之间没有升级关系，只有「哪一天的快照」。
- `originIds` 本版不读，留着给下一版的导入对账（配 `code`）。

### 11.5 字体：本版不进包

字体是**构建期资源**（`packages/web/src/assets/fonts/`，`import.meta.glob` 发现 + `FontFace` 注册，
Vite 哈希后落在 `dist/assets/`），它的宿主是**播放器**，不是数据。本版没有播放器，所以：

- 包里只在 manifest 记 `fonts[]`（这 N 关用到哪些族），**不带字体文件**。
- 每款约 925 KB（霞鹜文楷按 GB2312 一级裁字后）。塞进每个包就是 N 份同样的字节 ——
  而下一版的播放器本来就要自带一份。
- 播放器加载时与 `document.fonts` 对账，缺了走回退链（`fontFamilyStack` 已经这么做），
  **不阻断游戏**：字体不对只是难看，不是不能玩。
- **前提写死**：主题只能使用**构建内置的字体族**。作者上传自定义字体是另一件事（要上传、要裁字、
  要授权），列进 §15 不做。真要支持才需要 `files/fonts/` + `manifest.fonts[]` 指向文件，接口不用变。

### 11.6 本版不做：托管与播放（下一版的形状先写下来）

三件事一起推后：把包上传到服务器、`/bundles/{slug}/` 静态托管、在游戏页里加载包。
理由：这三件都必须先有**播放器**（一个不含工坊的独立构建），而播放器是一个独立交付物
（独立入口、独立依赖、独立体积预算）。把它塞进 v0.8.0 有两个坏处：拖慢主题功能，
以及让包的格式在**没有被真正消费过一次**之前就被定死。

导出流程因此只剩一步：

1. `GET /api/themes/:id/bundle` → 服务端按 §11.1 取材、§11.2 组包、§11.3 重编号，
   流式返回一个 zip 给作者下载。**不落盘、不登记、不托管** —— 所以这一版没有 `bundles` 表。

zip 需要一个写库：现有依赖里没有，**加一个 `archiver`**（流式、成熟）比手写 zip 划算。
不做导入与托管，就不需要解包库 —— 依赖只进不出地少一半。这一条要在实现时确认体积，
否则退回「目录 + tar.gz」（Node 的 `zlib` 还是要配 `tar`，也就省不掉库）。

把决定形状的东西先写下来，免得下一版做成「复制一份 GamePage」：

```ts
// 下一版：packages/web/src/lib/gameSource.ts（本版不实现）
export interface GameSource {
  readonly kind: 'api' | 'bundle';
  /** 主题首页：主题信息 + 关卡清单（来自 manifest.games） */
  loadTheme(code: string): Promise<{ theme: ThemePublic; games: GameSummary[] }>;
  /** 一关：画布 + 谜题 + 它引用到的资源与角色 */
  loadGame(key: string): Promise<{
    summary: MapGameSummary;
    map: MapDraft;
    puzzle: PuzzleDraft;
    assets: Asset[];
    characters: Character[];
    storageKey: string;
  }>;
  /** 图片地址：api 模式原样返回；bundle 模式把相对路径拼到包根 */
  resolveFile(path: string | null): string | null;
}
```

- `apiSource` = 今天游戏页那三个 query；`bundleSource` = `fetch('manifest.json')` + 按需取关卡。
- 渲染层只认 `assetsById: Map<number, Asset>`，包里 id 重编号（§11.3）就是为了让它**一行不改**。
- 存档键：api 模式 = 游戏 slug，bundle 模式 = `bundle:{themeCode}:{key}`。两套键不互通是**有意的**：
  离线包里的进度不该出现在线上，反之亦然。
- `file://` 打不开（`fetch` 跨域）—— 这条是下一版播放器的事，但要在本版的打包完成提示里先埋一句，
  否则作者拿到 zip 双击 index.html（现在压根没有）会更困惑。

### 11.7 代价

- 这一版交付的是一个**打不开的 zip**：解开是 `manifest.json` 与一堆 `.json` / `.webp`。
  「导出完成」的提示与文档都必须直说「包是数据，播放页面在下一版」，否则第一反应是「怎么坏了」。
- 少了三张东西（`bundles` 表、上传路由、静态托管），多了两件：**打包前体检**与
  **manifest 里那份 `games[]` 清单**（它是下一版播放器首页的唯一数据来源，字段少一个都得改格式）。

## 12. 迁移与 backfill

一次迁移 `20260101000037_v080_themes.ts`，一个事务：

1. 建 `themes`，写两条：
   - `('default', '默认', '无主题归属的历史内容', …)`，`is_default = true`
   - `('hlm', '红楼梦', …)`
2. `assets` / `characters` / `maps` / `puzzles` 各加 `theme_id bigint`（**nullable**）+ 索引。
3. **backfill（三段式，顺序不能乱）**：
   - ① 资源与角色按 `code` 前缀：`code LIKE 'hlm\_%'` → `hlm`，其余 → `default`；
   - ② 谜题与地图按**引用投票**：收集该行引用的 asset / character 的 `theme_id`，
     **全部为 `hlm` 且至少有一个引用** → `hlm`；否则 `default`。没有引用（空画布）的 → `default`；
   - ③ 剩下的全部落到 `default`（含未被引用的资源）。
   实测依据：8 个红楼梦谜题引用的资源与角色**100% 是 `hlm_`**，5 个默认谜题的**100% 不是**，
   所以第 ② 步在真实数据上没有一行落进「混合」分支。迁移里要把这句写成注释：
   **这是一次性的历史归档，不是通用规则**，别让后人以为「主题归属靠前缀推断」。
4. **先建约束，再收紧**：`UNIQUE (theme_id, code)` 换掉全局唯一 → `SET NOT NULL`。
5. `down`：恢复全局唯一 → 删索引 / 列 → 删表。

风险点写在这里：

- `maps` 的版本行与草稿行同表，backfill 按行做，同一血统可能被分到不同主题（若某版本的引用变了）。
  实测没有这种情况；迁移里加一次断言：**同一 `root_id` 的行必须同主题**，违反就报错中止
  （宁可让迁移失败，也不要产出一个自相矛盾的血统）。
- `games` 不加列（§3.1），所以没有 games 的 backfill。
- 迁移后立刻跑一次 §8 护栏 1 的**全库体检**（只报告、不改数据），确认零越界引用。

## 15. 看过没做

- **主题版本化**。理由见 §2：会和谜题版本化打架，且第二套没有真相。真要「主题的第 3 版」，
  用资源包 + 日期表达更诚实。
- **作者上传自定义字体进主题**。要上传、裁字、授权确认，还得让 `manifest.fonts` 与播放器
  的 `FontFace` 注册联动。本版只支持构建内置字体（§11.5），接口已经留好。
- **包内的播放器、包的上传与托管**。这是下一版的第一件事（§11.6）：独立入口、独立构建、
  独立体积预算。本版只交付数据包。
- **单局包**（一个包里只有一关）。不做：分发单关用 `/play/:slug` 链接更直接，
  包的意义是「一整套」。
- **单文件离线包（`file://` 直接可玩）**。要内联全部数据成 `bundle.js`，失去懒加载，
  且大图仍要单独文件。等真有「发 U 盘」的需求再说。
- **主题级搜索 / 跨主题全局搜索**。现在每个列表页各有搜索框；主题只是个筛选维度，
  再叠一层全局搜索会让「搜什么」变成新问题。
- **谜题在主题内的排序**（合辑顺序以外的编辑期顺序）。合辑有 `sort_order` 就够了，
  编辑期列表按更新时间排已经够用。
- **跨主题的复制 / 移动**。移动会扯动已发布的版本行（§8）；复制需要一套 code 去重与
  「复制到哪个主题」的对话框，还牵扯图片文件是复制还是共用（共用就等于没隔离）。两者都值得单独一版。
- **主题封面**。`themes` 没有 `cover_path`；合辑有封面就够了，主题卡片用色带 + 字标。
  加一列容易，但「两个封面看起来一样」会让作者困惑该改哪个。

### 16.1 一条作用域条，替掉四个下拉（覆盖 §7 的「工具栏加筛选」）

> **已被 §18.1 / §18.7 取代**：作用域条（连同按页分键的 `localStorage`）已删除，主题改为
> 地址的第一段。下面这段保留，用来解释当时为什么觉得 40px 是值得的。

前文写的是「五个列表页工具栏加一个主题筛选下拉」。三处不合适：

- **位置不够**。资源 / 角色页的左栏是 340px，已经排了「搜索 → 类型分段 + 状态下拉」两行；
  第三个控件会把 `flex-wrap` 挤成第三行，而这三行都在列表上方。
- **语义相反**。下拉默认「全部」，等于把 §2 定的边界在界面上变成**可选**的：作者在「全部」里看
  90 个资源，屏幕上没有任何一处说它们分属两个世界。
- **状态不可见**。下拉在工具栏里，滚走就没了 —— 而 §7 用吸顶横幅解决的正是「我总在哪个主题里」。
  两个做法在同一份文档里打架。

改为**一条作用域条**（`ThemeScopeBar`），钉在页头与内容之间：

```
主题   [ 红楼梦 ▾ ]                          49 资源 · 8 地图 · 32 角色 · 8 谜题
```

- 高 40px（与面板头 `PARTICIPANT_HEADER_HEIGHT` 同档），`border-b` 一条线，**不加底色**（原则 2）。
- 右侧计数是这条横条**存在的理由**：只换个位置的筛选器不值得 40px，但「这个边界里有多少东西」
  值得。计数走 `text-xs` + `text-muted-foreground`。
- 下拉里第一项写 `全部主题（90 资源）` —— 清空筛选的入口同时说明清空后会看到什么。
- 五页共用；`/themes/:id` 用的是同款外壳的吸顶横幅（§16.2），只是动作不同。

代价：每页多 40px 垂直空间。换回的是「边界常驻可读」+ 340px 左栏不必塞第三个控件。

### 16.2 主题工作台：四层常驻压成一层（覆盖 §7 的横幅 + tab + 三动作）

> **页面本身已由 §18.5 取代**（`/themes/:id` 这个屏不存在了，四个 tab 归顶栏），但
> 「一个主按钮 + 一个 `⋯`」这条规矩被 §18.5 继承下来。

按前文的写法，`/themes/:id` 顶部常驻四层：`AppShell` 顶栏 56 + 主题横幅 56 + tab 44，
外加工具条 —— 800px 高的笔记本上正文只剩一半。这是**一天要进几十次的屏**，常驻高度就是产能。

改成一行的 56px（与顶栏同高，不用新档）：

```
‹ 主题  红楼梦        资源 49 · 地图 8 · 角色 32 · 谜题 8              [上线]  ⋯
```

- 左：面包屑（`主题` 是 muted 的链接，`红楼梦` 是当前页）；中：tab，**每个 tab 带计数** ——
  不带计数就得点进去才知道哪个是空的；右：一个主按钮 + 一个 `⋯`。
- 主按钮只能是**一个**，且必须是「上线」——这一屏唯一有外部结果的动作。`⋯` 里放
  风格 / 导出资源包 / 重命名 / 删除主题。三个平级按钮并列，等于告诉作者「三件事一样常做」。
- 如果一定要保留两级（横幅 + tab 分开）：让 tab **不吸顶**，滚过之后把 `红楼梦 · 地图`
  以小字并进横幅。两种都可以，但别让两层都吸顶。

### 16.3 动词：『部署』被这一版用成了两个意思（承接 §6）

§6 刚把「主题」的三个意思收成一个，这一版又造了第二个二义词：同一个「部署」既指
「让玩家能在 `/play` 上玩」，又指「把一个静态包放到服务器上」。

| 说法 | 代码 | 含义 | 玩家侧 |
|---|---|---|---|
| **上线** | `deployTheme` / `deployGame` | 出现在 `/play/*` 上 | 「可玩」 |
| **导出资源包** | `exportThemeBundle` | 拿走一个 zip，不碰服务器 | 不出现 |
| （下一版）**发布包** | `publishBundle` | 把 zip 挂到 `/bundles/*` | 能打开 |
| 合辑 | `theme_deployment` | 一串关卡的目录 | 「故事」 |
| 主题 | `theme` | 边界本身 | 不出现（直接叫名字） |

规则：`deploy` 只给「上线」用，导出永远叫 `export`。不写这条，三个月后会出现 `deployBundle()`。

### 16.4 部署页：按主题分组，不是三段（覆盖 §9 的页面部分）

> **§18 之后**：在工作空间里这一页只剩**一个**组（当前主题）；分组逻辑仍在，用于无上下文的
> 渲染路径。组头保留 —— 它挂着「导出包」这个主题级动作。

这一页现在是一条行列表、无工具条（`design-system.md` §3.2）。加了合辑之后，作者打开它问的是
**「玩家现在能看到什么」**——三段纵排会把同一主题的合辑和它的 8 个单局劈到两大块里。

改成一页分组，组头是主题名：

```
红楼梦                                      6 关在线            [导出包]
  合辑「红楼梦」   /play/theme/hlm   6 关    [打开]  [取消上线]
    撕扇 v3 · 因麒麟伏白首双星 v2 · 玉带林中挂 v1 …       ← 单局行，缩进 24px、高 40
默认主题                                    4 关在线            [导出包]
未归入合辑                                  3 关                [—]
```

- 组头：`text-2xs` + `text-muted-foreground` + `border-t`，右侧「导出包」——包是**主题级**动作，
  挂在组头而不是某一行上。
- 组内先合辑行，再单局行。单局行缩进、压到 40px：它是细节，不是同级内容。
- 没有合辑的主题也要有组头（「导出包」在那儿才找得到）。

### 16.5 `/play`：两段互斥，别让同一关出现两次（覆盖 §10）

按前文，`/play` 是「主题大卡 + 现有单局列表不变」。红楼梦 8 关会**出现两次**：一次在大卡的
「8 关」里，一次在下面的 8 张卡里。玩家不知道该点哪个，而且两处数量还对不上（只上线了 6 关）。

- 单局段只列**不属于任何已上线合辑**的游戏。两段互斥，数量自然对得上。
- 大卡上的「8 关 · 已部署 6 关」是工坊话（「部署」玩家不懂）→ 玩家侧写「6 关可玩」，
  不足时补一句「还有 2 关在准备」。
- 合辑里某关被取消上线后，成员行还在（§9 的设计），卡片按**可玩数**算，不摆灰卡。

### 16.6 主题里的关卡不能丢上下文（补 §10）

`GameCard` 里硬编码了 `navigate('/play/${game.slug}')`。主题页复用它，玩家点进第 3 关之后，
屏幕上没有任何回到「红楼梦」的入口 —— 只能按浏览器返回。

- 主题内关卡走 `/play/theme/:slug/:key`（`key` = `game.slug`），游戏页左栏顶部出现「‹ 红楼梦」。
- 从单局入口（`/play/:slug`）进来时不出现这枚面包屑 —— 它表示「你从哪来」，不是装饰。
- 存档键仍按 `game.slug`（§10），URL 只用于寻址：两条路玩同一关还是同一份进度。

### 16.7 新建对话框：一枚「作用域胶囊」，不是四种写法（细化 §7.1）

> **前半被 §18.9 改写**：在工作空间里胶囊一律只读（地址已经定了主题）。「谜题锁底图」不变。

§7.1 说四个对话框「选择器位置在名称之前」。对谜题不成立：**谜题的主题由底图决定**，
先摆一个只读结论、后面才让人选地图，是先给答案再给原因。

- 顺序：谜题 = 名称 → 地图版本 → 主题（只读）；其余三个 = 名称 → 主题（可改）。
- 形状统一为一枚胶囊：`[ 主题 红楼梦 ▾ ]` 可点 = 可换；`[ 主题 红楼梦 · 来自底图 ]` 禁用 = 锁定。
  别用「一个下拉 + 一行说明」两种控件说同一件事。
- 在 `/themes/:id` 里新建时胶囊禁用，提示语写「回「主题」页可换」，而不是一个「锁定」图标。

### 16.8 风格那一行：正常状态也要在（改写 §5 的落点）

§5 写「仅当与主题风格有差异时出现」。这是反向的 —— **正常状态看不见**，作者反而无法确认
「这张图吃的是主题风格」，只有出问题时才有一行字。

- 常态：`风格来自主题「红楼梦」`（`text-xs` + muted，不可点）。
- 有差异：`与主题风格有 7 项不同 · 查看差异`（主色，可点）。
- 差异弹窗按 网格 / 边框 / 标签 / 光标 / 其他 分组，**只列不同的项**（二十几项全列没人看）。
- 页脚两个动作，都要有：
  - `应用主题风格`（改本图）；
  - `设为主题风格`（改主题，本图成为缺省）。成本只是写一次 `themes.data.style`，但作者调好一张图后
    一定会想把它变成新缺省 —— 没有这个动作，只能回主题抽屉里手抄一遍。
- **别用「同步」这个词**：它没说方向，而方向就是这个功能的全部。

### 16.9 主题卡片：两行计数，色带用自己的调色板（改写 §15 的「色带 + 字标」）

- 五个计数排一行（`49 资源 · 8 地图 · 32 角色 · 8 谜题 · 6 已部署`）= 五个数字都要读，其中一个是
  状态不是内容。改成两行：
  - 主行 `8 关 · 6 关在线`（这是主题唯一的对外结果）；
  - 次行 muted `49 资源 · 8 地图 · 32 角色`（这是库，不是结果）。
- 色带别凭空配：取 `themes.data.linkageColors` 的前 3–4 色横铺。那是**作者自己的调色板**，
  天然区分两个主题，也不违反原则 4 —— 这是引用作品的颜色，不是给界面新增配色。
  默认主题没有 `linkageColors` 时退回 `muted` 色带，不要发明颜色。
  > **§19 起**：「默认主题」改说「没有设过调色板的主题」（§19 删掉了默认主题这一档）。

### 16.10 导出对话框：先给清单，再给文件（改写 §11.7 的提示）

点「导出」→ 生成 → toast → 下载，这条路上作者**不知道自己拿到了什么**：几关？哪些关？
多少资源？而且「少了一关」这类问题在下载完的 zip 里永远不会被发现。

同一个对话框两态：

1. **清单**：`红楼梦 · 6 关`；逐关（名称 / 网格 / 难度 / 有无封面）；`资源 30 · 角色 12 · 图片 74 ·
   约 14 MB`；一行警示「包里没有播放页面，双击打不开（下一版）」；按钮 `导出 zip`。
2. **进度 → 完成**：进度条 + 文件名 + `releases/hlm-2026-10-29.zip` 这类落点，附「再导一次」入口。

清单里的数字同时是**打包前体检**的输出（§11.2）—— 缺文件就在这一步说，而不是生成一个坏包。

### 16.11 越界提示：说人名，不说 id；且要提前（改写 §8 护栏 1 的呈现）

§8 的例子是「资源 #4165（石板地）属于主题「红楼梦」」—— 把数据库 id 放在主句。单用户工具里
id 是噪音，作者认的是名字。

- 主句改成「「石板地」在主题「红楼梦」里」，id 收进灰色小字或 tooltip。
- 多条按类型聚合：「12 个资源、3 个角色不在本主题」，可展开；不要一次甩 15 行红字。
- 更靠前：等保存才拦太晚。编辑器里给越界引用**行内标记**（资源列表项左侧一枚 `text-warning` 点、
  名册卡片头像加一圈），作者在改的时候就看见。§8 已经让前端调一次 `assertThemeScope`，
  同一份结果画成标记即可，不用第二套逻辑。
- 文案别用「违规 / 非法」：这不是错误，是「它们在另一个世界」。

### 16.12 空态要第四种：被筛掉（扩展 `design-system.md` §3.6）

> **句式保留，末条作废**：「按路径分键记作用域、别跨页继承」正是 §18.1 要拆掉的东西 ——
> 跨页不继承的根因不是记法，是把主题当偏好存。

那里定了三种句式（无数据 / 搜索无果 / 面板短句）。有了作用域条就有第四种：**这个主题里没有**。

```
「红楼梦」里还没有地图            ← 被作用域筛掉
在「红楼梦」下新建地图             ← 主按钮直接带上主题
```

- 按钮带主题，别把作者丢回「全部」去新建 —— 那会让他再选一次，还可能选错（§7.1 说错就改不了）。
- 顺带一条：作用域**别跨页继承**。按路径分键记（`loredoku.themeFilter.maps`），不要五个页面共用一个值 ——
  共用的典型后果是「我明明有 90 个资源，怎么只剩 49 个」。

### 16.13 落地时要一起改的活文档

- `design-system.md` §3.1：导航「五项固定顺序」→ 六项。**实际落地时这项不是「主题」，是
  工作空间的首页「概览」**（§18.3）—— 主题自己搬出了顶栏。
- `design-system.md` §3.6：空态三句 → 四句（§16.12）。
- `design-system.md` §3.5：行列表语法补两档 —— 分组头 40px、缩进单局行 40px（`pl-10`）（§16.4）。
- `map-management-and-editor.md` §6：主题卡片色带用的是「作品的颜色」（`linkageColors`），
  确认它没被写进「不随主题变」的禁区 —— 它是引用，不是界面配色。同节顺带把「主题」这个
  二义词拆成「界面色主题」与「内容主题」两行（§6 的术语锁在文档层面也得执行）。

## 18. 主题即工作空间：把它挪进地址

> 这一节写于 §17 之后 —— 代码跑起来、真上手用过一阵才发现的问题。**数据层一行没动**，
> 改的全是界面骨架。它覆盖 §16 的四处：§16.1（作用域条）、§16.2（一行式主题工作台）、
> §16.7 的前半（新建时可换主题）、§16.12 的后半（作用域按路径分键存 `localStorage`）。

### 18.1 一次改口

§16 里主题是这么用起来的：

```
顶栏：主题 · 资源 · 地图 · 角色 · 谜题 · 部署
每页：[ 主题 默认主题 ▾ ]      49 资源 · 8 地图 · 32 角色 · 8 谜题
```

那套东西自洽，但说错了一件事：**主题不是你想看什么，是你在哪**。证据是它存在
`localStorage` 里、还按页分键（`loredoku.themeScope.maps` 与 `.assets` 是两个值）——
于是同一屏里「地图页记住了红楼梦、角色页还停在默认主题」，而换一台机器打开 `/maps`
会看到另一批数据，把链接发给同事也一样。一个决定整屏内容的量，被存成了私人偏好。

这一版把它放进地址：

```
/hlm/maps         红楼梦 · 地图
/hlm/basic        红楼梦 · 概览
/settings/themes  系统配置 · 主题列表
```

同一件事的三种说法（可刷新、可分享、可前进后退）一次到位，而「全部主题」这个视图
**没有了** —— 工作空间不提供「跨世界看东西」，要看全局请去系统配置或玩家侧。

### 18.2 路由表

| 地址 | 是什么 |
|---|---|
| `/` | 挑一个主题：**记住的那个** → 列表第一个，然后落 `/code/basic`（§19 去掉了「默认主题」这一档） |
| `/:code` | 工作空间索引，重定向到 `/:code/basic` |
| `/:code/basic` | 概览（§18.5） |
| `/:code/assets` `maps` `characters` `puzzles` `deployments` | 五个模块 |
| `/settings` | 系统配置索引，重定向到 `/settings/themes` |
| `/settings/themes` | 主题列表（§18.6） |
| `/maps/:mapId/edit` 等 | 整屏页，在两种外壳之外 |
| `/play` `/play/:slug` `/play/theme/:slug[/:key]` | 玩家侧，不变 |

**静态段压过动态段**，这是整张表能成立的前提：`/settings` 与 `/play` 比 `/:themeCode`
更「具体」，所以不会被当成主题编码；旧地址（`/maps`、`/assets`、`/themes`、`/items`、
`/cards`）也靠这一点留在最外层做重定向，书签不至于 404。

**保留字**：既然编码成了地址第一段，`settings` / `play` / `maps` … 这些顶层路径就成了
保留字 —— 一个叫 `settings` 的主题，自己的工作台永远打不开。`THEME_CODE_RESERVED` 在
创建时拦下，并直接说出被占用的那个词（`shared/src/schemas/theme.ts`）。

### 18.3 两种外壳

`AppShell` 只管一层壳，`variant` 决定里面装什么：

| | 工作空间 `/:code/*` | 系统配置 `/settings/*` |
|---|---|---|
| 导航 | 六个模块（概览 / 资源 / 地图 / 角色 / 谜题 / 部署） | **没有** |
| 中间 | —— | 「/ 系统配置」字样 |
| 右侧 | 主题切换器 · 日夜开关 · 游戏 | 返回工坊 · 日夜开关 |

共用一个 56px 高、一个 `max-w-7xl`、一套间距 —— 两边来回切，右边缘不跳。

为什么不给系统配置一套独立的 header 组件：两块壳的差异只有「中间那一段」，复制一份
就意味着**以后改任何一处间距都要改两遍**，而它们又必须长得一样。

### 18.4 顶栏的主题切换器

位置在日夜图标**之前**：两者都是「外壳的开关」，一个换世界、一个换明暗，不该分居顶栏两端。

触发器上写的是当前主题名（`Layers` 图标 + 名字 + `▾`，最长 176px 截断），所以顶栏里
始终有一句「你在哪个世界」，不用展开。

菜单只有两件事：

1. **换到另一个主题** —— 保留当前模块（`/hlm/puzzles` → `/default/puzzles`）。换主题是
   「换个世界接着干同一件事」，不是回首页重来。
2. **【主题配置】** —— 分隔线之后，带一句「新建、改名、删除」，通向 `/settings/themes`。
   它是一个出口，不是第三个主题，所以不跟主题项排在一起。

实现沿用仓库里已有的 portal 菜单（`EntryActionsMenu` 那套），没有引入下拉依赖。
菜单项是 `role="menuitemradio"` + `aria-checked`，当前主题打勾。

### 18.5 概览页（`/:code/basic`）

§16.2 的这一屏是「主题工作台」：面包屑 + 四个带计数的 tab + 一列平铺内容。有了工作空间
之后，那四个 tab 就是顶栏的四个模块 —— 同一件事说两遍，而且第二遍更弱（只能看，不能干活）。
所以概览页只剩「这个空间是什么」：

```
红楼梦                                            [上线] [⋯]
大观园里的推理。

[ 49 资源 → ] [ 8 地图 → ] [ 32 角色 → ] [ 8 谜题 → ]

编码        hlm            地址与资源包里都是它，创建后不可改
缺省风格    未设置          在任意一张地图的「基本信息」里设
上线        6 关在线        /play/theme/hlm-story
```

入口落在概览而不是地图：工作空间现在有自己的首页，替作者决定「进来就要画地图」是上一版
的惯性（那时没有首页可落）。概览把四扇门摆在第一屏，点一下就到。

几条判断：

- **四个计数是入口**（大数字 + 箭头 + 悬停位移），不是四个装饰数字。作者来这一页，
  八成是想去某一处。
- **事实行只写「别处改不了但必须知道」的东西**：编码不能改、风格只能在画布上设、上线是
  外部结果。可点的都做成入口或页头按钮，这一块不放任何点不动的控件。
- **主按钮只有「上线」**（§16.2 那条老规矩仍然成立），导出 / 改名 / 删除在 `⋯` 里。
- 页脚一句话交代「这一页以后会长出更多可配置项（字体、联动调色板）」—— **不画占位控件**。

### 18.6 系统配置 · 主题列表

卡片与 §16.9 一样（色带 + 名字 + 编码 + 两行计数），改了两处：

- 点卡片**进这间工作台的 `/code/basic`**，不再是「主题详情」；
- 新建对话框把服务端的拒绝理由**留在弹窗里**（重名、保留字、字符集）—— 关掉再 toast，
  作者就不知道该改哪一格。

### 18.7 删掉的东西

| 删掉 | 为什么 |
|---|---|
| `ThemeScopeBar`（40px 作用域条） | 地址已经写了主题。两个控件说同一件事，只会让人分不清哪个是权威 |
| `useThemeScope`（按页分键的 `localStorage`） | 主题不是偏好。现在只留一个键 `loredoku.theme`，存**最后一个进过的编码**，给旧地址与整屏页兜底 |
| 顶栏的「主题」模块 | 换工作空间不是内容操作。它搬去系统配置页，入口是切换器菜单里的【主题配置】 |
| `ThemeDetailPage`（含四个 tab 与 `ScopedList`） | 由 `/code/basic` 取代；四个 tab 的活在顶栏 |
| 「全部主题」视图 | 工作空间不提供跨世界视图。要看全局，去系统配置（数量）或 `/play`（能玩的） |

`ScopedEmpty` 留着，但不再自己查主题列表 —— 主题名从工作空间上下文递进来。一个主题在
顶栏、页头、空态里各查一次，改名时就会有三份不同步的名字。

### 18.8 兜底与边界

| 情形 | 行为 |
|---|---|
| 旧地址 `/maps` `/assets` … | 先挑主题（记住的 → 第一个），再重定向到 `/code/<module>`（§19：没有「默认」这一档） |
| 一个主题都没有 | 重定向到 `/settings/themes`（唯一该去那儿的情形） |
| 编码不存在 | 一屏说清「没有编码是 `xxx` 的主题」+「回到工坊」+「主题配置」。**不**悄悄落到别的主题 —— 别人发来的链接静默变成另一个世界，比 404 更糟 |
| 主题列表取不到 | 同一屏，但显示真正的原因（网络 / 服务端），不伪装成「主题不存在」 |
| 整屏页（编辑器 / 查看页）的返回 | `workshopPath('maps')` / `workshopPath('puzzles')` —— 读记住的编码，回到你进来的那个世界 |
| 地图编辑器里的风格行 | 仍按**地图自己的** `themeId` 取主题，与工作空间无关（一张图只属于一个主题） |

`useWorkspace()` 因此是**可空**的：不在工作空间时页面退回「不限定主题」。这条不是为了
省事，而是因为整屏页（`/maps/:id/edit`）本来就在外壳之外，硬要一个上下文就只能造假值。

### 18.9 新建对话框里的主题胶囊

工作空间已经定了主题，所以三个新建对话框（资源 / 角色 / 地图）里的胶囊从**可换**变
**只读**：

```
[ 主题 🔒 红楼梦 · 当前工作空间 ]
```

理由不变：`theme_id` 建行后不可改（§8 护栏 2），在工作空间里还能改主题，等于允许
「把东西建到隔壁去」。谜题那枚仍然锁在**底图**上（`来自底图`），比工作空间更具体。

`defaultThemeId` 这个 prop 留着，但降级成「没有工作空间上下文时的兜底」（单测、旧入口）。

六个模块链接全部指向 `/hlm/*`，没有一条还在老地址上；编码不存在时**点名那个编码**且不渲染
任何模块；系统配置的外壳里六个模块一个都不在、也没有切换器；概览页的四格计数是链接、
`⋯` 里才有导出、导出清单只含本主题上线的关。

### 18.11 未做

1. **每个主题记住自己的模块**：现在换主题保留模块（`/hlm/puzzles` → `/default/puzzles`），
   而不是回到那个主题上次看的页。后者要多存一份 `code → module` 的映射，收益不明显。
2. **新建主题后自动进入**：建完停在列表，得再点一次卡片。
3. **系统配置的第二个分区**：现在只有「主题」。账号 / 存储 / 字体进来时，左侧需要一列
   分区导航 —— 那时 config 形态才需要真正的二级结构。
4. **权限**：工作空间是天然的权限边界（按 `code` 授权），但本版没有登录。
5. **§16.11 的行内越界标记**、**§11.6 的托管与播放** —— 同 §17 的清单，没有被这一节推进。


## 19. 删掉 `is_default`，接口只认 `themeCode`

§18 把主题挪进了地址（`/hlm/basic`），但数据层和 HTTP 层还留着两截老尾巴：

1. `themes.is_default` —— 一列布尔 + 一条部分唯一索引（`WHERE is_default`），语义是「恰好一个真」；
2. 接口上仍然用 `themeId`（路径 `:id`、请求体 `themeId`、响应 `themeId`）。

两件事都要收掉。收的方式不一样：前者**删**，后者**换**。

### 19.1 为什么删 `is_default`

「默认主题」原来只在两个地方起作用：

- 老地址 `/maps` 不知道去哪个世界时，落到它；
- 新建资源时作者没选主题，静默放进去。

§18 之后第一个场景已经由「记住的编码 → 列表第一个」接管（§18.8），第二个场景根本**不该被支持**：
静默把资源塞进某个主题，作者下一步就找不到它了 —— 这不是兜底，是把一个错误藏起来。

更要紧的是它和编码构成了**第二套身份**。同一个问题——「这是哪个主题」——有了两个答案来源：
`code`，和「它是不是那个默认的」。两个来源就会打架：默认主题被改名了怎么办、被删了怎么办、
库里出现两个 `true` 怎么办（旧代码干脆加了一条部分唯一索引来防，等于用数据库约束掩盖语义重复）。

删掉之后，`themes` 的排序回到 `id asc`（创建顺序）。「谁排第一」不再是数据库的语义，
只是展示的顺序 —— 想按名字排、按活跃度排，都是列表页的事。

### 19.2 为什么接口用 `code`

`code` 已经进了地址（§18），也进了资源包 manifest（§11）。它是**跨环境的稳定名字**：
本地库里 `hlm` 是 `id=2`，别人机器上可能是 `id=17`，导出的包里根本没有 id。

id 是库内主键，出不了这一层：

| 层 | 认什么 |
|---|---|
| URL / API / 前端类型 / 资源包 | `code` |
| 仓储层、`theme_id` 外键、bundle 组装 | `id` |

`Theme` 这个类型现在**根本没有 `id` 字段** —— 前端连拿都拿不到，也就不可能再误用。
这比「约定不要用 id」可靠：类型里没有的东西，编译期就写不出来。

### 19.3 一条链路：code 在哪儿变成 id

写入方向（入口解析）：

```ts
// service/themeService.ts
export async function filterThemeId(code?: string): Promise<number | undefined>  // 列表筛选，不传 = 全局
export async function requireThemeId(code: string): Promise<number>              // 写入，不存在 → 400
```

读取方向（把 `theme_id` 翻译回 `code`）用标量子查询，而不是在 service 里拼一张 `id → code` 的表：

```ts
// repository/mapRepository.ts
export const THEME_CODE = db.raw(
  '(SELECT t.code FROM themes t WHERE t.id = m.theme_id) AS theme_code',
);
```

选它的理由：**一次查询、一份真相**。拼表要多一次往返，还要维护「这张表什么时候过期」；
子查询让 `MapEntry` / `MapGameSummary` / `PublishedMapVersion` 全都白得一个 `themeCode`，
不用各自再问一次。

代价是有的：`.returning('*')` 带不出子查询列（Postgres 只回表里的列），所以
`createMap` / `duplicateMap` 改成「写完再读一次」。多一次查询，换来「所有读路径同一个形状」。

### 19.4 字段变更

| 位置 | 之前 | 现在 |
|---|---|---|
| `themes` 表 | `is_default boolean` + 部分唯一索引 | 已删（迁移 `20260101000038`） |
| `Theme`（shared） | `{ id, code, name, …, isDefault }` | `{ code, name, … }` |
| `ThemeOption` | `{ id, code, name }` | `{ code, name }` |
| `MapEntry` / `MapEntrySummary` / `PublishedMapVersion` | `themeId: number` | `themeCode: string` |
| `MapGameSummary` | `themeId: number` | `themeCode: string` |
| `ThemeDeploymentSummary` | `{ id, themeId, … }` | `{ id, themeCode, … }`（`id` 是部署行自己的） |
| 新建资源 / 地图 / 角色 | `themeId: number`（可省 → 落默认主题） | `themeCode: string`（**必填**） |
| 列表筛选 | `?themeId=2` | `?themeCode=hlm` |
| 主题路由 | `/api/themes/:id` | `/api/themes/:code` |
| 引用体检报告 | `issue.themeId` | `issue.themeCode` |

`useWorkspace()` 也跟着只剩一个 `themeCode`。上一版它同时给了 `themeId` 和 `code`（同一个东西
两个名字），调用方一定会各挑一个 —— 现在没有可挑的。

### 19.5 三处能感觉到的行为变化

1. **新建不带 `themeCode` → 400**。不再有「自动放进默认主题」。
2. **筛选编码不存在 → 400**，不是空列表。空列表会被读成「这个主题里没有资源」，
   而真相是「没有这个主题」—— 这两句话该长得不一样。
3. **`DELETE /api/themes/:code` 不再拒绝任何主题**。原来那条「默认主题不可删」的守卫随列一起没了；
   剩下的判断只有一条：主题里还有东西就说不清 —— 「主题下还有 49 个资源、8 张地图…」。

### 19.6 迁移

`20260101000038_v080_drop_theme_default.ts`（本地库已跑到 `batch 27`）：

```ts
up:   先 DROP INDEX themes_default_unique，再 DROP COLUMN is_default
down: 加回列（默认 false）→ 把 code='default' 那一行标 true → 重建部分唯一索引
```

`down` 那段是**为了迁移可逆**，不是为了让旧代码复活：回滚之后新代码（不认识 `is_default`）
仍能正常跑，列会一直躺着没人读。

### 19.7 顺手清掉的垃圾：78 个主题尸体

跑完迁移先做了一次体检，结果比预想的糟：

```
themes 总数: 81     未软删: 3
t-xxxxxxxx 夹具主题: 78     其它: 1:default  2:hlm  75:test-fixture
```

原因是一条早已存在的设计缺口：`DELETE /api/themes/:code` 是**软删**（一条 UPDATE），
而 `themes.code` 是**普通 UNIQUE**。软删的行还占着编码，行本身也永远不会消失；
测试夹具每跑一次新建一个 `t-<hex>` 主题、跑完软删 —— 于是每跑一次就留一具尸体。

三件事一起改：

| 改法 | 落点 |
|---|---|
| 夹具主题**固定编码**、幂等创建，不再每个文件造一个 | `test/helpers.ts` → `fixtureTheme()` / `FIXTURE_THEME_CODE` |
| 物理删除：按外键顺序把一个主题整个抬走 | `test/purge.ts` → `purgeTheme(code)`（games → deployments → puzzles → assets → characters → maps → themes，全部 RESTRICT，没有一处能靠 CASCADE） |
| 全局收尾：每个 `npm test` 跑完清一遍 | `test/globalSetup.ts` 的 `teardown()`（`vitest.config.ts` 的 `globalSetup`） |

跑完一轮之后：`themes` 只剩 `1:default`、`2:hlm`。这条清理不是「顺手」，它把
**测试不许污染库**变成了强制：以前靠每个 `afterAll` 自觉，现在收尾兜住。

资源包文件名带的是 `code`；`DELETE /api/themes/:code` 对非空主题说人话。

### 19.9 部署页：认不出主题的行不上屏

§19 之后 `games.themeCode` / `theme_deployments.themeCode` 是接口给的**唯一**归属信息，
部署页据此分组。但分组时留了一个兜底桶：认不出主题的行塞进「未归入主题」组。

这个桶要撤掉。它在两处会装上东西：

1. 主题被删掉之后留下的行（`DELETE /api/themes/:code` 拒绝非空主题，所以只在物理清理、
   迁移这类场景出现）；
2. **工作空间里看别的主题**：`scoped` 只有一个主题时，其余主题的关全部掉进这个桶。

第 2 条是日常会遇到的那个 —— 在 `/hlm/deployments` 里看到一堆叫「未归入主题」的关，
点开却是默认主题的内容。这一页是**工作空间视角**（§18），不属于任何工作空间的行
没有可回答的问题，摊在屏幕上只会让作者以为自己的关丢了。

改法两条：

| 位置 | 之前 | 现在 |
|---|---|---|
| 分组 | `byCode.get(code) ?? orphans` | `byCode.get(code)?.games.push(…)` —— 认不出就不进 |
| 组头 | `group.theme?.name ?? '未归入主题'`，导出按钮按 `theme ? … : null` 条件渲染 | `group.theme.name`，组头恒有导出按钮（`Group.theme` 从 `Theme \| null` 收成了 `Theme`） |
| 页头计数 | `共 ${games.length} 个游戏在线` | 各组之和 —— 藏起来的不算「在线」 |

顺带修了同一处视角漏洞：部署弹窗的版本下拉原来不分主题（`usePuzzles({ kind: 'version' })`），
在红楼梦里能选到默认主题的谜题。部署完它落回自己那个主题，作者在当前这屏看不到，
看起来像「部署失败了」。现在工作空间里带上 `themeCode`，下拉只列这个主题的版本。

### 19.10 未做

1. **`theme_id` 换成 `theme_code` 做外键**：不做。编码会变（改名场景至今没出现，但契约上它可变），
   外键要的是永不改的东西。分层（对外编码 / 对内主键）比统一更省事。
2. **软删 + UNIQUE 这个组合本身**：`maps` / `puzzles` / `assets` 都有同样的问题（软删行占着
   `(theme_id, code)`）。现在只堵了主题这一处 —— 因为只有它是唯一被测试反复创建的东西。
   真要收，就得把唯一约束改成部分索引（`WHERE deleted_at IS NULL`），那是另一场迁移。
3. **主题列表的排序**：现在是 `id asc`。按名字 / 按最近编辑排，得先有人真的觉得它碍事。
