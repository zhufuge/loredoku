## 2. 方案

### 2.1 三态而非两态

| 模型 | 行为 | 问题 |
|---|---|---|
| 二态（浅 / 深） | 首次访问按系统初始化，之后**钉死** | 用户在操作系统里切外观，页面不再跟随——「默认按系统」只跟了第一次 |
| **三态（跟随系统 / 浅色 / 深色）** | `system` 是一个**可持续的状态**，OS 改变时实时跟随；手动选定后不被 OS 推翻 | 循环按钮必然有一次「逻辑变了但视觉没变」的转移（见 R10） |

选三态。用户说的「默认按照系统」不是「首次读一次系统」，而是「不选的时候一直跟着系统」。

### 2.2 交互：一个图标按钮

- 单击循环：`system → light → dark → system`。
- 图标表示**当前模式**（不是「点完会变成什么」）：`Monitor` / `Sun` / `Moon`。这样扫一眼就知道自己是「跟着系统」还是「钉死了」——否则用户会在 OS 切外观时怀疑页面坏了。
- `title` 与 `aria-label` 同步写成「主题：跟随系统（点击切换）」。

### 2.3 按钮放在哪

路由表里有 **5 个独立全屏页面**不在 `AppShell` 下（两个编辑器、两个只读预览、游戏首页与游戏页）。所以需要 6 个挂载点覆盖全部路由：

| 挂载点 | 覆盖的路由 | 位置 |
|---|---|---|
| `AppShell` 头部 | `/maps` `/items` `/characters` `/puzzles` | 「游戏」按钮左侧 |
| `GamesPage` | `/play` | 右上角「进入工坊」左侧 |
| `GamePage` | `/play/:slug` | 左栏品牌行右侧 |
| `EditorToolbar` | `/editor/:id`、`/puzzles/:id/edit` | 右侧第一组（与文档操作、保存/发布用分隔线断开） |
| `MapVersionViewPage` | `/maps/:projectId/:versionNo/view` | header 视图控件之后 |
| `PuzzleViewPage` | `/puzzles/:id/view` | header 视图控件之后 |

### 2.4 技术上怎么落地

真源是 **DOM 的 `.dark` 类 + `localStorage`**，React 只是订阅者：

```
index.html 内联脚本 ──┐（React 挂载前上色，防白闪）
localStorage ─────────┼──> lib/theme.ts（applyTheme：class + color-scheme）
matchMedia ───────────┘         │
                                └──> useTheme（useSyncExternalStore）──> 6 个按钮 + Toaster
```

- `lib/theme.ts`：三态解析、持久化、系统监听、跨标签页同步，**没有任何 React**。
- `hooks/useTheme.ts`：两个 `useSyncExternalStore` 订阅同一份外部状态（`mode` 与 `systemDark` 分开订阅 —— 只订阅 `mode` 的话，系统切深色时图标不会变）。
- **上色在 store 层同步做**（`setThemeMode` 里直接 `applyTheme`），不放在 `useEffect` 里：点击到上色之间没有空档，也不受组件是否挂载影响。`useTheme` 里那个 effect 只是兜底。

### 2.5 一条边界：画布是内容，不随主题变

地图背景色、物品/角色色块与图片、区域填充、参与者主题色、游戏标记的 `#000000` 描边 —— 这些都是**作者的作品数据**，必须与作者所见一致。主题只改「外壳」：页面底色、面板、边框、文字、工具条、徽标。

所以深色下会出现「深色界面 + 浅色画布」的组合，这是正确结果，不是漏改（R6）。

## 4. 深色适配：实际要改的比预想少

shadcn 的基础设施其实早就就位，这是本版能只改 3 类地方的前提：

| 现状 | 实测 |
|---|---|
| `tailwind.config.ts` | 已有 `darkMode: ['class']` |
| `index.css` | 已有完整的 `.dark` 变量组（30 个 HSL 变量） |
| 语义 token 覆盖率 | `bg-background` / `text-muted-foreground` / `border-border` 等已贯穿全站 |
| `bg-white` | **3 处**（三根浮动工具条） |
| `bg-slate-* / gray-* / zinc-*` | **0 处** |
| `text-black` / `text-white` | **0 处**（唯一命中是一句注释） |
| 六位十六进制色 | 22 处，**全部是内容色**（地图样式默认值、区域色板、参与者主题色、游戏标记描边） |
| `dark:` 变体 | 本版之前 **0 处** |
| `.dark` 的 `--primary-foreground` | 沿用 shadcn 默认的深蓝黑 `#0f172a`（浅色分支是 `#f8fafc`，两种模式文案不一致） |

改动只有四类：

1. **3 处 `bg-white` → `bg-background`**：编辑器/谜题底部工具条浮在画布上，深色下会变成一块白疤。
2. **品牌 logo 反色**：资产是黑（`#000000`）+ 深红（`#5C2223`）双色墨迹，深色页面几乎看不见。用 `filter: invert(1) hue-rotate(180deg)` —— 黑色翻成白色，深红转一圈色相后变成亮红而不是青色（R7）。
3. **Toast 跟随主题**：sonner 自己的 `theme` 默认是 `system`，手动选了深色而系统是浅色时会弹白 toast。
4. **主按钮前景色统一为浅色**：`.dark` 的 `--primary-foreground` 从 `222.2 47.4% 11.2%`（深蓝黑）改成与浅色分支相同的 `210 40% 98%`，即**蓝底白字贯穿两种模式**（R13）。`--primary-foreground` 全仓只有 `button.tsx` 的 `default` 变体一个消费者，改动无连带。

第 4 类不是纯审美，三态对比度算下来深字是单调变差的：

| 状态 | 底色 | 深字 | 白字 |
|---|---|---|---|
| 常态 `bg-primary` | `#3b82f6` | 4.85:1 | 3.52:1 |
| 悬停 `bg-primary/90`（叠 10% 深底） | `#3576e0` | **4.10:1** | 4.16:1 |
| 禁用 `disabled:opacity-50` | `#1f4587` | **1.92:1（等于看不见）** | 8.88:1 |

深字只在常态那一格领先，一进悬停就跌到 4.10，禁用态直接掉到 1.92 —— 截图里禁用按钮的文字几乎消失。白字反向单调上升。用白字不是「更合眼缘」，是唯一在全部交互态都保持可读的选择。

![深色下主按钮两种前景色对比](assets/v0.5.7-primary-foreground.png)

（上排为改后的浅色字，下排为改前的深蓝黑字；中列为 `hover:bg-primary/90`，右列为 `disabled:opacity-50`。）

## 5. 首屏防闪与 `color-scheme`

`index.html` 在 `<div id="root">` 之前插入一段同步脚本：读 `localStorage`，必要时给 `<html>` 加 `.dark`，并写 `colorScheme`。这样深色用户不会在 bundle 下载期间看到一帧白屏。

三处细节：

- `<meta name="color-scheme" content="light dark">` —— 让浏览器从第一帧就知道两种方案都支持，原生滚动条不会先画白。
- 脚本里 `?` 的兜底规则必须和 `resolveTheme` 同义：**只有明确存了 `light` 才是浅色**，其余（无值、非法值、`system`）都走系统。`theme.test.ts` 断言这条（R4）。
- `document.documentElement.style.colorScheme = resolved`（JS 侧）与 meta（HTML 侧）双保险：前者跟随手动切换，后者覆盖首帧。

## 8. 实现期裁定

| # | 问题 | 结论 |
|---|---|---|
| R1 | 二态还是三态？ | **三态**。二态在首次访问后就把主题钉死了，「跟随系统」变成一次性行为（§2.1） |
| R2 | 用 zustand 还是 `useSyncExternalStore`？ | **`useSyncExternalStore`**。真源在 DOM + localStorage，不在 React 状态树里；`useSyncExternalStore` 天生就是订阅外部可变源的，无需新建 store 文件、也无需手动同步「按钮 → store → DOM」三段 |
| R3 | `applyTheme` 放在 effect 还是 store 层？ | **store 层同步执行**，effect 只兜底。放 effect 里会有一帧延迟，且组件未挂载时主题不会应用（首屏就靠内联脚本，逻辑更统一） |
| R4 | 内联脚本与 `lib/theme.ts` 是两份实现，如何防漂移？ | **源码断言**。`theme.test.ts` 读 `index.html`，钉住三件事：存储键相同、兜底规则是「非 `light` 即跟随系统」、脚本确实写 `class` 与 `colorScheme`。另加一条「读到了 index.html」以防 glob 失配导致断言恒真 |
| R5 | 为什么必须设 `color-scheme`？ | 只加 `.dark` 类只改 CSS 变量，**滚动条、`<input>`、日期选择器这些原生控件仍按浅色绘制** —— 深色页面里拖出一条亮白滚动条。`color-scheme: dark` 才让浏览器把原生 UI 也切过去 |
| R6 | 深色化范围到哪？ | **只到「外壳」**。画布（地图背景、物品、区域、参与者色、游戏标记）是作者的作品数据，跨端必须一致，不参与主题（§2.5） |
| R7 | logo 怎么处理？做一个浅色版 SVG 吗？ | **CSS filter**：`invert(1) hue-rotate(180deg)`。资产是黑 + 深红双色，纯 `invert` 会把深红变青；转 180° 色相能还原成亮红。省一个资产、也不会有两份文件不同步的问题 |
| R8 | 主题常量放 shared 吗？ | **不放**。它只服务 web 的本地存储与 DOM，跨端没有消费者；shared 是跨包契约，塞进去反而是噪音 |
| R9 | 按钮尺寸怎么定？ | 组件默认用 `size="icon"`（40px），让调用方按上下文覆盖：`AppShell` / `GamesPage` 传 `h-9 w-9` 对齐 `sm` 按钮，`GamePage` 左栏与两个 header 用默认 40px 与既有图标按钮齐平 |
| R10 | 循环按钮必然有一次「逻辑变了但视觉没变」（系统是浅色时 `system → light`），要不要改成交互更强的方案？ | **保留循环**。三个逻辑模式、两个视觉结果，任何三态循环都至少有一次这种转移；用图标（Monitor→Sun）与 tooltip 提供即时反馈，比引入下拉菜单（多一次点击）更划算 |
| R11 | 加切换动画吗？ | **不加**。全站同时换色，若给 `color` / `background-color` 加 transition 会在大面积元素上抖动，反而廉价；瞬时切换是系统级主题切换的常见做法 |
| R12 | `system` 模式下用户手动改 OS 外观，会不会覆盖手动选择？ | **不会**。`handleSystemChange` 先读存储，只有 `system` 才跟随；手选的 `light` / `dark` 不被 OS 推翻（`ThemeToggle.test.tsx` 有专门用例） |
| R13 | 深色下蓝底主按钮该用深字还是浅字？ | **浅字**（与浅色模式同值 `210 40% 98%`）。深字常态 4.85:1 看似比白字 3.52:1 好，但 `hover:bg-primary/90` 把底色压暗一档后深字跌到 4.10、`disabled:opacity-50` 时跌到 1.92（实测截图里文字已经消失）；白字在悬停/禁用反而升到 4.16 / 8.88。**交互态的一致性比常态那一格的名义对比度重要**。代价：常态白字 3.52:1 未达 WCAG AA 的 4.5（只需 3.0 的大字门槛是过的），若日后要严格达标，把 `.dark` 的 `--primary` 亮度从 59.8% 压到约 52% 即可（`#156af4` + 白字 = 4.77），但那会连带影响 `text-primary` 在深底上的可读性，不在本版处理 |

### 10.2 使用方式

- 什么都不做：跟随系统。
