## 0. 一句话

列表第一次有了「作者说了算的顺序」，而不只是「最近部署的在前」；概览页则把
最后两行「这不是事实、是别处的替代品」删掉，剩下的四行正好回答「这个空间是什么」。

## 1. `games.sort_weight`：展示顺序

### 1.1 约定

| 项 | 值 |
|---|---|
| 类型 | `integer not null default 0` |
| 方向 | **升序** —— 数字小的排前面 |
| 并列 | 按访问路径（`slug`）升序，一个确定的兜底 |
| 区间 | `-999 … 999`（`GAME_SORT_WEIGHT_MIN/MAX`） |
| 迁移 | `20260101000039_v083_game_sort_weight.ts`（加列 + `(sort_weight, slug)` 索引） |

全部为 `0` 的存量数据 = 按访问路径排。这是刻意的：默认值不该是一种「顺序观点」，
它只该表示「还没排」。

### 1.2 为什么不复用 `sort_order`

`sort_order` 在本仓的既有语义是「同一容器内的序号」（资源形态、主题部署项），
由系统按插入位置维护；这一列是**作者手填的偏好**。同名的两列会被下一次改动
混用 —— 所以宁可多一个名字，也不让「谁在维护它」这件事含糊。

### 1.3 服务端

| 位置 | 改动 |
|---|---|
| `gameRepository.listGames` | `ORDER BY sort_weight ASC, slug ASC`（原来 `created_at DESC`） |
| `gameRepository.listGameRowsByTheme` | 同上 —— 资源包里的顺序与界面上一致 |
| `gameRepository.upsertGame` | 写入 `sort_weight`；**不传时沿用上一行** |
| `gameService.deployGame` | 透传 `body.sortWeight` |
| `gameDeploySchema` | `sortWeight` **不给 `.default()`** |

`upsertGame` 是 delete-then-insert（行换新 id），数据库默认值救不了「重新部署之后
顺序归零」。所以那个 `previous?.sort_weight ?? 0` 是这一版最不能省的一行：作者排好
的先后，会在某次「只想换个封面」之后悄悄散掉，而且没有任何提示。

`gameDeploySchema` 同理：一个 `.default(0)` 会把「这次没提」与「就排 0」抹平成
同一句话。缺省 → `undefined` → 仓储沿用；显式 `0` → 就排 0。

### 1.4 部署弹窗的「顺序」字段

放在难度之后（它是「这次部署」的第五项，不是「这个谜题」的属性）。三种提交语义：

```
空     → 不发这个键（服务端沿用上一行）
-5     → 就排 -5
1000   → 拦住，红字说清区间（不是静默改成 0）
```

输入框存的是**字符串**：清空再重打的中间状态必须存在，用 `number` 承载的话，
清空那一瞬就已经是 0 了。重新部署时回填那条部署自己的权重 —— 否则每次改封面
都会把它归零。

### 1.5 实测

部署三条 `ord-b(5) / ord-a(5) / ord-z(-1)`（故意乱序部署），`GET /api/games` 里
这三条的顺序是 `z / a / b` —— 权重优先、同权重按路径。再把红楼梦的「勘破三春」
改成 `-5`，部署页第一行立刻变成它：

```
puzzle-hlm-kanposanchun-hard  -5   ← 权重最小
puzzle-hlm-jiaoxiake-medium    0
puzzle-hlm-kanwairen-medium    0
...
```

同一主题其余七关权重都是 0，于是按 slug 字母序 —— 与「按部署时间倒序」是两种
完全不同的顺序，说明这条 SQL 真的生效了（而不是被原来的排序蒙对）。

### 1.6 测试

`packages/server/test/api.test.ts` +3：两级排序、重新部署不带权重时保留旧值、
越界（`1000 / -1000 / 1.5`）被拒。`packages/shared/src/schemas/game.test.ts` +4：
缺省不落 0、显式 0 与缺省不同、接受 -999/999、拒绝越界与非整数。
`GameDeployDialog.test.tsx` +5：回填、默认 0、清空不发键、填了就发、越界拦住不发请求。

## 2. 概览：第五格「部署」

`ThemeCounts.games` 早就在（`countsByTheme` 顺着 `puzzles.theme_id` 数活跃 game 行），
只是没人展示。现在它是第五张计数卡，取 `counts.games`：

| 格 | 数的东西 |
|---|---|
| 资源 / 地图 / 角色 / 谜题 | 这个空间**有**什么 |
| 部署 | 有几关**已经出门**了 |

它不是第五个「内容模块」—— 前四格数的是「这个空间里有什么」，第五格数的是
「有几关已经出门」，而 `lib/workspace.ts` 里的 `CONTENT_MODULES`（原本只服务这四格）
在这一版被删掉了：卡片集合不再等于内容模块集合，那张卡片表自己就写着顺序与标签，
常量只剩下「说一句别处已经说过的话」。`WORKSHOP_MODULES` 保留 —— 它才是顶栏的真相。

`COUNT_LINKS` 因此显式带两个键：`module`（去哪）与 `field`（数哪个计数）。这一版
之前它们是同一个值，所以只写了一个；`deployments → games` 是第一个不同名的组合
（部署计数的字段叫 `games`，因为数的是 game 行）。

布局：`lg:grid-cols-5`。实测 1440 下每格 **237px**、1024 下 **186px**，仍是「24px
图标 + 数字 + 箭头」一行放得下，没有截断。设计系统里原来那句「四格 ≤4 项，正好
卡在工作记忆上限；第五格要另起一块」随之作废 —— 见 §4。

## 3. 概览：信息卡只留四行

| 之前 | 现在 |
|---|---|
| 编码 / 识别色 / **缺省风格** / **上线** | 名称 / 编码 / 描述 / 识别色 |

删掉的两行各有各的问题：

- **缺省风格**：它不是一个事实，而是一条**操作指引**（「去地图的『基本信息』里用
  『设为主题风格』写入」）。读者来这一页是确认「这里是什么」，不是来学一套路径。
- **上线**：第五格已经在数部署了。同一页里「8 个部署」和「8 关在线」是同一个数
  说了两遍 —— 而且后者的合辑路径还带着一串 `/play/theme/...`。

顺带把页头的副标题去掉了：`PageHeader.description` 改成可选。因为「描述」现在是
信息卡里的第三行，页头再抄一遍就是 40px 之内的重复。**这一处是本次唯一动了共享
组件的地方** —— 其它五个模块页的页头不受影响（它们都传了 `description`）。

实测（1440 浅 / 深、1024 浅）：四行**全部 40px**，页头只剩余标题与「上线 / ⋯」。

## 4. 设计系统同步

`docs/design-system.md` 三处：

1. §3 页面骨架：`四格计数入口 ──16px── 事实行` → `五格计数入口 ──16px── 信息卡`；
2. §3.11 表格：「概览 · 四格计数」→「概览 · 五格计数」（含 237 / 186px 两个实测宽度）；
3. §3.11 表格：「概览 · 事实行」→「概览 · 信息卡」，写明四行固定、不许塞操作指引。

## 6. 没有做的

1. **部署行上不显示权重**。列表按它排好了，但行里没有一个「-5」这样的数字 ——
   想改只能重新打开那条部署的弹窗。加了就要回答「显示权重还是显示名次」：
   权重能解释「为什么它在这」，名次只解释「它在这」，而两者在有合辑、有并列时
   不是一回事。等真有人问「为什么这关排在第二」再加。
2. **合辑内部仍然是 `sort_order`**（`theme_deployment_puzzles`），没有换成
   `sort_weight`。合辑的排序是**部署目录**的事，与「游戏列表怎么排」不是同一层，
   这一版不动它。
3. **顺序没有独立入口**。改顺序 = 重新部署一次（覆盖同一条行，封面与路径都会带
   过去）。真要做拖拽排序，得先有一个 `PATCH /api/games/:id` 之类的写口。

## 7. 概览页的动作平铺

用户的原话是「上线按钮去掉，导出资源包去掉，三点不要，按钮平铺」。三处动作各有去处：

| 之前 | 现在 |
|---|---|
| 页头「上线」（一键整主题部署） | **删掉**。它是「把东西发出去」，属于部署页；留在这里时，同一页还要再解释一次 `/play/theme/...` |
| `⋯ → 导出资源包` | **删掉**。导出清单要的是「这个主题全部在线关」，而部署页本来就握着那份数据（v0.8.2 已把它挪到那里） |
| `⋯ → 编辑主题信息 / 删除主题` | 平铺成两个按钮：`outline` 编辑信息 + `ghost` 删除主题 |

结果是页头只有两个动作，`ThemeActionsMenu` 整个文件删掉。判断标准写在
`docs/design-system.md` §3.11：**动作 ≤3 个就平铺；`⋯` 是 ≥4 个动作时才划算的收纳。**

`useDeployTheme` 与 `POST /api/themes/:code/deploy` 保留（服务端能力没变，部署页
的合辑操作仍走同一条链路），只是概览页不再有它的入口 —— 见 §12。

## 8. 统一取色

### 8.1 之前是三种长相

| 位置 | 有什么 | 缺什么 |
|---|---|---|
| 地图信息抽屉、区域样式 | 色块 + hex 输入 | —— |
| 角色 / 资源的纯色块 | 只有色块，右边一串**只读**的 hex 文本 | 没有可编辑的 hex |
| 谜题联动主题色 | 色块 + hex | 得手打 hex |
| 地图编辑器「主题色」弹窗 | 一整块 15 色板 + 色块 + hex | 色板是唯一入口，改一个非预设色很绕 |
| 概览页识别色 | 色块 + hex | —— |

同一件事（挑一个颜色）在五个地方有至少三套长相，作者每换一个页面都要重新学一遍。

### 8.2 现在只有 `ColorField`

```
[ 色块（原生取色器） ] [ #RRGGBB 输入框 ]
```

- 两个零件，顺序固定：先色块（既是预览也是取色器），再 hex；
- hex 是草稿：一边打字一边把非法中间态留在框里（`#f`、`#ff00`），失焦 / 回车才提交，
  不合法就回滚。取色器即时生效。

改到的地方：`AppearanceField`、`PuzzleInfoDrawer` 的联动主题色、`MapInfoDrawer`
（所有 `ColorField` 处自动升级）、`ThemeColorDialog`、概览页的识别色与风格表单。

**唯一保留裸 `ColorInput` 的是「鼠标光标框 · 阴影环」**：它允许 `rgba()`（带透明度），
取色器给不出 alpha，硬塞进去会把作者填的 `rgba(0,0,0,0.15)` 抹成 `#000000`。

### 8.3 调色板整体去掉（本节收尾时按用户要求改的）

§8.2 的第一版还留着一个「调色板」开关，展开是 `THEME_COLOR_PALETTE` 那 15 颗色点。
用户随后说「不提供调色板功能，使用的地方，都去掉」，于是这一版把它**整块删掉**，
不是默认收起：

| 删了什么 | 在哪 |
|---|---|
| `ColorPalette` 组件 | `components/ui/color-palette.tsx`（整个文件） |
| `ColorField` 的开关、展开区、`paletteDefaultOpen` | `components/ui/color-input.tsx` |
| `THEME_COLOR_PALETTE` 常量（15 颗）与它的两条断言 | `shared/constants.ts`、`participant.test.ts` |
| 主题色弹窗里的 `paletteDefaultOpen` | `components/map-editor/ThemeColorDialog.tsx` |

理由：一份固定色板能选的永远只有那十几种，而「这个空间到底用什么颜色」本来就该由
作者决定 —— 原生取色器给出的色域比任何预设都宽，预设只会把所有人的界面推向同一套
配色。收起来也做不到「不提供」：只要开关在，界面上就还写着「调色板」这三个字。

**代价**：想快速挑一个「差不多」的颜色，现在要自己调。所以 hex 输入框留在手边 ——
手上有色值时打字永远比拖取色器快，这也是它不能被省掉的原因。

## 9. 缺省风格：从一句指引变成一张清单

v0.8.2 之前概览页有一行「缺省风格」，值是一句**操作指引**（「去地图的『基本信息』里用
『设为主题风格』写入」）。那一行在 v0.8.3 前半段被删掉（§3），现在换成一张真正的清单
加一个表单 —— 删除时删掉的是「指引」，不是「配置」。

### 9.1 清单

四组（网格 / 边框 / 标签 / 光标）、27 项，`sm:grid-cols-2 xl:grid-cols-3`，每项一行
「名字 —— 值」。颜色给 10px 色块 + hex，其余用等宽字（`1.5px` / `自适应` / 字体名）。

**标签与顺序不新写一份**：来自 `shared/mapStyleDiff.ts` 的 `MAP_STYLE_FIELDS`（差异弹窗
已经在用它）。这一版只把它 `export` 出来，web 侧补一张「怎么写回去」的表
（`lib/themeStyleFields.ts`：控件类型 + 区间），两者按 `key` 拼成
`THEME_STYLE_FIELDS`。少写一份标签表，就少一处「加了字段但没加标签」的漂移。

主题**没有**配过缺省风格时，清单显示 `DEFAULT_MAP_STYLE` —— 那正是新建地图会拿到的
一份，清单因此不会空着，也不会撒谎。

### 9.2 表单

- 同一个弹窗里按四组分段，`max-h-[64vh]` 滚动；数字用 `NumberField`（带 px 后缀），
  颜色用 `ColorField`，字体名与阴影环用文本框；
- 写回是**整份草稿**：`data = { ...theme.data, style }`，取消则什么都不发生；
- 左下角「恢复默认」= 把草稿换回 `DEFAULT_MAP_STYLE`（不直接落库，仍要按保存）；
- **方格大小**可以回到 `null`（自适应），右侧一个环形箭头按钮；别的字段不可空。

### 9.3 写回为什么按路径而不是手写展开

`writeStyleValue(style, 'regionLabel.hoverStrokeWidth', 6)` —— 深拷贝 + 按 `key.split('.')`
写。27 个字段手写展开意味着每处都要把三层对象都铺开，漏一层就抹掉兄弟字段；而路径就是
`MAP_STYLE_FIELDS` 里的 key，天然对得上。

## 10. 难度分级不再只有五档

### 10.1 数据

`themes.data.difficultyLevels?: Array<{ key, label }>`（缺省 = 内置五档，见
`shared/difficulty.ts` 的 `DEFAULT_DIFFICULTY_TIERS`）。

- **整份替换**，不是追加：追加语义会让作者删不掉「专家」这一档，而删掉正是最常见的诉求；
- 至少一档、最多 12 档、`key` 唯一（`.refine` 会说出重复的是哪一个）；
- **不存颜色**：徽章底色按这一档在列表里的**相对位置**落到内置那条五档热力坡上
  （三档 = 竹青 / 赭黄 / 绛，八档 = 相邻两档共用一格）。让作者选色的话，浅色下挑的淡色
  在深色界面里又会变成一块亮补丁 —— v0.7.8 已经为此把五个 hex 换成 CSS 变量。

### 10.2 界面

- 概览页一张清单卡：一排徽章（就是部署页 / 游戏卡上那一枚，所见即所得），
  「编辑难度分级」打开表单；
- 表单：名字可改（`maxLength 12`）、**标识不可改**（它落进 `games.difficulty`，改一次
  库里那些关就跟新名字对不上，而这里没有任何东西能替它们改回来）、上下移动、删除、
  添加一档（标识由 `nextDifficultyKey` 生成 `tier-1`、`tier-2` —— 中文名 slug 化只剩空串）；
- 「恢复内置五档」= **把键删掉**，回到「没配过」。写一份和内置一模一样的数组不行：
  以后内置改了，这类主题不会跟着改。

### 10.3 服务端：难度列从枚举放开

`games.difficulty` 上挂着 v0.4.0 的 `games_difficulty_check`（`IN ('veryEasy' … 'expert')`）。
新增第六档会撞在约束上，得到一个 500 —— 而界面上它明明保存成功了。所以：

| 迁移 | 做什么 |
|---|---|
| `20260101000040_v083_difficulty_tiers.ts` `up` | `DROP CONSTRAINT games_difficulty_check`；列宽 16 → 32 |
| `down` | 先把不在五档里的值改成 `medium`，再收窄列、装回约束（**会改写数据**，注释里写明） |

值域搬到应用层，分两层：

1. `gameDeploySchema.difficulty` 只把守**形状**（`GAME_DIFFICULTY_KEY_PATTERN`：
   字母开头 + 字母 / 数字 / 连字符，≤32）。大小写都收 —— 内置五档是 v0.4 定下的
   camelCase，收紧成纯小写就得改历史数据与旧包的 manifest；
2. `gameService.resolveDifficulty` 拿**谜题所属主题**去核对，并按主题补默认档。

**schema 里不给 `.default('medium')`**：缺省档取决于主题（内置五档是 `medium`，自定义
分级是正中间那一档）。写死 `medium` 的话，一个只有「热身 / 地狱」的主题连部署都做不了
—— 而作者根本没提难度。

### 10.4 展示

新增 `components/game/DifficultyBadge.tsx` + `shared/difficulty.ts` 的 `difficultyBadge()`：
一个标识 → 三个值（字、底、前景）。`GameCard`、`DeploymentsPage`、`ExportBundleDialog`、
部署弹窗四处原来各自 `GAME_DIFFICULTY_COLORS[key]`（四份同样的三行，四份都假设只有五个键），
现在都走它：

- 标识不在当前分级里（档被删了）→ 中性灰 + 原样显示标识，不报错；
- 部署弹窗的选项 = 主题的这几档；当前这条部署的难度若已不在分级里，**补在最后**
  —— 否则打开弹窗时没有任何一个按钮被选中，作者会以为这关没有难度；
- 徽章名从英文（`Very Easy` / `Expert`）换成中文（`极简` / `专家`）：界面其余部分都是
  中文，而分级现在由作者命名，两套语言并排会更怪。

### 10.5 修正：「改了名字保存不生效」

**症状**：把第一档「极简」改叫「入门」，点保存、提示「已保存」，清单上还是「极简」。

**根因**在 `DifficultyTiersDialog.submit()` 的一道判断：

```ts
// 第一版
const isBuiltIn =
  tiers.length === DEFAULT_DIFFICULTY_TIERS.length &&
  tiers.every((tier, index) => tier.key === DEFAULT_DIFFICULTY_TIERS[index]?.key);
if (isBuiltIn) delete data['difficultyLevels'];
```

这段的**本意**是「和内置一模一样 = 没配过，就别存一份快照」。但它只比 `key`：
改名字不动 `key`，于是「改名后的五档」仍被判成「还是内置五档」，`difficultyLevels`
被删掉，落库的 `data` 里根本没有这次编辑 —— 而名字恰恰是这一屏唯一能自定义的东西
（`key` 只读、颜色不存）。网络面板里看得很清楚：PATCH 的 body 只有
`{accent, version}`，一个字节都没提到分级。

**修法**：连 `label` 一起比。key 与名字都对得上，才算「就是内置那五档」。

```ts
tiers.every((tier, index) => {
  const builtin = DEFAULT_DIFFICULTY_TIERS[index];
  return builtin !== undefined && tier.key === builtin.key && tier.label === builtin.label;
});
```

顺带修了同一类「静默」：`useUpdateTheme` 原来**没有 `onError`**，400 的表现是
「点了保存、弹窗不关、什么提示都没有」，作者会以为自己没点上，再点两次然后报
「不生效」。现在失败会弹 toast，三个 `submit()` 也各自 `catch` 住 —— 失败**不关窗**，
草稿还在，改一处再点保存即可，而不是从头再来。

回归测试两条（`ThemeOverviewPage.test.tsx`）：只改名要写回、什么都没改不带该键。

## 13. 修 bug：删掉主题后「返回工坊」落到不存在的编码

### 13.1 症状

在某个主题里删掉它自己（概览页 →「删除主题」→ 确认），会落到 `/settings/themes`。
这时点右上角「返回工坊」，得到的是：

> 没有编码是 `tmp-del` 的主题。

再点那一页的「回到工坊」，还是这一页 —— 因为两个按钮拼的是同一个地址。

### 13.2 根因

`workshopPath('overview')` 在**没有显式给编码**时，读的是 `localStorage` 里
`loredoku.lastTheme`（「上一次在哪个工作空间」）。而删除这条链路没有人去清它：

1. `WorkspaceLayout` 在主题解析成功时写这个键 —— 删之前那一刻刚写过；
2. `useDeleteTheme` 只失效了主题列表，**没碰记忆**；
3. 系统配置页正是删完落脚的地方，它的「返回工坊」用的就是 `workshopPath`。

于是记忆里留着一个已经不存在的编码，两个按钮都把它拼进地址。`MissingWorkspace`
的「回到工坊」同样用 `workshopPath` —— 那一页因此成了自指的死循环。

### 13.3 改法（两处，各管一层）

| 层 | 改动 | 为什么在这一层 |
|---|---|---|
| 数据 | `lib/workspace.ts` 新增 `forgetThemeCode(code)`；`useDeleteTheme` 的 `onSuccess` 调它 | 删除是**唯一**会让记忆失效的动作，写在 mutation 里，将来多一个删除入口也自动生效。只删匹配的那一个：多标签页里开着 B 时，删 A 不该把 B 的记忆也抹掉 |
| 导航 | 「返回工坊」（配置页外壳）与「回到工坊」（`MissingWorkspace`）都改指 `/` | `/` 是 `ThemeEntryRedirect`：它把记住的编码对着**现有主题列表**验一遍，失效就落到第一间，一间都没有才去配置页。判断只有那一处，按钮只负责说「回去」 |

第二条是兜底：就算记忆因为别的原因失效（另一个标签页删的、接口换了、手改过
`localStorage`），按钮也不会把人送进错误页。第一条让**正常路径**根本不需要兜底 ——
删完再点，记忆已经是空的，直接就落在还开着的工坊上。

`workshopPath` 本身没改：它在工作空间内部（404 页、编辑器返回、谜题空态）调用时，
那里的编码是**上下文给的**，比 localStorage 更可信。

### 13.4 验证

真实浏览器走了一遍（headless Chrome + CDP）：

| 场景 | 结果 |
|---|---|
| 进 `tmp-del` 的概览 → 删掉它 → 点「返回工坊」 | `/settings/themes` → `/default/overview`（第一间），记忆 `tmp-del` 已被清空 |
| 记忆里是别的已删编码（模拟另一标签页删的）→ 配置页点「返回工坊」 | `/default/overview`，不经过错误页 |
| 手输 `/gone-xyz/overview` 进错误页 → 点「回到工坊」 | `/default/overview`，不再自指 |

`href` 断言 2 条），web **1047 / 87**；`typecheck`、`build` 全绿。验证用的临时主题

## 14. 新建主题：名称不再带动编码

### 14.1 之前

编码框在作者打字时**自己长出内容**：`derivedCode` 把名称小写化、空格换连字符，
`codeTouched` 标记「作者是否亲手改过」，没改过就显示推导值。

### 14.2 为什么要拆开

1. **只在一半情况下成立** —— 中文名推出来是空串。于是同一个输入框，英文名会自己
   填上，中文名空着，作者以为「有时候能自动填」。
2. **名字与编码本来就不是一件事** —— 名字给读者看，编码进地址与资源包。绑在一起
   等于建议作者用「名字的转写」当编码，而编码创建后**不可改**；改名字时作者会以为
   编码也跟着变了。
3. 推导只在**首次**生效：`codeTouched` 一旦变 true 就再也不跟名字了 —— 这层状态机
   本身就说明「跟着走」是个临时补丁，不是规则。

### 14.3 现在

| 字段 | 行为 |
|---|---|
| 名称 | 随便写，中英文都行，不影响编码 |
| 编码 | 作者自己填。规则写在**占位符里**：「小写字母、数字、下划线或连字符，创建后不可改」，框下不再单挂一行说明，也不给例子 |
| 「创建」 | 两个都填了才可用 —— 编码是**必填**，不是「有默认值」 |

`codeTouched` 与 `derivedCode` 一起删掉，`submit()` 直接用 `code.trim()`。

说明文字的位置换过一次：先是框下一行「进地址与资源包：…」的段落，读起来像在解释
它「进哪儿」，而那正是作者此刻不关心的；后来改成把**限制**塞进占位符、删掉段落 ——
空框的时候看到的就是能填什么，而不是一句介绍。例子（`hlm`、`tang-chao`）一并去掉：
作者照着抄一个跟自己的题材无关的词，比空着更糟。

保留字（`settings`、`play` …）因此不再提前说，改由服务端的报错兜住 ——
`「settings」是系统页面占用的路径，换一个编码`，那句话本来就带着被占用的词。

### 14.4 验证

浏览器里点开弹窗实测：输入 `hongloumeng` → 编码框仍是空的（占位符还在）、「创建」
灰着；改成 `红楼梦` 也一样；只有在编码框里写进 `hlm` 之后「创建」才可用。

占位符那句 22 个字在没有头 Chrome 里量：文本 308px、输入框可用宽度 372px
（`max-w-md` 弹窗、14px 字号），占 **83%**，整句显示完不截断 —— 再长一个分句就会
被切掉，所以保留字那句没有塞进来。（占位符的字体后来单独改正文字体，宽度仍是
308px，见 §14.5。）

测试 +4（`ThemesPage.test.tsx` 新建主题一组：英文名不带、中文名不带、编码必填、
提交的是手写的编码），web **1051 / 87**；`typecheck`、`build` 全绿。

### 14.5 占位符的字体

那句话换上之后，编码框里的字和下面「可选」看着不是一种字。

原因是等宽挂得太宽：`className="font-mono"` 落在 `<input>` **元素**上，而
`::placeholder` 是它的伪元素、字体从元素继承 —— 无害时没人注意，但占位符里放了
一句中文，等宽就变成了错配。上一版占位符是两个示例（`如 hlm、tang-chao`），等宽
反而**是对的**：它在教作者打一个标识符，字面就该长成标识符的样子。换成规则说明
之后，这句话是**描述**，不是编码。

改法是拆开：`className="font-mono placeholder:font-sans"`。等宽留给输入值（`l`/`1`、
`O`/`0` 要分得开，卡片上也用等宽显示编码），占位符回正文字体。

实测（无头 Chrome，读 `getComputedStyle(el, '::placeholder').fontFamily`）：

| | 元素字体 | `::placeholder` 字体 |
|---|---|---|
| 改前 | `ui-monospace, SFMono-Regular, Menlo, …` | 同左（继承） |
| 改后 | `ui-monospace, …`（不变） | `ui-sans-serif, system-ui, …`，与 `body` 一致 |

**老实说，在 Windows 上这一改像素上几乎看不出来**：中文在两种栈里都落到同一个
后备字体，整句宽度改前改后都是 308px（输入框可用 372px，占 83%），只有逗号、顿号的
字距略不同。但字体栈此前确实是错的 —— 在把 monospace 的中文后备映射到另一款字体的
系统上（macOS / Linux 常落到宋体或另一档中文字体），差别就是肉眼可见的字形不一致。
这一改是把占位符放回它该在的字体栈，而不是为了修肉眼可见的 bug。

## 15. 删主题：软删改成硬删

这一节不开新版本号 —— 它是同一版收尾时补的一笔，改动只有服务端一行语义。

### 15.1 软删是抄来的，不是想出来的

`themes` 建表时带了 `deleted_at`（v0.8.0 §4），因为旁边三张表都有。但那三张表的
软删各有硬需求，主题一条都不占：

| 表 | 软删在解决什么 | 主题占得上吗 |
|---|---|---|
| `maps` / `puzzles` | 版本号靠 `MAX(version) + 1` 不回收（尸体行参与计算）；软删行仍能按 `:id` 解析血统根 | ❌ 主题没有版本号，也没有任何行按 id 引用它 |
| `games` | 取消部署后 `slug` 靠部分唯一索引（`WHERE deleted_at IS NULL`）释放 | ❌ 主题的 `code` 是**普通** UNIQUE，软删不释放 |
| `themes` | 无 | —— |

而且子表的 `theme_id` 全是 `ON DELETE RESTRICT`，`deleteTheme` 另有一道「还有东西
就不让删」的计数护栏 —— 能走到删除这一步的主题**本来就是空的**，没有任何行引用它，
留一具尸体只是习惯。

### 15.2 它反而制造了两个麻烦

第一个是能力问题。`themes.code` 是普通 UNIQUE，尸体行永远占着编码，而
`createTheme` 的查重走 `findByCode`（带 `whereNull('deleted_at')`）看不见它 ——
于是同编码重建会直接撞唯一约束，而服务端没有 23505 的映射，作者收到的是
**500「服务器内部错误」**。实测（本地库，建 → 删 → 同编码再建）：

```
create #1  200   { code: "probe-soft", name: "探针主题" }
delete     200   主题已删除
get after  404   主题不存在
create #2  500   服务器内部错误        ← 尸体行还占着编码
db rows    [ { code: "probe-soft", deleted_at: 2026-10-30T06:05:14.082Z } ]
```

第二个是垃圾问题：v0.8.0 §19.7 体检时 `themes` 里有 **78 具尸体**（测试夹具每跑一次
软删一个），最后靠 `test/purge.ts` 物理删 + 全局 teardown 兜住 —— 那已经是在给软删
打补丁了。§19.10 也把它列成「未做」的设计缺口。

### 15.3 改法

| 位置 | 改动 |
|---|---|
| 迁移 `20260101000041_v083_themes_hard_delete.ts` | 先删掉历史尸体（只删「无任何子行引用」的，有引用的直接抛错让人人工看），再 `DROP COLUMN deleted_at` |
| `themeRepository` | `softDeleteTheme` → `deleteTheme`（`DELETE`）；`listThemeRows` / `findById` / `findByCode` / `updateTheme` 四处 `whereNull('deleted_at')` 一并去掉 |
| `themeService.deleteTheme` | 守栏加**合辑**；`DELETE` 的 23503 映射成 409 而不是 500 |

**顺手抬走僵尸子行。** 地图与谜题的删除分两种情况：草稿行硬删、版本行软删。所以
「作者眼里已经空了」的主题，库里可能还躺着几条软删的版本行 —— 它们仍然挂着
`theme_id`，硬删主题会撞外键 RESTRICT。于是 `repo.deleteTheme` 在一个事务里按
`games → 谜题僵尸行 → 地图僵尸行 → 主题` 拆干净，**只删 `deleted_at` 非空的**：
还活着的子行说明护栏没跑（或数据在变），外键该响就让它响。

合辑为什么单独拦：`theme_deployments.theme_id` 也是 RESTRICT，但它不在卡片计数里
（`ThemeCounts` 只有五个数），所以它排在那五条之前单独问一句，报错里点合辑的名字 ——
否则作者会看到「删不掉」却找不到东西在哪。

### 15.4 两个坑

1. **角色删的是「停用」，不是删除**。`DELETE /api/characters/:id` 只翻 `is_active`，
   而停用的角色仍然属于这个主题、卡片也照数 —— 所以主题会以「1 个角色」被拦。
   要真抬走必须 `?hard=true&clearReferences=true`。这条以前是隐性的（软删时代根本删
   不到那一步），现在藏不住了。
2. **迁移不能悄悄删有子行的主题**。那种行说明「它不是空的」，删了会牵走内容。迁移
   直接失败并报出编码，比猜一个结果强。

  （软删时代这里是 500）、有资源时 409 并说清数量、有合辑时 409 且点名合辑、只剩软删

### 15.6 没有做的

1. **`maps` / `puzzles` 的「软删 + UNIQUE」组合没动**。它们的问题和主题同源（软删行
   占着 `(theme_id, code)` / 版本号位），但软删在那两张表上有真用途，收它得把唯一
   约束换成部分索引 —— 那是另一场迁移，不是这一笔。
2. **`test/purge.ts` 保留**。接口现在只删空主题，而夹具主题身上挂着子行，收尾仍需
   按外键顺序自己拆；只是理由从「清理软删垃圾」换成了「夹具带子行」。
3. **编码复用现在是允许的**。同编码重建出来的是另一个主题，旧的 `/hlm/...` 链接与
   已导出的资源包 manifest 会指向新内容。真要禁止得单独做「保留已用编码」的表，
   本版不做 —— 单机工坊里没人有时间线值得这样保护。
