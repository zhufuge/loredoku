## 1. OPT-W01 作品页表头调整

**现状**：作品页表格共 9 列 —— 作品编号 / 地图名称（名称单元格内嵌「已部署」徽标）/
发布时间 / 尺寸 / 参与者数 / 区域数 / 物品数 / 备注 / 操作。

**目标**：表头固定为 5 列，顺序为 **名称 → 版本 → 部署状态 → 发布时间 → 操作**。

| 列 | 内容 | 与现状的对应关系 |
|---|---|---|
| 名称 | 地图（项目）名称，纯文本 | 原「地图名称」列，**徽标迁出到「部署状态」列** |
| 版本 | `v{N}` | 原「作品编号」列更名（值就是版本号） |
| 部署状态 | 「已部署」徽标（可点击，跳该地图游戏页）或「—」 | **新列** |
| 发布时间 | 版本发布时间（`formatDateTimeMinute`） | 原样保留 |
| 操作 | 查看效果 / 部署（重新部署）/ 导出 / 基于此作品创建草稿 / 删除 | 原样保留，顺序不变 |

- 被移除的列：作品编号（与版本合并）、尺寸、参与者数、区域数、物品数、备注。
- 搜索（关键词 / 日期 / 地图筛选）、分页、加载 / 错误 / 空态行为不变。
- 表格最小宽度（`min-w-[960px]`）可随列数减少调小（实现细节，不设硬性要求）。

**验收**

- 表头恰好 5 列且顺序为 名称 / 版本 / 部署状态 / 发布时间 / 操作；
- 行数据语义与原一致（版本号、发布时间、各操作按钮不变）；
- 「已部署」徽标只出现在「部署状态」列，名称列不再内嵌徽标。

## 2. OPT-W02 只有部署了的版本才标记已部署

**现状**：`deployed` 由后端按**项目**汇总（该地图存在游戏 → 它的**所有**版本行都带「已部署」徽标）。

**目标**：只有**被部署的那个版本**所在行标记「已部署」，其余行显示「—」。

- **后端**：作品列表的 `deployed` 判定从 `project_id` 命中改为 `project_id + version_no`
  双重命中（`map_games` 表已存储 `version_no`，无需改表）。
- **前端**：徽标渲染条件不变（仍读 `work.deployed`），语义随之后端收紧；
  点击徽标仍跳该地图的游戏页（同地图只有一个游戏，`gameIdByProject` 映射继续可用）。
- **重新部署的连锁反应**：把地图 A 的 v3 重新部署后，v2 行的徽标自然消失、v3 行出现
  （数据驱动，无需额外处理）。
- 操作列按钮文案维持 `deployed ? '重新部署' : '部署'`——收紧后只有真实部署过的行
  才显示「重新部署」。

**验收**

- 地图 A 部署了 v2：只有 v2 行显示「已部署」，v1 / v3 行显示「—」；
- 再把 v3 部署：v2 行变「—」，v3 行变「已部署」，点击进入同一个游戏页；
- 从未部署的地图，所有行都是「—」，按钮为「部署」。

## 3. OPT-W03 重新部署时回填封面与难度

**目标**：对已部署的地点「重新部署」时，弹窗默认填充**上次提交的值**：

- **难度** = 该游戏当前的 `difficulty`（五档中上次选中的那档高亮）；
- **封面** = 该游戏当前的封面（`coverUrl` 直接作为预览展示，状态为「已上传」，
  而非新选文件）。

**规则**

- 数据来源：`useGames()` 列表数据按 `projectId` 取整个游戏对象（`WorksPage` 现有的
  `gameIdByProject` 扩展为存 game 对象即可，不新增请求）。
- **名称**：维持现状（每次打开填 `work.projectName`）。是否回填上次自定义的游戏名，
  见 §14 Q4。
- **封面三态**（重新部署时）：
  1. **沿用**：不选新文件、不点移除 → 提交后封面不变；
  2. **替换**：选新文件 → 覆盖原封面；
  3. **移除**：点「移除」→ 提交后封面清空（游戏卡片 / 游戏页回退为首字占位）。
- 移除封面需要后端支持显式清空：部署 upsert 时封面字段传显式空值 → `cover_url` 置
  `NULL`；不传则保留原封面。**API 语义见 §14 Q5。**
- 首次部署（未部署过的地图）：行为与现在完全一致（难度默认档、无封面）。

**验收**

- 已部署地图打开部署弹窗：难度选中上次的档位；封面区显示现有封面预览，
  按钮为「替换 / 移除」；
- 不做任何修改直接部署：封面与难度均保持原值；
- 点「移除」后部署：封面为空，游戏首页卡片与游戏页信息区显示名称首字占位。

## 4. OPT-W04 部署新增「访问路径」填写项，游戏 URL 改用该名称

### 4.1 需求

部署弹窗**新增一个填写项：访问路径（slug）**，并把它作为游戏的**访问地址**：

| 项 | 值 |
|---|---|
| 游戏名称 | `Flower Garden` |
| 难度 | 非常简单（`veryEasy`） |
| **访问路径（默认填充）** | `puzzle-flower-garden-very-easy` |
| **游戏访问地址** | `/games/puzzle-flower-garden-very-easy` |

即：**默认填充规则 = `puzzle-` + 名称转写 + `-` + 难度转写**，全小写、连字符分隔；
用户可自行修改，修改后即最终地址。

### 4.2 弹窗形态

- 位置：游戏名称**下方**、封面上方。
- 控件：`Input`，`maxLength = GAME_SLUG_MAX_LENGTH`，下方一行灰色预览
  `/games/{当前值}`（随输入实时更新）。
- **可编辑 + 一键重生成**：右侧放一个「重新生成」小按钮，按当前名称与难度重算默认值。
- **打开时填充**：
  - 首次部署 → 按 `puzzle-{名称转写}-{难度转写}` 生成；
  - 重新部署 → **回填该游戏现有的访问路径**（与 OPT-W03 的难度 / 封面回填同一原则）。
- **自动跟随**：用户**没有手动改过**该字段时，改动「游戏名称」或「难度」会实时重算路径；
  一旦用户手动编辑过（`slugTouched = true`），就不再自动覆盖，只在点「重新生成」时更新。
  （与「名称」字段的缺省语义一致：后端只在字段缺省时才回退。）
- **重新部署时回填现有路径 → 视为已确定**（打开弹窗即 `slugTouched = true`）：
  用户仅改名称 / 难度**不会**冲掉已经对外发布过的路径；想改必须显式编辑或点「重新生成」。
- **缺省与空值两种情况语义不同**（与「名称」字段同构）：
  - **字段缺省**（请求体不带 `slug`）→ 后端按 §4.3 的规则补算；
  - **显式提交空串** → 报错「访问路径必填」，**不**回退为默认值——否则用户手动清空后
    看到的提示与实际落库值会不一致（Q13：报错要求手动填写）。
  弹窗侧本就在 `slugError` 拦截，提交按钮不会送出空串。
- **名称转写为空（全中文 / 纯符号）→ 不自动编造路径**：`buildDefaultSlug()` 返回空串，
  输入框下方显示「无法根据名称生成访问路径，请手动填写（仅限小写字母、数字与连字符）」，
  后端同样以 400 拒绝（见 §4.3 第 5 条、§14 Q13，以及 §15.2-1）。

### 4.3 转写规则（slugify）

`名称转写` 与 `难度转写` 的统一规则：

1. 字符串转小写；
2. 空格、下划线、`.`、`/` 等分隔符 → `-`；
3. 移除 ASCII 字母 / 数字 / `-` 之外的所有字符；
4. 连续多个 `-` 合并为一个，首尾 `-` 去掉；
5. 结果为空（名称全为中文 / 符号等）→ 见 §14 Q13。

难度转写用常量表固定（避免 `veryEasy` 这类驼峰泄漏到 URL）：

| 难度 | 转写 |
|---|---|
| `veryEasy` | `very-easy` |
| `easy` | `easy` |
| `medium` | `medium` |
| `hard` | `hard` |
| `expert` | `expert` |

示例：

| 名称 | 难度 | 默认路径 |
|---|---|---|
| `Flower Garden` | 非常简单 | `puzzle-flower-garden-very-easy` |
| `Fireside Beach` | 中等 | `puzzle-fireside-beach-medium` |
| `  Ancient Ruins  ` | 困难 | `puzzle-ancient-ruins-hard` |

### 4.4 校验规则

- 字符集：`^[a-z0-9-]+$`（提交前即校验，不合法字符直接拒绝并 toast 提示）；
- 长度：`3 ~ GAME_SLUG_MAX_LENGTH`（建议 80）；
- 不得以 `-` 开头或结尾；
- **全局唯一**：不同地图不能占用同一路径（`map_games.slug` 建 UNIQUE 索引）。
  冲突时**部署失败**并提示「该访问路径已被占用，请更换」，**不自动追加序号**
  （自动序号会产生 `puzzle-…-medium-2` 这类难记、难分享的地址）。是否改为自动去重见 §14 Q12。
- 该地图的**其它版本行**不构成冲突（同地图只有一个游戏，覆盖式 upsert）。

### 4.5 数据模型与迁移

| 层 | 变更 |
|---|---|
| DB | `map_games` **新增列** `slug varchar(80) NOT NULL` + **UNIQUE 索引**；迁移需为**存量行**按「名称 + 难度」回填（冲突时追加 `-2`/`-3`…），因此**本版有迁移**（v0.4.0 时为零迁移） |
| shared | `MapGameSummary` / `MapGameDetail` 增加 `slug: string`；`gameDeploySchema` 增加可选 `slug`；`GAME_SLUG_*` 与 `GAME_DIFFICULTY_SLUGS` 常量 |
| server | `upsertGame` 写入 `slug`；新增 `getGameBySlug()`；部署时校验唯一性并给出「路径已占用」错误 |

### 4.6 API 变更

| 方法 | 路径 | 变化 |
|---|---|---|
| `POST` | `/api/projects/:id/games` | 请求体新增可选 `slug`（缺省 / 空 → 后端按 4.3 计算） |
| `GET` | `/api/games` | 列表项新增 `slug` 字段（其余不变） |
| `GET` | `/api/games/slug/:slug` | **新增**：按访问路径取游戏详情（游戏页数据源） |
| `GET` | `/api/games/:id` | **保留**（内部 / 封面上传用），不破坏既有调用 |
| `POST` | `/api/games/:id/cover` | 不变（仍按 id，内部流程） |

> 路由顺序：`/games/slug/:slug` 必须注册在 `/games/:id` **之前**，否则 `slug` 段会被
> `/:id` 的数字校验拦截。

### 4.7 前端改造

| 位置 | 变化 |
|---|---|
| `router.tsx` | `/games/:gameId` → **`/games/:slug`**（顶层路由不变） |
| `gamesApi` | `detail(id)` → **`detailBySlug(slug)`**；`deploy` payload 增 `slug`；返回类型带 `slug` |
| `useGameDetail` | 参数由 `number \| null` 改为 **`string \| null`**（空串 / 未匹配路由 → `enabled: false`） |
| `GamesPage` / `GameCard` | 卡片点击 → `/games/${game.slug}` |
| `WorksPage` | `gameIdByProject` 改为保存整个 game 对象，「已部署」徽标点击 → `/games/${game.slug}` |
| `GameDeployDialog` | 新增路径输入 + 预览 + 重新生成 + `slugTouched` 逻辑 |
| `GamePage` | 参数由数字 id 改 slug；未匹配到游戏时显示「游戏不存在」而非崩溃 |

### 4.8 兼容性说明

- **旧链接失效**：v0.4.0 时期发出的 `/games/25` 这类地址在改版后不再可用
  （`slug` 无法从纯数字 id 反推）。是否需要保留 `/:id` 兼容跳转见 §14 Q14。
- 路径是**长期外链**：改名 / 改难度**不会**自动改变已有路径（避免已分享的地址失效），
  只有显式改路径字段或删除重部署才会变。

**验收**

- 名称 `Flower Garden` + 非常简单 → 路径字段默认 `puzzle-flower-garden-very-easy`，
  预览行显示 `/games/puzzle-flower-garden-very-easy`；
- 改名称为 `Fireside Beach`（未手动改过路径）→ 路径自动变 `puzzle-fireside-beach-…`；
- 手动改过路径后再改名称 → 路径保持用户值；
- 「重新部署」打开弹窗 → 路径回填现有值；
- 部署成功后游戏首页卡片点进去，地址栏为 `/games/{路径}`；
- 另一地图用同一路径部署 → 报错「该访问路径已被占用」，部署不生效；
- 输入 `Flower Garden!!` 之外的非法字符（如 `*`、`/`）→ 提交前即被拒绝；
- 直接访问不存在的路径 → 「游戏不存在」提示页。

## 5. SPEC-G05 参与者放置唯一性与放置后淡出

### 5.1 「放置」的定义

参与者的标记（**编号**或**头像**）出现在格子上，即该参与者「已放置」。

### 5.2 唯一性：每位参与者只能放置到一个格子

- 编号（短按）与头像（长按）**都计入**放置。
- 该参与者已在任意格子有标记时，点击**其它**格子 → **拒绝**，并 toast 提示
  （示例：`参与者 2 已放置在 R3 C4`，坐标 1 起）。
- **同格长按**：编号 → 头像属于「提升」，允许（不违反唯一性）。
- 该参与者的标记被**清除工具**清除、或被**回退**撤销后，恢复可放置状态。

### 5.3 放置后参与者框颜色变淡

- **时机**：放置成功（编号或头像落格）时，左侧参与者框中该参与者卡片整体
  「颜色变淡」。
- **形式（默认）**：主题色圆环与头像以透明度淡化（建议 `opacity: 0.45`），
  序号、线索、边框保持不变；是否追加「已放置」小字见 §14 Q6。
- **恢复**：该参与者的标记被清除或撤销后恢复原色。
- **隔离**：该效果只出现在游戏页的只读参与者面板（`ParticipantPanel readOnly`），
  编辑器页参与者面板不受影响（新增面板参数，如 `placedSlotIndices`）。

### 5.4 与九宫格多编号的关系（待确认，见 §14 Q7）

现行规则下同一格仍可叠放多位参与者的编号（9 宫格）。若「行/列互斥」是硬规则，
则同格两位参与者必然校验失败。默认实现**保留九宫格多编号**，由提交校验兜底；
若确认互斥为硬规则，则同时禁止同格多位参与者（九宫格退化为每格至多 1 个）。

**验收**

- 点击参与者 1 → 点格子 A 放编号 → 再点格子 B：拒绝且 toast 说明已放置位置；
- 在格子 A 长按同一参与者：编号提升为头像，允许；
- 放置成功后该参与者框变淡；清除该格 / 回退该步后恢复；
- 每位参与者全盘至多一处标记。

## 6. SPEC-G06 同行同列自动放置 ×

### 6.1 触发与范围

**触发**：放置态下成功放置参与者（编号或头像）到格子 (x, y) 时。

**范围**：第 x 行与第 y 列中，除 (x, y) 外满足以下条件的格子，自动放置 ×：

1. 可站立（无不可站立物品）；
2. 当前没有 ×；
3. 没有参与者头像。

### 6.2 对已有编号格子的处理（待确认，见 §14 Q8）

- **方案 A（默认）**：一并替换为 × —— 与手动放置 × 的既有规则一致（× 会先清除
  原编号）。被替换编号的参与者恢复「未放置」态（框颜色恢复、可再次放置），
  因为其唯一标记已被消除。
- **方案 B**：跳过有编号的格子，保留编号，冲突留给提交校验报告。

### 6.3 撤销与幂等

- 本次「放置 + 自动 ×」**合并为一个历史步**：回退一次同时撤销放置与全部自动 ×。
- 头像「提升」（同格长按）时重复执行自动 × 是幂等的（行列已是 ×，无视觉变化），
  按现有 `commit` 语义仍记一步。
- 不新增「同行/列已有其他参与者」的实时预检：自动 × 已保证后续无法落入该行列；
  自动 × 生效前遗留的冲突由提交校验（FEAT-V01）兜底。是否加实时预检见 §14 Q9。

### 6.4 边界

- 不可站立格不放置 ×（本来也放不了）；
- 已有头像的格不放置 ×；
- 自动 × 与手动 × 表现完全一致（黑色 × + 激活不可站立遮罩 + 可被清除工具清除）。

## 8. FEAT-V01 提交校验

**触发**：游戏页工具栏「提交」按钮——替代 v0.4.0 的「直接提交 + toast 已提交」。

**输入**：当前放置棋盘 + 快照中的参与者（编号 = 面板序号，1 起）+
各参与者的位置条件列表。

### 8.1 校验规则（按编号 1 → n 依次校验，收集全部问题，不在首个失败处停止）

| # | 规则 | 未通过信息（示例） |
|---|---|---|
| 1 | 参与者已放置 | `编号 3（张三）尚未放置` |
| 2 | 行互斥：其所在行不能有其他参与者 | `编号 1 与编号 3 同在第 2 行` |
| 3 | 列互斥：其所在列不能有其他参与者 | `编号 1 与编号 2 同在第 4 列` |
| 4 | 位置条件（OR）：所在格必须命中其条件列表之一；**无条件列表则跳过** | `编号 1 位于 R3 C5，不在其位置条件内（可选 R2 C2 / R3 C4）` |

### 8.2 结果呈现

- **全部通过** → 弹框提示「校验通过！」（可附统计：共校验 N 位参与者、放置 M 格）；
- **存在未通过** → 弹框**列出全部问题项**（按编号排序），底部「关闭」返回继续摆放；
  是否只报第一个见 §14 Q10。

### 8.3 与提交屏障的关系

- 校验通过：才执行 `submitPlacement`（设置 `submittedPastLength` 屏障）并置
  `hasSubmitted`；
- 校验失败：两者都不动，玩家继续摆放后可再次提交；
- 提交后仍可继续摆放并再次提交（v0.4.0 语义不变）。

### 8.4 纯函数

新增 `validatePlacement({ board, slots, conditions, gridSize })`：

```ts
{
  passed: boolean;
  issues: Array<{
    participantId: number;              // 1 起编号
    code: 'unplaced' | 'row' | 'column' | 'condition';
    message: string;
  }>;
}
```

**验收**

- 摆放正确且条件满足 → 弹「校验通过」，提交按钮进入已提交态；
- 制造行 / 列冲突 → 弹框列出冲突双方编号与行列；

## 9. BUG-G02 点击参与者后高亮不保持

**现象**（用户报告）：点击参与者，参与者没有一直高亮，移出鼠标就恢复了，
只有第一个参与者是正常的。

**复现**：游戏页 → 点击第 2 位（及以后）参与者 → 鼠标移开该卡片（如移向画布）
→ 参与者框高亮与画布联动高亮消失。第一位参与者在其卡片未被离开时表现正常。

**根因分析**（实现时最终确认）：`GamePage` 的 `onDeactivateHover` 在放置态下对
已武装参与者**重新发送 `click` 事件**以「恢复激活」，而 `reduceLinkageActivation`
中 `click` 是**toggle（切换）**——当鼠标离开的正是已武装参与者**自己的卡片**时，
等同于「再点一次」，激活被切换为关闭。第一位参与者只在指针停留其卡片上时看似正常。
编辑器页不受影响（其 `leave` 对 click 激活是 no-op）。

**修复方向**

1. 恢复激活改为**幂等**：仅当当前激活不是「该参与者的 click 激活」时才补发；
   或给 reducer 增加幂等的 `restore` / `pin` 事件（语义：无条件把某参与者设为
   click 激活），游戏页与编辑器 store 共用；
2. `linkageActivation.test.ts` 补充：放置态离开武装卡片 → 激活保持；
   离开他卡 → 恢复武装者激活；
3. 回归 v0.4.0 §9.4（放置态悬停他卡只切换预览、移开后恢复）不被破坏。

**验收**

- 点击任意一位参与者 → 鼠标移开其卡片 / 移向画布 → 高亮保持；
- 放置态悬停其他参与者卡片 → 显示其 hover 效果，移开 → 恢复武装者效果；
- 再次点击同一参与者 / 点工具按钮 / `Esc` → 退出放置态并清除高亮。

### 15.2 实现期裁定（对 §14 默认取值的细化，语义不变）

1. **Q13 的判定对象**：`buildDefaultSlug()` 在「名称转写结果为空」时返回**空串**，而不是 `puzzle-{难度}`
   —— 否则「不自动编造」无从体现。前端在**未手动编辑过**路径时直接把同一句提示显示在输入框下方，
   服务端在没有传 `slug`（或传了空值）时返回 400 并要求手填；手动填写合法路径后可正常部署。
   若按旧写法派生出 `puzzle-{难度}`，第二张全中文地图会撞上同一路径，报出的却是与 Q13 无关的
   「已被占用」。
2. **冲突后缀只属于迁移**：存量行回填时同名同难度会追加 `-2` / `-3`（§4.5）；**新部署**一律报错不追加
   （Q12）。后缀从 80 字符预算内**切出**后再拼接，避免超长名被截断回原值而死循环。
3. **迁移 `down()` 用 `dropUnique`**：`table.unique(cols, { indexName })` 建的是 UNIQUE **约束**而非裸索引，
   `DROP INDEX` 会以 `2BP01`（constraint requires it）失败；改为 `table.dropUnique(cols, name)` 后
   `rollback → migrate` 双向跑通。
4. **大写路径折叠而非拒绝**：弹窗输入时即 `normalizeSlugInput` 折叠，服务端也 `toLowerCase()`，
   两端一致；字符集 / 长度 / 首尾连字符 / 唯一性仍按 §4.4 严格拒绝。
5. **落点被拒时的反馈**：`placementBlockReason()` 是唯一真相（`canPlaceParticipant()` 只是它的薄封装），
   游戏页据此 `toast` 具体原因（不可站立 / 已有 × / 已有头像 / 该参与者已在别处 / 九宫格已满），
   而不是静默失败。
6. **Q9 保持不变**：放置时**不**实时阻止「同行 / 列已存在其他参与者」，只在提交时兜底（§8）。
