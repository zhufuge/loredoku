# 地图编辑器系统需求文档（v0.5.0）

**文档类型**：版本需求与验收（本文档只定义需求、设计与验收口径，不含代码实现）
**修订记录**：2026-10-16 首版 —— **功能范围重划分**：新增「谜题」模块、删除「作品」模块、地图改为「条目 + 版本」管理
**适用范围**：地图模块（`/projects`、`/editor/:projectId`）、谜题模块（`/puzzles`）、游戏模块（连带，`/games`）
**前置版本**：v0.4.3（`docs/v0.4.3.md`）
**实现载体**：`packages/shared` + `packages/server` + `packages/web`（**三包全动**，本版不是纯前端版本）

> **本版主题：把「地图」和「出题」彻底拆成两件事。**
>
> - **地图**：只负责**画布**——网格、背景、物体、区域、样式。**不再有**角色、参与者、联动主题色。
>   发布不再写「作品」，而是**新增一个带版本标记的地图条目**；条目一旦带版本就**不可原地修改**，
>   改它只会**新增条目**。
> - **谜题**：新模块，接住原本挂在地图上的**角色 + 参与者 + 线索 + 位置条件 + 联动主题色**，
>   并且**必须绑定一个已发布的地图版本**作为画布底图（只读）。它复用「作品列表页」作为自己的列表页。
> - **作品**：模块整体删除（`/works` 路由、导航项、页面），它的业务能力（预览 / 导出 / 部署 / 删除）
>   由**地图版本条目**与**谜题**分别接管。
>
> 一句话记法：**地图出画布，谜题出题；版本是地图的，参与者是谜题的。**

## 1. DEL-K15 删除作品模块

### 1.1 现状

- 路由（`packages/web/src/router.tsx`）：`/works` → `WorksPage`（跨地图作品表格）、`/works/:workId/view` → `WorkViewPage`（预览）。
- 导航（`packages/web/src/components/layout/AppShell.tsx` 的 `navItems`）：`地图 / 物品 / 角色 / 作品` 四项。
- 后端：`GET /api/versions`（`router/versions.ts` 唯一一条，供 `useAllWorks`）+ `GET /api/projects/:id/versions*`。
- 语义：`map_versions` 一行 = 一件「作品」（`version_no` 是它的编号，`snapshot_created_at` 是它的发布时间）。

### 1.2 需求

1. **删除「作品」这一模块与概念**：`/works` 路由、`AppShell` 的「作品」导航项、`WorksPage` 页面文件、`WorkViewPage` 作为「作品预览页」的身份，以及 UI 文案里的「作品」字样全部删除或改名。
2. **`map_versions` 表保留**，但它的语义回归**地图版本**（表名本来就叫这个）：一行 = 某个地图的一次发布快照，`version_no` 在同一个 `project_id` 内递增（已有 `uq_map_versions_project_no` 唯一约束）。
3. **`GET /api/versions`（跨地图平铺）保留**：谜题列表页需要它（老「作品列表页」的全部数据来源），但 DTO 从 `WorkSummary` 改名为 `PuzzleSummary`（见 §2）。
4. **页面实现不浪费**：`WorksPage` 的表格骨架**照搬到谜题列表页**（SPEC-K02），`WorkViewPage` 的只读画布骨架**照搬到谜题预览页**与地图条目预览页。
5. UI 文案中「作品」一律消失。新增全量扫描断言：`packages/web/src/**/*.{ts,tsx}`（除 `.test.`）**不含「作品」**（与既有 `wording.test.ts` 扫「项目」同款做法）。

### 1.3 验收

- `router.tsx` 不含 `/works`；`AppShell` 的 `navItems` 为 `地图 / 谜题 / 物品 / 角色`。
- `packages/web/src/pages/` 下不存在 `WorksPage.tsx` / `WorkViewPage.tsx`（已改名为 `PuzzlesPage.tsx` / `PuzzleViewPage.tsx`）。
- `wording.test.ts` 新增「作品」零出现断言。

## 2. FEAT-K01 + SPEC-K02 + FEAT-K03 谜题模块

### 2.1 数据模型

新表 `puzzles`（迁移 `20260101000017_v050_puzzles.ts`）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | `bigint` PK | |
| `name` | `varchar(100)` NOT NULL | 谜题名称 |
| `description` | `text` NULL | **新增字段**（用户需求） |
| `map_project_id` | `bigint` NOT NULL → `map_projects.id` ON DELETE RESTRICT | 所选版本**所属的**地图行 id（即 `map_versions.project_id`；**不是** `root_id`，见 §7.1 / §7.3） |
| `map_version_no` | `integer` NOT NULL | 所选**已发布**版本号 |
| `grid_size` | `integer` NOT NULL | 冗余自所选版本（谜题槽位长度 = `gridSize`，读写都要用） |
| `data` | `jsonb` NOT NULL | `PuzzleDraft`（见 §6） |
| `status` | `varchar(16)` NOT NULL DEFAULT `'draft'` | 沿用 `PROJECT_STATUSES` |
| `created_at` / `updated_at` | `timestamptz` NOT NULL | |

约束：
- `UNIQUE (map_project_id, map_version_no, name)` —— 同一地图版本下谜题不允许重名（**默认**，见 §15 Q4）。
- `CHECK (grid_size >= GRID_SIZE_MIN AND grid_size <= GRID_SIZE_MAX)`。
- `map_version_no >= 1`。

**为什么冗余 `grid_size`**：谜题槽位长度等于画布尺寸，读取谜题时**不需要**再去查地图版本；同时它是校验 `positionConditions` 越界的唯一依据。写入时由服务端从所选版本强制覆盖（与 `mapService.saveMap` 覆盖 `grid_size` 同款约定）。

### 2.2 API

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/puzzles` | 跨地图平铺的谜题表格数据（原 `GET /api/versions` 的谜题版，返回 `PuzzleSummary[]`） |
| `POST` | `/api/puzzles` | 新建（`name` + `description?` + `mapProjectId` + `mapVersionNo`） |
| `GET` | `/api/puzzles/:id` | 详情（`PuzzleDetail`，含 `data: PuzzleDraft`） |
| `GET` | `/api/puzzles/:id/map` | **只读画布**：谜题所引用地图版本的 `cells / regions / style / gridSize`（供编辑器渲染，见 §5.1） |
| `PUT` | `/api/puzzles/:id` | 保存草稿（`data` + `updatedAt` 乐观锁） |
| `PATCH` | `/api/puzzles/:id` | 改名 / 改描述 |
| `DELETE` | `/api/puzzles/:id` | 删除 |
| `POST` | `/api/puzzles/:id/duplicate` | 复制（**沿用同一个地图版本引用**，与地图复制沿用同一 `cover_path` 同款约定） |
| `POST` | `/api/puzzles/:id/games` | 部署为游戏（CONS-K16） |

`GET /api/puzzles` 的返回仍走**现有** `versionRepository.listAll` 那套 join（谜题 + 地图名 + 部署状态），只是把「版本行」换成「谜题行」。

### 2.3 SPEC-K02 列表页保持不变

**需求**：谜题列表页 = 现 `WorksPage` 的表格**原样照搬**（`packages/web/src/pages/PuzzlesPage.tsx`）。

保持不变的部分：

- 筛选条：关键词（搜索名称 / 版本号 / 备注）、发布日期区间、`MapFilter` 多选地图、重置。
- 分页条：`WORKS_PAGE_SIZE_OPTIONS` + 上一页 / 下一页。
- 行操作按钮：`查看效果` / `部署`（`已部署` 时显示「重新部署」）/ `导出` / `删除`。
- `lib/worksTable.ts` 纯函数整体保留（改名为 `lib/puzzlesTable.ts`，逻辑不变）。

**列的值语义映射**（表头不变，取值换成谜题的）：

| 列 | v0.4.3 取值（作品） | v0.5.0 取值（谜题） |

### 2.4 FEAT-K03 新建谜题

新建谜题弹窗（`components/puzzle/CreatePuzzleDialog.tsx`）三个字段：

1. **名称**（必填，`PUZZLE_NAME_MAX_LENGTH = 100`）。
2. **描述**（选填，多行，`PUZZLE_DESCRIPTION_MAX_LENGTH = 500`）——「新增描述字段」。
3. **地图版本**（必填，单选）——**只能选已发布的地图（带版本）**：
   - 数据源：`GET /api/projects/versions`（新增：跨地图列出所有**带版本的地图条目**）。
   - 每项显示：`{地图名} · v{版本号}`，副行显示 `{gridSize}×{gridSize} · 发布于 {时间}`。
   - 选择后弹窗内提示：**画布尺寸 `n×n` 由所选地图版本决定，创建后不可修改**（对应 SPEC-K07 的「尺寸仅展示」）。
   - 无任何已发布地图时：**禁用提交**，提示「还没有已发布的地图版本，请先到「地图」里发布一个版本」，并给一个跳转 `/projects` 的按钮。

创建后：
- 服务端从所选版本**读出** `gridSize` 并强制写入 `puzzles.grid_size`；
- 初始化 `data`：`characterSlots = Array(gridSize).fill(null)`（与地图编辑器现状一致，槽位长度 = `gridSize`）；
- `linkageColors` 初始 = 所选地图版本 `style.linkageColors`（若为空则 `DEFAULT_LINKAGE_COLORS`）；
- `status = 'draft'`；
- 创建成功后**直接跳转** `/puzzles/:id/edit`（与地图创建后进编辑器一致）。

```ts
    style: MapStyle;          // 含 linkageColors? 不含 —— 见下
  } | null;

  // —— 谜题自有数据（进撤销栈）——
  name: string;
  description: string;
  linkageColors: MapLinkageColor[];
  characterSlots: Array<CharacterSlotEntry | null>;

  // —— 视图 / 焦点（与 editorStore 同款）——
  zoom, pan, activeTool: 'select' /* 恒为 select，见 SPEC-K07 */,
  selection, selectedSlotIndex, activeParticipantId, activeLinkage, …

  // —— 撤销栈 ——
  past, future, dirty;

  // —— 唯一入口 ——
  setParticipantConfig(slotIndex, entry): void;   // 原子 + 可撤销（原 editorStore 逻辑整体搬来）
  assignSlot / clearCharacterSlot / swapSlots;
  setLinkageColors(colors): void;                 // 单一撤销步
  setDescription(text): void;
  toDraft(): PuzzleDraft;                          // FEAT-K08
  applyDraft(draft): void;                         // 导入 / 撤销
  init(detail): void;
}
```

要点：
- `mapContext.style` **剥掉 `linkageColors`**（调色板归谜题，避免两份真相）；渲染时由 `puzzleStore.linkageColors` 合并回 `style` 后再交给 `MapLayers`（`linkageColorFor(style, key)` 取色链路不变）。
- 撤销栈**只包含谜题自有数据**（`linkageColors` / `characterSlots` / `description`）；只读的 `mapContext` 变化**不入栈**。
- `snapshot()` 里的 `ensureEntry()` 必须保留 `positionConditions`（BUG-J04 的修复**随之搬到 `puzzleStore`**，见 §15 Q11）。
- 地图侧 `editorStore` **删除**参与者相关字段与方法（清单见 §9.2）。

## 5. 谜题的画布数据来源（只读引用）

### 5.1 引用而非复制

谜题**不复制**地图的 `cells / regions / style`，只存 `{ mapProjectId, mapVersionNo, gridSize }` 三个引用字段。理由：

1. **版本条目不可变**（SPEC-K11），引用天然稳定——不存在「地图改了谜题跟着变」的问题。
2. 一个地图版本可以被多个谜题引用，复制会产生 N 份冗余。
3. 用户需求「创建时添加地图选择功能，只能选已发布的地图（带版本）」正是「选底图」而非「拷底图」。

编辑器与预览页通过 `GET /api/puzzles/:id/map` 一次拿到只读画布（服务端从 `map_versions` 取该版本快照并剥离参与者字段后返回，见 §8.3）。

### 5.2 联动目标的跨表校验

`PuzzleDraft` 里的 `ParticipantTarget` 仍可指向四类目标，但只有两类能自校验：

| 目标类型 | 数据在哪 | 校验位置 |
|---|---|---|
| `character` | 谜题自己的 `characterSlots` | `puzzleDraftSchema`（zod superRefine） |
| `cell` | 谜题自己的 `gridSize` | `puzzleDraftSchema` |
| `item` | **所引用地图版本**的 `cells` | **服务端 service + 前端 `validatePuzzleReferences`** |
| `region` | **所引用地图版本**的 `regions` | 同上 |

- 新增纯函数 `packages/shared/src/puzzleRefs.ts` 的 `validatePuzzleReferences(draft, mapContext): PuzzleRefIssue[]`：在**合并上下文**上做与原 `validateParticipantReferences` 等价的检查（含 `color` 必须在谜题 `linkageColors` 里）。
- **`puzzleDraftSchema` 只做自洽校验**（`character` / `cell` / `color`）；item / region 引用由 `validatePuzzleReferences` 在「保存前」与「导入前」两处执行，失败给出与现状一致的中文提示（「联动目标物品 #N 不在地图中」/「联动目标区域 X 不在地图中」）。
- 服务端 `puzzleService.save` 在写库前同样调用它（**双保险**：前端可被绕过，导入 JSON 尤其危险）。

## 7. 地图侧：条目与版本（FEAT-K09 / K10 / K11 / K13）

### 7.1 FEAT-K09 首页列表添加版本概念

**核心设计（零数据搬迁）**：地图列表页展示的是**条目并集**，而不是两套数据结构：

- **工作条目** = `map_projects` 的一行（现有行为）。
- **版本条目** = `map_versions` 的一行（`version_no` 就是它的版本标记）。
- 某个地图（血缘根 `R`）的所有条目 = `map_projects WHERE root_id = R` 的工作条目 ∪ 这些工作条目名下的 `map_versions` 行。

**血缘（同属一个「地图」）的判定 = `map_projects.root_id`**（**Q3 = B**）：

| 条目 | 归属的地图（血缘根 id） | 版本标记 |
|---|---|---|
| 工作条目 `map_projects#P` | `P.root_id`（普通地图 = `P.id`；fork 出的条目 = 原地图的 root） | 无（显示「草稿」徽标） |
| 版本条目 `map_versions#V` | `V.project_id` 那一行的 `root_id` | `v{V.version_no}` |

- 存量数据：迁移回填 `root_id = id`，因此**普通地图的血缘根恒等于自己的 id**，与旧行为完全一致。
- **版本号连续**：某条工作条目发布时的 `nextVersionNo` 取**整个血统**的 `MAX(version_no) + 1`，而不是只看自己这一行（否则 fork 出的条目会从 `v1` 重数）。

### 7.2 FEAT-K10 发布创建一个新条目

**现状**：`versionService.publish` 已经在 `map_versions` 插一行（`version_no = current + 1`）并在 `map_projects` 上更新 `status` / `current_version_no`。

**需求**：行为**基本不变**，但语义与呈现改变 —— 这一行现在是一个「**带版本标记的新条目**」，出现在**地图列表页**（不再出现在作品页）。

具体：
1. `map_versions` 行新增/沿用字段展示：`snapshot_created_at`（= 条目的发布时间）、`notes`（发布备注）、`grid_size`。
2. 发布成功后，编辑器的成功弹窗从「已发布 v{N}」+「预览 / 前往作品页」改为「**已发布 v{N}，已在地图列表新增条目**」+「**查看该条目**（→ `/projects`）/ 预览」。
3. 发布**不删除、不覆盖**工作条目（`map_projects` 行的 `draft_data` 原样保留，用户可继续编辑并再次发布 v{N+1}）。
4. 版本条目与工作条目同名（都取 `map_projects.name`）；名称列展示时给版本条目加 `v{N}` 尾标以区分（与徽标不重复，徽标在副信息处）。

### 7.3 SPEC-K11 版本条目不原地修改

**需求**：打开一个版本条目并保存 → **新增条目**，绝不写回 `map_versions`。

交互流程（版本条目卡片/行上的「打开」= **「编辑此版本」**）：

1. 用户点版本条目的 `编辑此版本` → 前端调 `POST /api/projects/:id/versions/:versionNo/fork`（`id` = `projectId`）。
2. 服务端在**同一个事务**里：
   - 读 `map_versions(project_id = id, version_no)` 的 `data` 与 `grid_size`；
   - **新建一行 `map_projects`**：`name = 原地图名`、`description = 原地图描述`、`grid_size = 版本快照的 grid_size`、`draft_data = 版本快照的 data`、`draft_updated_at = now()`、`status = 'draft'`、`current_version_no = NULL`、`cover_path = 原地图的 cover_path`（沿用，不复制二进制，与 `duplicate` 同款约定）、**`root_id = 原地图的 root_id`**（Q3 = B）；
   - 返回新行（`ProjectDetail`）。
3. 前端 `navigate('/editor/{newId}')`，并 toast「已从 v{N} 新增一个条目」。

要点：
- **`map_versions` 行在本流程中零写入**（不可变性由「只读引用该行」保证，不需数据库层约束）。
- **新条目延续原血统（Q3 = B）**：`root_id` 沿用原地图，因此它与原地图**同组**，且下一次发布**接着整个血统的版本号**（上例是 `v4`），不会从 `v1` 重数。
- **谜题不受影响**：谜题引用的是 `(原 projectId, 原 versionNo)`，仍然有效（版本条目还在）。
- 旧接口 `POST /api/projects/:id/versions/:versionNo/draft`（「基于此作品创建草稿」，写回 `draft_data`）**保留但不再有 UI 入口**，加 `@deprecated` 注释说明「v0.5.0 起用 `fork`，此接口仅历史兼容」。见 §15 Q9。

### 7.4 SPEC-K13 编辑器内的发布与版本历史

1. **「发布」按钮保留在地图编辑器顶栏**（它是「在地图模块发布」），但确认弹窗文案按版本管理重写：

   - 说明：`将新增一个带 v{N} 标记的地图条目；当前工作条目不会被覆盖，你可以继续编辑并发布下一版。`

## 8. FEAT-K14 地图 JSON 结构（`MapDraft` v3）

### 8.1 常量

```ts
export const MAP_JSON_VERSION = 3;   // v0.4.3 为 2
```

### 8.2 结构变化

```diff
 interface MapDraft {
   version: number;                       // 2 → 3
   gridSize: number;
   cells: Record<string, DraftCell>;
   regions: DraftRegion[];
-  characterSlots: Array<CharacterSlotEntry | null>;   // → 移到 PuzzleDraft
   style?: MapStyle;
 }
```

```diff
 interface MapStyle {
   cellSize / canvasFrame / gridSeparator / mouseCursorBox / operationCursorBox /
   regionLabel / regionOutline / regionHighlight / ruler: 全部保留
-  linkageColors: MapLinkageColor[];    // → 移到 PuzzleDraft
 }
```

- `mapDraftSchema`：删除 `characterSlots` 字段；`mapStyleSchema` 删除 `linkageColors`（两者都是 `.strict()`，**旧形状的数据会被拒**，所以必须有 §8.3 的读取兼容层）。
- `validateParticipantReferences`（原 superRefine）**整体删除**（它检查的全是参与者联动）。地图层不再有跨字段引用需要校验，`mapDraftSchema` 退化为 `mapDraftBaseSchema`。
- **`MAP_JSON_VERSION` 的读兼容**：`mapDraftSchema` 接受 `version` 为**任意正整数**（现状即是），不做版本号硬校验，因此 v2 数据只要字段形状合法就能读。形状差异由 §8.3 的吸收层解决。

### 8.3 存量数据吸收层（必需）

存量 `map_projects.draft_data` 与 `map_versions.data` 是 v2 形状（带 `characterSlots`、`style.linkageColors`）。新 schema 是 `.strict()`，**直接解析会失败**。因此：

新增服务端辅助模块 `packages/server/src/service/mapDraftCompat.ts`（**不放 `db/migrations/`**，遵循项目约定）：

```ts
/** 把 v2 形状的草稿吸收成 v3 形状：剥离 characterSlots 与 style.linkageColors，版本号改写为 MAP_JSON_VERSION。 */
export function absorbLegacyMapDraft(raw: unknown): unknown;
```

- **唯一职责**：`{ version: 2, characterSlots: [...], style: { linkageColors: [...] } }` → `{ version: 3, style: {...} }`（其余字段原样）。
- **幂等**：v3 形状输入原样返回。
- 调用点：`mapService.getMap` / `versionService.detail` / `versionService.createDraft` / `gameService`（读快照）**在读库后、schema 解析前**调用。
- **不删除数据库里的旧字段**（保留可回滚），只是不再读取。
- 单测：`packages/server/test/mapDraftCompat.test.ts`（v2 输入 / v3 幂等 / 字段冻结 / `style` 缺失 / `characterSlots` 缺失）。

### 8.4 地图编辑器导入导出

- 导出：`MapDraft` v3（无 `characterSlots`、无 `style.linkageColors`）；文件名 `{地图名}-{id}.json`（现状不变）。
- 导入：`mapDraftSchema.safeParse`。**若文件含 `characterSlots` 或 `style.linkageColors`** → 提示「该 JSON 是旧版（含参与者 / 联动主题色），请先移除这两部分，或改用导入到谜题」并**拒绝**（不静默剥离，避免用户以为参与者被导入了）。见 §15 Q12。
- 撤销栈、自动保存、保存遮罩等**全部不变**。

## 10. CONS-K16 游戏模块连带改动

> 用户没提游戏，但**不处理就会坏**：游戏页读 `map_versions.data` 里的 `characterSlots` 渲染参与者面板；v0.5.0 起地图不再有参与者，参与者归谜题。所以部署对象必须从「作品」改成「谜题」。

### 10.1 数据

`map_games` 新增一列（与 `puzzles` 同一迁移或紧随其后）：

| 列 | 类型 | 说明 |
|---|---|---|
| `puzzle_id` | `bigint` NULL → `puzzles.id` ON DELETE SET NULL | 部署的谜题；存量行为 NULL |

- 新增 `UNIQUE (puzzle_id)`（WHERE `puzzle_id IS NOT NULL` 的部分唯一索引）：**一个谜题只能部署一个游戏**（原来是一张地图一个游戏，现在收窄到谜题）。

- `snapshot` 结构升级为 `MapGameSnapshot`：

```ts
export interface MapGameSnapshot {
  /** 画布：谜题所引用地图版本的 draft（v3 形状，无参与者）。 */
  map: MapDraft;
  /** v0.5.0 起：谜题数据（参与者 / 联动主题色 / 描述）。 */
  puzzle: PuzzleDraft | null;
  /** 存量兼容：v0.4.x 快照把参与者放在地图里。 */

}
```

- 游戏页的参与者来源：`snapshot.puzzle?.characterSlots ?? snapshot.legacyCharacterSlots ?? []`（存量游戏**继续可玩**，零修复）。
- 主题色调色板：`snapshot.puzzle?.linkageColors ?? snapshot.map.style?.linkageColors ?? DEFAULT_LINKAGE_COLORS`（存量快照的 `map.style.linkageColors` 仍在 JSON 里，因为快照是冻结的 jsonb）。

### 10.2 前端

- 部署入口：**谜题列表页的行按钮**（`GameDeployDialog` 的 `work` prop 改名 `puzzle`）；部署弹窗的「访问路径」默认填充改用**谜题名称**：`puzzle-{slugify(谜题名)}-{难度转写}`（`GAME_SLUG_PREFIX` 本来就是 `puzzle`，语义反而更贴）。

### 11.2 存量参与者数据的去向（`20260101000016` 内的数据搬运）

存量 `map_projects.draft_data` 与 `map_versions.data` 里有 `characterSlots`。为了让用户**看得见**这些数据，迁移里做一次搬运（纯函数放在 `src/service/puzzleBackfill.ts`，与 `gameSlugBackfill.ts` 同款约定）：

规则（对每个 `map_projects` 行 P，其 `draft_data` 非空时）：

1. 找出 P 的**最高版本号** `V = MAX(version_no) WHERE project_id = P`。
2. **没有版本**（`V` 为 null）→ **跳过**：谜题只能引用已发布版本，此时无法安置参与者；数据留在原 JSON 里（读取时被 §8.3 吸收层忽略）。
3. **有版本** → 若 P 名下**尚不存在**谜题，插入一行 `puzzles`：
   - `name = P.name`、`description = coalesce(P.description, '')`；
   - `map_project_id = P.id`、`map_version_no = V`、`grid_size = P.grid_size`；
   - `data` = `{ version: PUZZLE_JSON_VERSION, map: { projectId: P.id, versionNo: V, gridSize: P.grid_size }, name: P.name, description: coalesce(P.description,''), linkageColors: <取自 V 的快照 style.linkageColors 或 DEFAULT_LINKAGE_COLORS>, characterSlots: <取自 V 的快照 data.characterSlots，缺失则全 null 数组> }`；
   - `status = 'draft'`。
4. 迁移**幂等**：已存在同 `(map_project_id, map_version_no, name)` 的谜题就跳过（回滚重跑安全）。
5. 迁移**不修改** `map_projects.draft_data` / `map_versions.data`（不动旧数据，可回滚）。

`puzzleBackfill` 的纯函数：
- `buildPuzzleSeedFromMap(project, version, seedName): PuzzleDraft | null`（版本缺失 → `null`）
- `slotsFromLegacyDraft(raw, gridSize): Array<CharacterSlotEntry | null>`（长度补齐 / 截断到 `gridSize`）
- `linkageColorsFromLegacyDraft(raw): MapLinkageColor[]`（缺失 → `DEFAULT_LINKAGE_COLORS`）
